GUIA-DOTNET — Parte 8: O Pedidos recusa dado errado, junta itens e vai para o banco

Sessões: S24 (20/10/2026), S25 e S26 (21/10/2026), S27 (22/10/2026), S30 (23–24/10/2026) · Versão: 1.4 · Entradas: 8.1 a 8.10 (8.6 = diagnóstico; 8.7 = teste com banco real; 8.8 = projeto compartilhado e tamanho no domínio; 8.9 = regras de build, SKU em maiúsculas pela aplicação e ADR-009/ADR-010; 8.10 = o Cliente no banco e o POST /clientes) + juntando tudo + teste-se

Até a S23 o Pedido nascia com itens e recusava a lista vazia, mas aceitava qualquer valor nos outros campos, nunca juntava itens repetidos, gerava o próprio identificador (Guid) e não existia no banco. Esta parte explica o que entrou para o módulo Pedidos ficar pronto para guardar dados: cada campo do construtor validado, o teste que prova cada recusa, a regra do SKU repetido, o identificador criado pelo banco e a configuração do EF Core para um pedido que tem itens. Todo exemplo vem do código do Norte. A entrada 8.7 (S25) fecha o que ficou "não provado": um teste com Postgres de verdade que salva um Pedido com itens e lê de volta. A entrada 8.8 (S26) leva o limite de tamanho dos textos para o domínio, com um projeto compartilhado para as constantes, e registra a decisão do SKU em maiúsculas (ADR-008). A entrada 8.9 (S27) implementa o SKU em maiúsculas só pela aplicação (ADR-009), acrescenta ao build as regras de código sem uso e de nome de interface e registra o desenho do pedido no banco (ADR-010).

Onde estamos no mapa dos níveis (Parte 0): o trabalho foi em duas camadas do módulo Pedidos, o domínio (regras no construtor e junção por SKU) e a infraestrutura (EF Core, configuração das tabelas, migration). Ainda não existe endpoint de criação de pedido.

8.1 Validar no construtor com os métodos prontos do .NET

De → para

Como aparece nas vagas Nome no laboratório O mundo do aluno
guard clauses, invariants, fail fast, defensive programming ThrowIfNullOrWhiteSpace, ThrowIfNegativeOrZero, ThrowIfNegative, Enum.IsDefined if (x == null) throw ... escrito à mão em cada método, ou validação só no controller

Em uma frase: o construtor confere cada dado que recebe e lança exceção se ele não serve, então nenhum Pedido nem ItemPedido inválido chega a existir.

Campo Regra Código Exceção
Pedido.origem valor do enum Enum.IsDefined(origem) ArgumentOutOfRangeException
Pedido.criadoPor não nulo, não vazio, não só espaços ArgumentException.ThrowIfNullOrWhiteSpace null → ArgumentNullException; "" ou " " → ArgumentException
Pedido.clienteId, representanteId maiores que zero ArgumentOutOfRangeException.ThrowIfNegativeOrZero ArgumentOutOfRangeException
Pedido.itens pelo menos um if (!itens.Any()) throw (S23) ArgumentException
ItemPedido.sku não nulo, não vazio, não só espaços ThrowIfNullOrWhiteSpace idem acima
ItemPedido.quantidade, precoUnitario maiores que zero ThrowIfNegativeOrZero ArgumentOutOfRangeException
ItemPedido.valorDesconto não negativo e menor que preço × quantidade ThrowIfNegative + dois if ArgumentOutOfRangeException 
public ItemPedido(string sku, int quantidade, decimal precoUnitario, decimal valorDesconto)
{
    ArgumentException.ThrowIfNullOrWhiteSpace(sku, nameof(sku));
    ArgumentOutOfRangeException.ThrowIfNegativeOrZero(quantidade, nameof(quantidade));
    ArgumentOutOfRangeException.ThrowIfNegativeOrZero(precoUnitario, nameof(precoUnitario));
    ArgumentOutOfRangeException.ThrowIfNegative(valorDesconto, nameof(valorDesconto));

    if (valorDesconto == precoUnitario * quantidade)
        throw new ArgumentOutOfRangeException(nameof(valorDesconto), valorDesconto,
            "O valor do desconto não pode ser igual ao valor total do item.");

    if (valorDesconto > precoUnitario * quantidade)
        throw new ArgumentOutOfRangeException(nameof(valorDesconto), valorDesconto,
            "O valor do desconto não pode ser maior que o valor total do item.");

    Sku = sku;
    // ... demais atribuições
}

A ordem importa. O construtor para na primeira validação que falha; as atribuições vêm só depois de todas. Por isso o ParamName da exceção diz qual linha lançou.

Por que o desconto é "estritamente menor": o item de R$ 100,00 (preço × quantidade) com desconto de R$ 100,00 sairia de graça. A regra é do negócio e foi dita pelo aluno; se um dia item gratuito for aceito, a regra e o teste mudam juntos.

Nullable reference types não impedem null em tempo de execução. string criadoPor (sem ?) só avisa o compilador. Quem chama pode mandar null (outro projeto, reflexão, JSON). Por isso o domínio valida mesmo assim.

Como era (S23) Como é agora (S24) O que mudou
só a lista vazia era recusada todo campo do construtor é validado o Pedido não nasce com cliente 0 nem criadoPor vazio
ItemPedido aceitava qualquer valor o item recusa SKU vazio, quantidade 0, preço 0 e desconto absurdo idem
Ganho Preço
Validar no construtor vale para toda porta de entrada (API, importação, teste, outro módulo) todo código que cria o objeto precisa mandar dado válido; o teste de cada regra
Métodos prontos (ThrowIf...) menos código e mensagem padrão a mensagem é em inglês e genérica; o tipo da exceção depende do método

Na entrevista: "Onde você valida o dado: no controller ou no domínio?" — nos dois, com papéis diferentes (6.12): a validação da entrada protege a API; o construtor protege o domínio de qualquer entrada.

Erros comuns: achar que string sem ? garante que não vem null; esperar ArgumentException para null (vem ArgumentNullException); atribuir os campos antes de terminar as validações.

🧠 de cabeça: null → ArgumentNullException; vazio ou espaços → ArgumentException; número fora da regra → ArgumentOutOfRangeException. 🔎 onde encontrar: ArgumentException.ThrowIf... e ArgumentOutOfRangeException.ThrowIf....

Onde foi visto: S24 (PRs #27 e #28). Status: executado e provado por teste; os testes foram escritos pelo aluno, com apoio pequeno na diferença null × vazio.

8.2 Um teste de recusa por campo: Theory, tipo exato e ParamName

De → para

Como aparece nas vagas Nome no laboratório O mundo do aluno
parameterized tests, Theory, InlineData, negative tests Pedido_valida_criadoPor_vazio_ou_espacao_em_branco_deve_retornar_exception vários [Test] copiados com um valor diferente cada

Em uma frase: cada regra do construtor tem um teste que manda só aquele campo ruim, com os outros válidos, e confere o tipo da exceção e o ParamName.

[Theory]
[InlineData("")]
[InlineData("   ")]
public void Pedido_valida_criadoPor_vazio_ou_espacao_em_branco_deve_retornar_exception(string criadoPor)
{
    // Arrange — dados válidos, menos o criadoPor
    // Act + Assert — o que acontece com texto vazio ou só espaços?
    var excecao = Assert.Throws<ArgumentException>(
        () => new Pedido(OrigemPedido.App, criadoPor, 123, 23, itens));

    Assert.Equal("criadoPor", excecao.ParamName);
}
Escolha Por quê
Theory + InlineData o mesmo teste roda uma vez por valor ruim; cada valor aparece como um caso na saída
Assert.Throws<T> exato Throws<ArgumentException> não aceita ArgumentNullException, que é um tipo derivado; por isso null tem teste próprio
ParamName prova que a exceção veio da linha certa, e não de outra validação
null! manda null de verdade com um parâmetro string não nulo: o ! cala o aviso do compilador
um campo ruim por vez os outros ficam válidos para só uma regra poder falhar
valores esperados à mão o teste não calcula o esperado com o código que testa

Prova do vermelho (a mesma da 5.2 e da 7.5): comente a validação, rode o teste e veja vermelho; restaure. Se o teste continuar verde sem a validação, ele não protege nada.

Ganho Preço
Um teste por campo a falha aponta o campo muitos testes pequenos (24 casos no Pedidos ao fim da S24)
Theory menos repetição o nome do teste fala de vários valores; um caso a mais é uma linha

Na entrevista: "O que Assert.Throws<T> faz com um tipo derivado?" — não aceita; é exato. "Para que serve ParamName?"

Erros comuns: esperar ArgumentException para null; testar vários campos ruins num teste só; esquecer a prova do vermelho.

🧠 de cabeça: um campo ruim, tipo exato, ParamName. 🔎 onde encontrar: Assert.Throws, InlineData.

Onde foi visto: S24. Status: executado e provado (24 casos verdes no Pedidos); a prova do vermelho foi feita nas validações.

8.3 Itens com o mesmo SKU viram um item: a regra mora no Pedido

De → para

Como aparece nas vagas Nome no laboratório O mundo do aluno
aggregate invariant, domain rule, business rule JuntarItensComMesmoSku foreach no endpoint ou no service, ou GroupBy na tela

Em uma frase: se o mesmo SKU aparecer duas vezes, o Pedido soma a quantidade, mantém o preço e fica com o último desconto.

Situação Resultado
SKU novo entra como item novo
SKU que já existe soma a quantidade; preço igual; o desconto do último item vale
ABC e abc o mesmo SKU (a comparação ignora maiúscula e minúscula; S26: o ADR-008 decidiu guardar o SKU sempre em maiúsculas; S27: implementado (ADR-009), o que torna essa comparação redundante, mas inofensiva) 
private static List<ItemPedido> JuntarItensComMesmoSku(IReadOnlyList<ItemPedido> itens)
{
    var juntados = new List<ItemPedido>();

    foreach (var item in itens)
    {
        var indice = juntados.FindIndex(j =>
            string.Equals(j.Sku, item.Sku, StringComparison.OrdinalIgnoreCase));

        if (indice < 0)
            juntados.Add(item);
        else
        {
            var existente = juntados[indice];
            juntados[indice] = new ItemPedido(item.Sku,
                existente.Quantidade + item.Quantidade, item.PrecoUnitario, item.ValorDesconto);
        }
    }

    return juntados;
}

O item juntado é criado com new ItemPedido(...): o construtor valida de novo. A soma das quantidades continua passando pelas regras do item (por exemplo, o desconto continua menor que preço × quantidade).

Por que no Pedido e não no endpoint? É regra do negócio ("um SKU aparece uma vez por pedido"). Se ficasse só no endpoint, outra porta de entrada criaria pedido com SKU repetido. No Norte a classe Endpoint de cada funcionalidade guarda a lógica do caso de uso; a regra que protege o Pedido fica com o Pedido. O banco reforça: a chave do item é pedido + SKU (8.4).

Ganho Preço
Regra no domínio vale para qualquer origem do pedido (app, vendedor, importação) o construtor do Pedido fica mais comprido
"O último desconto vale" resolve sem esperar o cálculo real é uma simplificação: perde o desconto do primeiro item; reabrir quando existir o cálculo (forma de pagamento)
Comparar ignorando caixa ABC e abc não viram dois itens a chave do Catalogo diferencia maiúscula e minúscula; a normalização do SKU fica em aberto

Na entrevista: "Onde fica uma regra que envolve a lista de itens de um pedido?" — no agregado (o Pedido), porque só ele vê todos os itens.

Erros comuns: somar a quantidade e esquecer de validar o item novo; comparar SKU com == (diferencia caixa); pôr a regra só no endpoint.

🧠 de cabeça: mesmo SKU = soma a quantidade; o preço é o mesmo; o último desconto vale. 🔎 onde encontrar: FindIndex, StringComparison.OrdinalIgnoreCase.

Onde foi visto: S24 (PR #29). Status: executado e provado por 3 testes (soma e preço; último desconto; ABC e abc); a regra e a simplificação vieram do aluno.

8.4 O identificador vem do banco, a shadow property e a chave composta

De → para

Como aparece nas vagas Nome no laboratório O mundo do aluno
identity column, shadow property, composite key, foreign key UseIdentityByDefaultColumn, Property<int>("PedidoId"), HasKey("PedidoId", nameof(ItemPedido.Sku)) IDENTITY(1,1) no script, HasKey(x => new { x.A, x.B }), PedidoId como propriedade do item

Em uma frase: o PedidoId é um int que o banco cria, e o item se liga ao pedido por uma coluna que existe só no modelo do EF, não na classe.

a) PedidoId como int gerado pelo banco

Como era (S23) Como é agora (S24) O que mudou
PedidoId = Guid.NewGuid() no construtor public int PedidoId { get; } sem atribuição o domínio não gera o identificador; o banco cria (identity)
teste conferia Assert.NotEqual(Guid.Empty, ...) teste removido antes do INSERT o id vale 0

Preço: um pedido novo só tem número depois de salvo. Provado na S25 (8.7): o teste vê o número 0 antes de salvar e diferente de 0 depois (na S24 só a migration mostrava IdentityByDefaultColumn).

b) Shadow property. O ItemPedido não tem PedidoId na classe, mas a tabela precisa da coluna:

builder.Property<int>("PedidoId").HasColumnName("pedido_id");

c) Chave composta por nomes. O item não tem id próprio: é identificado por pedido + SKU. Como PedidoId é shadow, a chave é montada com nomes de propriedade:

builder.HasKey("PedidoId", nameof(ItemPedido.Sku));

d) A ligação entre as tabelas:

builder.HasOne<Pedido>()
    .WithMany(p => p.Itens)
    .HasForeignKey("PedidoId")
    .OnDelete(DeleteBehavior.Cascade);

HasOne<Pedido>() sem navegação de volta, porque o item não conhece o pedido. Cascade apaga os itens junto com o pedido. A chave composta também garante, no banco, que o mesmo SKU não aparece duas vezes no mesmo pedido (de acordo com 8.3).

Tipo da coluna Resultado na migration
pedido_id em pedidos integer, identity por padrão, chave primária
sku em itens_pedido character varying(20)
preco_unitario, valor_desconto numeric(10,2)
chave de itens_pedido PK_itens_pedido em (pedido_id, sku)
ligação FK_itens_pedido_pedidos_pedido_id, ON DELETE CASCADE
Ganho Preço
Identificador do banco número curto, sem Guid; o banco garante a unicidade só existe depois de salvar; o teste de domínio não vê o número
Shadow property a classe ItemPedido continua sem conhecer o pedido a coluna não aparece no código da classe: quem lê só a classe não a vê
Chave composta (pedido + SKU) o banco recusa SKU repetido no mesmo pedido todo lugar que identifica um item precisa dos dois valores

Na entrevista: "Como o EF Core mapeia uma propriedade que não existe na classe?" — shadow property. "Chave composta no Fluent API?" — HasKey com os dois nomes.

Erros comuns: escrever HasKey(p => p.Sku) e esquecer o pedido; tentar HasKey(p => p.PedidoId) sem a propriedade na classe (não compila); Property("PedidoId") sem o tipo.

🧠 de cabeça: shadow = existe no modelo, não na classe. 🔎 onde encontrar: Property<T>("Nome"), HasKey("A", "B").

Onde foi visto: S24 (PRs #30 e #31). Status: executado e aplicado no Postgres local; a configuração do item foi feita com o mentor ("Não consigo. Vamos fazer isso juntos"), ainda não sozinho.

8.7 Teste com banco real para o Pedidos: salvar, ler de volta e ver vermelho

De → para

Como aparece nas vagas Nome no laboratório O mundo do aluno
integration test with Testcontainers, test fixture, repository test, round trip PostgresFabrica, IClassFixture<T>, IAsyncLifetime, PedidoPersistenciaTests teste contra um banco instalado na máquina (ou SQLite/em memória) que cada um configurava do seu jeito

Em uma frase: a fábrica sobe um Postgres de verdade num container, aplica as migrations do módulo e entrega um PedidoDbContext novo a cada chamada; o teste grava com um contexto, lê com outro e confere o que voltou.

public sealed class PostgresFabrica : IAsyncLifetime
{
    private readonly PostgreSqlContainer _postgres = new PostgreSqlBuilder("postgres:18").Build();

    public async Task InitializeAsync()
    {
        await _postgres.StartAsync();
        await using var contexto = CriarContexto();
        await contexto.Database.MigrateAsync();
    }

    internal PedidoDbContext CriarContexto()
    {
        var opcoes = new DbContextOptionsBuilder<PedidoDbContext>()
            .UseNpgsql(_postgres.GetConnectionString(),
                npgsql => npgsql.MigrationsHistoryTable("__EFMigrationsHistory", PedidoDbContext.Schema))
            .Options;

        return new PedidoDbContext(opcoes);
    }

    public Task DisposeAsync() => _postgres.DisposeAsync().AsTask();
}
Peça O que faz
PostgreSqlBuilder("postgres:18") descreve o container (a mesma imagem do compose.yaml)
IAsyncLifetime o xUnit chama InitializeAsync antes e DisposeAsync depois
MigrateAsync() aplica as migrations do módulo: o teste usa as mesmas tabelas da migration CriaTabelasPedidos

Validar no domínio e na coluna erro claro antes do banco; vale por qualquer porta de entrada a regra existe em dois lugares; a constante mantém os dois iguais
public const simples e rápida o valor é gravado no código de quem usa: mudar no Compartilhado sem recompilar os outros deixa o número antigo (hoje o deploy é um só; importa no M7)

O SKU em maiúsculas (ADR-008, decidido na S26; implementado na S27 só pela aplicação, sem CHECK: ADR-009 e 8.9): o SKU passa a ter uma forma só, maiúscula. Preços: o valor devolvido pela API muda (inclusive o Location); testes e seed com minúsculas mudam; os dados existentes precisam ser convertidos antes da restrição; a regra se repete em cada módulo (tensão com o ADR-007). A alternativa B (índice único em upper(sku)) exigiria SQL escrito à mão na migration.

Mover o projeto da API: git mv para src/Api/Norte.Api; o Git registra renomeação (R); ajustar o .slnx, os caminhos de ProjectReference e o projeto de teste do Catalogo. O CI não mudou (usa só o Norte.slnx).

Erros comuns: esquecer o ProjectReference (o projeto de teste também precisa); deixar o HasMaxLength com o número solto; achar que internal atravessa projetos; usar maiúsculo com sublinhado em constante (CA1707); mudar uma public const sem recompilar os consumidores.

🧠 de cabeça: a mesma constante no domínio e na coluna; ganho e preço do compartilhado são o mesmo fato. 🔎 onde encontrar: Constantes, CA1707, CA1052, git stash push --, ToUpperInvariant.

Respostas

Mostrar respostas
  1. ThrowIfNullOrWhiteSpace lança ArgumentNullException para null e ArgumentException para "" ou espaços. Assert.Throws<T> exige o tipo exato, então cada caso precisa do seu teste.
  2. Não. A regra é "estritamente menor": desconto igual a preço × quantidade lança ArgumentOutOfRangeException com ParamName == "valorDesconto", porque o item sairia de graça.
  3. Um único item ABC (a comparação ignora maiúscula e minúscula), com as quantidades somadas, o preço mantido e o desconto do último.
