8.1 Validar no construtor com os métodos prontos do .NET

De → para

Como aparece nas vagas Nome no laboratório O mundo do aluno
guard clauses, invariants, fail fast, defensive programming ThrowIfNullOrWhiteSpace, ThrowIfNegativeOrZero, ThrowIfNegative, Enum.IsDefined if (x == null) throw ... escrito à mão em cada método, ou validação só no controller

Em uma frase: o construtor confere cada dado que recebe e lança exceção se ele não serve, então nenhum Pedido nem ItemPedido inválido chega a existir.

Campo Regra Código Exceção
Pedido.origem valor do enum Enum.IsDefined(origem) ArgumentOutOfRangeException
Pedido.criadoPor não nulo, não vazio, não só espaços ArgumentException.ThrowIfNullOrWhiteSpace null → ArgumentNullException; "" ou " " → ArgumentException
Pedido.clienteId, representanteId maiores que zero ArgumentOutOfRangeException.ThrowIfNegativeOrZero ArgumentOutOfRangeException
Pedido.itens pelo menos um if (!itens.Any()) throw (S23) ArgumentException
ItemPedido.sku não nulo, não vazio, não só espaços ThrowIfNullOrWhiteSpace idem acima
ItemPedido.quantidade, precoUnitario maiores que zero ThrowIfNegativeOrZero ArgumentOutOfRangeException
ItemPedido.valorDesconto não negativo e menor que preço × quantidade ThrowIfNegative + dois if ArgumentOutOfRangeException 
public ItemPedido(string sku, int quantidade, decimal precoUnitario, decimal valorDesconto)
{
    ArgumentException.ThrowIfNullOrWhiteSpace(sku, nameof(sku));
    ArgumentOutOfRangeException.ThrowIfNegativeOrZero(quantidade, nameof(quantidade));
    ArgumentOutOfRangeException.ThrowIfNegativeOrZero(precoUnitario, nameof(precoUnitario));
    ArgumentOutOfRangeException.ThrowIfNegative(valorDesconto, nameof(valorDesconto));

    if (valorDesconto == precoUnitario * quantidade)
        throw new ArgumentOutOfRangeException(nameof(valorDesconto), valorDesconto,
            "O valor do desconto não pode ser igual ao valor total do item.");

    if (valorDesconto > precoUnitario * quantidade)
        throw new ArgumentOutOfRangeException(nameof(valorDesconto), valorDesconto,
            "O valor do desconto não pode ser maior que o valor total do item.");

    Sku = sku;
    // ... demais atribuições
}

A ordem importa. O construtor para na primeira validação que falha; as atribuições vêm só depois de todas. Por isso o ParamName da exceção diz qual linha lançou.

Por que o desconto é "estritamente menor": o item de R$ 100,00 (preço × quantidade) com desconto de R$ 100,00 sairia de graça. A regra é do negócio e foi dita pelo aluno; se um dia item gratuito for aceito, a regra e o teste mudam juntos.

Nullable reference types não impedem null em tempo de execução. string criadoPor (sem ?) só avisa o compilador. Quem chama pode mandar null (outro projeto, reflexão, JSON). Por isso o domínio valida mesmo assim.

Como era (S23) Como é agora (S24) O que mudou
só a lista vazia era recusada todo campo do construtor é validado o Pedido não nasce com cliente 0 nem criadoPor vazio
ItemPedido aceitava qualquer valor o item recusa SKU vazio, quantidade 0, preço 0 e desconto absurdo idem
Ganho Preço
Validar no construtor vale para toda porta de entrada (API, importação, teste, outro módulo) todo código que cria o objeto precisa mandar dado válido; o teste de cada regra
Métodos prontos (ThrowIf...) menos código e mensagem padrão a mensagem é em inglês e genérica; o tipo da exceção depende do método

Na entrevista: "Onde você valida o dado: no controller ou no domínio?" — nos dois, com papéis diferentes (6.12): a validação da entrada protege a API; o construtor protege o domínio de qualquer entrada.

Erros comuns: achar que string sem ? garante que não vem null; esperar ArgumentException para null (vem ArgumentNullException); atribuir os campos antes de terminar as validações.

🧠 de cabeça: null → ArgumentNullException; vazio ou espaços → ArgumentException; número fora da regra → ArgumentOutOfRangeException. 🔎 onde encontrar: ArgumentException.ThrowIf... e ArgumentOutOfRangeException.ThrowIf....

Onde foi visto: S24 (PRs #27 e #28). Status: executado e provado por teste; os testes foram escritos pelo aluno, com apoio pequeno na diferença null × vazio.

8.2 Um teste de recusa por campo: Theory, tipo exato e ParamName

De → para

Como aparece nas vagas Nome no laboratório O mundo do aluno
parameterized tests, Theory, InlineData, negative tests Pedido_valida_criadoPor_vazio_ou_espacao_em_branco_deve_retornar_exception vários [Test] copiados com um valor diferente cada

Em uma frase: cada regra do construtor tem um teste que manda só aquele campo ruim, com os outros válidos, e confere o tipo da exceção e o ParamName.

[Theory]
[InlineData("")]
[InlineData("   ")]
public void Pedido_valida_criadoPor_vazio_ou_espacao_em_branco_deve_retornar_exception(string criadoPor)
{
    // Arrange — dados válidos, menos o criadoPor
    // Act + Assert — o que acontece com texto vazio ou só espaços?
    var excecao = Assert.Throws<ArgumentException>(
        () => new Pedido(OrigemPedido.App, criadoPor, 123, 23, itens));

    Assert.Equal("criadoPor", excecao.ParamName);
}
Escolha Por quê
Theory + InlineData o mesmo teste roda uma vez por valor ruim; cada valor aparece como um caso na saída
Assert.Throws<T> exato Throws<ArgumentException> não aceita ArgumentNullException, que é um tipo derivado; por isso null tem teste próprio
ParamName prova que a exceção veio da linha certa, e não de outra validação
null! manda null de verdade com um parâmetro string não nulo: o ! cala o aviso do compilador
um campo ruim por vez os outros ficam válidos para só uma regra poder falhar
valores esperados à mão o teste não calcula o esperado com o código que testa

Prova do vermelho (a mesma da 5.2 e da 7.5): comente a validação, rode o teste e veja vermelho; restaure. Se o teste continuar verde sem a validação, ele não protege nada.

Ganho Preço
Um teste por campo a falha aponta o campo muitos testes pequenos (24 casos no Pedidos ao fim da S24)
Theory menos repetição o nome do teste fala de vários valores; um caso a mais é uma linha

Na entrevista: "O que Assert.Throws<T> faz com um tipo derivado?" — não aceita; é exato. "Para que serve ParamName?"

Erros comuns: esperar ArgumentException para null; testar vários campos ruins num teste só; esquecer a prova do vermelho.

🧠 de cabeça: um campo ruim, tipo exato, ParamName. 🔎 onde encontrar: Assert.Throws, InlineData.

Onde foi visto: S24. Status: executado e provado (24 casos verdes no Pedidos); a prova do vermelho foi feita nas validações.

8.3 Itens com o mesmo SKU viram um item: a regra mora no Pedido

De → para

Como aparece nas vagas Nome no laboratório O mundo do aluno
aggregate invariant, domain rule, business rule JuntarItensComMesmoSku foreach no endpoint ou no service, ou GroupBy na tela

Em uma frase: se o mesmo SKU aparecer duas vezes, o Pedido soma a quantidade, mantém o preço e fica com o último desconto.

Situação Resultado
SKU novo entra como item novo
SKU que já existe soma a quantidade; preço igual; o desconto do último item vale
ABC e abc o mesmo SKU (a comparação ignora maiúscula e minúscula; S26: o ADR-008 decidiu guardar o SKU sempre em maiúsculas; S27: implementado (ADR-009), o que torna essa comparação redundante, mas inofensiva) 
private static List<ItemPedido> JuntarItensComMesmoSku(IReadOnlyList<ItemPedido> itens)
{
    var juntados = new List<ItemPedido>();

    foreach (var item in itens)
    {
        var indice = juntados.FindIndex(j =>
            string.Equals(j.Sku, item.Sku, StringComparison.OrdinalIgnoreCase));

        if (indice < 0)
            juntados.Add(item);
        else
        {
            var existente = juntados[indice];
            juntados[indice] = new ItemPedido(item.Sku,
                existente.Quantidade + item.Quantidade, item.PrecoUnitario, item.ValorDesconto);
        }
    }

    return juntados;
}

O item juntado é criado com new ItemPedido(...): o construtor valida de novo. A soma das quantidades continua passando pelas regras do item (por exemplo, o desconto continua menor que preço × quantidade).

Por que no Pedido e não no endpoint? É regra do negócio ("um SKU aparece uma vez por pedido"). Se ficasse só no endpoint, outra porta de entrada criaria pedido com SKU repetido. No Norte a classe Endpoint de cada funcionalidade guarda a lógica do caso de uso; a regra que protege o Pedido fica com o Pedido. O banco reforça: a chave do item é pedido + SKU (8.4).

Ganho Preço
Regra no domínio vale para qualquer origem do pedido (app, vendedor, importação) o construtor do Pedido fica mais comprido
"O último desconto vale" resolve sem esperar o cálculo real é uma simplificação: perde o desconto do primeiro item; reabrir quando existir o cálculo (forma de pagamento)
Comparar ignorando caixa ABC e abc não viram dois itens a chave do Catalogo diferencia maiúscula e minúscula; a normalização do SKU fica em aberto

Na entrevista: "Onde fica uma regra que envolve a lista de itens de um pedido?" — no agregado (o Pedido), porque só ele vê todos os itens.

Erros comuns: somar a quantidade e esquecer de validar o item novo; comparar SKU com == (diferencia caixa); pôr a regra só no endpoint.

🧠 de cabeça: mesmo SKU = soma a quantidade; o preço é o mesmo; o último desconto vale. 🔎 onde encontrar: FindIndex, StringComparison.OrdinalIgnoreCase.

Onde foi visto: S24 (PR #29). Status: executado e provado por 3 testes (soma e preço; último desconto; ABC e abc); a regra e a simplificação vieram do aluno.

8.4 O identificador vem do banco, a shadow property e a chave composta

De → para

Como aparece nas vagas Nome no laboratório O mundo do aluno
identity column, shadow property, composite key, foreign key UseIdentityByDefaultColumn, Property<int>("PedidoId"), HasKey("PedidoId", nameof(ItemPedido.Sku)) IDENTITY(1,1) no script, HasKey(x => new { x.A, x.B }), PedidoId como propriedade do item

Em uma frase: o PedidoId é um int que o banco cria, e o item se liga ao pedido por uma coluna que existe só no modelo do EF, não na classe.

a) PedidoId como int gerado pelo banco

Como era (S23) Como é agora (S24) O que mudou
PedidoId = Guid.NewGuid() no construtor public int PedidoId { get; } sem atribuição o domínio não gera o identificador; o banco cria (identity)
teste conferia Assert.NotEqual(Guid.Empty, ...) teste removido antes do INSERT o id vale 0

Preço: um pedido novo só tem número depois de salvo. Provado na S25 (8.7): o teste vê o número 0 antes de salvar e diferente de 0 depois (na S24 só a migration mostrava IdentityByDefaultColumn).

b) Shadow property. O ItemPedido não tem PedidoId na classe, mas a tabela precisa da coluna:

builder.Property<int>("PedidoId").HasColumnName("pedido_id");

c) Chave composta por nomes. O item não tem id próprio: é identificado por pedido + SKU. Como PedidoId é shadow, a chave é montada com nomes de propriedade:

builder.HasKey("PedidoId", nameof(ItemPedido.Sku));

d) A ligação entre as tabelas:

builder.HasOne<Pedido>()
    .WithMany(p => p.Itens)
    .HasForeignKey("PedidoId")
    .OnDelete(DeleteBehavior.Cascade);

HasOne<Pedido>() sem navegação de volta, porque o item não conhece o pedido. Cascade apaga os itens junto com o pedido. A chave composta também garante, no banco, que o mesmo SKU não aparece duas vezes no mesmo pedido (de acordo com 8.3).

Tipo da coluna Resultado na migration
pedido_id em pedidos integer, identity por padrão, chave primária
sku em itens_pedido character varying(20)
preco_unitario, valor_desconto numeric(10,2)
chave de itens_pedido PK_itens_pedido em (pedido_id, sku)
ligação FK_itens_pedido_pedidos_pedido_id, ON DELETE CASCADE
Ganho Preço
Identificador do banco número curto, sem Guid; o banco garante a unicidade só existe depois de salvar; o teste de domínio não vê o número
Shadow property a classe ItemPedido continua sem conhecer o pedido a coluna não aparece no código da classe: quem lê só a classe não a vê
Chave composta (pedido + SKU) o banco recusa SKU repetido no mesmo pedido todo lugar que identifica um item precisa dos dois valores

Na entrevista: "Como o EF Core mapeia uma propriedade que não existe na classe?" — shadow property. "Chave composta no Fluent API?" — HasKey com os dois nomes.

Erros comuns: escrever HasKey(p => p.Sku) e esquecer o pedido; tentar HasKey(p => p.PedidoId) sem a propriedade na classe (não compila); Property("PedidoId") sem o tipo.

🧠 de cabeça: shadow = existe no modelo, não na classe. 🔎 onde encontrar: Property<T>("Nome"), HasKey("A", "B").

Onde foi visto: S24 (PRs #30 e #31). Status: executado e aplicado no Postgres local; a configuração do item foi feita com o mentor ("Não consigo. Vamos fazer isso juntos"), ainda não sozinho.

8.15 Concorrência otimista na ficha de produto: xmin, ETag, If-Match, 412 e 428

De → para

Como aparece nas vagas Nome no laboratório O mundo do aluno
optimistic concurrency, row version, ETag / If-Match, lost update, 412 Precondition Failed TokenConcorrencia, IsRowVersion(), ETag, If-Match, DbUpdateConcurrencyException duas pessoas editam a mesma ficha; quem grava depois não apaga a alteração do outro sem saber

Em uma frase: a FichaProduto ganhou uma marca de versão (o xmin do Postgres, sem coluna nova); a API devolve a marca no ETag; PUT e DELETE só valem com o If-Match da marca que o cliente leu: marca velha dá 412, marca ausente dá 428 (ADR-015). Três PRs (#84, #85, #86), 190 testes.

a) O problema. Até a S35 dois PUT na mesma ficha terminavam com o último vencendo, sem aviso (lost update). A concorrência otimista não tranca nada: grava assumindo que ninguém mudou e confere na hora de gravar.

b) A marca é o xmin. Toda linha do Postgres tem a coluna de sistema xmin (a transação que a gravou), que muda a cada alteração.

// FichaProduto.cs
public uint TokenConcorrencia { get; private set; }

// FichaProdutoConfiguration.cs
builder.Property(f => f.TokenConcorrencia).IsRowVersion();

O Npgsql mapeia a propriedade para xmin (não existe coluna real) e o EF passa a incluir a marca no WHERE do UPDATE e do DELETE. O xmin vem de um contador global: serve só para igualdade, nunca para ordenar.

c) A marca viaja em cabeçalhos.

Cabeçalho Quem manda Onde
ETag: "820" servidor respostas de GET, POST e PUT (no PUT bem-sucedido, a marca nova)
If-Match: "820" cliente PUT e DELETE 
// forma do trecho nos endpoints (nomes exatos no arquivo real podem diferir)
uint? tokenLido = null;
if (uint.TryParse(ifMatch.Trim('"'), out var token))
    tokenLido = token;

d) O repositório compara a marca lida.

// AtualizarAsync e ExcluirAsync
db.Entry(ficha).Property(f => f.TokenConcorrencia).OriginalValue = tokenLido.Value;

Sem essa linha o EF compararia com a marca recém-carregada e nunca recusaria. Com ela, o UPDATE/DELETE afeta zero linhas se alguém mudou no meio e o EF lança DbUpdateConcurrencyException.

Ordem Pergunta Resultado Status
1 a ficha existe? NaoEncontrado 404
2 veio If-Match? TokenNaoInformado 428
3 grava; a marca bate? Atualizado / Excluido 200 / 204
4 a marca não bate TokenDesatualizado 412
— SKU repetido (só no PUT) Conflito 409

O 404 vem antes do 428 (pedir If-Match para ficha inexistente confundiria). O catch de DbUpdateConcurrencyException vem antes do de violação de unicidade, porque herda dele.

e) Por que 412 e 428, e não 409. 412 e 428 são os status do HTTP para condição de cabeçalho; o 409 continua só para duplicidade (SKU repetido) e o 400 para validação. Títulos: "Ficha alterada por outra requisição" (412) e "Versão obrigatória" (428).

f) O DELETE mudou. Com ExecuteDeleteAsync o DELETE vai direto ao banco e a marca não entra no WHERE. Passou a carregar a ficha, Remove e SaveChangesAsync. Da documentação do EF (conferida): ExecuteUpdate/ExecuteDelete não abrem transação implícita (cada chamada é uma transação), não passam pelo rastreador e não têm token de concorrência automático.

g) Limite conhecido. Um PUT com valores iguais aos atuais não gera UPDATE; a marca não é conferida. Nada mudou, nada se perdeu.

h) O nome (PR #86). Versao virou TokenConcorrencia para não parecer versionamento. A coluna se chama xmin por configuração explícita, então não houve migration (dotnet ef migrations has-pending-model-changes: "No changes" depois de ajustar o snapshot); a migration antiga mantém o nome antigo, como histórico. O enum ResultadoAtuaizarFichaProduto ganhou o nome certo.

i) Ciclo manual no .http. Pedido nomeado e leitura do cabeçalho da resposta:

# @name obterFicha
GET {{host}}/catalogo/fichas-produto/LUV-HTTP-01

###
PUT {{host}}/catalogo/fichas-produto/LUV-HTTP-01
If-Match: {{obterFicha.response.headers.ETag}}

(forma do trecho.) O pedido nomeado precisa ser enviado antes, manualmente; vale a última resposta. Resultado: 12 de 12 passos (201 "820"; PUT 200 "821"; 412; 428; 400; 404; DELETE 428, 412, 204, 404).

Ganho Preço
Concorrência otimista com xmin sem coluna nova, sem tranco; a atualização perdida vira 412 o cliente guarda e devolve a marca; PUT sem If-Match agora dá 428

Mostrar respostas
  1. ThrowIfNullOrWhiteSpace lança ArgumentNullException para null e ArgumentException para "" ou espaços. Assert.Throws<T> exige o tipo exato, então cada caso precisa do seu teste.
  2. Não. A regra é "estritamente menor": desconto igual a preço × quantidade lança ArgumentOutOfRangeException com ParamName == "valorDesconto", porque o item sairia de graça.
  3. Um único item ABC (a comparação ignora maiúscula e minúscula), com as quantidades somadas, o preço mantido e o desconto do último.
  4. Porque o construtor valida de novo. A soma das quantidades continua passando pelas regras do item, como a do desconto menor que preço × quantidade.
  5. Uma propriedade que existe só no modelo do EF, e não na classe. O ItemPedido não tem PedidoId na classe, mas a tabela precisa da coluna pedido_id para a chave composta e para a FK.
  6. Diz ao EF para preencher a lista guardada em _itens ao ler do banco, enquanto a classe expõe Itens só para leitura.
  7. O EF precisa de um construtor sem parâmetros para criar o objeto ao ler do banco. Ele não passa pelas validações: o dado já foi validado quando entrou.
  8. --project: onde a migration é gravada (o módulo). --startup-project: quem tem o Program.cs e a connection string (a API). --context: qual DbContext usar, porque cada módulo tem o seu.
  9. Vale 0, porque o identificador só é criado no INSERT. Desde a S25 existe teste que prova: depois de SaveChangesAsync, o PedidoId é diferente de 0 (e viu-se vermelho com o SaveChangesAsync comentado).
  10. Cria a branch e muda para ela. Sem o -c, o Git procura uma branch que já existe e dá erro.
  11. Porque o DbContext lembra o que carregou: se o mesmo contexto gravasse e lesse, o EF devolveria o objeto da memória, sem ir ao banco, e o teste passaria mesmo com a gravação errada.
  12. Vem vazio, porque o EF não carrega a coleção sozinho. Visto no vermelho: Expected: 2, Actual: 0.
  13. O IClassFixture faz o xUnit criar a fábrica, chamar o InitializeAsync (sobe o container e aplica as migrations) e o DisposeAsync no fim, uma vez por classe. Com new, ninguém chama o InitializeAsync e o banco não existe.
  14. Ganho: uma fonte única do número. Preço: todo módulo passa a depender do projeto, então uma mudança chega a todos. É o mesmo fato (a fonte única é o acoplamento), visto dos dois lados.
  15. O domínio recusa antes do banco, com erro claro e por qualquer porta de entrada; a coluna é a segunda defesa ("nunca confie só no banco"). A mesma constante mantém os dois iguais.
  16. public porque internal não atravessa projetos; static porque só tem membros estáticos (CA1052).
  17. O compilador grava o valor no código do consumidor; sem recompilar, ele fica com o número antigo. Hoje o deploy é um só; importa no M7.
  18. Para o teste acompanhar a constante: se o limite mudar, o teste muda junto; um 21 digitado ficaria errado em silêncio.
  19. Porque o Norte liga EnforceCodeStyleInBuild e TreatWarningsAsErrors. A IDE0051 só enxerga membros private: internal ou public sem uso passam.
  20. No construtor de FichaProduto e de ItemPedido e nos métodos do repositório que buscam por SKU (e no filtro da listagem). O construtor não basta porque a busca recebe o texto de fora, sem passar por ele.
  21. Um 500: a busca não acha a ficha, o cadastro tenta inserir e o Postgres lança 23505. O certo é 409.
  22. O banco aceita minúsculas se alguém gravar por fora da aplicação, e a aplicação não acharia essa linha. Reavaliar quando existir um segundo ponto de escrita ou quando um método novo de busca escapar da conversão.
  23. A listagem devolve 200 mesmo vazia: com o filtro quebrado o status continua 200. É preciso conferir as fichas que voltaram.
  24. 23505 vale para qualquer índice único; o ConstraintName (ix_clientes_cnpj) prova que foi o do CNPJ. A PostgresException está na InnerException da DbUpdateException.
  25. Um 500: as duas passam pela consulta e a segunda bate no índice (23505). Desde a S31 o repositório trata a violação e o usuário recebe 409.
  26. Porque o número é gerado pelo banco; o 1 só vale para o primeiro cliente da classe e o teste passaria a depender da ordem. Ler o clienteId do JSON funciona sempre.
  27. MemberData diz de onde o xUnit pega as linhas (um membro estático da classe); TheoryData<...> é a tabela tipada de linhas, uma coluna por parâmetro do teste. InlineData serve para poucas linhas de valores simples; MemberData para muitas linhas ou tipos variados.
  28. Porque o HttpValidationProblemDetails usa o nome da propriedade em C# (PascalCase) como chave de Errors.
  29. Para as 20 requisições começarem juntas (await no laço faria uma de cada vez). O vermelho é provável porque depende do tempo de cada requisição; passar sem a correção seria sorte.
  30. O when faz só a violação de unicidade (SqlState 23505) virar false; qualquer outro erro do banco continua subindo como exceção.
  31. Porque a validação do Request recusa antes todo valor que as guardas do domínio recusariam; a API não chega ao ArgumentException, e um mapeamento global esconderia bugs verdadeiros.
  32. Porque o Clientes e o Pedidos vão precisar perguntar um ao outro (o DELETE de cliente pergunta ao Pedidos); com a interface dentro do módulo haveria referência circular, que o .NET não aceita. Um projeto de contratos sem referências quebra o ciclo e mantém o interior do módulo internal.
  33. O compilador garante que a interface existe e que o consumidor a usa certo (ProjectReference). Só a execução garante que alguém registrou uma implementação no contêiner de DI; sem registro, a primeira requisição que pedir a interface falha.
  34. A pergunta é "existe?": AnyAsync vira EXISTS e devolve bool, sem trazer a linha. FirstOrDefaultAsync traz a linha inteira, o que só vale se os dados forem usados.
  35. O teste troca a implementação do contrato: WithWebHostBuilder + AddScoped<IConsultaClientes>(_ => new ConsultaClientesFake(existe: false)). O contêiner usa a última registração de uma interface, e o dublê é registrado depois do AddClientes.
  36. Stub devolve o que foi combinado; fake é uma implementação simples que funciona; mock também confere como foi chamado. O ConsultaClientesFake devolve o bool que o teste mandou (na prática um stub); o nome segue o padrão de Tests.
  37. Atributo só aceita constante e decimal não é constante de atributo, então os limites vão como texto. Sem ParseLimitsInInvariantCulture o "0.01" seria lido com a cultura do servidor (em pt-BR o ponto é separador de milhar).
  38. O Range não pode ler o enum (atributo só aceita constante), então o limite é escrito à mão. O teste confere por reflexão que mínimo e máximo do Range são os do enum e que não há buracos; se o enum crescer e o Range não, o teste fica vermelho.
  39. Porque a regra olha três campos (desconto, preço e quantidade) e um atributo no campo só enxerga um. O erro aparece em ValorDesconto, porque o ValidationResult recebe [nameof(ValorDesconto)].
  40. O estouro de PrecoUnitario * Quantidade no decimal: o cálculo lançaria uma exceção de estouro e a API devolveria 500. Faltam preço e quantidade máximos (dívida anotada).
  41. Porque o POST grava o valor e o Assert confere o valor lido; se as fórmulas diferem, o teste falha por erro do próprio teste (Expected: 1 Actual: 2), não por defeito do código.
  42. O Pedidos oferece Norte.Pedidos.Contratos (interface pública num projeto quase vazio) e o Clientes referencia só esse projeto. Se referenciasse o Norte.Pedidos, haveria ciclo com o Pedidos → Clientes.Contratos.
  43. A fábrica derivada é descartada antes de o teste usar o cliente: ObjectDisposedException. O using var fica no teste.
  44. O endpoint consulta o Clientes (cliente existe?) e o Catalogo (SKU existe?); sem o fake de qualquer um, a API usa a implementação real e o teste cai em 500.
  45. O construtor do ItemPedido guarda o SKU em maiúsculas (ADR-009) e o Catalogo guarda assim; consultar o texto em minúsculas diria "não existe" para um SKU que existe.
  46. Dono do dado é o módulo que cria e altera o dado (ADR-011). O representante é o elo da carteira de clientes e pedidos; por isso tem módulo próprio, com o vínculo do cliente ainda provisório.
  47. Porque os dois mecanismos validam a mesma entrada e a regra deixaria de ter um dono só. O ADR-013 exige um validador e um teste do caso inválido para todo request; sem isso, um request sem validador passa direto, sem aviso.
  48. A exceção de ligação (BadHttpRequestException) só vira 400 sozinha em Development (onde ThrowOnBadRequest está ligada); nos outros ambientes sobe até o UseExceptionHandler() e vira 500. false = a exceção não é desse tratador, o próximo continua; true = já respondeu e o middleware para.
  49. Porque em Development o seed do catálogo roda e procura uma tabela que o banco descartável ainda não tem. Ligar só a opção, mantendo Testing, deixa o framework lançar a exceção sem rodar o seed.
  50. Clientes (400 "Existem clientes cadastrados"), pedidos (400 "Existem pedidos cadastrados"), depois apaga (204) ou 404. Sem o fake, o endpoint usaria a implementação real do Pedidos, que lê uma tabela inexistente naquele banco; o último registro no contêiner vence.
  51. Porque a precisão e a escala estão na configuração do modelo; lendo dali o teste não precisa de banco e prende a constante PrecoMaximo à coluna: mudar uma ponta sem a outra deixa o teste vermelho.
  52. Porque o bloco pode ser interrompido no meio; se o git checkout estiver só no fim, a mutação fica no arquivo. Aconteceu uma vez na S35.
  53. Duas gravações em sequência em que a segunda apaga a primeira sem aviso. Toda linha do Postgres já tem o xmin (a transação que a gravou), que muda a cada alteração; serve só para igualdade.
  54. A que o cliente leu. A linha faz o UPDATE/DELETE comparar com essa marca (no WHERE); sem ela o EF compararia com a recém-carregada e nunca recusaria.
  55. 404 (não existe), 428 (sem If-Match), grava; marca diferente: 412; SKU repetido: 409. 412 e 428 são os status do HTTP para condição de cabeçalho; o 409 fica para duplicidade.
  56. Porque ele apaga direto no banco e a marca não entra no WHERE; agora carrega, Remove e SaveChanges. O PUT de valores iguais não gera UPDATE, então a marca não é conferida (limite aceito).
  57. A coluna se chama xmin por configuração explícita; só o nome da propriedade C# mudou (has-pending-model-changes: "No changes" depois do ajuste do snapshot).
  58. O % no começo impede a árvore de usar a ordem; o pg_trgm guarda pedaços de três letras num índice GIN e acha o meio do texto. A prova é o EXPLAIN (ANALYZE): Seq Scan sem o índice, Bitmap Index Scan com ele.
  59. Gera o código do log na compilação (CA1848). Campos nomeados ({Sku}, {Cnpj}) permitem buscar por campo; o Representantes não loga CPF/e-mail porque dado pessoal não entra em log (regra (dd)).
  60. Produzir (ILogger, Activity, Meter), transportar (OpenTelemetry/OTLP), guardar e buscar (painel Aspire).
  61. O tempo foi gasto no código da aplicação, onde não existe span (o "buraco"), não no banco.
  62. A métrica P99 da rota subiu; o trace mostrou o tempo nos spans postgresql; db.query.text era o LIKE '%...%'; o EXPLAIN mostrou Seq Scan; recriar o índice trouxe o tempo de volta (de ~300 ms para ~50 ms).
  63. O campo de texto procura só no nome do trace (GET /catalogo/...). Funciona o filtro avançado url.path contains <SKU>.
  64. A média esconde a cauda lenta; o P99 mostra os piores 1%. Zero na janela vazia é ausência de dado, não latência zero.
