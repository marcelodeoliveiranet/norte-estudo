GUIA .NET MODERNO — Apêndice B: Comandos do dia a dia (dotnet, Git, GitHub e PowerShell)

v1.2 · 21/10/2026 (depois da S25) · Apêndice do guia. Não tem entradas numeradas: é um guia de consulta, organizado pelo que você precisa fazer.

O que mudou na v1.1 (S23): git add . (e quando usar), o git commit -m com duas mensagens (título e corpo), o erro de usar -u no commit (o -u é só do push), git log -n --oneline e gh pr status.

O que mudou na v1.2 (S25): o aviso de que o dotnet test --no-build roda a DLL antiga (depois de editar um teste ele não vê a edição; na prova do vermelho use dotnet test normal) e de que o dotnet test dos testes com Testcontainers exige o Docker aberto.

Para que serve. Reunir os comandos usados nas sessões do laboratório, dizer o que cada um faz, por que usá-lo, dar um exemplo do Norte e separar o que um desenvolvedor usa todo dia do que serve só para inspecionar.

Como se mantém. Uma linha nova quando um comando novo entra numa sessão. Nada é apagado: o comando que deixar de ser usado é marcado, não removido.

Como ler

Cada comando aparece com o que faz, por que usar, um exemplo do Norte e o grupo a que pertence.

Grupo Significa Exemplos
Todo dia Um desenvolvedor digita sem pensar. Vale decorar. git status, git switch -c, git add, git commit, git push, dotnet build, dotnet test, gh pr create
De vez em quando Resolve uma situação específica. Saiba que existe. git fetch --prune, dotnet test --filter, gh pr checks, git restore, git log --oneline
Diagnóstico Serve para inspecionar o que está no disco quando não há IDE à mão, ou para mostrar o estado do terminal a quem ajuda. Na prática a IDE faz o mesmo com um clique. Basta reconhecer. (Get-Content arquivo).Count, git show --stat

O terminal do laboratório é o Windows PowerShell 5.1. Três diferenças em relação ao que se vê em tutoriais, que usam bash:

  • Para chamar o curl de verdade, escreva curl.exe. O curl sozinho é apelido de outro comando do PowerShell.
  • No lugar de grep use Select-String; no lugar de cat use Get-Content; no lugar de head use Select-Object -First.
  • A barra de caminho é \ (como em src\Norte.Api). O Git e o dotnet aceitam as duas.

Preciso rodar build, testes e a API

Comando O que faz Por que usar Exemplo no Norte Grupo
dotnet build Norte.slnx Compila todos os projetos da solution Ver os erros antes de commitar; no Norte todo aviso é erro (4.1) dotnet build Norte.slnx Todo dia
dotnet test Norte.slnx Compila e roda todos os testes Provar que nada quebrou; exige o Docker aberto (6.9) dotnet test Norte.slnx Todo dia
dotnet test Norte.slnx --no-build Roda os testes sem compilar de novo Ganhar tempo logo depois de um build verde (o CI faz assim) dotnet test Norte.slnx --no-build Todo dia
dotnet test --filter "FullyQualifiedName~Nome" Roda só os testes cujo nome completo contém o texto Repetir um teste sem esperar a suíte inteira, na prova do vermelho por exemplo (6.13) dotnet test --filter "FullyQualifiedName~ExcluirFichaProdutoComBancoApiTests" De vez em quando
dotnet test Norte.slnx --list-tests Lista os testes sem executar Descobrir o nome certo para o filtro Veja o bloco abaixo De vez em quando
dotnet run --project src\Norte.Api --environment Development Sobe a API em Development Testar na mão com o .http (3.4); o seed só roda em Development (6.14) A API sobe em http://localhost:5071 Todo dia
dotnet sln add <projeto> Inclui um projeto na solution Projeto criado pelo terminal só aparece no Solution Explorer depois disso (1.1) dotnet sln Norte.slnx add tests\Modulos\Pedidos\Norte.Pedidos.Tests De vez em quando

Listar e filtrar pelo nome (o | encadeia a saída de um comando na entrada do outro):

dotnet test Norte.slnx --list-tests | Select-String "ExcluirFichaProdutoComBancoApiTests"

Cuidado que já custou tempo: com a API rodando, o build e o test falham com MSB3026 (arquivo bloqueado por Norte.Api). Feche a API (Ctrl+C no terminal dela) antes de compilar.

Atenção ao --no-build (S25): ele roda a DLL que já existe. Se você editou um teste (ou estragou o código para ver o vermelho) e rodou com --no-build, o resultado é o do código antigo. Na prova do vermelho, use dotnet test sem o --no-build.

Atenção ao total: 0: se o resumo do dotnet test mostra total: 0, nenhum teste rodou. Isso quase sempre é nome errado no filtro, e não é sucesso.

Preciso começar um trabalho novo

No Norte, cada objetivo de sessão tem a sua branch (1.11). Nunca se trabalha direto na main, e todo experimento também vai para uma branch.

Comando O que faz Por que usar Exemplo no Norte Grupo
git switch main Troca para a main Começar sempre de uma base atualizada git switch main Todo dia
git pull Traz da origem os commits novos da branch atual Atualizar a main depois de um merge git pull Todo dia
git switch -c <branch> Cria uma branch e já troca para ela Um objetivo, uma branch git switch -c test/catalogo-excluir-sku-maior-que-20 Todo dia
git branch --show-current Mostra em que branch você está Conferir antes de commitar git branch --show-current De vez em quando
git fetch --prune Atualiza o que existe na origem e remove as referências a branches que já foram apagadas lá Limpar o que sobrou depois do merge de um PR git fetch --prune De vez em quando
git branch -d <branch> Apaga a branch local já mesclada Manter a lista de branches curta git branch -d test/pedido-criar-pedido-com-itens De vez em quando

O nome da branch segue <tipo>/<modulo>-<assunto>, em português. O git switch e o git restore substituem os usos antigos do git checkout. Se o dedo for no checkout, funciona, mas o idioma atual é este.

Preciso ver o que mudou

Antes de commitar, olhe o que vai entrar. É o hábito que mais evita commit errado.

Comando O que faz Por que usar Exemplo no Norte Grupo
git status Lista os arquivos alterados, novos e já preparados Saber em que ponto está; é o primeiro comando de qualquer sessão git status Todo dia
git diff Mostra as linhas alteradas que ainda não foram preparadas Revisar o que você mexeu git diff Todo dia
git diff --staged (ou --cached) Mostra as linhas que já estão preparadas para o commit Revisar exatamente o que vai para o commit git diff --staged Todo dia
git diff --cached --stat Resume por arquivo: quantas linhas entraram e saíram Achar surpresas, como arquivo vazio (0 inserções) ou deleção inesperada Na S21 revelou o template de PR vazio e uma deleção no teste De vez em quando
git log --oneline -3 (ou git log -3 --oneline) Mostra os últimos commits, um por linha. O número diz quantos Conferir em que commit você está git log -4 --oneline Todo dia
git log --oneline --graph -20 O mesmo, com o desenho das branches Entender merges git log --oneline --graph -20 De vez em quando
git show --stat <commit> Mostra um commit e os arquivos que ele tocou Conferir um commit específico git show --stat c9eb7cc Diagnóstico
git diff main...HEAD --stat Alcance da sua branch em relação à main (três pontos) Escrever a descrição do PR git diff main...HEAD --stat De vez em quando
git log main..HEAD --pretty=format:"%s%n%b%n---" Lista os commits da branch, com o corpo Material para a descrição do PR Copiar a saída e resumir De vez em quando

Dois pontos × três pontos: main..HEAD são os commits que a sua branch tem e a main não. main...HEAD compara a sua branch com o ponto em que ela saiu da main, e é o que mostra o seu trabalho sem o ruído do que a main ganhou depois.

Preciso guardar e enviar o trabalho

Comando O que faz Por que usar Exemplo no Norte Grupo
git add <arquivo> Prepara um arquivo para o próximo commit Escolher o que entra, em vez de levar tudo git add tests\Modulos\Pedidos Todo dia
git add . Prepara tudo o que mudou na pasta atual e abaixo Só depois de conferir o git status e ver que são só os arquivos que você quer. Sem o add o commit sai vazio (no changes added to commit) git add . Todo dia
git commit -m "tipo(escopo): descrição" Grava o que está preparado Um commit é uma mudança coerente que deixa o build verde git commit -m "test(catalogo): provar o 400 do delete com sku de 21 caracteres" Todo dia
git commit -m "título" -m "corpo" Grava com uma mensagem de duas partes: o primeiro -m é o título; o segundo, o corpo Quando o título não explica o porquê git commit -m "feat(pedidos): recusa lista de itens vazia" -m "o pedido sem item não faz sentido para o negócio" De vez em quando
git push -u origin <branch> Envia a branch para o GitHub e guarda o vínculo A primeira vez de cada branch; depois basta git push git push -u origin test/catalogo-excluir-sku-maior-que-20 Todo dia
git push Envia os commits novos da branch Depois do primeiro push git push Todo dia

-m × -u: o -m é do commit (a mensagem). O -u é só do push (liga a branch local à remota). Escrever git commit -u "..." não funciona. Na S23 esse erro apareceu quatro vezes seguidas.

Formato do commit no Norte: <tipo>(<escopo>): <descrição>. O tipo fica em inglês (feat, fix, test, docs, build, ci, refactor, chore). O escopo e a descrição ficam em português, em minúsculas, sem ponto final e com até 72 caracteres. O escopo é o módulo (catalogo, pedidos); sem módulo, omita. A mensagem diz o que o código passa a fazer (a regra), não o que o teste faz.

Regra de ouro: commit que já foi enviado não se reescreve. Corrigir erro de digitação em commit enviado é deixar como está.

Preciso abrir, acompanhar e fechar um PR

O gh é a linha de comando do GitHub. Ele faz pelo terminal o que a página do GitHub faz. Você não depende dele, mas ele salva a sessão quando a página falha (na S21 o GitHub mostrou "Unable to load page" e o merge foi feito por ele).

Comando O que faz Por que usar Exemplo no Norte Grupo
gh pr create --web Abre no navegador o formulário do PR já preenchido Escrever a descrição com calma, vendo o template Veja o bloco abaixo Todo dia
gh pr list Lista os PRs abertos Ver o que está pendente gh pr list De vez em quando
gh pr status Mostra o PR da branch atual, os que você abriu e o resultado dos checks Ver de uma vez se o PR foi mesclado e se o CI passou gh pr status De vez em quando
gh pr view <número> Mostra o título, a descrição e o estado de um PR Conferir um PR sem abrir o navegador gh pr view 24 De vez em quando
gh pr checks <número> Mostra o resultado do CI do PR Esperar o verde antes do merge. O CI avisa, mas não impede o merge (5.1) gh pr checks 24 Todo dia
gh pr merge <número> --merge Faz o merge criando um commit de merge O Norte não usa squash, para manter os commits individuais gh pr merge 24 --merge De vez em quando

O comando completo, com cada parte explicada:

gh pr create --base main --head test/catalogo-excluir-sku-maior-que-20 --title "test(catalogo): provar o 400 do delete com sku de 21 caracteres" --web
  • --base main: a branch de destino, para onde as mudanças vão.
  • --head <branch>: a branch de origem, a que tem os seus commits. Se você já está nela, pode omitir.
  • --title "...": o título, no mesmo formato do commit (Conventional Commits). As aspas fecham o texto; sem elas o PowerShell corta o título no primeiro espaço.
  • --web: abre o formulário no navegador em vez de criar direto, para você preencher a descrição e só então clicar em Create pull request.

Depois do merge, volte à base e limpe: git switch main, git pull, git fetch --prune, git branch -d <branch>.

Onde fica a descrição: no GitHub, no PR. A descrição do PR não é do Git. O template do repositório (.github/pull_request_template.md) já traz as três seções: o que muda, como verificar e decisões.

Preciso desfazer algo

Comando O que faz Por que usar Exemplo no Norte Grupo
git restore <arquivo> Descarta as mudanças locais do arquivo e volta à última versão commitada Desfazer o estrago depois da prova do vermelho git restore src\Modulos\Pedidos\Norte.Pedidos\Dominio\Pedido.cs Todo dia
git restore --staged <arquivo> Tira o arquivo do que foi preparado, sem perder a mudança Você deu git add no arquivo errado git restore --staged Norte.slnx De vez em quando
git commit --amend --no-edit Acrescenta ao último commit sem mudar a mensagem Esqueceu um arquivo; só antes do push git commit --amend --no-edit De vez em quando

Cuidado com o git restore <arquivo>: ele apaga o trabalho não commitado daquele arquivo, sem pergunta e sem volta. Por isso o Norte exige, na prova do vermelho, commitar o teste antes de estragar o código. Assim o restore só desfaz o estrago.

Reescrever histórico (amend, rebase -i) é livre antes do push e proibido depois, em branch compartilhada.

Preciso olhar arquivos e criar pastas

Na prática, você abre o arquivo na IDE. Estes comandos servem quando não há IDE (um servidor, o CI) ou quando é preciso uma prova do que está no disco.

Comando Equivalente no bash O que faz Exemplo no Norte Grupo
Get-Content <arquivo> cat Mostra o conteúdo do arquivo Get-Content .github\pull_request_template.md Diagnóstico
(Get-Content <arquivo>).Count wc -l Conta as linhas. Foi assim que se descobriu que um .csproj colado no terminal tinha quebrado (Get-Content tests\Modulos\Pedidos\Norte.Pedidos.Tests\Norte.Pedidos.Tests.csproj).Count (esperado: 25) Diagnóstico
Select-String "texto" <arquivo> grep Procura um texto dentro de arquivos Select-String "InternalsVisibleTo" src\Modulos\Pedidos\Norte.Pedidos\*.csproj De vez em quando
Get-ChildItem (ou ls) ls Lista arquivos e pastas Get-ChildItem tests\Modulos Todo dia
New-Item -ItemType Directory -Path <pasta> mkdir Cria uma pasta New-Item -ItemType Directory -Path tests\Modulos\Pedidos\Norte.Pedidos.Tests De vez em quando
curl.exe curl Faz uma requisição HTTP curl.exe -i http://localhost:5071/catalogo/fichas-produto De vez em quando

Duas dicas de segurança:

  • Nunca cole um bloco grande no terminal. Na S22 isso quebrou linhas duas vezes. Crie o arquivo pelo editor e confira com (Get-Content arquivo).Count.
  • Para o dia a dia de requisições, o arquivo .http do módulo (Catalogo.http) é mais confortável que o curl.exe.

O que decorar primeiro e o que só reconhecer

Decore (uns doze comandos cobrem 90% do dia):

  1. git status, git diff, git diff --staged
  2. git switch -c, git switch main, git pull
  3. git add, git commit -m, git push -u origin
  4. dotnet build, dotnet test, dotnet run --project
  5. gh pr create --web, gh pr checks

Saiba que existe, procure quando precisar: --filter, --list-tests, git fetch --prune, git restore, git log main..HEAD, gh pr merge, gh pr status.

Só reconheça: Get-Content, Select-String, git show --stat, git diff --cached --stat. São ferramentas de inspeção, e a IDE costuma fazer o mesmo com um clique.

Dica: mantenha uma lista curta e viva com o que você usou de verdade na semana. Uma lista curta que se abre vale mais que uma completa que ninguém consulta.
