4.1 Directory.Build.props e TreatWarningsAsErrors: a configuração comum e o aviso que vira erro

De → para

  • No mercado: Directory.Build.props, MSBuild property inheritance, TreatWarningsAsErrors, warnings as errors, build guardrails, quality gates.
  • No laboratório: Directory.Build.props na raiz do repositório norte · ADR-004 (S13).
  • No seu mundo: cada .csproj com o seu TargetFramework e o seu Nullable, e a janela de saída do Visual Studio com dezenas de avisos amarelos que ninguém lia.

Em uma frase: um arquivo na raiz que o MSBuild aplica sozinho a todos os projetos abaixo dele, e que no Norte também diz: todo aviso do compilador é erro.

Pergunta que responde: "como garantir que todos os projetos da solution compilam com as mesmas regras, sem copiar a mesma configuração em cada .csproj?"

O problema (visto na S13, no código): os quatro .csproj do Norte repetiam as mesmas três linhas (TargetFramework, Nullable, ImplicitUsings). Com o 5º módulo, seriam cinco cópias, e basta uma esquecida para um projeto compilar diferente dos outros. E os avisos de nulo (CS8604) apareciam em amarelo e o build passava.

Como era Como é agora (Norte, S13) O que mudou
<TargetFramework>net10.0</TargetFramework> em cada .csproj uma vez, no Directory.Build.props mudar a versão do .NET = mudar uma linha
aviso de nulo (CS8604) em amarelo; o build passa TreatWarningsAsErrors → error CS8604; o build para o aviso não pode mais ser "deixado para depois"
regras de qualidade (CAxxxx) só como sugestão no editor AnalysisMode Recommended + EnforceCodeStyleInBuild a regra roda no build, igual no seu computador e no CI
projeto novo: copiar a configuração de outro .csproj projeto novo herda tudo, só por estar abaixo da pasta não há o que esquecer

O arquivo do Norte, propriedade por propriedade:

<Project>
  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>

    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
    <AnalysisLevel>latest</AnalysisLevel>
    <AnalysisMode>Recommended</AnalysisMode>
    <EnforceCodeStyleInBuild>true</EnforceCodeStyleInBuild>
  </PropertyGroup>
</Project>
Propriedade O que faz Onde tem impacto O que acontece sem ela
TargetFramework = net10.0 diz para qual versão do .NET o projeto compila todos os 4 projetos cada .csproj precisaria declarar a sua (era assim até a S12)
Nullable = enable liga a análise de nulos: string não aceita null; string? aceita todo código C# o compilador não avisa quando um null pode chegar onde não deveria
ImplicitUsings = enable inclui os using mais comuns sem escrever (1.5) todo código C# using System;, using System.Linq;… em cada arquivo
TreatWarningsAsErrors = true todo aviso do compilador e dos analyzers vira erro o resultado do build os avisos ficam amarelos e o build passa
AnalysisLevel = latest usa o conjunto de regras de qualidade (CAxxxx) mais recente do SDK as regras de qualidade o SDK usa o padrão (que hoje também é latest): deixamos explícito
AnalysisMode = Recommended quantas regras de qualidade viram aviso no build as regras de qualidade modo Default: poucas regras no build, o resto só como sugestão no editor
EnforceCodeStyleInBuild = true faz as regras de estilo (IDExxxx, do .editorconfig) rodarem no build o .editorconfig (4.2) as regras de estilo só aparecem no editor; o dotnet build (e o CI) não as vê

Os modos do AnalysisMode (documentação oficial, do mais leve ao mais rigoroso): None (tudo desligado) · Default · Minimum · Recommended · All (todas as regras como aviso, menos algumas poucas). Começamos em Recommended porque All gera uma avalanche de erros de uma vez, e o objetivo é aprender com cada um. Subir o modo é decisão para depois (ADR-004).

Como o MSBuild acha o arquivo. Ao compilar um projeto, o MSBuild procura um arquivo chamado exatamente Directory.Build.props na pasta do projeto e subindo pelas pastas até a raiz do disco; usa o primeiro que encontrar. Como o do Norte está na raiz do repositório, vale para src/ e tests/. É importado antes do conteúdo do .csproj: o .csproj ainda pode sobrescrever uma propriedade, se precisar (ex.: um projeto legado com TreatWarningsAsErrors false).

Ver acontecer (S13):

Passo O que você fez Resultado Por quê
1 aplicou os arquivos; dotnet build (previsão sua: "vai acusar o namespace") error IDE0161 no PedidosModulo.cs o .editorconfig cobra namespace com escopo de arquivo; o aviso virou erro
2 corrigiu o namespace build verde; 4 testes verdes nenhuma outra regra do Recommended acusou o código atual
3 apagou um ! no Executar (previsão sua: "falha") error CS8604 o mesmo aviso de nulo que passava ontem agora para o build
4 restaurou o ! verde —

O preço (o "e daí" que faltou no fim da S13). Com qualquer aviso, o build quebra; sem build, a API não roda. Então nem um rascunho ou um experimento roda sem corrigir antes. Exemplo do próprio dia: o throw no início do Executar precisou de um if para não gerar CS0162 (código inalcançável), que também viraria erro. O preço é aceito porque o aviso ignorado custa mais caro: o null chega em produção como NullReferenceException.

Pergunta que responde No Norte
Ganho o que eu evito? avisos que nunca eram corrigidos; configuração divergente entre projetos
Preço o que eu pago? nem rascunho compila com aviso; exceção só no .editorconfig, com justificativa

Por que usamos · alternativa · custo. Usamos porque a convenção passa a ser verificada pela máquina, sem depender de quem revisa. A alternativa é a revisão manual (o CLAUDE.md + você + eu): custo zero de configuração, mas cada ocorrência custa uma rodada de revisão e, cedo ou tarde, escapa — o PedidosModulo com chaves é a prova. A outra alternativa é AnalysisMode All e analyzers de terceiros desde o início (o que a newsletter de Anton Martyniuk sugere: Meziantou, SonarAnalyzer, Roslynator): mais regras, mas muitos erros de uma vez, sem tempo de entender cada um.

Quando não usar TreatWarningsAsErrors em tudo: projeto legado que já tem centenas de avisos. Ligar de uma vez gera centenas de erros e trava o time. Nesse caso, liga-se por projeto (no .csproj dos novos) ou só no CI, e os antigos são limpos aos poucos (dica da própria newsletter).

Não confunda:

  • Directory.Build.props (propriedades, antes do .csproj) × Directory.Build.targets (alvos e etapas de build, depois). No Norte só existe o .props.
  • Directory.Build.props × Directory.Packages.props (4.3): o primeiro configura o build; o segundo, as versões dos pacotes.
  • TreatWarningsAsErrors × CodeAnalysisTreatWarningsAsErrors: o segundo controla só os avisos de qualidade (CAxxxx). Com o primeiro ligado, ele já vale para tudo.

Ponte com limite. O Directory.Build.props lembra uma "classe base" de .csproj: todos herdam dele. Mas a herança é por pasta, não por declaração: um projeto fora da árvore do repositório não herda nada, e um Directory.Build.props numa subpasta substitui o da raiz (a menos que importe o de cima explicitamente).

Na entrevista. "Como você garante qualidade de código num time?" → "Primeiro no build: um Directory.Build.props na raiz com Nullable, TreatWarningsAsErrors e os analyzers do SDK, e as convenções no .editorconfig com EnforceCodeStyleInBuild. O build local e o CI cobram as mesmas regras, e a revisão humana fica para o que a máquina não vê, como nome e design. O custo é que nenhum rascunho compila com aviso; num legado, eu ligaria por projeto, para não travar o time."

Erros comuns:

  • nome errado do arquivo (Directory.Build.prop, directory.build.props em sistema que diferencia maiúsculas) → o MSBuild simplesmente não acha, sem erro;
  • arquivo fora da raiz (ex.: dentro de src/) → tests/ não herda;
  • calar uma regra com #pragma warning disable espalhado ou NoWarn no .csproj, em vez de uma exceção justificada no .editorconfig (regra do Norte, CLAUDE.md);
  • manter TargetFramework no .csproj depois de criar o .props (duas fontes da verdade).

🧠 o que o arquivo resolve; aviso × erro e o preço; por que Recommended e não All; quando não ligar tudo de uma vez. · 🔎 os nomes exatos das propriedades e os valores do AnalysisMode.

4.2 .editorconfig e analyzers: as convenções do Norte cobradas pelo compilador

De → para

  • No mercado: .editorconfig, Roslyn analyzers, code style rules (IDExxxx), code quality rules (CAxxxx), rule severity, naming rules.
  • No laboratório: .editorconfig na raiz do norte · ADR-004 (S13).
  • No seu mundo: padrão combinado de boca, numa wiki ou no comentário do PR ("aqui é sem chaves"), e as "lâmpadas" do Visual Studio que cada um seguia ou não.

Em uma frase: o .editorconfig é um arquivo texto que diz quais são as convenções e quão grave é violar cada uma; os analyzers são o código que verifica; com EnforceCodeStyleInBuild e TreatWarningsAsErrors, a violação quebra o build.

Pergunta que responde: "onde a convenção do Norte fica escrita de um jeito que a máquina cobra?"

Duas famílias de regra (as duas existem no SDK do .NET, sem pacote extra):

Família Prefixo O que verifica Exemplo no Norte Ligada por
Estilo (code style) IDE a forma do código: namespace, nomes, var… IDE0161 (namespace com escopo de arquivo) · IDE1006 (regra de nomes) .editorconfig + EnforceCodeStyleInBuild
Qualidade (code quality) CA problemas de correção, desempenho, segurança CA1707 (sem _ em nomes) — desligada nos testes AnalysisMode + .editorconfig
(do compilador) CS o que a própria linguagem avisa CS8604 (nulo), CS0162 (código inalcançável) Nullable + TreatWarningsAsErrors
Como era Como é agora (Norte, S13) O que mudou
"aqui é file-scoped" dito na revisão (S11, S12) csharp_style_namespace_declarations = file_scoped + severidade warning o build acusa IDE0161
cada IDE com a sua formatação .editorconfig na raiz: VS, VS Code, Rider e o dotnet build leem o mesmo arquivo uma regra para todos, inclusive o Claude local
sugestão do editor (pontinhos cinza) que se podia ignorar severidade warning + TreatWarningsAsErrors não dá para ignorar
exceção: "nos testes pode" (combinado verbal) seção [tests/**.cs] com a exceção e o motivo escrito a exceção fica documentada e restrita

O arquivo do Norte, bloco por bloco:

root = true

Diz "pare de procurar .editorconfig nas pastas de cima". Sem isso, um .editorconfig perdido em D:\Projetos\ poderia misturar regras.

[*]
charset = utf-8
indent_style = space
insert_final_newline = true
trim_trailing_whitespace = true

Vale para todo arquivo. Codificação, espaço (não tab), quebra de linha no fim do arquivo e sem espaço sobrando no fim da linha. Atenção: essas quatro são aplicadas pelo editor ao salvar; o dotnet build não as cobra. Cobrança automática fica para o CI (a conferir: dotnet format --verify-no-changes).

[*.{csproj,props,targets,slnx,xml,json}]
indent_size = 2

[*.md]
trim_trailing_whitespace = false

Arquivos XML e JSON com 2 espaços (o costume do mercado). Em Markdown, dois espaços no fim da linha são quebra de linha, então não podem ser apagados.

[*.cs]
indent_size = 4

csharp_style_namespace_declarations = file_scoped
dotnet_diagnostic.IDE0161.severity = warning

Duas linhas por regra de estilo: a opção (o que se prefere: file_scoped) e a severidade (quão grave: warning, que o TreatWarningsAsErrors transforma em erro).

dotnet_naming_rule.metodos_async_terminam_em_async.symbols  = metodos_async
dotnet_naming_rule.metodos_async_terminam_em_async.style    = sufixo_async
dotnet_naming_rule.metodos_async_terminam_em_async.severity = warning
dotnet_naming_symbols.metodos_async.applicable_kinds   = method
dotnet_naming_symbols.metodos_async.required_modifiers = async
dotnet_naming_style.sufixo_async.required_suffix = Async
dotnet_naming_style.sufixo_async.capitalization  = pascal_case
dotnet_diagnostic.IDE1006.severity = warning

Uma regra de nomes tem três peças, sempre: a quem se aplica (symbols: métodos com async) · como deve ser (style: termina em Async, PascalCase) · quão grave (severity). Os nomes metodos_async e sufixo_async são nossos (rótulos livres). A regra IDE1006 é a que reporta violações de nomes.

[tests/**.cs]
dotnet_diagnostic.CA1707.severity = none
dotnet_naming_rule.metodos_async_terminam_em_async.severity = none

Exceções dos testes, com motivo: o nome do teste é a regra em português com _ (Recusa_ficha_sem_sku_e_devolve_400, ADR-001); a documentação oficial da CA1707 diz que suprimi-la em código de teste é seguro. E o método de teste async não leva Async porque o nome é a regra, não o método. A seção mais específica ([tests/**.cs]) sobrescreve a geral ([*.cs]) só onde repete a chave.

Nulos "como erro": não há linha no .editorconfig para isso. Com Nullable ligado, os avisos CS86xx já existem, e o TreatWarningsAsErrors os transforma em erro. (A newsletter de Anton Martyniuk faz isso regra a regra, dotnet_diagnostic.CS8604.severity = error; no Norte o TreatWarningsAsErrors cobre todas de uma vez.)

Severidades possíveis: none (desligada) · silent (só o editor oferece a correção) · suggestion (pontinhos cinza) · warning · error. No build, só warning e error aparecem.

Ponte com limite. O .editorconfig lembra o "guia de estilo" da wiki do time. Mas é lido pelas ferramentas: o que não está nele não é cobrado. E ele não sabe julgar design ou nome ruim (ShipmentHelper passa em qualquer regra) — isso continua na revisão humana (e na revisão do Claude local).

Por que usamos · alternativa · custo. Usamos porque é nativo do SDK (zero pacote) e todas as ferramentas leem. Alternativas: analyzers de terceiros (Meziantou, SonarAnalyzer, Roslynator, citados na newsletter) — mais regras, mais erros de uma vez, e cada pacote é uma dependência a acompanhar; no Norte entram um de cada vez, com necessidade (ADR-004). O custo da nossa escolha: o .editorconfig precisa de manutenção (cada regra nova, uma decisão), e as exceções precisam de disciplina para não virar "desliga tudo".

Na entrevista. "Para que serve o .editorconfig?" → "Para escrever as convenções do time num lugar que todas as ferramentas leem: IDE, dotnet build e CI. Com EnforceCodeStyleInBuild e a severidade warning (que vira erro com TreatWarningsAsErrors), a convenção quebra o build. As exceções ficam no próprio arquivo, por pasta e com motivo — no meu projeto, os testes podem ter _ no nome."

Erros comuns:

  • escrever a severidade no formato antigo opcao = valor:warning (como em dotnet_style_qualification_for_field = false:warning) e esperar que o build cobre: esse formato é respeitado pelo editor, mas o build lê a severidade de dotnet_diagnostic.IDExxxx.severity (a conferir caso a caso na documentação de cada regra);
  • esquecer o EnforceCodeStyleInBuild: as regras IDE só aparecem no editor;
  • desligar a regra no [*.cs] inteiro quando o problema é só em tests/;
  • achar que o build cobra insert_final_newline e trim_trailing_whitespace (não cobra).

🧠 estilo (IDE) × qualidade (CA) × compilador (CS); opção + severidade; as três peças da regra de nomes; exceção por pasta, com motivo; o que o build não cobra. · 🔎 os nomes exatos das opções, os números das regras, a sintaxe das seções.

Referências:

  • Configuration files for code analysis rules (Microsoft Learn) — oficial: como o .editorconfig é lido, seções e precedência.
  • IDE0160/IDE0161 — namespace declaration preferences (Microsoft Learn) — oficial.
  • Code-style naming rules (Microsoft Learn) — oficial: as três peças da regra de nomes.
  • CA1707: Identifiers should not contain underscores (Microsoft Learn) — oficial: "é seguro suprimir em código de teste".
  • Anton Martyniuk, newsletter de 06/10/2026 (link em 4.1) — exemplo de .editorconfig mais amplo.

4.3 Central Package Management: uma versão por pacote, num lugar só

De → para

  • No mercado: Central Package Management (CPM), Directory.Packages.props, ManagePackageVersionsCentrally, PackageVersion, version drift.
  • No laboratório: Directory.Packages.props na raiz do norte · ADR-004 (S13).
  • No seu mundo: <PackageReference Include="..." Version="..." /> em cada .csproj, e dois projetos da mesma solution com versões diferentes do mesmo pacote (o "funciona aqui, quebra ali").

Em uma frase: as versões de todos os pacotes NuGet ficam num arquivo só; os .csproj dizem qual pacote usam, sem a versão.

Pergunta que responde: "como evitar que dois projetos da solution usem versões diferentes do mesmo pacote?"

Como era Como é agora (Norte, S13) O que mudou
<PackageReference Include="xunit" Version="2.9.3" /> no .csproj <PackageVersion Include="xunit" Version="2.9.3" /> no Directory.Packages.props + <PackageReference Include="xunit" /> no .csproj a versão sai do projeto
atualizar um pacote = procurar em todos os .csproj atualizar = uma linha uma linha no diff do PR
projetos com versões diferentes sem ninguém perceber uma versão por pacote na solution não há como divergir sem querer

O arquivo do Norte:

<Project>
  <PropertyGroup>
    <ManagePackageVersionsCentrally>true</ManagePackageVersionsCentrally>
  </PropertyGroup>
  <ItemGroup Label="Testes">
    <PackageVersion Include="coverlet.collector" Version="6.0.4" />
    <PackageVersion Include="Microsoft.AspNetCore.Mvc.Testing" Version="10.0.12" />
    <PackageVersion Include="Microsoft.NET.Test.Sdk" Version="17.14.1" />
    <PackageVersion Include="xunit" Version="2.9.3" />
    <PackageVersion Include="xunit.runner.visualstudio" Version="3.1.4" />
  </ItemGroup>
</Project>
Peça O que faz
ManagePackageVersionsCentrally = true liga a CPM para todos os projetos abaixo da pasta
<PackageVersion Include="X" Version="..." /> declara a versão do pacote X para a solution inteira. Não adiciona o pacote a nenhum projeto
<PackageReference Include="X" /> (no .csproj, sem Version) diz que este projeto usa X; a versão vem do arquivo central
Label="Testes" só um rótulo para organizar (opcional)

Regras que pegam quem começa:

  • com a CPM ligada, um PackageReference com Version no .csproj é erro de build (o NuGet acusa; a newsletter de Anton Martyniuk cita exatamente isso como vantagem: ninguém, nem um agente de IA, inventa versão escondido num projeto);
  • dotnet add package X com a CPM ligada já escreve no lugar certo (a versão vai para o Directory.Packages.props) — conferir o diff;
  • exceção pontual: VersionOverride="..." no PackageReference de um projeto (existe; no Norte, não usamos);
  • o MSBuild usa o Directory.Packages.props mais próximo do projeto, igual ao Directory.Build.props.

Ponte com limite. Lembra o package.json de um monorepo, ou o pubspec.yaml do Flutter (a confirmar), com as versões num lugar só. Mas aqui cada projeto ainda escolhe quais pacotes usa: declarar a versão não instala o pacote em ninguém.

Por que usamos · alternativa · custo. Usamos porque o Norte vai ter um projeto por módulo (ADR-002) e cada um pode usar EF Core, Npgsql, etc.: com 8 módulos, 8 lugares para a mesma versão divergirem. Alternativa: versões em cada .csproj (custo: divergência e atualização trabalhosa). O custo da nossa: um arquivo a mais, e quem não conhece a CPM estranha o PackageReference sem versão.

Na entrevista. "Como você gerencia versões de pacotes numa solution grande?" → "Com Central Package Management: as versões ficam no Directory.Packages.props e os projetos referenciam sem versão. Uma versão por pacote na solution, atualização numa linha, e o build recusa versão escondida num .csproj. Existe desde o .NET 7 e funciona em projetos .NET 8 e 9 também."

Erros comuns: esquecer o ManagePackageVersionsCentrally (as versões centrais são ignoradas); deixar o Version no .csproj (erro); achar que PackageVersion adiciona o pacote ao projeto.

🧠 o problema (versões divergentes) e as duas peças (PackageVersion × PackageReference sem versão). · 🔎 o nome da propriedade, o VersionOverride.

Juntando tudo

Quando você roda dotnet build (ou o CI, quando existir), o MSBuild compila cada projeto. Antes de ler o .csproj, ele importa o Directory.Build.props da raiz: todos os projetos passam a ter .NET 10, nulos ligados, implicit usings, os analyzers do SDK no modo Recommended, as regras de estilo rodando no build e todo aviso tratado como erro. As regras de estilo e as exceções vêm do .editorconfig — namespace com escopo de arquivo, métodos async com sufixo Async, e nos testes o _ permitido no nome. As versões dos pacotes vêm do Directory.Packages.props; o .csproj só diz quais pacotes usa. Resultado: o PedidosModulo com chaves e o ! esquecido param o build no seu computador, antes de chegar a um PR — e o preço é que nenhum rascunho compila com aviso.

Teste-se (sem consultar; uma pergunta por vez)

  1. O Norte tem 4 projetos. Em quantos arquivos fica hoje o <TargetFramework>net10.0</TargetFramework>, e qual é?
  2. Ontem, um string? passado para o construtor da FichaProduto (que exige string) gerava CS8604 e o build passava. Hoje o build falha. Que propriedade mudou isso?
  3. Qual o preço de ligar o TreatWarningsAsErrors no Norte?
  4. O .editorconfig tem csharp_style_namespace_declarations = file_scoped. Sem a propriedade EnforceCodeStyleInBuild no Directory.Build.props, o dotnet build acusaria o namespace com chaves?
  5. Uma regra de nomes no .editorconfig tem três peças. Quais?
  6. Por que a CA1707 está desligada só em tests/ e não em todo o Norte?
  7. O .editorconfig tem trim_trailing_whitespace = true. O dotnet build falha se houver espaço no fim de uma linha?
  8. Com a Central Package Management ligada, o que acontece se alguém escrever <PackageReference Include="xunit" Version="2.9.0" /> num .csproj?
  9. Num projeto legado com 800 avisos, você ligaria o TreatWarningsAsErrors em todos os projetos de uma vez? Por quê?
  10. AnalysisMode Recommended ou All para começar? Qual o custo de cada um?

Respostas

Mostrar respostas
  1. Um só: o Directory.Build.props, na raiz; os .csproj herdam (4.1).
  2. TreatWarningsAsErrors = true: o aviso virou erro (4.1).
  3. Com qualquer aviso o build quebra, e sem build a API não roda: nem um rascunho ou experimento roda sem corrigir antes (4.1).
  4. Não. As regras IDE apareceriam só no editor (4.1, 4.2).
  5. A quem se aplica (symbols) · como deve ser (style) · quão grave (severity) (4.2).
  6. Porque o _ no nome é convenção dos testes (nome = regra em português, ADR-001); no código de produção a regra continua valendo (4.2).
  7. Não. O editor aplica ao salvar; o build não cobra. Cobrança automática fica para o CI (4.2).
  8. Erro de build: com a CPM, a versão só pode ficar no Directory.Packages.props (4.3).
  9. Não: geraria 800 erros de uma vez e travaria o time. Ligaria nos projetos novos (ou só no CI) e limparia os antigos aos poucos (4.1).
  10. Recommended: menos regras, cada erro dá para entender. All: mais proteção, mas uma avalanche de erros de uma vez. O Norte começou em Recommended (ADR-004) (4.1).
