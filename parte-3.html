PARTE 3 — A primeira funcionalidade e o primeiro teste

Onde isso fica no mapa (Parte 0): os níveis 1 e 2, solution e módulos, já estavam prontos. A Parte 3 é o nível 3, a funcionalidade: uma ação de negócio dentro de um módulo. É também o primeiro passo do caminho da requisição. Como ficou na S14:

HTTP POST /catalogo/fichas-produto
  → [UseExceptionHandler + UseStatusCodePages]     host: todo erro sai no formato padrão (3.15)
  → MapPost (CatalogoModulo)                       liga a rota ao método
  → validação nativa ([Required] no Request)       recusa a entrada inválida — 400 com todos os erros
  → CadastrarFichaProdutoEndpoint.Executar         cria e guarda
  → FichaProdutoRepository                         guarda (hoje em memória; amanhã EF Core)
  ← 201 Created   (ou, se algo falhar: 400 / 404 / 500, sempre em application/problem+json)

O teste de unidade chama o Executar direto, sem HTTP. O teste de integração faz a requisição de verdade e passa por todas as etapas (3.12). O teste do 500 troca uma peça só dentro do teste (3.16).

3.1 A funcionalidade no estilo REPR: Request, Endpoint, Repository

De → para

  • No mercado: REPR pattern (Request–Endpoint–Response), divulgado por Steve Smith ("Ardalis") e usado por bibliotecas como FastEndpoints. Também aparece como Handler no lugar de Endpoint. É a base do Vertical Slice (M2).
  • No laboratório: CadastrarFichaProdutoRequest · CadastrarFichaProdutoEndpoint.Executar · FichaProdutoRepository.
  • No seu mundo: Controllers/ + DTOs/ + Services/ + Repositories/.

Em uma frase: cada funcionalidade tem o que entra (Request), o que ela faz (Endpoint) e o que sai (Response). Onde se guarda fica com o Repository. O papel de cada um está no sufixo do nome, não na pasta.

Pergunta que responde: "quem faz o quê, agora que não há Controller nem Service?"

Como era (Clean com pastas técnicas) Como é agora (Norte) O que mudou
Controllers/FichaProdutoController.cs com [HttpPost] grupo.MapPost("/fichas-produto", CadastrarFichaProdutoEndpoint.Executar); O "controller" virou uma linha que liga a rota ao método
DTOs/CadastrarFichaProdutoDto.cs CadastrarFichaProdutoRequest (record) Dto → Request; e é um record (3.2)
Services/FichaProdutoService.Cadastrar() CadastrarFichaProdutoEndpoint.Executar() Um service por entidade vira um método por funcionalidade
Repositories/FichaProdutoRepository.cs FichaProdutoRepository Mesmo papel. Hoje guarda numa lista
IActionResult Results<Created<FichaProduto>, ValidationProblem> Os retornos possíveis ficam no tipo (3.3)

O código do Norte (S11, com um if; na S12 viraram três e depois saíram):

internal static class CadastrarFichaProdutoEndpoint
{
    public static Results<Created<FichaProduto>, ValidationProblem> Executar(
        CadastrarFichaProdutoRequest request,   // vem do CORPO da requisição (JSON), pelo tipo
        FichaProdutoRepository fichas)          // vem da DI, pelo tipo
    {
        if (string.IsNullOrWhiteSpace(request.Sku))
        {
            var erros = new Dictionary<string, string[]>
            {
                { "sku", new[] { "O SKU é obrigatório." } }
            };
            return TypedResults.ValidationProblem(erros);
        }

        var ficha = new FichaProduto(request.Sku, request.Descricao ?? "", request.Ncm ?? "");
        fichas.Adicionar(ficha);

        return TypedResults.Created($"/catalogo/fichas-produto/{ficha.Sku}", ficha);
    }
}

Atualização S12. A regra cresceu para "Ficha exige SKU, descrição e NCM" (três if), e depois os if saíram: a validação passou a ser nativa (3.11). O arquivo foi para a pasta CadastrarFichaProduto/ (3.13). O Executar hoje só cria e guarda.

Ponte com limite. O Executar faz o papel do service que você usava, mas atende uma funcionalidade só. Um FichaProdutoService cresceria com Cadastrar, Alterar, Excluir e Listar no mesmo arquivo. Aqui, cada um vira o seu próprio Endpoint. E o FichaProdutoRepository de hoje é provisório: quando o EF Core entrar, decide-se se ele vira um repositório de verdade ou se o DbContext basta.

Por que usamos · alternativa · custo. Usamos porque a funcionalidade fica inteira num lugar (fácil de achar e de testar) e porque o teste chama o método direto, sem "mockar" nada. A alternativa é o controller com service, que é comum nos projetos existentes. O custo dela: o service por entidade cresce sem limite e mistura regras de funcionalidades diferentes. O custo da nossa: mais arquivos pequenos, e quem vem de pastas técnicas estranha no começo (você, S11).

Quando não usar: numa API com dois ou três endpoints triviais, o próprio lambda no MapGet basta (forma 1 de 1.9).

Na entrevista. "Como você organiza uma API nova?" → "Por funcionalidade: cada uma com o seu request, o seu endpoint e a sua resposta, no padrão REPR. Fica fácil achar tudo o que 'cadastrar ficha' faz e testar isoladamente. O custo é ter mais arquivos, e o time precisa combinar os nomes."

Erros comuns. Achar que "não tem service, então não tem lugar para a regra" (a regra está no Executar, ou, para regra de entrada, no Request — 3.11). Nome que diz como e não o quê: o mentor chamou o repositório de FichasProdutoEmMemoria e o papel sumiu (correção da S11).

🧠 os quatro papéis e o sufixo de cada um; por que um método por funcionalidade. · 🔎 o nome "REPR".

Onde foi visto · status: S11 · feito com esqueleto do mentor · S12: regra do NCM e da descrição escritas sem esqueleto.

3.2 record: dados que entram e saem

De → para

  • No mercado: records, immutable DTOs, value equality (C# 9, .NET 5).
  • No laboratório: FichaProduto e CadastrarFichaProdutoRequest.
  • No seu mundo: DTOs como class com { get; set; }.

Em uma frase: um record declara em uma linha um tipo de dados imutável que compara pelo valor.

Como era (class) Como é agora (record) O que mudou
class com propriedades { get; set; } e construtor escrito à mão record FichaProduto(string Sku, string Descricao, string Ncm); O compilador gera o construtor e as propriedades
propriedades com set propriedades init O objeto não muda depois de criado
dois objetos com os mesmos dados são diferentes dois records com os mesmos dados são iguais Comparação por valor: o teste compara a ficha inteira de uma vez
copiar mudando um campo: new + copiar tudo à mão var outra = ficha with { Ncm = "40151000" }; with cria uma cópia alterada

Onde isso apareceu no teste:

Assert.Equal(new FichaProduto("LUV-001", "Luva nitrilica", "40151900"), criado.Value);
// funciona porque FichaProduto é record: compara Sku, Descricao e Ncm.
// com uma class comum, compararia a referência e falharia.

Ponte com limite. O record lembra o seu DTO, mas é imutável e compara por valor. Serve para dados que entram e saem. Não serve para entidade com regra que muda de estado: em M2 o Pedido vai ser class, com métodos que protegem as regras. A FichaProduto é record hoje porque, por enquanto, é só dado.

Na entrevista. "Quando você usa record?" → "Para dados imutáveis: request, response, value object. A igualdade por valor ajuda em teste e em comparação. Para entidade com identidade e estado que muda, uso class."

🧠 imutável + igualdade por valor; quando não usar. · 🔎 a sintaxe do with.

Onde foi visto · status: S11 · usado (você: "muito melhor hoje") · S12: atributos de validação nos parâmetros do record (3.11).

3.3 Respostas tipadas: Created, ValidationProblem e o 400 no formato ProblemDetails

De → para

  • No mercado: TypedResults, Results<T1, T2> (union return types), ProblemDetails (RFC 9110/9457), validation problem.
  • No laboratório: o retorno do CadastrarFichaProdutoEndpoint.Executar.
  • No seu mundo: IActionResult com Ok(), BadRequest(ModelState), CreatedAtAction().

Em uma frase: o tipo Results<Created<FichaProduto>, ValidationProblem> diz, na assinatura, que o endpoint devolve ou 201 com uma ficha ou 400 com erros de validação.

Como era Como é agora O que mudou
return CreatedAtAction(nameof(Obter), new { sku }, ficha); return TypedResults.Created($"/catalogo/fichas-produto/{sku}", ficha); URI escrita por você; vira o cabeçalho Location
return BadRequest(ModelState); return TypedResults.ValidationProblem(erros); 400 no formato padrão application/problem+json
retorno IActionResult: qualquer coisa retorno Results<Created<...>, ValidationProblem> OpenAPI e teste sabem exatamente o que pode voltar

O que o cliente recebeu na S11 (pelo .http):

HTTP/1.1 400 Bad Request
Content-Type: application/problem+json

{"type":"https://tools.ietf.org/html/rfc9110#section-15.5.1",
 "title":"One or more validation errors occurred.",
 "status":400,
 "errors":{"sku":["O SKU é obrigatório."]}}

Por que usamos · alternativa · custo. O formato ProblemDetails é um padrão (RFC): todo cliente sabe ler status, title e errors sem combinar nada com você. A alternativa é cada API inventar o próprio JSON de erro, e o custo é cada cliente escrever um tratamento diferente.

Atualização S12. A checagem saiu do Executar para a validação nativa (3.11). Duas diferenças apareceram no .http: as chaves vêm com o nome da propriedade em C# ("Sku", e não "sku"), e o Content-Type veio application/json (sem o problem+json), porque o AddProblemDetails ainda não estava registrado.

Atualização S14. O AddProblemDetails() já está registrado (3.15): o 400 da validação nativa agora sai em application/problem+json (visto no .http), com a chave Sku (maiúsculo). O Executar ainda declara ValidationProblem no tipo de retorno, mas não o devolve mais (a validação responde antes dele): ajuste pendente (tipo de retorno × documentação OpenAPI; nenhum analyzer acusou).

Na entrevista. "Por que TypedResults e não Results?" → "Porque o tipo concreto entra na assinatura: o OpenAPI documenta as respostas sozinho e o teste lê o resultado como objeto C#, sem conversão. Com IResult, nenhum dos dois sabe o que volta."

🧠 os retornos possíveis ficam no tipo; por que ProblemDetails. · 🔎 os nomes exatos (TypedResults.Created, ValidationProblem), o using Microsoft.AspNetCore.Http.HttpResults.

Onde foi visto · status: S1 (aquecimento), S9 (retenção, lacuna no teste), S11 · usado no código e no teste · S12: retenção ✅ (IsType no teste) · S14: formato padrão ligado no host.

3.4 Arquivo .http: as requisições da API dentro do repositório

De → para

  • No mercado: HTTP files, .http / .rest files, REST Client.
  • No laboratório: src/Modulos/Catalogo/Norte.Catalogo/Catalogo.http (desde a S12; antes, src/Norte.Api/Norte.Api.http).
  • No seu mundo: Postman, ou o Swagger UI.

Em uma frase: um arquivo texto com requisições HTTP que o Visual Studio executa com um clique em "Send request".

Como era Como é agora O que mudou
coleção do Postman na sua máquina .http no repositório Versionado com o código; o time inteiro tem as mesmas requisições
curl com aspas escapadas no PowerShell texto puro, sem escape Sem briga com a versão do PowerShell (S11)
um arquivo só para a API inteira (S11) um arquivo por módulo, na pasta do módulo (S12, proposta sua) Cada arquivo fica pequeno; se o módulo virar serviço (M7), as requisições vão junto 
@HostAddress = http://localhost:5071

### Cadastrar ficha completa (esperado: 201)
POST {{HostAddress}}/catalogo/fichas-produto
Content-Type: application/json

{ "sku": "LUV-001", "descricao": "Luva nitrilica", "ncm": "40151900" }

### Cadastrar ficha sem NCM (esperado: 400, erro em ncm)
POST {{HostAddress}}/catalogo/fichas-produto
Content-Type: application/json

{ "sku": "LUV-003", "descricao": "Luva nitrilica", "ncm": "" }

@HostAddress declara uma variável (cada arquivo declara a sua); {{HostAddress}} usa; ### separa as requisições. Cada funcionalidade nova acrescenta as suas requisições ao arquivo do módulo. Uma requisição por lado da regra: só o campo que se quer testar fica errado (na S12, a antiga "sem SKU" também vinha sem NCM e violava duas regras).

Não é do .NET 10: é recurso da IDE. Veio do VS Code (extensão REST Client) e das IDEs JetBrains; chegou ao Visual Studio 2022 em 2023 (17.5/17.6). Desde o .NET 8, o dotnet new webapi já cria o arquivo.

Ponte com limite. O .http é teste manual: alguém precisa clicar e olhar a resposta. Não substitui o teste automático (3.6, 3.12), que roda sozinho no dotnet test e no CI.

🧠 manual × automático; por que versionar; um arquivo por módulo. · 🔎 a sintaxe (@, {{}}, ###).

Onde foi visto · status: S11 · usado · S12: reorganizado por módulo (decisão sua) · S14: usado para ver o 404, o 500 e o 400 em problem+json.

3.5 O projeto de testes: xUnit, referência e InternalsVisibleTo

De → para

  • No mercado: test project, xUnit, InternalsVisibleTo.
  • No laboratório: tests/Modulos/Catalogo/Norte.Catalogo.Tests/.
  • No seu mundo: projetos *.Tests (se havia).

Em uma frase: cada módulo tem um projeto de testes no caminho espelhado de src/, que referencia o módulo e enxerga o que é internal nele.

Os comandos (S11):

dotnet new xunit -n Norte.Catalogo.Tests -o tests/Modulos/Catalogo/Norte.Catalogo.Tests
dotnet sln Norte.slnx add tests/Modulos/Catalogo/Norte.Catalogo.Tests/Norte.Catalogo.Tests.csproj
dotnet add tests/Modulos/Catalogo/Norte.Catalogo.Tests/Norte.Catalogo.Tests.csproj reference src/Modulos/Catalogo/Norte.Catalogo/Norte.Catalogo.csproj

O nome. Norte.Catalogo.Tests: o sufixo técnico fica em inglês, como Handler e Request (ADR-001). O nome de cada teste fica em português (Recusa_ficha_sem_sku_e_devolve_400).

Por que o InternalsVisibleTo. Pelo ADR-002, tudo no Catalogo é internal (1.3), então o projeto de testes não veria o endpoint. No Norte.Catalogo.csproj:

<ItemGroup>
  <InternalsVisibleTo Include="Norte.Catalogo.Tests" />
</ItemGroup>
Como era Como é agora O que mudou
[assembly: InternalsVisibleTo("...")] num AssemblyInfo.cs <InternalsVisibleTo Include="..." /> no .csproj Mesma função, declarada no projeto

Ponte com limite. O InternalsVisibleTo abre o internal só para o projeto nomeado. O Pedidos continua sem enxergar nada do Catalogo além do CatalogoModulo (e, desde o ADR-003, dos *Request — 3.11).

Desde a S12: o mesmo projeto também tem os testes de integração do módulo, em classes ...ApiTests, com o pacote Microsoft.AspNetCore.Mvc.Testing e referência ao Norte.Api (3.12). Desde a S14, é o InternalsVisibleTo que permite ao teste do 500 citar o FichaProdutoRepository (internal) para trocá-lo (3.16).

🧠 por que o teste precisa do InternalsVisibleTo. · 🔎 os comandos e o XML.

3.6 Anatomia de um teste: Arrange, Act, Assert

De → para

  • No mercado: unit test, AAA (Arrange–Act–Assert), [Fact], assertions.
  • No laboratório: CadastrarFichaProdutoEndpointTests.
  • No seu mundo: teste de controller com mock do service.

Em uma frase: um teste prepara a entrada (Arrange), executa a funcionalidade (Act) e confere o resultado contra a regra (Assert).

O teste do Norte, linha por linha (S11):

[Fact]                                            // marca o método como teste para o xUnit
public void Recusa_ficha_sem_sku_e_devolve_400()  // o nome diz a REGRA e o resultado esperado
{
    // Arrange: o que o endpoint receberia da DI e do corpo da requisição
    var repositorio = new FichaProdutoRepository();
    var request = new CadastrarFichaProdutoRequest(null, "Luva nitrilica", "40151900");

    // Act: chama o método direto, sem HTTP e sem subir a API
    var resultado = CadastrarFichaProdutoEndpoint.Executar(request, repositorio);

    // Assert: o resultado é o 400, com erro no campo sku
    var problema = Assert.IsType<ValidationProblem>(resultado.Result);
    Assert.Equal(400, problema.StatusCode);
    Assert.Contains("sku", problema.ProblemDetails.Errors.Keys);
}

Atualização S12. Este teste (e os do NCM e da descrição) foi apagado: com a validação nativa, a regra saiu do Executar, e o teste de unidade deixou de passar por ela. A recusa hoje é testada por integração (3.12). O raciocínio desta entrada continua valendo para tudo o que o Executar ainda faz (o teste do 201).

A peça-chave: resultado.Result. O Results<Created<...>, ValidationProblem> guarda qual dos dois aconteceu. O Assert.IsType<ValidationProblem> confere o tipo e devolve o objeto tipado, de onde se lê StatusCode e ProblemDetails. É a resposta da lacuna da S9: com IResult, o teste não saberia o que veio.

Como era Como é agora O que mudou
new FichaProdutoController(mockService.Object) new FichaProdutoRepository() + Executar(...) Nada para "mockar": o método recebe tudo por parâmetro
converter IActionResult para ObjectResult e ler .StatusCode Assert.IsType<ValidationProblem>(resultado.Result) O tipo diz o que voltou

Cada Assert precisa poder falhar. Na S11, duas linhas foram cortadas por isso:

  • Assert.NotEmpty(Errors): passaria também com um erro só de NCM, então não prova a regra do SKU. Trocado por Assert.Contains("sku", ...).
  • Assert.Null(repositorio.ObterPorSku("LUV-001")): nenhuma ficha LUV-001 foi enviada nesse teste, então a linha era sempre verdadeira.

E na S12 (relatório do Claude local): depois de Assert.IsType<ValidationProblem>, as linhas Assert.Equal(400, problema.StatusCode) e Assert.NotNull(problema.ProblemDetails) não conseguem falhar — o ValidationProblem é sempre 400 e a propriedade nunca é nula. Não estão erradas, mas não provam nada a mais.

Teste de unidade × teste de integração. Este teste chama o método direto: é rápido e mostra exatamente onde quebrou, mas não passa pelo que acontece antes do Executar (rota, leitura do JSON, DI, validação). A S12 mostrou o custo disso na prática: ver 3.12.

Na entrevista. "Como você testa um endpoint?" → "Teste de unidade chamando o handler direto para o que ele faz, porque é rápido e aponta o erro exato. E testes de integração pela API, com WebApplicationFactory, para o que acontece antes dele: rota, serialização, DI e validação. O de unidade não pega erro de configuração; o de integração é mais lento."

Erros comuns. Copiar o teste-modelo e esquecer de trocar o Assert (você, S11). Assert que nunca falha. Nome de teste que não diz a regra (Teste1), ou que diz o contrário (Cadastra_ficha_sem_ncm_e_devolve_400, S12: a ficha não é cadastrada). Teste que repete outro já existente (S12: Cadastra_ficha_com_ncm_e_devolve_201 = o teste do 201). S14: o critério fraco ProblemDetails não nulo (um {} passaria) — o teste do 500 confere status, tipo de conteúdo, traceId e a ausência de detail e exception (3.16).

🧠 AAA; o nome do teste diz a regra; todo Assert precisa poder falhar; unidade × integração. · 🔎 os nomes dos Assert.*.

Onde foi visto · status: S11 · 1º teste com esqueleto do mentor; 2º escrito por você com revisão · S12: testes do NCM e da descrição sem ajuda, Assert certo de primeira · em melhora (núcleo de M1).

3.7 Vermelho → verde: como saber que o teste protege a regra

De → para

  • No mercado: red–green(–refactor), TDD, "see the test fail", mutation testing (a versão automatizada da ideia).
  • No laboratório: comentar o if do SKU (S11) ou tirar o [Required] (S12) ou tirar o UseExceptionHandler() (S14) e rodar o dotnet test.

Em uma frase: um teste só prova alguma coisa se você já o viu falhar quando a regra estava quebrada.

O que aconteceu na S11, na ordem:

Passo Testes existentes if do SKU Resultado Por quê
1 só Cadastra_ficha_com_sku_e_devolve_201 comentado 🟢 1 aprovado O teste manda com SKU: nunca passa pelo if. Não protege a regra
2 + Recusa_ficha_sem_sku_e_devolve_400 comentado 🔴 1 falhou Sem o if, o endpoint devolve 201, e o teste exige 400
3 os dois descomentado 🟢 2 aprovados A regra está lá, e o teste confirma

Na S12, com a validação nativa: sem o [Required] da descrição, só Recusa_ficha_sem_descricao_e_devolve_400 ficou vermelho; os do SKU e do NCM seguiram verdes. Isso prova que cada teste protege um lado da regra, nem mais nem menos.

Na S14, o caso mais difícil: o teste do 500 nasceu verde e continuou verde sem a linha que devia proteger (a página do desenvolvedor de Development fazia o trabalho). Só ficou vermelho quando o teste passou a rodar em Production (3.16). Moral: o vermelho tem de ser visto também em teste que nasce verde — o ambiente do teste pode estar mascarando a falta.

A regra do laboratório (decisão sua, 08/10/2026): todo teste novo precisa ser visto vermelho pelo menos uma vez — ou porque foi escrito antes do código, ou porque você tirou o código e ele falhou. Não é o TDD completo (teste primeiro, refatoração guiada): é a parte do TDD que dá a garantia, sem o custo de mudar o jeito de trabalhar.

A pergunta que você fez no passo 1, "não deveria dar erro?", é a pergunta central de quem testa. A resposta: um teste só protege o que ele exercita.

Cuidado com o "vermelho pelo motivo errado". A primeira versão do teste da recusa também ficou vermelha no passo 2, mas porque o Assert copiado do modelo esperava 201. Com o if de volta, ela continuaria vermelha. Vermelho só vale como prova quando fica verde ao restaurar a regra.

Na entrevista. "Como você sabe que um teste está testando alguma coisa?" → "Eu o vejo falhar. Quebro a regra de propósito (comento a linha, tiro o atributo), rodo, e o teste tem de ficar vermelho. Depois restauro e ele fica verde. Teste que nunca falhou pode estar passando por acaso."

🧠 o ciclo e o porquê; "vermelho pelo motivo errado"; teste que nasce verde também se prova. · 🔎 o nome mutation testing (ferramenta: Stryker.NET, só como vocabulário).

Onde foi visto · status: S11 · feito por você · S12: feito 3 vezes, sem pedir · S14: 4 combinações vistas no teste do 500; regra adotada em 08/10.

3.8 A sintaxe mais curta do C# moderno (o que já apareceu no Norte)

3.10 Como pensar um teste: da frase do negócio ao Assert

De → para

  • No mercado: Given / When / Then (BDD), test case design, equivalence classes, boundary values, one behavior per test.
  • No laboratório: o método de testes do Norte (decisão sua, 02/10): português estruturado antes do código, em 4 degraus. É adaptação do laboratório, montada sobre o Dado/Quando/Então do mercado.
  • No seu mundo: "sempre empurrei com a barriga" (você, S11).

Em uma frase: o teste nasce de uma frase do negócio; o código do teste é só a tradução dessa frase — o Assert não se inventa, se traduz.

Os 6 passos:

  1. A regra numa frase do negócio: "Ficha exige SKU, descrição e NCM."
  2. Um exemplo que respeita e um que quebra (por lado da regra): ficha completa × ficha sem NCM.
  3. O que o sistema faz em cada um: completa → 201 com a ficha; sem NCM → 400 com erro no NCM.
  4. O nome do teste = a frase do passo 3: Recusa_ficha_sem_ncm_e_devolve_400.
  5. O código: Arrange = o exemplo (só o campo do teste errado) · Act = uma linha · Assert = cada pedaço do passo 3, traduzido.
  6. Cada Assert consegue falhar? Prove com 🔴 → 🟢 (3.7).

Exemplo resolvido, em português estruturado (S12):

Cadastra_ficha_com_sku_e_devolve_201 Recusa_ficha_sem_ncm_e_devolve_400
Dado uma ficha com SKU LUV-001, descrição e NCM 40151900 uma ficha com SKU e descrição, sem NCM
Quando eu cadastro a ficha eu cadastro a ficha
Então 201, e a ficha criada é a que eu enviei 400, e o erro aponta o campo NCM

Tabela de tradução: frase → Assert (🔎, consulte à vontade):

Frase do "Então" Assert
"o resultado é um 400 de validação" Assert.IsType<ValidationProblem>(resultado.Result) (unidade) · Assert.Equal(HttpStatusCode.BadRequest, resposta.StatusCode) (integração)
"o erro aponta o campo X" Assert.Contains("X", problema.Errors.Keys)
"a ficha criada é a que eu enviei" Assert.Equal(new FichaProduto(...), criado.Value)
"existe / foi guardada" Assert.NotNull(...)
"não existe / não foi guardada" Assert.Null(...)
"lança erro" Assert.Throws<TipoDaExcecao>(() => ...)
"o cliente recebe 500 em formato padrão, sem vazar a causa" (S14) Assert.Equal(HttpStatusCode.InternalServerError, ...) + ContentType.MediaType = application/problem+json + Assert.Contains("traceId", ...Extensions.Keys) + Assert.Null(problema.Detail) + Assert.DoesNotContain("exception", ...Extensions.Keys) (3.16)

Os 4 degraus (um por vez): (1) ler um teste pronto em português estruturado → (2) escrever só o português estruturado, e o mentor revisa o raciocínio → (3) traduzir para código → (4) provar com 🔴 → 🟢.

O checklist anti-sobra (decisão sua, 05/10): ao adaptar um teste-modelo, para cada linha copiada: "esta linha ainda é verdade para o caso novo?". Na S12 ele pegou: o corpo da requisição (só o campo do teste vazio), a chave do Assert e o ?? "" que ficou sem sentido no Executar. Escapou uma vez: nome e comentário do teste do NCM.

Não confunda: um teste por lado da regra (3 lados = 3 testes de recusa + o caminho feliz) × um teste que confere tudo de uma vez (quando falha, não diz qual lado quebrou).

Na entrevista. "Como você decide o que testar?" → "Parto da regra em uma frase de negócio. Para cada lado dela, um exemplo que respeita e um que quebra; o resultado esperado vira o nome do teste e o Assert. E vejo cada teste falhar com a regra quebrada, para saber que ele protege alguma coisa."

🧠 os 6 passos; "o Assert é tradução"; um teste por lado da regra. · 🔎 a tabela frase → Assert.

3.11 Validação nativa do .NET 10: a regra de entrada declarada no Request

De → para

  • No mercado: built-in validation for Minimal APIs (.NET 10), DataAnnotations, AddValidation(), validation source generator. Alternativa comum: FluentValidation.
  • No laboratório: [Required] nos parâmetros do CadastrarFichaProdutoRequest + services.AddValidation() no AddCatalogo · ADR-003.
  • No seu mundo: [Required] no modelo + [ApiController] devolvendo 400 sozinho, nos controllers.

Em uma frase: no .NET 10, uma Minimal API valida a entrada antes de chamar o endpoint, a partir dos atributos do Request, e devolve 400 com todos os erros de uma vez.

Pergunta que responde: "onde mora a validação de entrada, agora que não há [ApiController]?"

O problema que resolveu (visto no .http, S12): com três if no Executar, uma ficha com SKU, descrição e NCM vazios recebia um erro (o do SKU), porque cada if faz return no primeiro problema. Quem usa a API precisava de três idas e voltas. E cada campo obrigatório novo pedia mais 7 linhas iguais.

Como era Como é agora (.NET 10) O que mudou
controllers: [Required] + [ApiController] → 400 automático Minimal APIs: [Required] no record + services.AddValidation() Minimal APIs não tinham validação embutida até o .NET 9 (era if ou FluentValidation)
validação antes da action validação antes do Executar, no caminho da requisição o Executar só roda com entrada válida
if manual, um erro por vez (S12, manhã) 400 com os três erros a regra fica declarada, não programada

O código do Norte (S12):

// CadastrarFichaProduto/CadastrarFichaProdutoRequest.cs
using System.ComponentModel.DataAnnotations;

namespace Norte.Catalogo.CadastrarFichaProduto;

public record CadastrarFichaProdutoRequest(              // public: exigência do gerador (ADR-003)
    [Required(ErrorMessage = "O SKU é obrigatório.")] string? Sku,
    [Required(ErrorMessage = "A descrição é obrigatória.")] string? Descricao,
    [Required(ErrorMessage = "O NCM é obrigatório.")] string? Ncm);

// CatalogoModulo.cs, dentro do AddCatalogo
services.AddValidation();   // no MÓDULO: o gerador só enxerga os tipos do projeto onde é chamado

// CadastrarFichaProdutoEndpoint.Executar — os três if saíram
var ficha = new FichaProduto(request.Sku!, request.Descricao!, request.Ncm!);

Resposta ao POST com os três campos vazios:

HTTP/1.1 400 Bad Request
{"title":"One or more validation errors occurred.",
 "errors":{"Sku":["O SKU é obrigatório"],"Descricao":["A descrição é obrigatória"],"Ncm":["O NCM é obrigatório"]}}

Como funciona por baixo. Um gerador de código (source generator, que roda no build) procura os tipos usados como parâmetro dos endpoints (MapPost…) e gera o código que lê os atributos. O AddValidation() registra esse código e liga um filtro que roda antes do endpoint. O [Required] recusa null, "" e texto só com espaços (o mesmo que o IsNullOrWhiteSpace fazia).

As três regras que a S12 ensinou (do jeito difícil):

  1. Só tipos public. O gerador do .NET 10 ignora internal — sem erro e sem log: a validação simplesmente não roda e o endpoint aceita qualquer coisa (o nosso 201 com ficha vazia). Por isso o ADR-003 abriu uma exceção ao ADR-002 só para os *Request.
  2. AddValidation() no projeto do tipo. O gerador só cria validação para os tipos do projeto onde o AddValidation() é chamado. Como o Request mora no Norte.Catalogo, a chamada fica no AddCatalogo — o ponto de entrada do módulo (ADR-002) é o lugar natural. Chamar só no Program.cs do host não cobre a biblioteca.
  3. Não precisa mexer no .csproj. O SDK do .NET 10 já liga o que o gerador precisa (interceptors) em todo projeto net10.0. Artigos da época de teste (preview) mandavam acrescentar InterceptorsNamespaces — não vale mais (foi a hipótese errada do mentor).

Por que o ! no Executar. Sem os if, o compilador avisa que request.Sku pode ser nulo (CS8604): ele não enxerga a validação, que só existe com a aplicação rodando. O ! é uma promessa ao compilador: "isso já foi garantido em outro lugar". Antes, com os if, o ! era sobra (o IsNullOrWhiteSpace já informava o compilador); agora é necessário. A promessa só vale se o Executar for chamado depois da validação — e é exatamente isso que o teste de unidade não faz (3.12).

Registro S14. Na main (merge do PR #3), o request.Sku sem o ! não compilava (CS8604, confirmado compilando a main numa cópia limpa com git worktree). O ! entrou, sem ser percebido, no commit do PR #4. A causa de a main ter ficado quebrada não foi investigada. Sem CI, nada acusou: é um dos motivos da S15 (3.17).

Por que usamos · alternativa · custo — a comparação justa (correção do mentor, S14 parte 2). Na S12, esta entrada tratava o FluentValidation de passagem ("licença aberta, muito comum, mais uma dependência"), o que não dava ao leitor como decidir. Como você precisa defender A ou B em entrevista, a comparação certa é por critério, e o critério de escolha é a complexidade da regra (decisão sua, 06/10):

Critério Validação nativa (.NET 10) FluentValidation
Onde a regra fica em atributos no próprio Request numa classe validadora separada (AbstractValidator<T>)
Regra condicional ("se o canal é X, o campo Y é obrigatório") só com IValidatableObject ou um atributo próprio: código dentro do tipo When(...)/Unless(...) na API fluente
Regra sobre listas (cada item do pedido) atributos nos itens; regra entre itens exige código próprio regras por item e sobre a coleção (RuleForEach)
Dados de fora / assíncrona ("o SKU existe?") tratar como não suportada até prova em contrário (hipótese em aberto). Mas isso não é validação de entrada: é regra de negócio existe regra assíncrona (a conferir ao adotar). Continua sendo regra de negócio e fica no endpoint/domínio
Composição e reuso atributo reutilizável; tipos aninhados pelo gerador validador dentro de validador; regras compartilhadas
Teste por integração (a validação roda antes do handler; S12) o validador se testa sozinho, sem HTTP (a conferir ao adotar)
Ligação nas Minimal APIs automática: AddValidation() + filtro manual (chamar o validador no endpoint ou num filtro); não há integração nativa (a conferir antes de adotar)
Dependência nenhuma (faz parte do .NET 10) um pacote NuGet; licença aberta (Apache 2.0, verificada em 2025 — conferir de novo antes de afirmar)
O que eu pago Request public (ADR-003); chaves PascalCase; regra complexa vira código dentro do tipo; teste por integração dois estilos de validação na mesma solution; ligação manual; uma dependência a mais

Critério do Norte: forma da entrada (obrigatório, tamanho, formato, faixa) → validação nativa, levada ao limite no Catalogo; regra composta, condicional ou sobre listas → FluentValidation, a começar pelo CriarPedido no Pedidos (M1), em 3 passos (tentar com a nativa e ver o limite; resolver com FluentValidation + ADR na hora; meia página sua comparando ganho e preço). Regra que depende de dados de fora → regra de negócio, no endpoint ou no domínio.

Quando não usar: regra que depende de dados de fora (ex.: "SKU não pode repetir", que precisa consultar o banco) não é validação de entrada: mora no endpoint ou no domínio. A validação nativa é para a forma da entrada (obrigatório, tamanho, formato).

Não confunda: validação de entrada (o JSON veio com o que precisa?) × regra de negócio (isso é permitido agora?). Pergunta de entrevista de M1: "onde fica a validação de entrada e onde fica a regra de negócio?".

Na entrevista. "Como você valida entrada numa Minimal API no .NET 10?" → "Com a validação nativa: atributos de DataAnnotations no request e AddValidation(). Ela roda antes do handler e devolve todos os erros num ProblemDetails. Cuidados: o tipo precisa ser público, a chamada precisa estar no projeto do tipo, e a regra passa a ser testada por integração, porque o handler chamado direto não passa pela validação. Para regra condicional ou sobre listas, eu avaliaria o FluentValidation: ele separa a regra num validador testável sozinho, ao preço de um segundo estilo de validação e de ligar o validador à mão."

Erros comuns: Request internal (validação some em silêncio); AddValidation() só no host; achar que o teste de unidade continua protegendo a regra; deixar os avisos de nulo no código.

🧠 roda antes do endpoint; todos os erros de uma vez; só public; AddValidation() no projeto do tipo; a consequência para os testes; o critério pela complexidade da regra e o preço de cada lado. · 🔎 o using System.ComponentModel.DataAnnotations, a sintaxe do [Required(ErrorMessage = ...)], o DisableValidation().

3.12 Teste de integração com WebApplicationFactory: o teste passa por onde a regra mora

De → para

  • No mercado: integration test, WebApplicationFactory<TEntryPoint>, in-memory test server (TestServer), Microsoft.AspNetCore.Mvc.Testing, class fixture.
  • No laboratório: CadastrarFichaProdutoApiTests (3 testes de recusa + o do 500, S14).
  • No seu mundo: subir a API e testar no Postman, à mão.

Em uma frase: o WebApplicationFactory<Program> sobe a API inteira em memória e o teste faz requisições HTTP de verdade — por isso ele cobre tudo o que acontece antes do endpoint.

Pergunta que responde: "a regra saiu do endpoint; como eu provo que ela continua valendo?"

A frase-chave: o teste precisa passar por onde a regra mora.

Requisição HTTP → [rota] → [JSON → Request] → [validação nativa] → Executar → resposta
                                                     ↑                 ↑
                                         a regra de entrada     o teste de UNIDADE
                                         mora aqui (S12)        entra aqui
                  ↑
          o teste de INTEGRAÇÃO entra aqui

O que aconteceu na S12, na ordem (o "porquê" que não fixou no dia — leia devagar):

Passo O que foi feito Resultado Por quê
1 três if no Executar; 3 testes de recusa de unidade 🟢 a regra estava dentro do Executar, e o teste chamava o Executar
2 os if saíram; [Required] no Request .http: 400 com os 3 erros ✅ a regra foi para o caminho HTTP, antes do Executar
3 dotnet test (previsão sua: "3 vermelhos") 🔴🔴🔴 + 🟢 o teste de unidade chama o Executar direto: pula a validação; o Executar recebe os nulos, cria a ficha (os !) e devolve 201
4 3 testes de recusa de integração 🟢🟢🟢 a requisição passa pela validação, como em produção
5 os 3 de unidade apagados; o do 201 fica 4 🟢 o 201 testa o que o Executar ainda faz (criar e guardar)
6 sem o [Required] da descrição só o da descrição 🔴 cada teste protege um lado da regra

Unidade × integração:

Teste de unidade (...EndpointTests) Teste de integração (...ApiTests)
Chama o método Executar, direto a API, por HTTP (HttpClient)
Passa pela rota, JSON, DI e validação? não sim
Velocidade muito rápido mais lento (sobe o host; uma vez por classe)
Quando falha, aponta a linha exata do Executar "a requisição não deu o esperado" (mais amplo)
Protege, no Norte criar e guardar a ficha (201) a regra "Ficha exige SKU, descrição e NCM"

using System.Net.Http.Json;
using Microsoft.AspNetCore.Http;
using Microsoft.AspNetCore.Mvc.Testing;

namespace Norte.Catalogo.Tests.CadastrarFichaProduto;

// IClassFixture: o xUnit cria UMA fábrica (uma API em memória) para todos os testes desta classe.
public class CadastrarFichaProdutoApiTests(WebApplicationFactory<Program> fabrica)
    : IClassFixture<WebApplicationFactory<Program>>
{
    [Fact]
    public async Task Recusa_ficha_sem_sku_e_devolve_400()
    {
        // Arrange: um cliente HTTP falando com a API em memória, e o corpo da requisição
        var cliente = fabrica.CreateClient();
        var corpo = new { sku = "", descricao = "Luva nitrilica", ncm = "40151900" };

        // Act: requisição de verdade — passa pela validação nativa antes do Executar
        var resposta = await cliente.PostAsJsonAsync("/catalogo/fichas-produto", corpo);

        // Assert: 400, com erro no campo Sku (e só a falta do SKU explica o erro)
        Assert.Equal(HttpStatusCode.BadRequest, resposta.StatusCode);
        var problema = await resposta.Content.ReadFromJsonAsync<HttpValidationProblemDetails>();
        Assert.NotNull(problema);
        Assert.Contains("Sku", problema.Errors.Keys);

}

WebApplicationFactory<Program> sobe o Norte.Api (o Program do host) com todos os módulos, em memória, sem porta
IClassFixture<...> + construtor primário o xUnit cria uma fábrica e a passa para todos os testes da classe
fabrica.CreateClient() um HttpClient que fala com essa API em memória

async Task o teste espera a resposta HTTP

Program no .NET 10. Com Program.cs sem classe (top-level statements), o Program era internal e o projeto de testes não o enxergava; até o .NET 9 era preciso escrever public partial class Program { } no fim do Program.cs. No .NET 10 o SDK gera isso sozinho.

Cuidado: estado compartilhado. A fábrica (e, com ela, o FichaProdutoRepository registrado como Singleton) é a mesma para todos os testes da classe. Hoje não importa (os testes de recusa não guardam nada). Quando um teste depender do que outro guardou — por exemplo, "não aceita SKU repetido" —, cada teste precisa usar dados próprios ou um banco limpo. Isso volta com o EF Core e, mais adiante, com Testcontainers.

Atualização S14. A fábrica compartilhada é a base para trocar uma peça só num teste: o WithWebHostBuilder cria uma cópia da API com o ajuste, sem mexer na fábrica dos outros testes (no log aparecem dois hosts). Visto no teste do 500 — 3.16. Também vale: por padrão, a API do teste roda em ambiente Development (documentação oficial + log).

Ponte com limite. O teste de integração lembra o teste manual no Postman, mas roda sozinho no dotnet test (e no CI), sem subir processo nem abrir porta. Ele não substitui o teste de unidade: é mais lento e, quando falha, aponta menos precisamente.

Na entrevista. "Teste de unidade do handler ou teste de integração pela API?" (pergunta do banco de M1) → "Os dois, cada um onde a regra mora. O que o handler faz, testo por unidade: é rápido e aponta a linha. O que acontece antes dele — rota, serialização, DI, validação — só um teste que passe pelo HTTP prova; uso WebApplicationFactory. No .NET 10 isso ficou claro: a validação nativa roda antes do handler, então o teste de unidade passaria verde mesmo com a validação quebrada."

Erros comuns (S12): achar que o teste de unidade continua protegendo a regra depois que ela saiu do endpoint; deixar os testes antigos comentados em vez de apagados (com os mesmos nomes dos novos, o Test Explorer pareceu mostrar os novos falhando); conferir a chave em minúscula ("sku") quando a validação nativa devolve "Sku".

De → para

/// <summary>
/// Protege o <c>UseExceptionHandler()</c> do <c>Program.cs</c>: sem ele, uma exceção
/// inesperada vaza o rastro do erro para o cliente. O teste força a exceção trocando o
/// repositório por um que lança, e confere o 500 em <c>application/problem+json</c>,
/// sem <c>detail</c> nem <c>exception</c>.
/// O ambiente é <c>Production</c> de propósito: em <c>Development</c> a página de exceção
/// do desenvolvedor captura o erro e devolve 500 mesmo sem o <c>UseExceptionHandler()</c>,
/// e o teste passaria sem proteger nada.
/// </summary>
[Fact]
public async Task Erro_inesperado_devolve_500_em_problem_details_sem_vazar_detalhes()
{
    // Dado: a API do teste, em ambiente Production, recebe um repositório que lança exceção
    var cliente = fabrica
        .WithWebHostBuilder(construtor =>
        {
            construtor.UseEnvironment("Production");
            construtor.ConfigureTestServices(servicos =>
                servicos.AddSingleton<FichaProdutoRepository>(
                    _ => throw new InvalidOperationException("Falha simulada no repositorio")));
        })
        .CreateClient();

    // Quando: uma ficha válida é enviada
    var corpo = new { sku = "LUV-001", descricao = "Luva nitrilica", ncm = "40151900" };
    var resposta = await cliente.PostAsJsonAsync("/catalogo/fichas-produto", corpo);

    // Então: o cliente recebe 500, no formato padrão de erro, sem detalhes internos
    Assert.Equal(HttpStatusCode.InternalServerError, resposta.StatusCode);
    Assert.Equal("application/problem+json", resposta.Content.Headers.ContentType?.MediaType);

    var problema = await resposta.Content.ReadFromJsonAsync<ProblemDetails>();
    Assert.NotNull(problema);
    Assert.Contains("traceId", problema.Extensions.Keys);
    Assert.Null(problema.Detail);
    Assert.DoesNotContain("exception", problema.Extensions.Keys);
}

Respostas

Mostrar respostas
  1. CadastrarFichaProdutoEndpoint, no método Executar (3.1).
  2. Assert.IsType<ValidationProblem>(resultado.Result) (ou Created<FichaProduto>): confere o tipo e devolve o objeto tipado (3.6).
  3. Verde. Ele nunca exercita a recusa, então não protege a regra. Quem protege é o teste de recusa (3.7).
  4. Porque record compara por valor: os três campos iguais = objetos iguais. Com class comum, compararia a referência e falharia (3.2).
  5. O <InternalsVisibleTo Include="Norte.Catalogo.Tests" /> no Norte.Catalogo.csproj (3.5).
  6. Qualquer outro erro de validação, por exemplo um erro só do NCM. Por isso o Assert certo é Assert.Contains com a chave do campo (3.6).
  7. O .http é manual: você clica e olha. O projeto de testes é automático: roda sozinho no dotnet test (e, mais adiante, no CI) e falha sem ninguém olhar (3.4).
  8. Com os if: um (o primeiro return). Com a validação nativa: três (3.11).
  9. 201, com a ficha vazia gravada: o gerador ignora tipos internal, sem erro nem log (3.11, 3.14).
  10. Porque o gerador só cria validação para os tipos do projeto onde o AddValidation() é chamado, e o Request mora no Norte.Catalogo (3.11).
  11. 201. A validação roda no caminho HTTP, antes do Executar; chamado direto, o Executar não passa por ela (3.12).
  12. Teste de integração (CadastrarFichaProdutoApiTests): a regra mora na validação, antes do Executar, e só um teste que faz a requisição de verdade passa por lá (3.12).
  13. Usado por uma funcionalidade → pasta dela; usado por várias funcionalidades do módulo → raiz (3.13).
  14. A página de exceção do desenvolvedor (DeveloperExceptionPageMiddleware), ligada sozinha pelo CreateBuilder em Development; é ela que manda o corpo, com rastro. O ProblemDetails só escreve o corpo quando alguém o pede; não captura nada (3.15).
  15. AddProblemDetails() escreve; UseExceptionHandler() captura; UseStatusCodePages() preenche o corpo vazio (3.15).
  16. Porque em Development a página do desenvolvedor captura a exceção e também devolve 500. No log, a categoria do fail: muda de ExceptionHandlerMiddleware para DeveloperExceptionPageMiddleware (3.15, 3.16).
  17. new cria um repositório normal, que não lança; herdar é impossível (internal sealed, sem interface). A fábrica só roda quando o framework pede o repositório, e aí lança (3.16).
  18. No log (fail: ...ExceptionHandlerMiddleware[1] + a exceção completa), não no corpo. O traceId do corpo é o que o cliente informa para achar essa entrada no log (3.15).
  19. Efeito no cliente: quem já consumia a API e assumia 404 sem corpo precisa se adaptar (quem só confere o status não muda); o 404 de rota inexistente passa a ter o mesmo formato genérico de um 404 de "ficha não encontrada" (3.15).
  20. É condicional, então o critério do Norte aponta para o FluentValidation (When(...)); a nativa só faria com IValidatableObject ou atributo próprio, com o código dentro do tipo. O preço: dois estilos de validação na solution, ligação manual do validador nas Minimal APIs e uma dependência a mais (conferir licença e integração antes de adotar) (3.11).
