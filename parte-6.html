GUIA-DOTNET — Parte 6: O código grava no banco

Sessão: S16 (12/10/2026) · Versão: 1.0 · Entradas: 6.1 a 6.8 (6.8 = diagnóstico) + juntando tudo + teste-se

Até a S15 o Catalogo guardava as fichas numa lista em memória: a API reiniciava e o cadastro sumia. Esta parte explica o que entrou para a ficha sobreviver: o EF Core 10 falando com o PostgreSQL, a tabela criada por migration, um schema por módulo e a reorganização das pastas do módulo. Todo exemplo vem do código do Norte.

Onde estamos no mapa dos níveis (Parte 0): a funcionalidade passou a ter persistência real. O caminho da requisição ficou completo: endpoint → validação → repositório → DbContext → banco.

6.1 O Postgres local, a connection string e o provider

De → para

Como aparece nas vagas Nome no laboratório O mundo do aluno
connection string, configuration providers, EF Core provider ConnectionStrings:Norte, Npgsql.EntityFrameworkCore.PostgreSQL appsettings.json + Startup.ConfigureServices com UseSqlServer; no Norte o banco é Postgres e o provider é Npgsql

Em uma frase: para gravar, o programa precisa de três coisas fora do código C#: um banco rodando, o texto que diz como entrar nele (a connection string) e o pacote que ensina o EF Core a falar com esse banco (o provider).

Pergunta que responde: de onde a API tira onde o banco está e como entrar nele?

Como era (.NET 6) Como é agora (.NET 10) O que mudou
appsettings.json lido no Startup, services.AddDbContext(o => o.UseSqlServer(Configuration.GetConnectionString("X"))) appsettings.Development.json lido pelo Program.cs; o AddCatalogo(builder.Configuration) recebe a configuração e chama UseNpgsql(...) a configuração já vem carregada pelo host; o módulo recebe o IConfiguration na assinatura
banco instalado na máquina ou compartilhado Postgres 18 num container (compose.yaml na raiz) o banco do laboratório sobe e some com um comando
versão do pacote no .csproj versão no Directory.Packages.props (ADR-004) uma versão por pacote, num lugar só

O que é cada peça no Norte

Peça Onde fica Observação
Postgres 18 compose.yaml (raiz): container norte-postgres, porta 5432, volume norte-postgres-dados no Postgres 18 o volume aponta para /var/lib/postgresql; nas versões até a 17 era /var/lib/postgresql/data
connection string src/Norte.Api/appsettings.Development.json, seção ConnectionStrings, chave Norte formato: Host=localhost;Port=5432;Database=norte;Username=norte;Password=<senha do container local>
provider Npgsql.EntityFrameworkCore.PostgreSQL 10.0.3 no Norte.Catalogo traz o Microsoft.EntityFrameworkCore 10.0.4 como dependência transitiva

Dependência transitiva. Você não adicionou o Microsoft.EntityFrameworkCore: ele veio dentro do provider. Para ver: dotnet list src/Modulos/Catalogo/Norte.Catalogo package --include-transitive. Na S16 a saída mostrou o Microsoft.EntityFrameworkCore 10.0.4, junto com Abstractions, Analyzers, Relational e o Npgsql.

Onde a connection string fica, por ambiente. O .NET lê a configuração em camadas; a de baixo vence se repetir a chave:

Camada Vale em Pode ter senha?
appsettings.json todo ambiente não (vai para o git)
appsettings.{Ambiente}.json só naquele ambiente só se for descartável (container local)
user-secrets só Development, na máquina do desenvolvedor sim, mas não existe em stage
variáveis de ambiente qualquer ambiente sim
argumentos de linha de comando qualquer ambiente sim

user-secrets e appsettings não competem: cada ambiente usa as camadas que existem nele. Em stage e produção a senha vem por variável de ambiente (ou cofre, M6). No Norte de hoje (só Development, banco de container), a connection string fica no appsettings.Development.json.

Por que usamos, qual a alternativa e quanto ela custa

Connection string no appsettings.Development.json (usado) Senha em appsettings.json versionado Variável de ambiente já agora
Ganho simples; o clone do repositório já roda nenhum além de ser o mais curto senha fora do git em qualquer ambiente
Preço só vale porque a senha é de um container local descartável a senha fica no histórico do git para sempre; apagar depois é difícil cada ambiente precisa ser configurado por quem faz o deploy

Não confunda: Options Pattern (IOptions<T>) liga uma seção da configuração a uma classe sua; a connection string do DbContext segue outro caminho: GetConnectionString("Norte") → UseNpgsql(...) → o contexto recebe o resultado por um objeto do próprio EF, o DbContextOptions. Os dois usam a configuração por DI, mas são mecanismos separados.

Na entrevista: "Onde fica a connection string e como muda por ambiente?" — camadas de configuração; user-secrets só em desenvolvimento; senha de stage e produção por variável de ambiente ou cofre; nunca senha real no git.

Erros comuns: achar que o user-secrets serve para stage; confundir transitivo com "faltou instalar"; esquecer que a chave "Norte" do GetConnectionString tem de ser igual à do appsettings.

🧠 saber de cabeça: as camadas de configuração e qual vale onde; por que senha real não vai para o git; o que é dependência transitiva. 🔎 saber onde encontrar: o formato exato da connection string do Npgsql; o compose.yaml.

Onde foi visto: S16. Status: visto; a decisão de como ficam os outros ambientes é de M6.

6.2 A entidade vira classe (ADR-005)

De → para

Como aparece nas vagas Nome no laboratório O mundo do aluno
entity, reference equality, change tracking FichaProduto como internal sealed class classes de modelo com { get; set; } e construtor vazio

Em uma frase: o EF Core precisa tratar uma ficha do banco como um objeto único (igualdade por referência); o record compara por valor, então a entidade persistida é uma class.

Pergunta que responde: posso manter o FichaProduto como record agora que ele vai para o banco?

O que a documentação diz. O EF Core usa igualdade por referência para manter uma instância por entidade (rastreamento de mudanças, Find). A documentação do C# trata record como inadequado para tipo de entidade e avisa que o EF Core não atualiza entidades imutáveis. Hoje (só cadastrar e consultar) o record funcionaria; a primeira alteração de uma ficha é o ponto de quebra. Um blog de terceiros diz que dá para usar com cuidado: é opinião de autor, não regra da Microsoft.

Como era (S11) Como é agora (S16) O que mudou
internal sealed record FichaProduto(string Sku, string Descricao, string Ncm) internal sealed class FichaProduto com construtor de três parâmetros e três propriedades com private set perde-se a igualdade por valor; ganha-se uma entidade que o EF rastreia

A forma final da classe

internal sealed class FichaProduto
{
    public FichaProduto(string sku, string descricao, string ncm)
    {
        Sku = sku;
        Descricao = descricao;
        Ncm = ncm;
    }

    public string Sku { get; private set; }
    public string Descricao { get; private set; }
    public string Ncm { get; private set; }
}

Por que assim, ponto a ponto

Escolha Motivo
construtor com parâmetros o EF liga cada parâmetro à propriedade de mesmo nome (parâmetro em camelCase, propriedade em PascalCase) e chama esse construtor; o construtor também garante que a ficha nasce completa (substitui o = "")
private set propriedade sem setter não é mapeada por convenção; com private set o EF mapeia e o código de fora não altera a ficha
sem construtor vazio no EF Core moderno ele não é exigido: a documentação diz que, achando um construtor cujos parâmetros casam com propriedades mapeadas, o EF chama esse; o construtor vazio era exigência do EF antigo (idioma antigo)
internal sealed ADR-002 (fronteira do módulo); sealed porque nada herda da ficha

Três caminhos e o preço de cada um (ADR-005)

O que muda Preço
A) sealed class (escolhido) mesmo construtor; propriedades sem alteração por fora perde a igualdade por valor; teste que compara fichas com Assert.Equal ou usa with precisa de ajuste
B) record + classe de persistência separada dois tipos e um código que converte entre eles dobra o modelo de um módulo que é CRUD (cerimônia)
C) manter o record e seguir nada hoje o problema aparece na primeira alteração, com erro mais difícil de entender

Consequência nos testes. O teste de unidade do cadastro que comparava a ficha devolvida passou a conferir propriedade por propriedade (Assert.NotNull + três Assert.Equal). Depois, quando o repositório passou a exigir o contexto, esse teste foi apagado (ver 6.6).

Quando usar e quando não: entidade persistida pelo EF → classe. record continua certo para objetos de valor sem identidade e para contratos de entrada e saída (*Request).

Na entrevista: "Por que não record como entidade do EF?" — igualdade por referência × por valor; rastreamento de mudanças; entidade imutável não é atualizada. E o preço: perde-se a igualdade automática.

Erros comuns: achar que o EF exige construtor vazio; deixar public set e perder o encapsulamento; esquecer que a chave Sku precisa ser declarada (6.3).

🧠 de cabeça: por que record não serve de entidade; para que serve o private set. 🔎 onde encontrar: a regra de ligação construtor ↔ propriedade (página de Entity types with constructors, nas fontes abaixo).

Fontes: Entity types with constructors · Entity Types

6.3 O DbContext e o mapeamento da tabela

De → para

Como aparece nas vagas Nome no laboratório O mundo do aluno
DbContext, DbSet<T>, Fluent API, IEntityTypeConfiguration<T> CatalogoDbContext, FichasProduto, FichaProdutoConfiguration DbContext com OnModelCreating e uma pasta Configuration com uma classe por entidade

Em uma frase: o DbContext é a classe que representa a conversa do programa com o banco: sabe quais tabelas existem (os DbSet) e é quem grava e lê os objetos nelas; o mapeamento diz como cada classe vira tabela.

Pergunta que responde: como o código diz ao EF qual tabela guarda a FichaProduto e qual coluna é a chave?

Como era (.NET 6) Como é agora O que mudou
DbContext com OnModelCreating cheio; ou pasta Configuration com uma classe por entidade o mesmo, com a pasta Configuracoes/ (português, ADR-001) e classe internal sealed só o nome da pasta, o internal sealed e o file-scoped namespace
entity.HasMaxLength(150).IsUnicode(false) e entity.Seed() sem os dois o limite de tamanho entra quando houver regra validada na API; IsUnicode(false) é conceito do SQL Server; não há dados iniciais

O CatalogoDbContext

internal sealed class CatalogoDbContext : DbContext
{
    internal const string Schema = "catalogo";

    public CatalogoDbContext(DbContextOptions<CatalogoDbContext> options) : base(options)
    {
    }

    public DbSet<FichaProduto> FichasProduto => Set<FichaProduto>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.HasDefaultSchema(Schema);
        modelBuilder.ApplyConfigurationsFromAssembly(typeof(FichaProdutoConfiguration).Assembly);
    }
}
Trecho O que faz
: DbContext a classe base do EF Core
construtor com DbContextOptions<CatalogoDbContext> recebe as opções (provider e connection string) montadas no registro da DI (6.1)
DbSet<FichaProduto> FichasProduto diz que FichaProduto é uma entidade; por convenção o nome da propriedade é o nome da tabela, mas o mapeamento o sobrescreve
HasDefaultSchema(Schema) tabelas do módulo nascem no schema catalogo (6.5)
ApplyConfigurationsFromAssembly(...) acha todas as classes IEntityTypeConfiguration<T> do assembly e as aplica; uma linha por módulo, não por entidade

A configuração da entidade (Configuracoes/FichaProdutoConfiguration.cs, internal sealed) usa Fluent API para: nomear a tabela fichas_produto; declarar a chave em Sku (a convenção do EF só reconhece Id ou FichaProdutoId, então a chave precisa ser declarada); nomear as colunas sku, descricao, ncm; marcar as três como obrigatórias (IsRequired()). Nomes de tabela e coluna em minúsculas com sublinhado, em português (ADR-001).

Por que um arquivo por entidade e não tudo no OnModelCreating

Tudo no OnModelCreating IEntityTypeConfiguration<T> por entidade (escolhido)
Ganho tudo num arquivo só o OnModelCreating não cresce a cada entidade; cada tabela tem o seu arquivo
Preço o arquivo vira longo quando o módulo cresce um arquivo a mais por entidade e um nível de indireção; é preciso abrir o outro arquivo para ler o mapeamento

Decisão barata de desfazer (mover o código de volta leva minutos): sem ADR. A ideia veio do próprio aluno, que já usava a pasta Configuration no .NET 6.

ApplyConfigurationsFromAssembly enxerga classes internal? Foi a dúvida da sessão (as configurações do Norte são internal, ADR-002). Provado: sim — a migration gerou a tabela fichas_produto com a chave em sku.

Fluent API × DataAnnotations: o Norte usa Fluent API; a FichaProduto fica sem atributos de persistência, e a regra de como a tabela é montada fica fora da classe de domínio. Preço: o mapeamento está longe da classe.

Na entrevista: "O que é o DbContext?" (a conversa com o banco: tabelas + gravar/ler); "Fluent API ou atributos?" (onde mora o mapeamento; domínio sem atributo de persistência); "Como o EF sabe a chave?" (convenção Id/TipoId ou declarada).

Erros comuns: esquecer a chave quando a propriedade não se chama Id; achar que DbSet define o nome da tabela depois de um ToTable; esquecer de registrar o contexto na DI (6.6).

🧠 de cabeça: o que o DbContext faz; que a chave Sku precisa de declaração. 🔎 onde encontrar: a sintaxe do Fluent API (HasKey, Property, ToTable).

Onde foi visto: S16. Status: o aluno descreveu o DbContext sem consulta (herda de DbContext, DbSet por tabela, Fluent API no OnModelCreating); a escrita foi guiada.

6.4 Migrations: a tabela criada pela ferramenta

De → para

Como aparece nas vagas Nome no laboratório O mundo do aluno
migration, model snapshot, dotnet ef CriaTabelaFichasProduto, pasta Migrations/ Add-Migration e Update-Database no Package Manager Console

Em uma frase: a migration é um arquivo de código gerado que descreve como levar o banco do estado atual ao estado do modelo; o EF guarda o último estado conhecido (o snapshot) e registra o que já foi aplicado numa tabela de histórico.

Pergunta que responde: como a tabela fichas_produto passa a existir no Postgres sem eu escrever SQL?

As quatro peças

# Peça O que é
1 a ferramenta dotnet ef programa de linha de comando que cria e aplica migrations (global, versão 10.0.11 na máquina do aluno)
2 o pacote Microsoft.EntityFrameworkCore.Design no Norte.Api o que a ferramenta usa para ler o modelo do host; PrivateAssets all para não vazar para quem referencia o host
3 migrations add gera os arquivos (a migration, o .Designer.cs e o snapshot)
4 database update executa a migration no Postgres e registra na tabela de histórico

Dois projetos no comando. A documentação distingue o projeto de destino (onde os arquivos são criados) e o projeto de inicialização (o que a ferramenta compila e executa para descobrir a configuração e a connection string). No Norte o contexto está num projeto e o host em outro:

dotnet ef migrations add <Nome> --project src/Modulos/Catalogo/Norte.Catalogo --startup-project src/Norte.Api -- --environment Development
dotnet ef database update --project src/Modulos/Catalogo/Norte.Catalogo --startup-project src/Norte.Api -- --environment Development
Parte Para que serve
--project onde a pasta Migrations/ é criada (o módulo)
--startup-project o host, que a ferramenta executa para ler a configuração
-- --environment Development tudo depois do -- é repassado ao aplicativo; passa o ambiente, porque a connection string só existe no appsettings.Development.json

A página da CLI não diz qual é o ambiente padrão da ferramenta; por isso o ambiente é passado explicitamente.

O que sai na pasta Migrations/

Arquivo O que é
<carimbo>_CriaTabelaFichasProduto.cs a migration: Up (cria) e Down (desfaz)
<carimbo>_CriaTabelaFichasProduto.Designer.cs o modelo naquele instante
CatalogoDbContextModelSnapshot.cs o modelo atual; a próxima migration é a diferença entre o modelo e este arquivo

A pasta mantém o nome em inglês (Migrations), ao contrário de Configuracoes: ela pertence à ferramenta; trocar exigiria --output-dir em todo comando. O código gerado usa namespace em bloco; por isso a pasta tem um .editorconfig próprio que desliga só a regra IDE0161 (ADR-004: exceção no .editorconfig, com motivo).

Desfazer e recomeçar (só em banco local)

Comando Efeito
dotnet ef database drop --dry-run mostra qual banco seria apagado, sem apagar (conferir antes)
dotnet ef database drop --force apaga o banco, sem pedir confirmação
dotnet ef migrations remove apaga a última migration (código) e atualiza o snapshot; se for a única, o snapshot some

A página da CLI traz a opção --offline (remover sem conectar) como adicionada no EF Core 11: no Norte (EF 10) não existe. Migration já aplicada em banco compartilhado não se remove: entra uma migration nova.

database update e produção. A página de migrations diz que database update é ideal para desenvolvimento local e menos adequado para produção; para produção há bundle e script SQL revisado (M6).

Por que migration e não EnsureCreated: o EnsureCreated cria o banco uma vez e não evolui; a migration registra a história e muda o banco sem apagar os dados. Preço da migration: arquivos gerados no repositório e uma tabela de histórico no banco.

Na entrevista: "Como você aplica migrations em produção?" — não pelo database update da máquina do desenvolvedor: script SQL revisado ou bundle, no pipeline. "O que é o snapshot?" (o último modelo conhecido; base da próxima migration).

Erros comuns: esquecer o --startup-project e a ferramenta não achar a connection string; rodar sem --environment e usar o ambiente errado; editar a migration à mão depois de aplicada; versionar o snapshot desatualizado.

🧠 de cabeça: o que é migration, snapshot e histórico; a diferença entre projeto de destino e de inicialização. 🔎 onde encontrar: as opções de cada comando (página da CLI).

Fontes: Referência da CLI do EF Core · Migrations

Onde foi visto: S16 (migration criada, aplicada, removida e recriada). Status: executado em passos guiados.

6.5 Um schema do Postgres por módulo (ADR-006)

De → para

Como aparece nas vagas Nome no laboratório O mundo do aluno
schema per module, modular monolith database schema catalogo tabelas todas em dbo/public, sem separação por módulo

Em uma frase: o schema é a fronteira do módulo no banco, como o projeto é a fronteira no código.

Pergunta que responde: quando existir um segundo módulo com banco, como saber de qual módulo é cada tabela?

O problema. Sem configuração o EF cria as tabelas no schema padrão do banco (no Postgres, public). Na primeira migration do Catalogo, a tabela fichas_produto e a tabela de histórico __EFMigrationsHistory foram parar em public. Com um segundo módulo, as tabelas conviveriam sem marca de módulo e os dois contextos usariam a mesma tabela de histórico. Não foi conferido como o EF se comporta com dois contextos na mesma tabela de histórico; a decisão evita a situação.

Duas configurações, que não se substituem

O que Para que serve Onde fica
HasDefaultSchema(Schema) as tabelas do contexto nascem em catalogo OnModelCreating do contexto
MigrationsHistoryTable("__EFMigrationsHistory", Schema) a tabela de histórico do módulo nasce em catalogo nas opções do provider, no AddCatalogo

Se faltar a primeira, a tabela vai para public. Se faltar a segunda, só o histórico vai para public — a divisão que não se quer com dois módulos. A documentação do EF avisa que HasDefaultSchema vale também para outros objetos, como sequências.

public static IServiceCollection AddCatalogo(this IServiceCollection services, IConfiguration configuration)
{
    services.AddValidation();
    services.AddScoped<FichaProdutoRepository>();

    services.AddDbContext<CatalogoDbContext>(opcoes =>
        opcoes.UseNpgsql(
            configuration.GetConnectionString("Norte")
            ?? throw new InvalidOperationException("Connection string 'Norte' não encontrada."),
            npgsql => npgsql.MigrationsHistoryTable("__EFMigrationsHistory", CatalogoDbContext.Schema)));

    return services;
}
Detalhe Por quê
Schema numa constante do contexto o nome "catalogo" aparece em dois lugares (modelo e histórico) e fica escrito uma vez
?? throw dentro da função do AddDbContext GetConnectionString devolve string? e o UseNpgsql pede string (CS8604, erro pelo ADR-004); dentro da função, a leitura só acontece quando o contexto é usado, não na subida da API
AddCatalogo(services, configuration) o módulo declara que precisa de configuração, na assinatura; o host passa builder.Configuration

A migration agora traz EnsureSchema("catalogo") e cria a tabela dentro do schema. A migration antiga (que já estava na main, com a tabela em public) foi removida e recriada, em vez de ganhar uma segunda que movesse a tabela, porque nada existia fora do banco local e uma segunda migration deixaria o histórico em public.

Provado (12/10/2026): \dt catalogo.* listou fichas_produto e __EFMigrationsHistory; \dt public.* não listou tabela nenhuma; o cadastro e a consulta de LUV-001 pela API gravaram e leram em catalogo.fichas_produto.

Três opções e o preço (ADR-006)

Descrição Preço
A) um schema por módulo (escolhido) catalogo, depois pedidos; histórico dentro do schema duas configurações por módulo; o nome do schema aparece em SQL escrito à mão
B) tudo em public com prefixo no nome da tabela catalogo_fichas_produto a fronteira é só hábito de nome; o histórico segue compartilhado
C) um banco por módulo mais um container/banco por módulo transações entre módulos ficam muito mais caras; exagero hoje

O que o schema não faz. Ele separa por organização, não por impedimento: o banco e o usuário são os mesmos, uma consulta que atravessa schemas continua possível. "Módulo não lê a tabela de outro" é regra de convenção e de revisão, como o internal no código. Permissões por schema no Postgres seriam um reforço (não adotadas).

Na entrevista: "Como você isola os dados de cada módulo num monolito modular?" — schema por módulo + DbContext por módulo; o preço (organização, não impedimento); a alternativa de um banco por módulo e por que é cara.

Erros comuns: configurar só o HasDefaultSchema e deixar o histórico em public; esquecer o schema em SQL escrito à mão (catalogo.fichas_produto); achar que o schema impede o acesso.

🧠 de cabeça: as duas configurações e o que cada uma move; o que o schema não garante. 🔎 onde encontrar: o nome exato do método do histórico para o provider.

Fonte: Entity Types — Table schema

Onde foi visto: S16. Status: provado no banco; a decisão foi do mentor, com ADR.

6.6 Repositório e endpoints assíncronos

De → para

Como aparece nas vagas Nome no laboratório O mundo do aluno
async/await, scoped lifetime, no-tracking query AdicionarAsync, ObterPorSkuAsync, AddScoped, AsNoTracking() repositório com _context.Add(x) + _context.SaveChanges()

Em uma frase: o repositório deixa de guardar uma lista e passa a conversar com o CatalogoDbContext; como o banco é externo, a conversa é assíncrona.

Como era no Norte (S11–S15) Como é agora O que mudou
List<FichaProduto> dentro da classe CatalogoDbContext recebido no construtor os dados saem da memória do processo
Adicionar = list.Add AdicionarAsync = Add + await SaveChangesAsync() o Add só marca a ficha como nova; quem faz o INSERT é o SaveChangesAsync
ObterPorSku = FirstOrDefault na lista ObterPorSkuAsync = AsNoTracking().FirstOrDefaultAsync(...) AsNoTracking diz ao EF que a leitura é só leitura: não rastreia a entidade
AddSingleton<FichaProdutoRepository>() AddScoped<FichaProdutoRepository>() o contexto vive uma requisição; um singleton não pode depender dele
Executar devolve Results<...> ExecutarAsync devolve Task<Results<...>> o endpoint espera o banco sem prender a thread da requisição 
public async Task AdicionarAsync(FichaProduto ficha)
{
    contexto.FichasProduto.Add(ficha);
    await contexto.SaveChangesAsync();
}

public Task<FichaProduto?> ObterPorSkuAsync(string sku) =>
    contexto.FichasProduto.AsNoTracking().FirstOrDefaultAsync(f => f.Sku == sku);

(Forma do repositório; os nomes do campo e do parâmetro no arquivo real podem diferir.)

Tempo de vida. AddDbContext registra o contexto como scoped (uma instância por requisição). Um objeto singleton que dependa de um scoped prenderia aquela instância para sempre; o contêiner de DI do ASP.NET Core acusa isso em desenvolvimento (não conferido na documentação durante a S16), e a regra de design vale de qualquer jeito. Por isso o repositório passou a AddScoped.

Sufixo Async. A regra IDE1006 do .editorconfig (ADR-004) exige o sufixo em método async; foi por isso que Executar virou ExecutarAsync. Em tests/ a regra está desligada (o nome do teste é a regra).

O teste que sumiu. O CadastrarFichaProdutoEndpointTests fazia new FichaProdutoRepository(); esse construtor deixou de existir e o que o teste protegia (uma lista em memória) sumiu junto. Foi apagado. Ficam 4 testes (3×400 e 1×500) e nenhum toca o banco. O teste de integração com Postgres real (Testcontainers) é a próxima lacuna.

6.7 Pastas do módulo e rota por recurso

Em uma frase: o que é de uma funcionalidade fica junto na pasta dela; o que é do módulo inteiro (entidade, mapeamento) tem lugar fixo; e na rota o método HTTP diz a ação e o endereço é o substantivo.

Não criar Servicos/, Repositorios/, Dtos/ no nível do módulo sem decisão registrada: seria voltar à organização por tipo de arquivo.

Por que Funcionalidades/ e Dominio/ ao mesmo tempo. A raiz do módulo misturava dois critérios (pastas por funcionalidade e pastas por tipo). Com o agrupamento, cada pasta tem um critério. O argumento do aluno para Dominio/: "ao bater o olho sabemos onde está; não faz sentido ter Configuracoes e não ter Dominio". Os dois agrupamentos não ferem nenhuma regra do monolito modular: a fronteira do módulo (projeto, internal, schema) fica fora dessa pasta e não mudou.

O preço. Mover custa using e namespace (e o histórico do Git mostra renomeação, R); a pasta Dominio/ convida a criar outras pastas por tipo — por isso a regra de duas linhas. O Visual Studio pode reindentar um arquivo inteiro ao mover; o git diff --cached --stat mostra: um arquivo movido deve ter poucas linhas alteradas.

O preço da convenção. Ela cabe bem em cadastrar, consultar, alterar e excluir uma coisa. Ações que não são isso ("aprovar pedido") ficam sem encaixe natural e viram algo como POST /pedidos/{id}/aprovar — o jeito antigo de volta. O ramo morto do 400. O ObterFichaProdutoEndpoint tinha um if que devolvia 400 para SKU vazio. O caminho de uma requisição, agora completo:

  1. POST /catalogo/fichas-produto chega ao Program.cs → MapCatalogo → grupo /catalogo.
  2. A validação nativa (ADR-003) olha o CadastrarFichaProdutoRequest; falha → 400 em problem+json.
  3. CadastrarFichaProdutoEndpoint.ExecutarAsync monta a FichaProduto (classe, 6.2) e chama o repositório.
  4. FichaProdutoRepository.AdicionarAsync faz Add + SaveChangesAsync no CatalogoDbContext (scoped, 6.6).

Teste-se (sem consultar, uma pergunta por vez)

  1. A FichaProduto nasceu como record. Por que ela virou class quando o banco entrou, e o que se perde com isso?
  2. O que o private set faz no EF Core, e por que o construtor vazio não é necessário?
  3. Dê duas coisas que a configuração Schema do CatalogoDbContext move para o schema catalogo, e o que acontece se faltar a MigrationsHistoryTable.
  4. Qual a diferença entre --project e --startup-project no dotnet ef, e por que o Norte usa os dois?
  5. O que o Add faz e o que o SaveChangesAsync faz? E por que o repositório é AddScoped e não AddSingleton?
  6. Cadastrar o mesmo SKU duas vezes devolve 500. Qual é a causa (em uma frase) e qual deveria ser o status?
  7. Por que GET /catalogo/fichas-produto/ devolve 405 e não 400 nem 404?
  8. Por que o schema por módulo não impede que um módulo leia a tabela de outro, e o que impede?

Respostas

Mostrar respostas
  1. O EF Core usa igualdade por referência para manter uma instância por entidade (rastreamento, Find); o record compara por valor, e a documentação trata record como inadequado para entidade e diz que o EF não atualiza entidades imutáveis. Perde-se a igualdade por valor automática (e o with); testes que comparam fichas inteiras precisam conferir propriedade por propriedade.
  2. Propriedade sem setter não é mapeada por convenção; com private set o EF mapeia e o código de fora não altera a ficha. O construtor vazio não é necessário porque, achando um construtor cujos parâmetros casam com as propriedades mapeadas (nome e tipo, camelCase × PascalCase), o EF chama esse.
  3. HasDefaultSchema move as tabelas do modelo (e outros objetos, como sequências); MigrationsHistoryTable move a tabela de histórico. Sem a segunda, só o __EFMigrationsHistory vai para public, e dois módulos dividiriam a mesma tabela de histórico.
  4. --project é o projeto de destino, onde os arquivos da migration são criados (o módulo, Norte.Catalogo); --startup-project é o que a ferramenta compila e executa para descobrir a configuração e a connection string (o host, Norte.Api). Usa os dois porque o contexto está numa biblioteca e o host em outro projeto.
  5. Add só marca a ficha como nova no contexto; o INSERT acontece no SaveChangesAsync. O repositório é AddScoped porque depende do DbContext, que é scoped (uma instância por requisição); um singleton dependendo de um scoped prenderia aquela instância para sempre.
  6. A chave primária em sku (PK_fichas_produto): o banco recusa o segundo INSERT (23505) e o EF lança DbUpdateException, que o tratamento de erros do host transforma em 500. Deveria ser 409 Conflict, uma regra de negócio ainda por decidir.
  7. A barra final casa com a rota do cadastro (POST /fichas-produto): o caminho existe, mas só para POST; o roteamento responde 405 com Allow: POST e o endpoint de consulta nem é chamado.
  8. Porque o schema separa por organização, não por impedimento: o banco e o usuário são os mesmos, e uma consulta atravessa schemas. O que impede é convenção e revisão (e, como reforço não adotado, permissões por schema no Postgres).
