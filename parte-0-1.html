PARTE 0 — O mapa dos níveis

Antes de qualquer peça, o todo. Um sistema .NET moderno se lê em quatro níveis, de fora para dentro:

NÍVEL 1  SOLUTION          Norte.slnx — agrupa os projetos (não executa nada)
   │
NÍVEL 2  MÓDULOS           Norte.Api (host)  +  Norte.Catalogo  +  Norte.Pedidos  + ...
   │                       cada módulo = regras que valem juntas + dados próprios (critério: 1.12)
   │
NÍVEL 3  FUNCIONALIDADES   dentro de cada módulo: CadastrarFichaProduto/, ConsultarFichaProduto/...
   │                       (pasta por funcionalidade — o "feature-first" que você usava no Flutter)
   │
NÍVEL 4  CAMADAS           dentro de cada funcionalidade: endpoint → validação → handler →
                           domínio → EF Core → banco

E o caminho de uma requisição, que atravessa os níveis:

HTTP GET /catalogo/status
   │
   ▼
Norte.Api (host) ── app.MapCatalogo() ligou as rotas do módulo
   │
   ▼
Norte.Catalogo ── grupo "/catalogo" ── endpoint "/status"
   │
   ▼
TypedResults.Ok("Catalogo ativo")  →  200 OK

Onde estamos agora: ver o índice (GUIA-DOTNET-MODERNO.md), que é atualizado a cada sessão.

Comparação com o seu mundo:

Nos projetos em que você trabalhou No Norte
Nível 2 projetos por camada técnica: Api, Application, Domain, Infrastructure projetos por conjunto de regras de negócio: Catalogo, Pedidos…
Nível 3 pastas técnicas: Controllers/, Services/, Repositories/ pastas por funcionalidade
Nível 4 a camada é o primeiro corte a camada é o último corte, dentro da funcionalidade

PARTE 1 — A estrutura da solution (S9–S10)

1.1 Solution no formato .slnx (e as pastas virtuais do Visual Studio)

De → para

  • Como você vai ouvir no mercado: SLNX, XML solution format, solution folders.
  • No laboratório: Norte.slnx.
  • No seu mundo: o .sln que o Visual Studio criava, cheio de GUIDs, que dava conflito de merge.

Em uma frase: o .slnx é o mesmo arquivo de solution de sempre, reescrito em XML curto e legível; no .NET 10 é o formato padrão.

Pergunta que responde: "que projetos fazem parte deste sistema, e como eles aparecem no IDE?"

O que é. A solution não executa nada. É uma lista de projetos (e de pastas virtuais para organizá-los no IDE), usada pelo Visual Studio, pelo VS Code e pelo dotnet build quando você compila "tudo de uma vez".

Antes × agora:

Como era (.sln) Como é (.slnx)
Conteúdo texto proprietário, GUID por projeto, blocos de configuração repetidos XML com a lista de projetos
Merge conflitos frequentes e difíceis de resolver conflitos raros e legíveis
dotnet new sln gerava .sln gera .slnx (mudança do SDK 10)

O Norte.slnx real, no fim da S10 (aproximado):

<Solution>
  <Folder Name="/Solution Items/">
    <File Path="CLAUDE.md" />
  </Folder>
  <Folder Name="/src/">
    <Project Path="src/Norte.Api/Norte.Api.csproj" />
  </Folder>
  <Folder Name="/src/Modulos/" />
  <Folder Name="/src/Modulos/Catalogo/">
    <Project Path="src/Modulos/Catalogo/Norte.Catalogo/Norte.Catalogo.csproj" />
  </Folder>
  <Folder Name="/src/Modulos/Pedidos/">
    <Project Path="src/Modulos/Pedidos/Norte.Pedidos/Norte.Pedidos.csproj" />
  </Folder>
</Solution>

Pastas da solution × pastas do disco (S10 — a armadilha do Visual Studio).

Onde você cria a pasta no VS O que ela é Existe no disco?
Na solution, acima dos projetos (src, Modulos, Solution Items) solution folder: só um <Folder> no .slnx, para organizar a vista ❌ não
Dentro de um projeto (botão direito no projeto → Add → New Folder) pasta real ✅ sim

Na S10, o projeto Norte.Pedido foi criado pelo VS dentro de pastas de solution src/Modulos/Pedido, mas fisicamente na raiz (norte\Norte.Pedido\). O VS Code não tem solution folders — mostra sempre o disco —, por isso parece "mais honesto".

Como trabalhar no VS sem cair nisso:

Situação Jeito seguro
Criar projeto Terminal: dotnet new classlib -n Norte.X -o src/Modulos/X/Norte.X + dotnet sln Norte.slnx add ... — o dotnet sln add cria as solution folders espelhando o disco
Criar projeto pelo VS Criar a pasta física antes e apontar o campo Location para ela
Ver o disco como no VS Code Solution Explorer → botão Switch between solutions and available views → Folder View
Arquivo fora de projeto (CLAUDE.md, .gitignore) O VS o mostra em Solution Items (solution folder); o arquivo continua onde está
Tirar algo da solution Remove (tira da vista). Delete apaga o arquivo físico

Por que usamos · alternativa · custo. Legibilidade e menos conflito. Alternativa: manter .sln (dotnet new sln --format sln). Custo do .slnx: ferramentas antigas de terceiros podem não reconhecer. VS 2026, VS Code, Rider e SDK 10 reconhecem.

Como usar (comandos da S9–S10):

dotnet new sln -n Norte                                   # cria Norte.slnx
dotnet sln add src/Norte.Api src/Modulos/Catalogo/Norte.Catalogo
dotnet sln Norte.slnx remove Norte.Pedido/Norte.Pedido.csproj   # tira da solution (não apaga)

Na entrevista. Raramente perguntam; se aparecer: "é o novo formato de solution, XML, padrão no .NET 10; o ganho é legibilidade e menos conflito de merge".

🧠 que a solution só organiza, não executa; solution folder não existe no disco. · 🔎 os comandos.

Onde foi visto · status: S9 · visto e usado; S10 · solution folders na prática (projeto movido).

1.2 Monolito modular: host + um projeto por módulo

De → para

  • Como você vai ouvir no mercado: modular monolith, module, host, composition root.
  • No laboratório: Norte.Api (host) + Norte.Catalogo e Norte.Pedidos (módulos); decisão no ADR-002.
  • No seu mundo: a solution com Api/Application/Domain/Infrastructure — um monolito cortado por camada, não por negócio.

Em uma frase: monolito modular = uma solution, um deploy, vários módulos; cada módulo reúne as regras que valem juntas e os seus dados, com as suas funcionalidades, e só conversa com os outros pelo contrato público.

Pergunta que responde: "como dividir um sistema grande sem pagar o custo de microsserviços?"

O que é. Três regras definem o conceito:

  1. Coesão: o que muda junto por uma razão de negócio fica no mesmo módulo.
  2. Contrato público explícito: cada módulo decide o que os outros podem usar; o resto é interno.
  3. Nenhum acesso por fora do contrato: um módulo não usa classe interna nem tabela de outro.

O corte vertical (por negócio) × o corte horizontal (por técnica):

Monolito em camadas (seu mundo)        Monolito modular (Norte)
┌─────────────── Api ───────────────┐   ┌─ Catalogo ─┐ ┌─ Pedidos ─┐
├──────────── Application ──────────┤   │ endpoints  │ │ endpoints │
├────────────── Domain ─────────────┤   │ regras     │ │ regras    │
└─────────── Infrastructure ────────┘   │ dados      │ │ dados     │
                                         └────────────┘ └───────────┘

Monolito modular × microsserviços (a confusão mais comum):

Monolito modular Microsserviços
Deploys 1 para o sistema todo 1 por capacidade de negócio
Comunicação entre partes chamada em memória, pelo contrato do módulo rede (HTTP, mensageria)
Processo um só, com todas as DLLs dos módulos um por serviço
No Norte M1 a M6 M7: um módulo extraído

O que torna o deploy único NÃO é a solution — é o host. Norte.Api é o único projeto executável e referencia os projetos dos módulos (que são bibliotecas, .dll). Publicar o host gera um processo com todas as .dll dentro:

Norte.slnx  (só organiza; não é executado)
├── Norte.Api        ← executável (o host)
│     referencia ↓
├── Norte.Catalogo   ← biblioteca (.dll)
└── Norte.Pedidos    ← biblioteca (.dll)

dotnet publish src/Norte.Api  →  Norte.Api.dll + Norte.Catalogo.dll + ...  →  1 processo

Solution organiza. Host executa. Quantos hosts existem = quantos deploys existem.

Consequência do processo único: os módulos compartilham o destino (S10).

Tipo de bug num módulo O que acontece Por quê
Exceção dentro de uma requisição (ex.: NullReferenceException num endpoint do Catalogo) só aquela requisição recebe 500; Pedidos continua respondendo o ASP.NET Core captura a exceção da requisição
Bug que derruba o processo (memória esgotada, StackOverflowException, exceção não tratada numa thread de fundo) todos os módulos caem são DLLs dentro do mesmo processo

Módulos ficam isolados no código (projetos, internal, contrato), não em execução. Isolar falha e deploy por módulo é o que microsserviços resolvem (M7), ao custo de rede, consistência eventual e operação distribuída.

Por que um projeto por módulo (opção B) e não pastas num projeto só (opção C). As duas fazem o corte vertical. A diferença é quem garante a regra 3:

C: pastas num projeto só B: um projeto por módulo
internal em C# não protege: vale para o assembly inteiro protege: tipo internal de Norte.Catalogo não existe para Norte.Pedidos
Quem garante a fronteira disciplina do time (e testes de arquitetura) o compilador
Quando a violação aparece no code review, se alguém notar no build, sempre

Motivo da escolha agora (e não em M3): o entregável de M1 é Catálogo + Pedido simples; Pedidos vai precisar de dados de Catalogo ainda neste marco. Custo: mais cerimônia — um ponto de entrada por módulo (1.8), FrameworkReference (1.6), mais .csproj. Limite: o projeto separado protege as classes, não o banco; schema e DbContext por módulo entram em M3.

Ponte com limite. A pasta do módulo lembra a pasta de feature do Flutter — mas aqui o módulo vai ganhar banco (schema) e contrato próprios, e outro módulo não poderá ler as tabelas dele. E "módulo" aqui não é o Module do DDD de Evans (que é um namespace/pacote dentro de um modelo): no Norte, cada módulo corresponde a um contexto inteiro (ver 1.12).

Na entrevista. "Um monolito modular é um deploy só, dividido por regras de negócio, com contrato explícito entre módulos. Separo cada módulo num projeto para o compilador impedir o acesso a detalhes internos. O custo é mais cerimônia, os módulos compartilham o processo — um vazamento de memória num módulo derruba todos —, e o banco ainda precisa de isolamento próprio."

Erros comuns. Achar que o deploy único vem da solution (vem do host). Confundir "um deploy de uma capacidade de negócio" (microsserviço) com monolito modular. Achar que os outros módulos seguem vivos quando o processo cai (você, S10).

🧠 as 3 regras; o que torna o deploy único; processo compartilhado; B × C e o custo. · 🔎 os comandos para criar projeto e referência.

Onde foi visto · status: S9 · exposto; S10 · host/deploy único ✅ sem consulta; falha do processo ❌ (corrigido) · frágil.

1.3 public × internal: a fronteira garantida pelo compilador

De → para

  • No mercado: access modifiers, encapsulation at assembly level.
  • No laboratório: o ponto de entrada do módulo é public; todo o resto do módulo tende a ser internal.
  • No seu mundo: você provavelmente marcava tudo como public (num projeto por camada, era preciso).

Em uma frase: em C#, uma classe sem modificador é internal — visível só dentro do próprio projeto; para outro projeto enxergá-la, ela precisa ser public.

Por que importa no Norte: é o mecanismo que faz a opção B funcionar. Norte.Api é outro projeto: ele só enxerga o que Norte.Catalogo declarar public.

// Em Norte.Catalogo
public static class CatalogoModulo { ... }   // o host PRECISA ver: ponto de entrada
internal class FichaProduto { ... }           // detalhe interno: ninguém de fora vê

// Em Norte.Pedidos
var ficha = new FichaProduto();   // erro CS0122: inacessível devido ao nível de proteção

Erro real da S9: se a classe CatalogoModulo ficar sem public, o host não a encontra (o compilador a esconde). Ver 1.10.

🧠 sem modificador = internal; public = contrato do módulo. · 🔎 o código de erro.

Onde foi visto · status: S9 · visto.

1.4 Program.cs moderno: de Startup.cs para builder e app

De → para

  • No mercado: minimal hosting model, WebApplicationBuilder, top-level statements.
  • No laboratório: o Program.cs do Norte.Api.
  • No seu mundo: Program.cs + Startup.cs com ConfigureServices e Configure.

Em uma frase: o que estava espalhado em Program.cs + Startup.cs hoje fica num arquivo só, em duas fases: antes do Build() você registra serviços (o antigo ConfigureServices); depois do Build() você monta o pipeline e as rotas (o antigo Configure).

O de-para (formato padrão):

Como era Como é agora O que mudou
class Program + Main + Host.CreateDefaultBuilder(...).UseStartup<Startup>() top-level statements + WebApplication.CreateBuilder(args) O compilador gera a classe e o Main; os mesmos padrões (appsettings, logging, Kestrel) numa chamada
Configuration injetado no Startup builder.Configuration Mesmo objeto, outro lugar
ConfigureServices(IServiceCollection services) builder.Services.Add... (antes do Build()) Mesma coleção, IServiceCollection
Configure(IApplicationBuilder app, IWebHostEnvironment env) app.Use... / app.Map... (depois do Build()) Mesmo pipeline; env virou app.Environment
UseRouting() + UseEndpoints(e => e.MapControllers()) app.Map... direto no app O WebApplication liga o roteamento sozinho
A divisão entre as fases era garantida pelos dois métodos A divisão é a linha builder.Build() O compilador não impede registrar depois; o erro só aparece em execução

Detalhe importante sobre "versão": esse modelo já existia no .NET 6 — foi a novidade daquela versão. Mas a maioria das empresas migrou para o .NET 6 mantendo o Startup.cs. Por isso o de-para honesto para você é "como você fazia" × "como se faz hoje".

Como você fazia:

// Program.cs
public class Program
{
    public static void Main(string[] args) =>
        Host.CreateDefaultBuilder(args)
            .ConfigureWebHostDefaults(web => web.UseStartup<Startup>())
            .Build()
            .Run();
}

// Startup.cs
public class Startup
{
    public void ConfigureServices(IServiceCollection services)      // FASE 1: registrar
    {
        services.AddControllers();
        services.AddScoped<IProdutoService, ProdutoService>();
    }

    public void Configure(IApplicationBuilder app)                   // FASE 2: pipeline e rotas
    {
        app.UseRouting();
        app.UseEndpoints(endpoints => endpoints.MapControllers());
    }
}

Como se faz hoje (o Program.cs do Norte, fim da S10):

using Norte.Catalogo;
using Norte.Pedidos;

var builder = WebApplication.CreateBuilder(args);   // cria o "construtor" da aplicação

builder.Services.AddCatalogo();                     // FASE 1 (= ConfigureServices)
builder.Services.AddPedidos();

var app = builder.Build();                          // fecha a fase 1: os serviços ficam somente-leitura

app.MapCatalogo();                                  // FASE 2 (= Configure)
app.MapPedidos();

app.Run();                                          // sobe o servidor (Kestrel) e fica escutando

O que NÃO mudou — a injeção de dependência em si. AddScoped, AddTransient, AddSingleton e a injeção pelo construtor continuam iguais ao que você usava. Mudou onde você escreve os registros (builder.Services em vez de ConfigureServices), não como. A ordem dos middlewares também continua importando.

Por que as duas fases. O Build() pega a lista de registros e constrói o contêiner (IServiceProvider). A partir daí a coleção fica somente leitura: adicionar um serviço depois do Build() lança InvalidOperationException ("The service collection cannot be modified because it is read-only"). Ordem obrigatória: registrar → construir → configurar pipeline e rotas → rodar.

Nuance descoberta pelo seu experimento (S10). Você moveu builder.Services.AddCatalogo() para depois do Build() e nada aconteceu. Motivo: o AddCatalogo() ainda não registra nenhum serviço (só devolve services). A exceção só acontece quando algo é adicionado à coleção. Prova: builder.Services.AddProblemDetails() depois do Build() compila, mas a aplicação não sobe. Lição de diagnóstico: o erro é de execução, na subida — o compilador não avisa.

Ponte com limite. O Build() faz o papel da divisão entre ConfigureServices e Configure — mas antes a divisão era garantida pela estrutura (dentro de Configure não existia services); agora tudo está no mesmo arquivo e a disciplina das duas fases é sua.

Por que usamos · alternativa · custo. Menos arquivos e menos cerimônia; tudo o que a aplicação liga está à vista, de cima para baixo, na ordem real. Alternativa: continuar com Startup.cs (ainda funciona). Custo do modelo novo: o Program.cs pode virar um arquivo enorme — por isso cada módulo tem seus pontos de entrada (1.8) e o Program.cs só os chama; e a fronteira entre as fases deixou de ser garantida pelo compilador.

Na entrevista. "No modelo atual, o Program.cs tem duas fases: antes do Build() registro serviços, depois configuro pipeline e endpoints. Corresponde ao ConfigureServices e ao Configure do Startup. A DI em si não mudou. Registrar depois do Build() compila, mas falha na subida, porque o contêiner já foi construído."

🧠 as duas fases; o Build() como fronteira; o erro só na execução. · 🔎 a lista do que o CreateBuilder configura por padrão.

Onde foi visto · status: S1 (duas fases, no aquecimento), S9, S10 · correspondência ConfigureServices/Configure ✅; aplicada sozinha no Pedidos ✅ · frágil → em melhora.

1.5 Implicit usings e os using que faltam numa biblioteca

Em uma frase: desde o .NET 6, cada tipo de projeto importa automaticamente um conjunto de namespaces (implicit usings); o projeto Web importa os do ASP.NET Core, a classlib não.

Projeto O que já vem importado
Norte.Api (Sdk="Microsoft.NET.Sdk.Web") System, System.Linq… e também Microsoft.AspNetCore.Builder, Microsoft.AspNetCore.Http, Microsoft.AspNetCore.Routing, Microsoft.Extensions.DependencyInjection e outros
Norte.Catalogo (Sdk="Microsoft.NET.Sdk", classlib) só o básico: System, System.Collections.Generic, System.IO, System.Linq, System.Net.Http, System.Threading, System.Threading.Tasks

Consequência: no CatalogoModulo.cs estes using precisam ser escritos:

using Microsoft.AspNetCore.Builder;              // MapGroup, MapGet
using Microsoft.AspNetCore.Http;                 // TypedResults
using Microsoft.AspNetCore.Routing;              // IEndpointRouteBuilder
using Microsoft.Extensions.DependencyInjection;  // IServiceCollection

Atalho: Ctrl+. em cima do tipo sublinhado oferece o using — mas só se o tipo existir nas referências do projeto (ver 1.6 e 1.10).

🧠 por que no host "funciona sozinho" e no módulo não. · 🔎 o nome de cada namespace.

Onde foi visto · status: S9 · visto; S10 · repetido no Pedidos sem dificuldade.

1.6 FrameworkReference do ASP.NET Core

Em uma frase: a linha que dá a uma classlib acesso aos tipos do ASP.NET Core (IEndpointRouteBuilder, TypedResults, MapGet) sem pacote do NuGet, porque o ASP.NET Core já vem instalado com o runtime.

Como era Como é agora O que mudou
Biblioteca que precisava de tipos web instalava pacotes NuGet soltos (Microsoft.AspNetCore.Http.Abstractions…) <FrameworkReference Include="Microsoft.AspNetCore.App" /> Uma linha dá acesso ao framework inteiro, na versão que vem com o SDK
Versões dos pacotes atualizadas à mão Nenhuma versão a gerenciar O framework vem com o .NET 10 instalado
— O projeto continua Microsoft.NET.Sdk (biblioteca), não .Web Só o host é executável 
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
  </PropertyGroup>

  <ItemGroup>
    <FrameworkReference Include="Microsoft.AspNetCore.App" />
  </ItemGroup>

</Project>

Problema que resolve: o módulo declara os próprios endpoints. Sem essa referência, a biblioteca não conhece nada de HTTP e o build falha com "tipo ou namespace não encontrado".

Alternativa · custo. Alternativa: declarar todos os endpoints no host — o host passaria a conhecer os detalhes de todos os módulos. Custo da FrameworkReference: o módulo passa a depender do ASP.NET Core, o que é coerente, porque ele expõe endpoints HTTP.

Antes × agora. Existe desde o .NET Core 3.0. Nos seus projetos por camada, só o projeto Api falava HTTP; as outras camadas não precisavam disso. No monolito modular, cada módulo expõe seus endpoints — por isso a referência aparece em cada módulo.

🧠 por que o módulo precisa dela. · 🔎 a sintaxe do XML.

Onde foi visto · status: S9 · visto; S10 · aplicada sozinha no Pedidos ✅.

1.7 Métodos de extensão

De → para

  • No mercado: extension methods (C# 3, 2007).
  • No laboratório: AddCatalogo(), MapCatalogo(), AddPedidos(), MapPedidos().
  • No seu mundo: você usa métodos de extensão todo dia sem perceber: todo .Where(), .Select() do LINQ, e todo services.AddScoped(...), services.AddDbContext(...).

Em uma frase: um método estático que, por causa da palavra this no primeiro parâmetro, aparece como se fosse um método do próprio tipo.

O de-para (formato padrão):

Como era (método estático comum) Como é agora (método de extensão) O que mudou
public static class PedidosSetup public static class PedidosModulo Igual: classe static (e public, para o host ver)
public static IServiceCollection Registrar(IServiceCollection services) public static IServiceCollection AddPedidos(this IServiceCollection services) Só o this antes do primeiro parâmetro
Chamada: PedidosSetup.Registrar(builder.Services); Chamada: builder.Services.AddPedidos(); Parece um método da própria coleção
— using Norte.Pedidos; no arquivo que chama Sem o using, o método não aparece (CS1061)

Como se escreve — três exigências:

public static class CatalogoModulo                    // 1. classe static (e public, para outro projeto ver)
{
    public static IServiceCollection AddCatalogo(     // 2. método static (e public)
        this IServiceCollection services)             // 3. "this" no primeiro parâmetro
    {
        return services;
    }
}

Como se chama: o compilador transforma uma chamada na outra.

builder.Services.AddCatalogo();                 // o que você escreve
CatalogoModulo.AddCatalogo(builder.Services);   // o que o compilador gera

Para o compilador achar a extensão, o namespace da classe estática precisa estar importado com using no arquivo que chama. (Foi exatamente o erro da S9 — ver 1.10.)

Por que o .NET inteiro registra coisas assim. Cada biblioteca (EF Core, autenticação, o seu módulo) entrega um AddAlgumaCoisa() que agrupa os registros dela. Quem usa chama uma linha, sem conhecer os detalhes internos, e o IntelliSense em builder.Services. mostra tudo o que pode ser registrado. É o mesmo motivo do Norte: o host não conhece o interior do módulo.

Por que retorna services: para permitir encadear: builder.Services.AddCatalogo().AddPedidos();.

Erros comuns. Esquecer o this (vira método comum, que não aparece "dentro" do tipo). Classe não static. Classe sem public quando chamada de outro projeto. Faltar o using do namespace da extensão.

Na entrevista. "Método de extensão é um método estático com this no primeiro parâmetro; o compilador permite chamá-lo como se fosse do tipo. O .NET usa esse padrão para registrar bibliotecas na DI: AddDbContext, AddAuthentication. Uso o mesmo padrão para registrar cada módulo."

🧠 as três exigências e por que o .NET usa esse padrão. · 🔎 nada — isto é para saber de cabeça.

1.8 Pontos de entrada do módulo: AddCatalogo() e MapCatalogo()

Em uma frase: cada módulo expõe dois métodos de extensão públicos — um para registrar seus serviços, outro para declarar suas rotas — e o host só chama esses dois.

Problema que resolve: se cada endpoint de cada módulo fosse declarado no Program.cs, o host conheceria os detalhes de todos os módulos, e o arquivo cresceria a cada funcionalidade. A fronteira criada pelos projetos separados vazaria pelo Program.cs.

Ponto de entrada Fase do Program.cs O que faz
Add<Modulo>(this IServiceCollection) antes do Build(), em builder.Services registra os serviços do módulo
Map<Modulo>(this IEndpointRouteBuilder) depois do Build(), no app declara os endpoints do módulo

Convenção do ADR-002 (nomes): classe public static <Modulo>Modulo, no namespace Norte.<Modulo>, igual ao nome do projeto; grupo de rotas "/<modulo>" em minúsculo. No Pedidos (S10): PedidosModulo, Norte.Pedidos, "/pedidos".

O código do Norte, linha a linha (src/Modulos/Catalogo/Norte.Catalogo/CatalogoModulo.cs):

using Microsoft.AspNetCore.Builder;              // MapGroup, MapGet
using Microsoft.AspNetCore.Http;                 // TypedResults
using Microsoft.AspNetCore.Routing;              // IEndpointRouteBuilder
using Microsoft.Extensions.DependencyInjection;  // IServiceCollection

namespace Norte.Catalogo;                        // tem de ser igual ao "using" do Program.cs

public static class CatalogoModulo               // public: é o contrato do módulo com o host
{
    public static IServiceCollection AddCatalogo(this IServiceCollection services)
    {
        // registros do módulo entram aqui quando existirem
        return services;
    }

    public static IEndpointRouteBuilder MapCatalogo(this IEndpointRouteBuilder app)
    {
        var grupo = app.MapGroup("/catalogo");   // tudo declarado em "grupo" começa com /catalogo

        grupo.MapGet("/status", () => TypedResults.Ok("Catalogo ativo"));   // GET /catalogo/status (provisório)

        return app;
    }
}

Por que IEndpointRouteBuilder e não WebApplication: WebApplication (o app) implementa essa interface. Pedir a interface deixa o módulo depender só do necessário: "algo onde se declaram rotas".

Antes × agora:

Como você fazia Agora
Quem descobre os endpoints AddControllers() + MapControllers() varrem os assemblies e acham todo controller sozinhos o host chama explicitamente o ponto de entrada de cada módulo
Controle o host não escolhe o que entra cada módulo decide o que expõe; o host decide que módulos liga
Organizar registros extensões AddXyz() para limpar o Startup.cs o mesmo padrão, mas agora é a fronteira pública do módulo

Ponte com limite. Lembra os AddXyz() que se escreviam para organizar o Startup.cs — mas aqui o método não é só organização: é a única coisa do módulo que o host enxerga.

Checklist anti-sobra (S10). Ao criar um módulo copiando outro, procure com Ctrl+F o nome do modelo no arquivo novo: nenhum Catalogo pode sobrar no Pedidos (namespace, classe, métodos, rota, texto). Na S9 sobrou /consignacoes; na S10, PedidosCatalogo e /pedido.

Na entrevista. "Cada módulo expõe um AddModulo() e um MapModulo(). O host só chama esses dois; o resto do módulo é interno. Assim, adicionar uma funcionalidade não mexe no host."

🧠 por que existem, em que fase cada um entra, por que o host não declara rotas. · 🔎 os using.

1.9 Minimal APIs: as formas de declarar um endpoint, e o MapGroup

De → para

  • No mercado: Minimal APIs, route groups, endpoint handlers.
  • No laboratório: endpoints declarados no MapCatalogo() e no MapPedidos().
  • No seu mundo: controllers ([ApiController], [Route], [HttpGet], IActionResult).

Em uma frase: um endpoint é declarado com MapGet/MapPost/MapPut/MapDelete, passando a rota e o código que responde; não precisa de classe controller.

O de-para (formato padrão — a tabela que você aprovou na S10):

Controller Minimal API O que mudou
[Route("catalogo")] na classe app.MapGroup("/catalogo") O prefixo vira um objeto (o grupo), não um atributo
[HttpGet("status")] no método grupo.MapGet("/status", ...) Verbo e rota numa chamada só
Método de ação (Status()) dentro de uma classe Um delegate: lambda ou método Não precisa de classe nem de herdar ControllerBase
AddControllers() + MapControllers() descobrem as classes por reflexão Cada Map... registra explicitamente o endpoint Nada é descoberto. Se ninguém chamar MapCatalogo(), a rota não existe (404)
IActionResult / Ok(...) TypedResults.Ok(...) (tipo concreto Ok<string>) O tipo do retorno carrega a informação para o OpenAPI e o teste
parâmetros com [FromRoute], [FromBody], [FromServices] inferidos pelo nome e pelo tipo (abaixo) Menos atributos

O mesmo endpoint, nos dois estilos:

// Como você fazia: controller
[ApiController]
[Route("catalogo")]
public class CatalogoController : ControllerBase
{
    [HttpGet("status")]
    public IActionResult Status() => Ok("Catalogo ativo");
}

// Agora: Minimal API
var grupo = app.MapGroup("/catalogo");
grupo.MapGet("/status", () => TypedResults.Ok("Catalogo ativo"));

Quem liga a rota ao código (S10): antes, o MVC, sozinho, procurando por reflexão as classes que terminam em Controller. Agora, você, explicitamente: o MapGet dentro do MapCatalogo() cria a rota, e a chamada app.MapCatalogo() no Program.cs a ativa.

As formas de escrever o código do endpoint:

// 1. Lambda sem parâmetros (S9)
grupo.MapGet("/status", () => TypedResults.Ok("Catalogo ativo"));

// 2. Lambda com parâmetros: cada parâmetro vem de um lugar, inferido pelo framework
grupo.MapGet("/fichas/{id:int}", (int id, AlgumServico servico) => ...);
//          {id:int} na rota → "int id" vem da ROTA, pelo nome
//          AlgumServico registrado na DI → vem do CONTÊINER, pelo tipo
//          (num POST, um tipo complexo vem do CORPO da requisição, em JSON)

// 3. Método nomeado (forma usada nas funcionalidades reais: legível e testável)
grupo.MapGet("/fichas/{id:int}", ObterFicha);

static async Task<Results<Ok<FichaResponse>, NotFound>> ObterFicha(int id, ...)
{
    ...
}

MapGroup (desde o .NET 7): agrupa endpoints sob um prefixo comum e permite aplicar configurações ao grupo todo (tag do OpenAPI, autorização, filtros). A rota dentro do grupo é relativa: MapGroup("/catalogo") + MapGet("/status") = /catalogo/status. Escrever MapGet("/catalogo/status") dentro do grupo gera /catalogo/catalogo/status.

Ponte com limite. O MapGroup faz o papel do [Route] no controller, mas não é uma classe: é um prefixo mais uma configuração compartilhada, e os endpoints de um grupo não precisam estar no mesmo arquivo. É isso que, em M2, permite uma pasta por funcionalidade em vez de um controller por entidade com 20 ações.

TypedResults × Results (retenção S1): TypedResults.Ok(x) devolve o tipo concreto Ok<T>; com vários retornos, a assinatura fica Results<Ok<T>, NotFound>. O gerador do OpenAPI lê o tipo e documenta as respostas sozinho; o teste de unidade chama o método e confere status e corpo como objetos C#. Com Results.Ok(x) (devolve IResult), nenhum dos dois enxerga o que volta sem configuração ou conversão manual.

Por que usamos · alternativa · custo. Menos cerimônia, sem o pipeline do MVC, e o endpoint fica perto da funcionalidade (encaixa na pasta por funcionalidade de M2). Alternativa: controllers — muito comuns em projetos existentes, e o laboratório tem um spike de controllers na Trilha B de M1. Custo das Minimal APIs: menos convenção pronta; a organização (grupos, pontos de entrada, métodos nomeados) é responsabilidade sua.

Literatura × mercado. Projetos existentes usam muito controllers; projetos novos, cada vez mais Minimal APIs (julgamento pedagógico; frequência nas vagas a conferir no Vagas.md na virada de M1). Em entrevista, saber as duas e o custo de cada uma é o que se espera.

Na entrevista. "Minimal APIs declaram o endpoint com MapGet e um handler; uso MapGroup para o prefixo do módulo e TypedResults para o OpenAPI e o teste enxergarem os retornos. Controllers continuam válidos, principalmente em base existente; o custo das Minimal APIs é organizar por conta própria."

🧠 o de-para com controllers; quem liga a rota; de onde vem cada parâmetro; por que TypedResults. · 🔎 a assinatura exata de Results<...>.

1.12 Módulo × funcionalidade × departamento: o critério para criar módulo

De → para

  • Como você vai ouvir no mercado: module, bounded context, feature/use case, "como você define a fronteira de um módulo/serviço?".
  • No laboratório: módulos Catalogo, Pedidos, Precificacao, Vendas…; funcionalidades como CriarPedido, CadastrarFichaProduto.
  • No seu mundo: "módulo Comercial", "módulo RH" dos ERPs, organizados por menu e departamento; no Flutter, a pasta por feature.

Em uma frase: módulo é o conjunto de regras que valem juntas sobre um assunto, com dados próprios; funcionalidade é uma ação dentro dele; departamento é quem trabalha — e não decide a divisão.

Pergunta que responde: "isto é um módulo novo, uma funcionalidade de um módulo existente, ou só o nome de uma área da empresa?"

As três coisas lado a lado:

Departamento Módulo (no Norte) Funcionalidade
O que é pessoas organizadas na empresa regras que valem juntas sobre um assunto + dados próprios uma ação que alguém faz no sistema
Gramática nome de área substantivo: o assunto verbo: a ação
Exemplos no Norte Comercial, Logística Catalogo, Precificacao, Pedidos, Vendas, Estoque CriarPedido, AdicionarItem, AprovarDesconto
Quem decide o limite o organograma as regras (onde a mesma palavra passa a seguir outra regra) o caso de uso
No código não aparece um projeto (Norte.Pedidos) e, a partir de M3, um schema uma pasta dentro do módulo (M2): Pedidos/CriarPedido/

O critério. Pergunta principal: a mesma palavra segue regras diferentes? Se segue, são módulos diferentes; se não, é o mesmo módulo — mesmo que o trabalho aconteça em departamentos, momentos ou pessoas diferentes. (É o sinal principal do GUIA-ESTRATEGICO.md, 2.2; pessoas diferentes e "um lado muda sem afetar o outro" são reforço.)

Exemplo — por que não um módulo "Comercial":

Assunto dentro do departamento Comercial Regra que vale sempre Módulo
Prospect da feira pode existir sem CNPJ Crm
Tabela de preço muda quando o gerente reajusta; tem vigência Precificacao
Pedido muda até ser convertido; preço travado no item Pedidos
Venda nunca muda; correção vira devolução Vendas

Num módulo "Comercial", uma classe Pedido teria de obedecer a "muda" e "não muda" ao mesmo tempo — a regra vira if espalhado:

public void AlterarQuantidade(int qtd)
{
    if (Status == StatusPedido.Faturado || Status == StatusPedido.Vendido)
        throw new InvalidOperationException("...");
    // ...
}

Multiplicado por dezenas de métodos, é o service gigante dos sistemas antigos. Separar Pedidos de Vendas faz a regra "não muda" morar num lugar só.

Exemplo de fora do Norte (ilustração do raciocínio) — RH:

Assunto no RH Regra que vale sempre Módulo provável
Candidato pode ser descartado; não tem salário Recrutamento
Marcações de ponto ajustáveis até o fechamento do período Ponto
Folha da competência depois de fechada, não muda (corrige-se com outra folha) Folha

"Colaborador" segue regras diferentes em cada linha — é isso que separa os módulos. "RH" é quem trabalha com eles.

Ponte com limite. A pasta por feature do Flutter corresponde à funcionalidade daqui (CriarPedido/) — mas o módulo é um nível acima, e um módulo não lê os dados de outro: pede por contrato. E o nome de um módulo pode coincidir com um departamento (Financeiro), mas o motivo da divisão tem de ser a regra (no Norte, a reserva de crédito), não o organograma.

"Módulo" tem dois sentidos na literatura:

Onde "Módulo" significa Nível
Livro do Evans (DDD tático) agrupamento de conceitos dentro de um modelo (namespace/pacote) abaixo do bounded context
Monolito modular (mercado, Norte) um bounded context no código: projeto, regras e dados próprios igual ao bounded context

No Norte, "módulo" é sempre o segundo sentido.

Cartão de bolso:

  1. É verbo ou substantivo? Verbo → funcionalidade. Substantivo → candidato a módulo.
  2. A mesma palavra segue regra diferente em outro lugar? Sim → módulos diferentes.
  3. O nome veio do organograma? Desconfie e volte à pergunta 2.

Nome no código. O módulo é o assunto, no plural quando for coleção (Pedidos, projeto Norte.Pedidos, rota /pedidos); a classe de domínio que nasce dentro dele fica no singular (Pedido). Lista de módulos: ADR-001.

Onde isso entra no DDD. Módulo = bounded context no código; o critério é o mesmo do bounded context. Detalhe em GUIA-ESTRATEGICO.md (2.1 e 2.2).

Na entrevista. "Como você define a fronteira de um módulo?" → "Pelas regras, não pelo departamento. Onde a mesma palavra passa a seguir outra regra — pedido muda, venda não muda — existe outro módulo. Cada módulo tem dados próprios e expõe um contrato. O custo é algum dado duplicado e a necessidade de integrar os módulos."

Erros comuns. Decidir o módulo pelo departamento ou pelo menu (você, S8 e S10). Tratar uma ação (verbo) como módulo. Nome do módulo no singular, vindo da classe (Norte.Pedido, S10).

🧠 o critério (regra, não departamento); verbo × substantivo; o exemplo do Comercial. · 🔎 a lista de módulos (ADR-001).
