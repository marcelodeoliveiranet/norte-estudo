ESTUDO-S21 — Catálogo: o 404 do PUT fica, e dois testes o provam

Material para estudar sozinho. Cada tema é uma página: o que é, o ganho, o preço, o que foi provado e o que não foi. Sessão de 15/10/2026 (tarde). Tempo líquido: 2h13. Resultado: PRs #18 e #19 mergeados, 31 testes verdes (eram 29), CI verde.

Por que esta sessão existe. A S20 deixou uma lacuna conhecida: PUT /catalogo/fichas-produto/{sku} com SKU de 21 caracteres devolve 404, enquanto o GET e o DELETE devolvem 400. O plano era dar ao PUT um Request com o SKU da rota. A sessão terminou sem mudar o código de produção: a lacuna virou decisão, e a decisão virou teste.

Mapa da sessão

Tema Em uma frase
1. Decidir não mudar O PUT continua devolvendo 404 para SKU de 21+ caracteres, e o preço fica escrito
2. Teste: NCM vazio devolve 400 A validação nativa do corpo do PUT ganha a cobertura que só a descrição tinha
3. Teste: SKU de 21 caracteres devolve 404 A decisão do tema 1 fica fixada por um teste de API
4. Provar que cada teste protege Estragar o código de propósito e ver o vermelho, com commit antes
5. Template de Pull Request Três perguntas já escritas na descrição do PR, para não depender da memória

1. Decidir não mudar: o 404 do PUT

O problema. A rota do PUT recebe o SKU como string sku solta. Não há [StringLength(20)] nela, então a validação nativa não vê o tamanho. O SKU de 21 caracteres chega ao repositório, a busca não acha nada e o endpoint responde 404 com o título "Ficha não encontrada".

Duas saídas pensadas.

Deixar como está Dar ao PUT um Request com o SKU
Resposta para SKU de 21 caracteres 404 "Ficha não encontrada" 400 (validação nativa), como no GET e no DELETE
Código nenhum um parâmetro a mais no Request do corpo, ou um segundo Request só para a rota, com [AsParameters]
Preço duas respostas diferentes para o mesmo erro de entrada: 400 no GET/DELETE, 404 no PUT o corpo (descricao, ncm) e a rota (sku) passam a morar no mesmo tipo ou em dois tipos; mais mudança num endpoint que já funciona

O argumento que decidiu. Para o PUT, SKU com mais de 20 caracteres e SKU que não existe levam ao mesmo lugar: nenhuma ficha. A busca devolve null e o endpoint já trata null com 404. Nenhuma ficha é gravada ou alterada por engano. A consequência para quem chama é só a mensagem: "não existe" em vez de "tem caracteres demais".
Ganho Nenhum código novo num endpoint que funciona; o 404 já é consistente com "a ficha não existe".
Preço Quem chama o PUT com um SKU longo não é avisado de que o problema é o tamanho. A API responde de dois jeitos ao mesmo erro de entrada. Além disso, não há como consultar o banco por um SKU que a coluna (character varying(20)) nunca poderia ter guardado: a resposta 404 é correta por acaso, não por regra.
Provado PUT com SKU de 21 caracteres devolve 404 com o título "Ficha não encontrada" (teste do tema 3).
Não provado Que quem usa a API prefira 404 a 400 nesse caso. É decisão de contrato, sem usuário real para confirmar.

Sem ADR. A decisão é barata de desfazer: trocar para 400 depois é dar um Request à rota e atualizar um teste.

2. Teste: NCM vazio no PUT devolve 400

Antes: o AtualizarFichaProdutoComBancoApiTests cobria o caminho feliz, o SKU inexistente e a descrição vazia. O NCM vazio não tinha teste de API, embora o Request o exija:

public sealed record AtualizarFichaProdutoRequest(
    [Required(ErrorMessage = "A Descrição é obrigatória")] string? Descricao,
    [Required(ErrorMessage = "O Ncm é obrigatório")] string? Ncm);

O teste (Arrange/Act/Assert, cada parte com a pergunta que responde):

[Fact]
public async Task Atualizar_com_ncm_vazio_devolve_400()
{
    // Arrange: um corpo válido em tudo, menos no ncm, que vai vazio
    var cliente = fabrica.CreateClient();
    var sku = Guid.NewGuid().ToString().Substring(0, 8);
    var corpo = new { descricao = "Luva nitrilica", ncm = "" };

    // Act: requisição de verdade — passa pela validação nativa antes do Executar
    var resposta = await cliente.PutAsJsonAsync($"/catalogo/fichas-produto/{sku}", corpo);

    // Assert: 400, com erro no campo Ncm (e só a falta do ncm explica o erro)
    Assert.Equal(HttpStatusCode.BadRequest, resposta.StatusCode);
    var problema = await resposta.Content.ReadFromJsonAsync<HttpValidationProblemDetails>();
    Assert.NotNull(problema);
    Assert.Contains("Ncm", problema.Errors.Keys);
}
Parte Pergunta que responde
Arrange O que precisa existir para que só o NCM esteja errado? (descricao válida; o SKU nem precisa existir, porque a validação acontece antes da busca)
Act Qual é a ação que o cliente da API faz? (um PUT, de verdade, pelo HttpClient da fábrica)
Assert Como saber que o 400 veio do NCM, e não de outra coisa? (a chave Ncm está em Errors)

Detalhe do corpo. O corpo do teste usa descricao = "Luva nitrilica" (e não "Luva de latex"): o teste da descrição vazia já usa outra, e o texto não é regra de negócio. O que importa é que a descrição esteja preenchida.
Ganho Se alguém tirar o [Required] do Ncm, o PUT passa a aceitar NCM vazio e este teste fica vermelho.
Preço Mais um teste com banco real (Testcontainers): a suíte roda um pouco mais devagar. Este teste nem toca no banco, mas está na classe que sobe o container.
Provado Prova do vermelho no tema 4.
Não provado O NCM com tamanho errado (3 dígitos) passa: o Request só exige que não seja vazio.

3. Teste: SKU de 21 caracteres devolve 404 com o título da regra

Este teste fixa a decisão do tema 1. Sem ele, o 404 é um acaso do código; com ele, qualquer mudança futura (um Request na rota, por exemplo) quebra o teste de propósito e obriga a rever a decisão.

[Fact]
public async Task Atualizar_com_sku_maior_que_20_caracteres_devolve_404_com_o_titulo_da_regra()
{
    // Arrange: ficha com SKU de 20 caracteres gravada; SKU de 21 (o mesmo + "X") que não existe
    var cliente = fabrica.CreateClient();
    var skuCadastrado = Guid.NewGuid().ToString().Substring(0, 20);
    var cadastro = new CadastrarFichaProdutoRequest(skuCadastrado, "Luva nitrilica", "40151900");
    var respostaCadastro = await cliente.PostAsJsonAsync("/catalogo/fichas-produto", cadastro);
    Assert.Equal(HttpStatusCode.Created, respostaCadastro.StatusCode);
    var skuLongo = skuCadastrado + "X";
    var corpo = new { descricao = "Luva nitrilica", ncm = "40151900" };

    // Act: só a requisição, com o SKU de 21 caracteres na rota
    var resposta = await cliente.PutAsJsonAsync($"/catalogo/fichas-produto/{skuLongo}", corpo);

    // Assert: 404 + título "Ficha não encontrada"
    Assert.Equal(HttpStatusCode.NotFound, resposta.StatusCode);
    var problema = await resposta.Content.ReadFromJsonAsync<ProblemDetails>();
    Assert.NotNull(problema);
    Assert.Equal("Ficha não encontrada", problema.Title);
}

Por que o Arrange grava uma ficha antes? Para o teste ser capaz de falhar do jeito certo. A ficha gravada tem 20 caracteres, e o PUT usa esses mesmos 20 mais um X. Se o 404 viesse da regra de tamanho, o SKU de 20 deveria ser aceito; o X extra é a única diferença. Assim, o teste não confunde "o SKU não existe" com "o SKU é longo demais".
Ganho A decisão do tema 1 passa a ter um teste. Um SKU longo parecido com um SKU existente continua sem alterar a ficha existente.
Preço O Arrange fica mais longo (um POST antes do PUT) e o teste depende do POST funcionar: se o cadastro quebrar, este teste falha por outra razão (por isso o Assert do 201 dentro do Arrange).
Provado Prova do vermelho no tema 4: sem o X, o PUT devolve 200.
Não provado O DELETE com SKU de 21 caracteres continua sem teste (o Request dele tem o limite, mas ninguém o exercitou).

4. Provar que cada teste protege

Teste que nunca foi visto vermelho pode estar passando à toa. Regra do laboratório: todo teste novo é visto falhar pelo menos uma vez. Nesta sessão a prova foi feita dois jeitos, e deu errado de um jeito que ensina.

Teste O estrago O que se viu
NCM vazio remover [Required] do Ncm no AtualizarFichaProdutoRequest Expected: BadRequest / Actual: NotFound: sem a validação, o corpo passa e o endpoint responde 404 (SKU inexistente)
SKU de 21 trocar skuCadastrado + "X" por skuCadastrado (sem o X) Expected: NotFound / Actual: OK: o SKU agora existe, o PUT atualiza e devolve 200

Ordem do procedimento (aprendida na sessão):

  1. Commit do teste antes do estrago. O teste do NCM foi commitado antes (adb62bb). O do SKU de 21 foi estragado sem commit antes: um git restore para desfazer o estrago teria apagado o próprio teste, que ainda não estava salvo no Git. Foi desfeito editando a linha à mão e conferindo com Select-String.
  2. Um passo só para o estrago, e o git status confirma que a alteração está lá antes de rodar.
  3. Rodar o teste e ler o Expected/Actual: a causa do vermelho precisa ser a que se espera, não outra. O vermelho do NCM apareceu com Actual: NotFound, que é a consequência certa de tirar o [Required].
  4. Desfazer o estrago e rodar de novo para ver o verde.

Um erro de filtro. Rodar dotnet test --filter com o nome errado (..._vazia_... em vez de ..._vazio_...) devolve total: 0 e não falha: nenhum teste foi executado. total: 0 não é "verde".
Ganho Cada um dos 2 testes novos protege uma coisa específica, vista falhar pelo motivo certo.
Preço Mexer no código de produção de propósito: se o estrago for commitado ou esquecido, vira defeito de verdade. O commit do teste antes e o git status depois são o freio.
Provado Os dois vermelhos acima; depois, 31 testes verdes.
Não provado Que os 5 testes de API do PUT protejam contra todos os estragos possíveis (só se provou um por teste).

5. Template de Pull Request

O problema (dito pelo aluno). Depois de tantas idas e vindas, na hora de abrir o PR ele não lembrava o que escrever. Descrição de PR escrita de memória, no fim, sai pobre.

A solução. Um arquivo .github/pull_request_template.md na main: o GitHub pré-preenche o campo da descrição de todo PR novo com o texto dele.

Seção Pergunta que ela faz
## O que muda O que este PR faz, em poucas linhas?
## Como verificar Como quem revisa confirma que funciona? (comandos, testes)
## Decisões Que decisão foi tomada, o que evito e o que PAGO?

Cada seção tem um comentário HTML (<!-- ... -->) com a pergunta de apoio; ele não aparece na página do PR.

Como funciona:

Fato Detalhe
Onde fica .github/pull_request_template.md, na branch padrão (main)
Quando vale A partir do próximo PR depois do merge do template; o PR que cria o template não o usa
Se não aparecer O PR foi aberto antes do merge, ou o arquivo está em outra pasta/nome
Ganho A descrição nasce com as três perguntas; o campo "Decisões" cobra o preço (ponto fraco recorrente do aluno).
Preço Mais texto para apagar quando o PR é pequeno; um template ruim vira ritual sem conteúdo.
Provado O arquivo foi commitado, o CI passou e o PR #19 foi mergeado; main em 3c407c3.
Não provado Que o template aparece no próximo PR. Ainda não foi visto acontecer: é a primeira coisa a conferir.

Provado × não provado (resumo)

Provado Não provado
PUT sem NCM devolve 400 com a chave Ncm (vermelho visto: sem [Required], Actual: NotFound) O template de PR aparecer no próximo PR
PUT com SKU de 21 caracteres devolve 404 "Ficha não encontrada" (vermelho visto: sem o X, Actual: OK) DELETE com SKU de 21 caracteres
31 testes verdes local e no CI (PRs #18 e #19) Cancelamento por CancellationToken; AdicionarAsync e ObterPorSkuAsync não recebem o token
O 404 do PUT com SKU longo é igual ao 404 de SKU inexistente (mesmo título) Concorrência: dois PUT simultâneos
A causa de o CI do PR #18 ter travado 7m39s em dotnet test e passar em 1 min ao ser reexecutado

Pontos para explicar numa entrevista

  1. Lacuna de comportamento pode virar decisão: nem toda inconsistência pede código. Escreve-se o preço e fixa-se com um teste.
  2. Por que o teste do 404 grava uma ficha antes: para separar "o SKU não existe" de "o SKU é longo".
  3. Prova do vermelho: estragar o código de propósito e ler o Expected/Actual, com o teste já commitado.
  4. total: 0 não é verde: filtro errado roda zero testes.
  5. Template de PR: como transformar um hábito difícil de lembrar em um formulário.

Teste-se

1. Por que o PUT com SKU de 21 caracteres continua devolvendo 404, e qual é o preço dessa escolha?

Porque o SKU solto na rota não passa por validação de tamanho; a busca não acha nenhuma ficha e o endpoint já responde 404 para "não existe". O preço: o mesmo erro de entrada recebe 400 no GET/DELETE e 404 no PUT, e quem chama não é avisado de que o problema é o tamanho.

2. No teste do NCM vazio, o que o Arrange precisa garantir e como o Assert prova que o 400 veio do NCM?

O Arrange garante que tudo esteja válido, menos o NCM (descrição preenchida, NCM ""). O Assert confere o status 400 e que a chave Ncm está em Errors: só a falta do NCM explica o erro.

3. Por que o teste do SKU de 21 caracteres grava antes uma ficha de 20?

Para a única diferença entre o SKU gravado e o SKU do PUT ser o caractere X a mais. Assim o 404 só pode vir do SKU a mais, e a prova do vermelho (tirar o X) devolve 200.

4. Como se prova que o teste do NCM protege? O que foi visto?

Remove-se o [Required] do Ncm no Request e roda-se o teste: ele fica vermelho com Expected: BadRequest e Actual: NotFound. Devolvido o atributo, volta ao verde.

5. Por que o teste deve estar commitado antes de estragar o código para a prova do vermelho?

Porque desfazer o estrago com git restore descarta todas as alterações não commitadas do arquivo, inclusive o teste novo. Com o teste commitado, o git restore só desfaz o estrago.

6. dotnet test --filter mostrou total: 0. Isso significa que o teste passou?

Não. Significa que nenhum teste foi executado (o filtro não achou o nome). É preciso ver total: 1 (ou mais) com succeeded igual.

7. Quando o template de PR passa a valer, e como se confirma que funciona?

A partir do próximo PR aberto depois do merge do template na main. Confirma-se abrindo um PR e vendo o campo da descrição já preenchido com as três seções.

8. Por que não foi escrito um ADR para a decisão do 404?

Porque é barata de desfazer: trocar para 400 é dar ao PUT um Request com o SKU e atualizar um teste. O preço ficou registrado no PR #18 e no teste.
