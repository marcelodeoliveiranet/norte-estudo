Norte · S31 — Testes de API do cadastro de Cliente e 409 nas requisições simultâneas

Segunda 26/10/2026 · tempo líquido: 6h14 (2h03 + 4h11) · Marco M1

Hoje o POST /clientes ganhou testes de verdade e um defeito foi achado e corrigido. O endpoint já existia desde a S30, mas nenhum teste passava pela API inteira. Agora passam: 201, 409 e 400 (13 casos), todos vistos vermelhos antes de confiar. Depois, o teste das requisições simultâneas (20 ao mesmo tempo, mesmo CNPJ) ficou vermelho com um 500, o repositório foi corrigido e o resultado certo apareceu: um 201 e dezenove 409.

A ideia para guardar: um teste só vale depois de ser visto vermelho, e um erro só é erro de verdade se a API consegue chegar até ele. Duas coisas que pareciam pendentes (ArgumentException virando 400 e corpo vazio) foram examinadas e descartadas por esse critério.

2. Onde isso está no mapa dos níveis

Camada de testes de API do módulo Clientes (o teste passa pelo HTTP, pelo endpoint, pelo repositório e pelo Postgres real) e um ajuste na infraestrutura (o repositório). Mesmo desenho que o Catalogo tem desde a S17.

3. Conceitos

3.1 Teste de API com banco real (guia 8.11)

Como era (S17, Catalogo) Como é agora (S31, Clientes) O que mudou
ApiComPostgresFabrica do Catalogo PostgresFabrica do Clientes com WebApplicationFactory<Program> cada módulo tem a sua fábrica
UseEnvironment("Testing") igual o seed e outras coisas de Development não rodam
um container por classe de teste igual os testes da classe dividem o banco

Consequência prática: cada teste usa um CNPJ diferente, porque o banco é um só dentro da classe e o CNPJ é único.

3.2 O 201 e o Location

O teste do 201 confere três coisas: o status Created, o cabeçalho Location não nulo e o Location igual a /clientes/{id}. O id não é escrito no teste: é lido do corpo da resposta (clienteId) e comparado.

Primeira ideia Problema Jeito certo
escrever /clientes/1 o banco gera o número; o 1 só vale se este for o primeiro cliente da classe (depende da ordem) ler clienteId do JSON e montar /clientes/{clienteId}
validar o Location com regex mais complicado do que o necessário comparar com o texto montado

Pergunta boa do aluno: "um humano pensaria assim?" Não. Se o teste ficou difícil, normalmente o teste está pedindo o dado errado.

3.3 Theory com MemberData e TheoryData (primeira vez)

[Fact] roda uma vez. [Theory] roda uma vez por linha de dados. Os dados podem vir de [InlineData] (escritos em cima do teste) ou de [MemberData] (uma lista guardada em outro lugar da classe). Para 13 casos com 5 valores cada, a lista fica melhor num membro da classe.

Peça Papel
TheoryData<string, string, string, int, string> uma tabela tipada: cada linha tem 5 colunas, nesta ordem: CNPJ, razão social, nome fantasia, representante, campo que deve acusar erro
[MemberData(nameof(RequisicoesInvalidas))] diz ao xUnit: "pegue as linhas desse membro"
parâmetros do método de teste recebem as 5 colunas, na mesma ordem

Forma da tabela (a lista completa está no arquivo do teste):

public static TheoryData<string, string, string, int, string> RequisicoesInvalidas => new()
{
    // cnpj, razaoSocial, nomeFantasia, representanteId, campo que deve acusar o erro
    { "", "Razão", "Fantasia", 1, CampoCnpj },
    { "40.7DK.4BT/0001-47", "", "Fantasia", 1, CampoRazaoSocial },
};

Os 13 casos: CNPJ (14 dígitos, minúsculo com máscara, misturado sem máscara, 18 dígitos sem máscara, vazio), razão (nula, vazia, mais de 120), fantasia (nula, vazia, mais de 120) e representante (−1 e 0).

Tropeços do dia e o que ensinam: uma aspa a mais (""DCV") quebra a linha inteira; uma const não vai dentro do inicializador, vai no nível da classe; string que recebe null na tabela pede ! ao montar o Request (aviso CS8604).

3.4 O que o 400 devolve: chaves em PascalCase

O corpo do 400 de validação é um HttpValidationProblemDetails. O campo Errors é um dicionário campo → mensagens, e as chaves usam o nome da propriedade em C#: Cnpj, RazaoSocial, NomeFantasia, RepresentanteId. Escrever cnpj em minúsculo falha. O Assert é:

Assert.Contains(campo, problema.Errors.Keys);

Por isso a quinta coluna da TheoryData existe: ela diz qual campo o teste espera ver reclamado.

3.5 Prova do vermelho com sabotagem mínima

Teste Sabotagem O que apareceu
201 tirar a linha que grava (AdicionarAsync) vermelho (eu tinha previsto verde; errei)
409 estrago mínimo na regra do 409 (feito no início da sessão) vermelho
400 estragar o [RegularExpression] do Request 4 vermelhos, 9 verdes

Regra: commit do teste antes, estrago de uma linha, dotnet test sem --no-build, git restore no fim.

O 400 ensina uma coisa fina: com a regex sabotada, o CNPJ vazio continua verde. Não é falha do teste; é o [Required] barrando antes. Cada garantia tem o seu dono.

Outra descoberta: se a validação de entrada some, o ArgumentException do domínio sai da API como 500. A validação de entrada é o que impede o domínio de ser tocado com dado ruim.

3.6 Requisições simultâneas (antes chamado de "corrida")

O termo "corrida" foi mal escolhido; o nome do assunto é requisições simultâneas. O problema:

Passo Requisição A Requisição B
1 consulta o CNPJ: não existe consulta o CNPJ: não existe
2 grava: ok (201) grava: o índice único recusa (23505)
3 sem tratamento: 500

Consultar antes de gravar não basta, porque o passo 1 das duas acontece antes de qualquer gravação. A garantia final é o índice do banco; o código precisa entender a recusa do banco e responder 409.

3.7 O teste das 20 requisições

// forma do teste (o arquivo completo está no repositório)
var tarefas = Enumerable.Range(0, 20)
    .Select(_ => cliente.PostAsJsonAsync("/clientes", request))
    .ToList();

var respostas = await Task.WhenAll(tarefas);
Detalhe Por quê
as 20 tarefas são criadas antes de esperar com await dentro do laço seria uma de cada vez, e nada seria simultâneo
nenhum POST antes do Act o primeiro POST faria os outros 19 serem 409 comuns, sem testar nada novo
conferir todas as respostas conferir só a última esconde o problema
asserts: nenhum 500, exatamente um 201, dezenove 409 descrevem o que o negócio quer
CNPJ próprio do teste não colide com o teste do 409

O vermelho aqui é provável, não garantido: depende do tempo. Com 20 requisições, na prática, ficou vermelho. Se um dia ficar verde sem a correção, é sorte, não proteção.

3.8 A correção: o repositório entende o 23505

public async Task<bool> AdicionarAsync(Cliente cliente, CancellationToken ct)
{
    try
    {
        // ... Add + SaveChangesAsync
        return true;
    }
    catch (DbUpdateException ex)
        when (ex.InnerException is PostgresException { SqlState: PostgresErrorCodes.UniqueViolation })
    {
        return false;
    }
}

O endpoint faz if (!gravou) return CnpjJaCadastrado(request.Cnpj); e a mesma função monta o 409 da consulta e o 409 da recusa do banco (CnpjJaCadastrado).

Ganho Preço
Tratar o 23505 no repositório a resposta certa (409) mesmo com requisições simultâneas o repositório conhece um detalhe do Postgres (PostgresException)
Manter também a consulta antes 409 sem exceção no caminho normal (o comum) duas verificações do mesmo fato
Devolver bool o endpoint decide a resposta false não diz o motivo; hoje só existe um motivo possível

O filtro when é importante: só a violação de unicidade vira false. Qualquer outro erro do banco continua subindo como exceção.

3.9 O que foi examinado e descartado

Candidato Resultado Por quê
ArgumentException do domínio → 400 descartado a API nunca chega lá: a validação do Request ([Required] recusa até espaços) cobre todas as guardas do domínio. Um mapeamento global esconderia bugs verdadeiros
Corpo vazio e JSON malformado no POST descartado no ambiente Testing os dois dão 400 (teste verde sem valor). Em Development dão 500
Dois POST extras no Clientes.http removidos só mostravam o 500 de Development

Sobre o 500 de Development: o log mostrou uma BadHttpRequestException (corpo ruim), que o UseExceptionHandler transforma em 500. Em Testing a mesma exceção vira 400. A hipótese é que o Development configura o servidor para lançar a exceção em vez de responder 400; não foi verificado em Production.

3.10 ADR-002: uma exceção anotada

O ADR-002 diz que tudo no módulo é internal. O CadastrarClienteRequest é public por causa da validação nativa (ADR-003). A nota registra: o Request public é a exceção prevista; Response, endpoint, repositório, DbContext e domínio continuam internal; rever no .NET 11.

6. Avaliação

Fez bem: perguntou o que cada teste agregava antes de aceitar; leu os vermelhos do jeito certo; pegou o id fixo; escreveu a tabela dos 13 casos; achou as chaves em PascalCase pelo próprio erro; conferiu "foi feito tudo relacionado a esta sessão?"; transformou a dúvida do 500 em investigação com .http e log.

Com ajuda: Theory com MemberData e TheoryData (construção nova, ajuda 2); o teste das requisições simultâneas (a primeira versão rodava uma de cada vez); a correção do 23505 (padrão já visto na S30).

O mentor conduziu mal: previu que a sabotagem do 201 ficaria verde (ficou vermelha); previu 400 para o JSON vazio (era 500); listou como pendência o ArgumentException → 400 sem provar que a API chega lá; explicou Theory/MemberData longo demais e sem mostrar o exemplo primeiro; usou o termo "corrida" sem explicar; entregou código incompleto; insistiu em detalhe de PR que o aluno não escreveria.

7. Pontos a melhorar

  • Você: o caminho do .csproj no texto de um PR veio com o nome de outro módulo (Catalogo em vez de Clientes); conferir o que o PR afirma contra o que o git diff --stat mostra.
  • Mentor: mostrar o exemplo pequeno antes da explicação; uma ação por mensagem; provar que um erro é alcançável antes de listá-lo como pendência; nunca prever o que o servidor vai responder.
  • Código (S32): GET /clientes/{id:int} e os outros endpoints do cliente; o mesmo teste de requisições simultâneas e a mesma correção no FichaProduto (SKU); depois o contrato "o cliente existe e tem a ficha completa?".

8. Teste-se

  1. Por que o teste do 201 lê o clienteId do corpo em vez de escrever /clientes/1?
  2. O que é cada coluna da TheoryData<string, string, string, int, string> do teste do 400?
  3. Por que as chaves do erro são Cnpj e RazaoSocial, e não cnpj?
  4. Com a regex sabotada, por que o CNPJ vazio continua verde?
  5. O que acontece quando duas requisições com o mesmo CNPJ passam pela consulta ao mesmo tempo? Que resposta o usuário recebia antes da correção?
  6. Por que as 20 tarefas são criadas antes do Task.WhenAll?
  7. Por que o vermelho do teste simultâneo é "provável" e não "garantido"?
  8. Qual exceção e qual código o repositório captura, e por que o when é necessário?
  9. Por que o ArgumentException do domínio nunca chega a virar resposta da API?

Respostas

Mostrar respostas
  1. Porque o número é gerado pelo banco. O 1 só vale se este for o primeiro cliente da classe; o teste passaria a depender da ordem. Ler o clienteId do corpo funciona sempre.
  2. Na ordem: CNPJ, razão social, nome fantasia, RepresentanteId (número) e o nome do campo que deve aparecer no erro.
  3. Porque o HttpValidationProblemDetails usa o nome da propriedade em C# (PascalCase) como chave. A chave em minúsculo não existe no dicionário.
  4. Porque o [Required] barra o CNPJ vazio antes da regex. Cada garantia tem o seu dono; o teste de CNPJ vazio protege o [Required], não a regex.
  5. As duas passam pela consulta (ninguém gravou ainda). A primeira grava; a segunda bate no índice único do Postgres e o erro 23505 não tratado saía como 500. O certo é 409.
  6. Para as 20 requisições começarem juntas. Com await dentro do laço seria uma de cada vez e não haveria simultaneidade.
  7. Depende do tempo de cada requisição. Com 20 requisições costuma falhar sem a correção, mas se um dia passar sem ela, foi sorte, não proteção.
  8. DbUpdateException cuja InnerException é uma PostgresException com SqlState igual a 23505 (violação de unicidade). O when garante que só esse caso vira false; qualquer outro erro do banco continua subindo.
  9. Porque a validação do Request ([Required], regex, [StringLength], [Range]) recusa antes todo valor que as guardas do domínio recusariam. Sem a validação de entrada, o ArgumentException viraria 500; com ela, o domínio não é tocado.
  10. Em Development, a BadHttpRequestException do corpo ruim chega ao UseExceptionHandler e vira 500; em Testing a mesma situação vira 400. A hipótese (configuração do servidor que lança a exceção só em Development) não foi verificada, e o comportamento em Production também não.
