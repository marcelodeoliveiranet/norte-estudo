3. Conceitos (resumo — detalhe no guia)

Conceito Em uma frase Guia
.slnx a solution em XML curto; só organiza, não executa 1.1
Monolito modular uma solution, um deploy, vários módulos; cada um é uma capacidade de negócio e só conversa pelo contrato público 1.2
Host o único projeto executável; é ele que torna o deploy único 1.2
Projeto por módulo o compilador garante a fronteira, porque internal só esconde entre projetos 1.2, 1.3
Program.cs moderno antes do Build() = antigo ConfigureServices; depois = antigo Configure. A DI em si não mudou 1.4
Implicit usings o projeto Web importa os namespaces do ASP.NET Core sozinho; a biblioteca não 1.5
FrameworkReference dá ao módulo os tipos do ASP.NET Core sem NuGet 1.6
Método de extensão método static com this no 1º parâmetro, chamado como se fosse do tipo 1.7
Pontos de entrada AddCatalogo() (serviços) e MapCatalogo() (rotas): a única coisa do módulo que o host vê 1.8
Minimal APIs e MapGroup MapGet("/rota", handler) no lugar do controller; MapGroup dá o prefixo 1.9

Exemplo do seu mundo: o Startup.cs com ConfigureServices/Configure e os controllers com [Route]/[HttpGet] — o guia mostra cada um lado a lado com o código do Norte.

4. Termos técnicos da sessão

  • Host: projeto executável que sobe a aplicação e liga os módulos.
  • Módulo (Norte): biblioteca com uma capacidade de negócio; ≠ Module do DDD (namespace).
  • internal: visível só no próprio projeto; padrão de classe sem modificador.
  • Ponto de entrada: método público pelo qual o host liga o módulo.
  • MapGroup: grupo de rotas com prefixo comum (.NET 7+).
  • FrameworkReference: referência ao ASP.NET Core já instalado com o runtime.
  • CS0246 / CS1061: tipo não encontrado / método (ou extensão) não encontrado.
  • obj/: pasta de trabalho da compilação; ignorada pelo git; nunca guarda código.

5. Dúvidas suas e as respostas

  • "O projeto OpenAPI foi excluído; não íamos usar?" — A pergunta era sobre a especificação OpenAPI (o JSON que descreve a API), que o Norte vai usar em M1. Apagar o código do aquecimento não tem problema.
  • "Opção B (projeto por módulo) está mais alinhada ao monolito modular?" — Sim, porque garante a regra "nenhum acesso por fora do contrato" pelo compilador. Guia 1.2.
  • "Módulo do DDD é a mesma coisa?" — Não: o Module de Evans é um namespace dentro de um modelo; o módulo do Norte é um contexto inteiro.
  • "Monolito = um deploy de uma capacidade de negócio?" — Não, isso é microsserviço. Monolito modular = um deploy com várias capacidades.
  • "É a solution que torna o deploy único?" — Não, é o host. Solution organiza; host executa.
  • "Fiz tudo na main; reverter?" — Não havia nada a reverter: os arquivos estavam sem commit. Branch criada e commits feitos nela.
  • "Precisa abrir branch para o próximo passo?" — Não: uma branch por objetivo de sessão.
  • "Por que o Ctrl+. não oferece o using?" — Ele só oferece tipos que o projeto conhece; ou falta a FrameworkReference, ou o VS Code precisa recarregar.

Respostas das perguntas de recuperação

Mostrar respostas
  1. O host. Norte.Api é o único executável e referencia os módulos (bibliotecas); publicado, vira um processo só. A solution só organiza projetos para o IDE e para o build.
  2. Antes: ConfigureServices (registros) e Configure (pipeline e rotas). Hoje: builder.Services antes do builder.Build(), e o app depois dele.
  3. Porque o host é outro projeto e só enxerga tipos public. Sem modificador, a classe é internal, visível só dentro do próprio projeto — o compilador a esconde.
  4. Classe static, método static e this no primeiro parâmetro (e public, se usado de outro projeto).
  5. Confirmar o status (curl.exe -i ou F12); depois seguir o código: Program.cs chama MapCatalogo()? O MapGroup tem o prefixo certo? O MapGet está no grupo e com a rota relativa? A aplicação foi reiniciada depois da última alteração?
