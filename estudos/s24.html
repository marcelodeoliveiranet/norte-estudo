3. Conceitos

3.1 Construtor que recusa dado errado (guard clauses)

Um guard clause é um if (ou um método pronto) no começo do construtor que lança exceção quando o dado não serve. Assim nenhum objeto inválido chega a existir.

Campo Regra Como foi escrito
origem tem de ser um valor do enum Enum.IsDefined(origem) → ArgumentOutOfRangeException
criadoPor não pode ser nulo, vazio nem só espaços ArgumentException.ThrowIfNullOrWhiteSpace
clienteId, representanteId maiores que zero ArgumentOutOfRangeException.ThrowIfNegativeOrZero
itens pelo menos um ArgumentException (S23)
sku (item) não pode ser nulo, vazio nem só espaços ThrowIfNullOrWhiteSpace
quantidade, precoUnitario (item) maiores que zero ThrowIfNegativeOrZero
valorDesconto (item) não negativo e menor que preço × quantidade ThrowIfNegative + dois if

Duas diferenças que o teste mostra:

  • null e texto vazio lançam exceções diferentes. ThrowIfNullOrWhiteSpace lança ArgumentNullException para null e ArgumentException para "" ou espaços. Por isso criadoPor tem dois testes, um para cada.
  • A ordem das validações importa. O construtor para na primeira que falha. O ParamName da exceção diz qual linha lançou; é assim que o teste prova que a exceção veio da regra certa.

Sobre o desconto: o item de R$ 100,00 (preço × quantidade) com desconto de R$ 100,00 sairia de graça. Por isso a regra é estritamente menor: igual ou maior lança ArgumentOutOfRangeException com ParamName == "valorDesconto".

3.2 Nullable reference types não impedem null em tempo de execução

O string criadoPor (sem ?) avisa o compilador de que não deve vir null, mas quem chama pode mandar null mesmo assim (outro projeto, reflexão, JSON). Por isso o domínio valida. No teste, para simular isso, usa-se null!: o ! cala o aviso do compilador, e o teste continua mandando null de verdade.

3.3 Os testes de validação

Para campos com vários valores ruins, o Theory com InlineData roda o mesmo teste para cada valor:

[Theory]
[InlineData("")]
[InlineData("   ")]
public void Pedido_valida_criadoPor_vazio_ou_espacao_em_branco_deve_retornar_exception(string criadoPor)
{
    // Arrange — dados válidos, menos o criadoPor
    // Act + Assert — o que acontece com texto vazio ou só espaços?
    var excecao = Assert.Throws<ArgumentException>(
        () => new Pedido(OrigemPedido.App, criadoPor, 123, 23, itens));

    Assert.Equal("criadoPor", excecao.ParamName);
}
Regra de escrita Por quê
Assert.Throws<T> é exato Throws<ArgumentException> não aceita ArgumentNullException, que é um tipo derivado; por isso null ganha teste próprio
Conferir o ParamName prova que a exceção veio do campo certo, e não de outro if
Valores esperados escritos à mão o teste não pode calcular o resultado com o mesmo código que está testando
Um campo ruim por vez os outros campos ficam válidos, para só uma regra poder falhar

Prova do vermelho: para cada regra, comente a validação, rode o teste e veja o vermelho; depois restaure. Se o teste continuasse verde sem a validação, ele não protegeria nada.

3.4 Junção de itens com o mesmo SKU

A regra veio do negócio, dita por você: se o mesmo SKU aparecer duas vezes, soma a quantidade e recalcula. Na vida real o preço do mesmo SKU no mesmo pedido é igual; se o desconto vier diferente, vale o último.

Situação Resultado
SKU novo entra como item novo
SKU que já existe soma a quantidade; mantém o preço; o desconto do último item vale
ABC e abc são o mesmo SKU (a comparação ignora maiúscula e minúscula)

O código mora no Pedido, em um método privado chamado pelo construtor:

private static List<ItemPedido> JuntarItensComMesmoSku(IReadOnlyList<ItemPedido> itens)
{
    var juntados = new List<ItemPedido>();

    foreach (var item in itens)
    {
        var indice = juntados.FindIndex(j => string.Equals(j.Sku, item.Sku, StringComparison.OrdinalIgnoreCase));

        if (indice < 0)
            juntados.Add(item);
        else
        {
            var existente = juntados[indice];
            juntados[indice] = new ItemPedido(item.Sku, existente.Quantidade + item.Quantidade,
                item.PrecoUnitario, item.ValorDesconto);
        }
    }

    return juntados;
}

Repare que o item juntado é criado com new ItemPedido(...): o construtor valida de novo. A soma das quantidades continua passando pelas regras do item (por exemplo, o desconto continua menor que preço × quantidade).

Por que no domínio e não no endpoint? É uma regra do negócio: vale para qualquer origem do pedido (app, vendedor, importação). No Norte a classe Endpoint de cada funcionalidade guarda a lógica do caso de uso, mas a regra que protege o Pedido fica com o Pedido.

Preço: o "último desconto vale" é uma simplificação. O cálculo real do desconto (que depende da forma de pagamento) ainda não existe; quando existir, essa regra será revista.

3.5 PedidoId como int gerado pelo banco

O PedidoId era Guid.NewGuid() dentro do construtor. Agora o domínio não gera o identificador: o banco gera. Na classe: public int PedidoId { get; } (só leitura). O EF preenche depois do INSERT.

Como era Como é agora
PedidoId = Guid.NewGuid() no construtor sem atribuição; o banco cria (identity)
teste conferia Assert.NotEqual(Guid.Empty, ...) teste removido; antes do INSERT o id vale 0

Preço: um pedido novo só tem número depois de salvo. E nenhum teste ainda prova que o banco gera o número; isso fica para um teste com banco real (Testcontainers).

3.6 Persistência do Pedidos com EF Core

Como no Catalogo: um DbContext por módulo e um schema por módulo (ADR-006).

Peça O que faz
PedidoDbContext o contexto do módulo; HasDefaultSchema("pedidos")
ApplyConfigurationsFromAssembly varre o assembly uma vez e aplica todas as classes IEntityTypeConfiguration<T>
PedidoConfiguration tabela pedidos, pedido_id com UseIdentityByDefaultColumn(), colunas em snake_case, enums gravados como int
ItemPedidoConfiguration tabela itens_pedido, chave composta, FK com cascata
MigrationsHistoryTable("__EFMigrationsHistory", "pedidos") a tabela de histórico das migrations fica dentro do schema do módulo
AddPedidos(services, configuration) registra o contexto com UseNpgsql e a connection string Norte; o Program.cs chama

Três ideias novas, todas no ItemPedidoConfiguration e no Pedido:

a) Shadow property. O ItemPedido não tem a propriedade PedidoId (decisão da S23). Mesmo assim a tabela precisa dessa coluna. Uma shadow property existe só no modelo do EF, não na classe:

builder.Property<int>("PedidoId").HasColumnName("pedido_id");

b) Chave composta por nomes. O item não tem id próprio: ele é identificado por pedido + SKU. Como PedidoId é shadow, a chave é montada por nomes de propriedade:

builder.HasKey("PedidoId", nameof(ItemPedido.Sku));

Isso também garante no banco que o mesmo SKU não aparece duas vezes no mesmo pedido, em acordo com a regra da junção.

c) Campo de apoio (backing field). O Pedido expõe IReadOnlyList<ItemPedido> Itens, mas guarda os itens em _itens (uma List). Para o EF conseguir preencher a lista ao ler do banco:

builder.Navigation(p => p.Itens).HasField("_itens");

Ligação entre as duas tabelas:

builder.HasOne<Pedido>()
    .WithMany(p => p.Itens)
    .HasForeignKey("PedidoId")
    .OnDelete(DeleteBehavior.Cascade);

HasOne<Pedido>() sem navegação de volta, porque o item não conhece o pedido. Cascade apaga os itens junto com o pedido.

Construtor privado vazio. O EF precisa de um construtor que não receba parâmetros para criar o objeto ao ler do banco. Ele é private, com o comentário de que só o EF usa, e não passa pelas validações (o dado já foi validado quando entrou). Por isso as propriedades de texto levam = null!: dizem ao compilador "o EF vai preencher".

dotnet ef migrations add CriaTabelasPedidos
    --project src/Modulos/Pedidos/Norte.Pedidos
    --startup-project src/Norte.Api
    --context PedidoDbContext
    -- --environment Development
Parte Para que serve
--project onde a migration será gravada (o módulo)
--startup-project quem tem o Program.cs e a connection string (a API)
--context qual DbContext, porque o Norte tem um por módulo
-- --environment Development o que vem depois do -- vai para o host: lê o appsettings.Development.json

O mesmo vale para dotnet ef database update. Resultado no Postgres: schema pedidos com pedidos, itens_pedido e __EFMigrationsHistory; o schema public continua vazio.

Dois detalhes que apareceram:

  • Na primeira execução, o fail: do SELECT na tabela de histórico é esperado: o EF verifica se a tabela existe antes de criá-la.
  • O código gerado usa namespace em bloco e dispara o aviso IDE0161 no build. Solução: um .editorconfig dentro de Migrations/ com dotnet_diagnostic.IDE0161.severity = none (o mesmo do Catalogo). O código gerado não é seu; a regra de estilo vale para o que você escreve.

5. Dúvidas e respostas

Por que null e "" têm testes separados? Porque lançam exceções de tipos diferentes e Assert.Throws<T> exige o tipo exato.

Por que o desconto igual ao total é recusado? O item sairia de graça. A regra foi escrita como "estritamente menor"; se o negócio aceitar item gratuito, a regra muda e o teste junto.

A junção por SKU não deveria ficar no endpoint? Não. É regra que protege o Pedido, e o endpoint de criação ainda não existe. Se ficasse só no endpoint, outra porta de entrada criaria pedido com SKU repetido.

O Pedido não valida o tamanho do SKU (20) nem do criadoPor (50). Verdade: hoje o limite existe só na coluna do banco. Um SKU maior que 20 só falha ao salvar. Registrado como pendência.

Como saber que o banco gera o PedidoId? Hoje só pela migration e pela leitura do esquema. Um teste de integração (Testcontainers) vai provar isso.

Respostas

Mostrar respostas
  1. ThrowIfNullOrWhiteSpace lança ArgumentNullException para null e ArgumentException para "" ou espaços. Assert.Throws<T> exige o tipo exato, então cada caso precisa do seu teste.
  2. Não. A regra é "estritamente menor": desconto igual a preço × quantidade lança ArgumentOutOfRangeException com ParamName == "valorDesconto", porque o item sairia de graça.
  3. Um único item ABC (a comparação ignora maiúscula e minúscula) com as quantidades somadas, o preço mantido e o desconto do último.
  4. Porque o construtor valida de novo. A soma das quantidades continua passando pelas regras do item, como a do desconto menor que preço × quantidade.
  5. Uma propriedade que existe só no modelo do EF, e não na classe. O ItemPedido não tem PedidoId na classe, mas a tabela precisa da coluna pedido_id para a chave composta e para a FK.
  6. Diz ao EF para preencher a lista guardada em _itens ao ler do banco, enquanto a classe expõe Itens só para leitura.
  7. O EF precisa de um construtor sem parâmetros para criar o objeto ao ler do banco. Ele não passa pelas validações: o dado já foi validado quando entrou.
  8. --project: onde a migration é gravada (o módulo). --startup-project: quem tem o Program.cs e a connection string (a API). --context: qual DbContext usar, porque cada módulo tem o seu.
  9. Cria a branch e muda para ela. Sem o -c, o Git procura uma branch que já existe e dá erro.
