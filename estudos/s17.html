Norte · S17 — 409 no SKU duplicado e teste com Postgres real

Terça, 13/10/2026 · 09:31 → 15:01 · 3h42 líquidas (pausas de 0h17 e 1h31) · Marco M1

Objetivo da sessão: transformar o 500 do SKU duplicado numa resposta de negócio (409 Conflict) e protegê-la com um teste que fala com um Postgres de verdade. Entregue (dois PRs na main): o 409 e o teste de integração com Testcontainers (PR #10, f02deda) e o fechamento da imagem do CI em ubuntu-24.04 (PR #11, d59e84f). A main termina com 5 testes verdes.

Antes de ler: a sessão fecha a pendência que a S16 deixou aberta ("o duplicado devolve 500; o certo é 409; nenhum teste toca o banco"). A explicação completa de cada peça está nas entradas 6.9 a 6.11 da Parte 6 do guia. Esta página é o roteiro de estudo da sessão.

1. O problema que a sessão resolve

Ao fim da S16, cadastrar o mesmo SKU duas vezes dava:

Passo Resultado
POST /catalogo/fichas-produto com LUV-001 201 Created
o mesmo POST de novo 500 — DbUpdateException → 23505 duplicate key value violates unique constraint "PK_fichas_produto"

O banco fez o trabalho certo (recusou), mas o cliente recebeu "erro do servidor" para algo que ele pode corrigir. Isso é uma regra de negócio ("não existem duas fichas com o mesmo SKU") e o status certo é 409 Conflict.

2. As peças

# Peça O que você faz Onde mora
1 Pacote do Testcontainers acrescenta Testcontainers.PostgreSql (4.16.0) no Directory.Packages.props e a PackageReference no projeto de testes Directory.Packages.props, Norte.Catalogo.Tests.csproj
2 Postgres descartável no teste sobe um container postgres:18 por execução de testes ApiComPostgresFabrica.cs
3 API de teste apontada para esse banco WebApplicationFactory<Program> com a connection string trocada e MigrateAsync mesmo arquivo
4 Regra do 409 consulta o SKU antes de gravar; se existe, devolve TypedResults.Problem(409) CadastrarFichaProdutoEndpoint.cs
5 Tipo de retorno do endpoint troca ValidationProblem por ProblemHttpResult no Results<...> mesmo arquivo
6 O teste da regra POST válido → 201; mesmo POST → 409 com título "Sku já cadastrado" CadastrarFichaProdutoComBancoApiTests.cs
7 Imagem do runner do CI runs-on: ubuntu-24.04 em vez de ubuntu-latest .github/workflows/ci.yml

Regra de decisão da ordem: a fábrica e o teste vêm antes do código do 409. O teste precisa ser visto vermelho pelo motivo certo (o duplicado devolve 500); só então o código o deixa verde. Um teste que nunca foi visto vermelho não prova que protege nada.

Os commits do PR #10, na ordem: build(catalogo): adicionar testcontainers… → test(catalogo): adicionar fábrica da api com postgres em container → fix(catalogo): recusar sku duplicado com 409 → test(catalogo): proteger o 409 do sku duplicado com postgres real. O PR #11 tem um commit: ci: fixar runner no ubuntu-24.04.

3. Como ler o código

3.1 O endpoint com o 409

public static async Task<Results<Created<FichaProduto>, ProblemHttpResult>> ExecutarAsync(
    CadastrarFichaProdutoRequest request,
    FichaProdutoRepository fichas)
{
    var fichaExistente = await fichas.ObterPorSkuAsync(request.Sku!);
    if (fichaExistente is not null)
    {
        return TypedResults.Problem(
            statusCode: StatusCodes.Status409Conflict,
            title: "Sku já cadastrado",
            detail: $"O sku {request.Sku} já está cadastrado");
    }

    var ficha = new FichaProduto(request.Sku!, request.Descricao!, request.Ncm!);
    await fichas.AdicionarAsync(ficha);

    return TypedResults.Created($"/catalogo/fichas-produto/{ficha.Sku}", ficha);
}
Trecho Significado
ObterPorSkuAsync antes de AdicionarAsync verifica antes de gravar: pergunta ao banco se o SKU existe
TypedResults.Problem(statusCode: 409, ...) resposta em application/problem+json, com o status que você escolheu e um título legível
title: "Sku já cadastrado" o teste confere esse texto; mudar o título quebra o teste (o título é parte do contrato)
ProblemHttpResult no Results<...> o método agora devolve 201 ou um problem; ValidationProblem deixou de ser devolvido aqui (o 400 da validação nativa acontece antes do endpoint)
request.Sku! o ! é uma promessa: "a validação nativa já garantiu que não é nulo" (ver seção 5)

Por que TypedResults.Problem(...) e não TypedResults.Conflict()? O Conflict() devolve só o status; o Problem leva título e detalhe que o cliente consegue ler. O preço é que o título passa a ser contrato com o teste.

3.2 A fábrica da API com banco real

public sealed class ApiComPostgresFabrica : WebApplicationFactory<Program>, IAsyncLifetime
{
    private readonly PostgreSqlContainer _postgres = new PostgreSqlBuilder("postgres:18").Build();

    public async Task InitializeAsync()
    {
        await _postgres.StartAsync();
        using var escopo = Services.CreateScope();
        var contexto = escopo.ServiceProvider.GetRequiredService<CatalogoDbContext>();
        await contexto.Database.MigrateAsync();
    }

    protected override void ConfigureWebHost(IWebHostBuilder builder)
    {
        builder.UseSetting("ConnectionStrings:Norte", _postgres.GetConnectionString());
    }

    public new Task DisposeAsync() => _postgres.DisposeAsync().AsTask();
}
Passo O que faz Sem ele
1. StartAsync() sobe o container postgres:18 um Postgres só para a execução dos testes não há banco para falar
2. UseSetting("ConnectionStrings:Norte", …) a API de teste aponta para o container, não para o banco de desenvolvimento os testes gravam no banco do Compose e deixam lixo
3. MigrateAsync() cria o schema catalogo e a tabela dentro do container a tabela não existe; o primeiro INSERT falha
4. DisposeAsync() descarta o container sobram containers parados na máquina

O Docker precisa estar aberto para os testes rodarem. Com o container, a suíte passou de ~4,5 s para ~11 s.

3.3 O teste (Arrange / Act / Assert)

Parte Pergunta que responde No teste do 409
Arrange em que situação o sistema está? a API ligada a um Postgres real e vazio; um corpo válido com SKU gerado de um Guid (nunca existiu antes)
Act que ação o usuário faz? o mesmo cadastro enviado duas vezes (o 1º POST é só preparação)
Assert o que o sistema deve mostrar? o 1º POST devolve 201; o 2º devolve 409 com o título "Sku já cadastrado"

O SKU por Guid faz o teste não depender de execução anterior; o banco novo a cada execução garante que não sobra dado de uma rodada para outra.

4. O preço de cada decisão (ganho × preço)

Decisão Ganho Preço
Verificar antes de gravar (consulta + INSERT) o 409 sai do código de negócio, explícito no endpoint, sem tipo do Npgsql e sem conceito novo uma consulta a mais em todo cadastro; corrida: duas requisições simultâneas passam pela consulta e a segunda cai no 23505 → 500
Tratar a exceção 23505 (alternativa não adotada, anotada como evolução) uma ida só ao banco; sem corrida o endpoint passa a conhecer PostgresException e o código 23505 (detalhe do Postgres no código de negócio)
Testcontainers (Postgres real) banco novo e vazio a cada execução; o mesmo teste roda local e no CI exige Docker na máquina e no CI; a suíte ficou mais lenta (~4,5 s → ~11 s); a 1ª execução baixa a imagem
Postgres do Compose no teste (rejeitado) nenhum pacote novo SKU fixo falharia na 2ª execução; com SKU único funciona, mas o CI exigiria um Postgres externo
Provider em memória / SQLite (rejeitados) rápidos, sem Docker passam onde o Postgres reprovaria: o 23505 só existe no Postgres
Fixar ubuntu-24.04 no CI o CI fica na imagem em que o teste passou e não muda sozinho quando o ubuntu-latest migrar para o Ubuntu 26 alguém precisa testar o 26.04 e trocar a fixação antes de 19/11
Não proteger a main agora nenhuma configuração inútil o CI avisa, mas não impede o merge; ver seção 7

O risco registrado: com "verificar antes de gravar", a corrida entre duas requisições continua devolvendo 500. Foi aceito e ficou no ADR; a defesa completa seria verificar antes e também tratar o 23505.

5. O experimento do public → internal no Request

O CadastrarFichaProdutoRequest é public por exigência do gerador da validação nativa (ADR-003). Na revisão espaçada da abertura, a previsão foi "se virar internal, dá erro de build". O experimento foi feito em branch descartável (teste/catalogo-request-internal) para ver o que realmente acontece.

Observação Resultado
dotnet build Norte.slnx passa — Build succeeded, sem erro e sem aviso
dotnet test 3 de 5 testes falham: esperavam 400 BadRequest, receberam 409 Conflict

O que isso prova, na ordem em que acontece:

  1. Com internal, o gerador da validação não enxerga o tipo; a validação deixa de rodar, sem aviso.
  2. Os corpos dos testes de recusa têm um campo vazio (sku = "", descricao = "" ou ncm = ""); sem a validação, eles chegam ao endpoint.
  3. O endpoint consulta o SKU e grava. No banco de desenvolvimento, o primeiro teste gravou uma ficha com SKU vazio e os seguintes encontraram esse SKU → 409 em vez de 400.

Consequências para guardar:

  • O build não avisa. O erro só aparece em tempo de execução, e só se existir um teste que cubra a validação. A previsão "erro de build" estava errada; a consequência (a validação deixa de proteger) é o ponto da regra do ADR-003.
  • O ! em request.Sku! só é seguro porque a validação rodou; sem ela, o endpoint trabalha com valores que ninguém verificou.
  • O resultado dependeu de os testes gravarem no banco de desenvolvimento: é sintoma de teste que toca o banco do desenvolvedor (seção 6).

Depois do experimento, git restore desfez a alteração, a linha de SKU vazio foi apagada do banco e a main voltou limpa.

6. O que a sessão deixou à vista

Achado Por que importa
Os três testes de recusa 400 usam WebApplicationFactory<Program> simples, contra o banco de desenvolvimento quando a validação falha, eles gravam lixo
O construtor de FichaProduto não valida quem não passa pela API (outro módulo, um teste) cria ficha com SKU vazio
O teste do 409 existiu antes do código que o satisfaz foi visto vermelho (500) e depois verde (409)
Insight seu: "o teste não tem lógica de negócio; ele só testa o comportamento esperado" quando a lógica mora no lugar certo, o teste fica simples. Ajuste: o teste reflete o que a regra exige, não como ela foi implementada

Sobre o insight: o mesmo teste do 409 continuaria verde se a regra fosse implementada tratando o 23505 (opção B), sem mudar uma linha. É isso que significa testar o comportamento e não a implementação.

Respostas

Mostrar respostas
  1. Há uma chave primária em sku; o banco recusa o 2º INSERT (23505) e o tratamento global devolve 500, que significa "erro do servidor". O cliente pode corrigir o problema (não reenviar o SKU), então o status é 409 Conflict, uma regra de negócio.
  2. Verificar antes consulta o SKU e só então grava: lê-se fácil e não conhece o Postgres, mas faz uma consulta a mais em todo cadastro e deixa uma janela de corrida. Tratar o 23505 grava e reage à exceção: uma ida só e sem corrida, mas o endpoint passa a conhecer PostgresException e o código do Postgres.
  3. Duas requisições com o mesmo SKU passam pela consulta antes de qualquer uma gravar; a segunda a gravar cai no 23505 e devolve 500 em vez de 409.
  4. Porque o 23505 e o schema por módulo só existem no Postgres; provider em memória e SQLite aceitam o duplicado ou se comportam de outro jeito e o teste passaria sem proteger nada.
  5. Sobe o container postgres:18; troca a connection string da API de teste para o container; aplica as migrations; ao terminar, descarta o container.
  6. Não falha: o build passa. A validação nativa deixa de rodar (o gerador não enxerga o tipo) e os valores inválidos chegam ao endpoint. Só se descobre em tempo de execução, e só se houver teste que exija o 400 (aqui, 3 de 5 testes ficaram vermelhos).
  7. Promete "este valor não é nulo porque a validação já rodou". Deixa de valer quando a validação não executa (por exemplo, Request internal) ou quando o endpoint é chamado fora da API (um teste de unidade, outro módulo).
  8. Usam a API com o banco de desenvolvimento; se a validação falhar e o endpoint gravar, a linha fica lá. Solução: usar a fábrica com Postgres descartável.
  9. Alguém precisa testar o Ubuntu 26 e trocar a imagem (prazo: antes de 19/11); o CI deixa de acompanhar o ubuntu-latest automaticamente.
  10. Arrange: API ligada a um Postgres real e vazio, corpo válido com SKU novo. Act: enviar o mesmo cadastro duas vezes. Assert: 1ª resposta 201; 2ª resposta 409 com o título "Sku já cadastrado".
  11. AddProblemDetails() escreve o corpo; UseExceptionHandler() captura a exceção não tratada; UseStatusCodePages() preenche o corpo de um 4xx/5xx vazio.
