Norte · S25 — Pedidos: o primeiro teste com banco real

Quarta, 21/10/2026 · tempo líquido: 3h11 (abaixo do limite de 5h) · Marco M1

Hoje você fez o que a S24 deixou sem prova: guardou um Pedido com dois itens no Postgres de verdade e leu de volta (PRs #32 e #33). Você escreveu a fábrica do banco, os dois testes e os comandos de Git; o mentor conferiu. A ideia para guardar: um teste de persistência só prova alguma coisa quando quem grava e quem lê são contextos diferentes, e quando você já viu o teste ficar vermelho. O que antes era "a migration mostra que deve funcionar" agora é "o teste mostra que funciona".

2. Onde isso está no mapa dos níveis

Solution → módulos → funcionalidades → camadas. Hoje o trabalho foi na camada de testes do módulo Pedidos, falando com a infraestrutura (EF Core + Postgres) através do PedidoDbContext. Os testes não passam pela API: o endpoint de criação do pedido ainda não existe. É um teste que fala direto com o DbContext.

3. Conceitos

3.1 A fábrica do banco: IAsyncLifetime, IClassFixture e MigrateAsync

No Catalogo (S17) a fábrica sobe a API inteira. No Pedidos não há API ainda, então a fábrica é menor: sobe só o banco e entrega um DbContext pronto.

public sealed class PostgresFabrica : IAsyncLifetime
{
    private readonly PostgreSqlContainer _postgres = new PostgreSqlBuilder("postgres:18").Build();

    public async Task InitializeAsync()
    {
        await _postgres.StartAsync();
        await using var contexto = CriarContexto();
        await contexto.Database.MigrateAsync();
    }

    internal PedidoDbContext CriarContexto()
    {
        var opcoes = new DbContextOptionsBuilder<PedidoDbContext>()
            .UseNpgsql(_postgres.GetConnectionString(),
                npgsql => npgsql.MigrationsHistoryTable("__EFMigrationsHistory", PedidoDbContext.Schema))
            .Options;

        return new PedidoDbContext(opcoes);
    }

    public Task DisposeAsync() => _postgres.DisposeAsync().AsTask();
}
Peça O que faz Por quê
PostgreSqlBuilder("postgres:18") descreve o container (mesma imagem do compose.yaml) o teste roda no mesmo Postgres de verdade, não num substituto
IAsyncLifetime o xUnit chama InitializeAsync antes e DisposeAsync depois subir e derrubar o container são operações assíncronas
MigrateAsync() aplica as migrations do módulo no banco novo o teste usa as mesmas tabelas que a migration CriaTabelasPedidos cria; se a migration estiver errada, o teste quebra
MigrationsHistoryTable(..., PedidoDbContext.Schema) põe a tabela de histórico dentro do schema pedidos o mesmo que o AddPedidos faz (ADR-006); sem isso o EF procuraria o histórico no schema errado
CriarContexto() entrega um contexto novo a cada chamada o teste 2 precisa de dois contextos (3.2)
internal só o projeto de teste enxerga InternalsVisibleTo (S22); a fábrica em si é public sealed para o xUnit

Como o teste usa a fábrica: a classe de teste declara IClassFixture<PostgresFabrica> e recebe a fábrica no construtor primário. O xUnit cria uma fábrica por classe de teste: o container sobe uma vez, os dois testes usam o mesmo banco.

public class PedidoPersistenciaTests(PostgresFabrica fabrica) : IClassFixture<PostgresFabrica>

Dois erros que apareceram no caminho (bons para guardar):

  • new PostgresFabrica() dentro do teste: cria uma fábrica sem o xUnit chamar o InitializeAsync, e o banco nunca sobe. Quem entrega a fábrica é o IClassFixture.
  • Classe de teste internal: o xUnit não enxerga. A classe de teste é public (a regra da S22 continua valendo).
Ganho Preço
Fábrica com o container real o teste prova o que o banco faz (identity, chave composta, FK, tipos) precisa de Docker aberto e o teste é mais lento que o de domínio (o container sobe uma vez por classe)
Uma fábrica por classe o banco sobe uma vez só os dois testes dividem o mesmo banco: os dados de um ficam para o outro (hoje sem problema, porque cada pedido tem o seu número)

3.2 Gravar com um contexto, ler com outro, e o Include

O DbContext lembra o que já carregou (é o rastreamento). Se o mesmo contexto grava e depois lê, o EF devolve o objeto que ele já tem na memória e nem vai ao banco. O teste passaria mesmo se o banco guardasse errado. Por isso:

await using var contextoA = fabrica.CriarContexto();
await using var contextoB = fabrica.CriarContexto();
// ...
await contextoA.Pedidos.AddAsync(pedido);
await contextoA.SaveChangesAsync();
var pedidoLido = await contextoB.Pedidos
                                .Include(p => p.Itens)
                                .FirstOrDefaultAsync(p => p.PedidoId == pedido.PedidoId);
Linha Pergunta que responde
contextoA grava os dados chegam ao banco?
contextoB (novo) lê o banco devolve o que foi gravado, sem ajuda da memória do contexto A?
.Include(p => p.Itens) quero também a lista de itens junto com o pedido
FirstOrDefaultAsync(p => p.PedidoId == pedido.PedidoId) o número que o banco gerou na gravação acha o pedido de volta?

O Include não é enfeite. O EF não carrega itens sozinho (é o padrão do EF Core): sem Include, o pedido volta com Itens vazio. Visto no vermelho: Assert.Equal(2, pedidoLido.Itens.Count) falhou com Expected: 2, Actual: 0. A mesma consulta com o Include voltou os dois itens.

Assert por campo. O teste confere SKU, quantidade, preço e desconto de cada item, comparando com as variáveis do Arrange (não com literais copiados). Isso prova que os numeric(10,2) e os varchar voltam com o mesmo valor.

Ganho Preço
Dois contextos prova a ida e a volta pelo banco o teste é mais comprido (dois await using)
Include explícito o teste mostra de onde vêm os itens quem esquece o Include na vida real recebe a lista vazia, sem erro
Assert por posição (Itens[0], Itens[1]) simples de ler assume a ordem em que o banco devolve os itens; sem OrderBy o Postgres não promete ordem. Hoje passa; a ordem não está provada

3.3 A prova do vermelho em teste de persistência

A mesma regra da S21 ao S24, agora com banco: o teste novo precisa ser visto vermelho, senão não se sabe se ele protege.

Passo O que se fez Resultado
1 commit do teste verde antes do estrago o git restore não apaga o teste
2 estrago mínimo no teste 1: comentar await contexto.SaveChangesAsync(); git status mostra a mudança
3 rodar vermelho: Assert.NotEqual() Failure: Expected: Not 0, Actual: 0 (o pedido não foi salvo; o número continua 0)
4 desfazer o estrago verde de novo
5 o mesmo no teste 2, tirando o Include vermelho: Expected: 2, Actual: 0

Como ler o vermelho: o teste é o contrato; o Actual errado mostra que o código (ou o que foi desfeito) está errado, não o teste. Nos dois casos você leu certo.

Cuidado com o comando: dotnet test --no-build roda a DLL antiga. Depois de editar um teste, o --no-build não vê a edição. Foi o erro da primeira descrição do PR #32 (os passos de vermelho/verde usavam --no-build) e foi corrigido. Para a prova do vermelho: dotnet test normal (que compila).

4. Termos da sessão

Termo Em uma linha
Testcontainers biblioteca que sobe um container (aqui, o Postgres) durante o teste e o derruba no fim

--no-build roda sem compilar: usa a DLL antiga

5. Dúvidas e respostas

Por que o teste não usa a API? Porque ainda não existe endpoint de criação do pedido, e o que queríamos provar é do banco e do EF, não da API. Quando o endpoint nascer, ele ganha o seu próprio teste.

Por que um container real e não o provider em memória? Decisão da S17: o provider em memória não tem chave composta de verdade, identity nem tipos do Postgres; o teste passaria com um banco que não existe. Docker aberto é o preço, e já era o preço do Catalogo.

A tabela de histórico das migrations precisa ficar no schema pedidos? Sim. O AddPedidos configura assim (ADR-006), e a fábrica faz o mesmo para o MigrateAsync achar o histórico no lugar certo.

Um teste com dois itens prova a junção por SKU? Não. A junção é regra do Pedido e tem os seus testes de domínio (S24). Hoje os SKUs são diferentes (SKU123 e SKU321); o que o teste prova é a ida e volta pelo banco.

O banco já recusa SKU maior que 20 ou criado_por maior que 50? A coluna recusa ao salvar (erro do Postgres). O domínio ainda não valida o tamanho, e nenhum teste prova isso. É a pendência que você apontou no fim do dia.

Como ver as tabelas no DBeaver? A árvore mostra os schemas catalogo, pedidos e public. Se uma tabela não aparece, atualize a árvore (F5): ela estava desatualizada. Na migration CriaTabelasPedidos existem pedidos e itens_pedido, e a consulta no DBeaver mostrou as três tabelas do schema (com a __EFMigrationsHistory).

Respostas

Mostrar respostas
  1. Porque o DbContext lembra o que carregou. Se o mesmo contexto gravasse e lesse, o EF devolveria o objeto da memória sem ir ao banco, e o teste passaria mesmo com a gravação errada. O contexto B, novo, só tem o que o banco devolve.
  2. Vem vazio (o EF não carrega a coleção sozinho). O teste viu isso: Expected: 2, Actual: 0.
  3. O IClassFixture faz o xUnit criar a fábrica, chamar o InitializeAsync (sobe o container e aplica as migrations) e o DisposeAsync no fim, uma vez por classe. Com new, ninguém chama o InitializeAsync e o banco não existe.
  4. Aplica as migrations no banco novo do container, para o teste usar as mesmas tabelas que a migration CriaTabelasPedidos cria.
  5. Para o EF guardar e procurar a tabela de histórico no schema pedidos, como o AddPedidos faz (ADR-006). Sem isso o MigrateAsync olharia o lugar errado.
  6. O defeito estava no código: sem o SaveChangesAsync, o pedido não foi salvo e o número continuou 0. O teste é o contrato; o Actual errado mostra que o que está sendo testado está errado, não o teste.
  7. Porque o --no-build roda a DLL antiga: a edição do teste (o estrago) não entra, e o resultado não mostra o vermelho.
  8. Assume que o banco devolve os itens na ordem em que foram gravados. Sem OrderBy, o Postgres não promete ordem; hoje passa, mas a ordem não está provada.
  9. O teste de domínio prova as regras do objeto na memória (validações, junção por SKU). O de persistência prova que o banco e o EF guardam e devolvem o que o domínio aceitou: o número gerado, a chave composta, a FK, os tipos e a lista de itens.
