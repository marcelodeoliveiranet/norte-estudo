R2 — A qualidade no build, testada de ponta a ponta

Sábado, 10/10/2026 · revisão da semana de 05/10 · 15:25 → 22:06 · fora da sessão · Marco M1

Esta revisão pegou um único tema da reconstrução (T1, a qualidade no build) e o testou até o fim, com experimentos em projetos descartáveis (Zero.*), fora do repositório norte. T2 (tratamento de erros e teste do 500) e T3 (CI) não foram feitos: ficam para o sábado seguinte ou para quando você decidir.

Este material tem três partes: o que ficou provado (e como ver de novo), o que não foi provado (para não virar certeza falsa) e um Teste-se no fim. Onde diz "provado", houve um experimento com saída vista; onde diz "inferido", não houve.

1. Como o MSBuild encontra os arquivos de configuração

Cada projeto procura os arquivos subindo as pastas a partir da sua própria pasta e usa o primeiro que achar.

Arquivo Quem procura Regra provada
Directory.Build.props MSBuild, antes do .csproj o mais próximo vence; o de cima não é herdado sozinho
Directory.Build.targets MSBuild, depois do .csproj mesma busca; dotnet new buildtargets cria
Directory.Packages.props NuGet (Central Package Management) o mais próximo vence; precisa de <Project> na raiz
.editorconfig compilador/analyzers todos os arquivos do caminho valem, até um com root = true

Herdar do nível de cima é uma decisão explícita: um Import do arquivo de cima (GetPathOfFileAbove) ou o dotnet new buildprops --inherit. Sem isso, o arquivo mais próximo "esconde" o de cima.

<Project>
  <Import Project="$([MSBuild]::GetPathOfFileAbove('Directory.Build.props', '$(MSBuildThisFileDirectory)../'))" />
  <!-- propriedades só deste nível -->
</Project>

Precedência no .editorconfig

  1. Dentro do mesmo arquivo, a linha mais abaixo vence.
  2. Entre arquivos, o mais fundo (mais perto do .cs) vence.
  3. [seção] define o alcance: uma linha colocada depois de [tests/**.cs] vale só ali.
  4. root = true para a subida; nada acima dele é lido.

Armadilha vista: uma linha de regra global colada depois de um [tests/**.cs] vira regra só dos testes — o build do código de produção deixa de cobrar e ninguém avisa. Regra global fica antes de qualquer seção.

2. Central Package Management (CPM)

Situação Resultado Por quê
Version dentro do PackageReference do .csproj NU1008 com CPM a versão só mora no Directory.Packages.props
PackageReference sem PackageVersion correspondente NU1010 o projeto pede um pacote cuja versão ninguém definiu
PackageVersion posto no Directory.Build.props NU1010 o NuGet só lê PackageVersion no Directory.Packages.props
Directory.Packages.props sem <Project> na raiz CPM não aplica, sem erro o arquivo é ignorado em silêncio
dotnet add package com CPM ligado grava os dois lados PackageReference no projeto e PackageVersion no arquivo central
duas versões do mesmo pacote não existe: uma versão por pacote exceção explícita: VersionOverride no PackageReference

O "sem erro" da linha 4 é o perigoso: o CPM desligado parece funcionar até alguém ver duas versões do mesmo pacote na solution.

3. TreatWarningsAsErrors e o nível da análise

TreatWarningsAsErrors=true transforma todo aviso do compilador (CS) e dos analyzers (CA) em erro.

AnalysisMode O que liga
None nenhuma regra extra
Default o conjunto padrão do SDK
Minimum só as regras mais críticas
Recommended o padrão + regras recomendadas (o Norte usa este)
All tudo; numa classe mínima acendeu CA1002, CA1062 e CA2007
  • Existem AnalysisMode<Categoria> (ex.: por categoria de regras) e o AnalysisLevel composto (latest-recommended etc.).
  • Os conjuntos moram no SDK, em arquivos .globalconfig: C:\Program Files\dotnet\sdk\10.0.401\Sdks\Microsoft.NET.Sdk\analyzers\build\config\analysislevel_10_all.globalconfig (e ..._recommended). Neles se vê o que cada nível liga — a fonte é o SDK instalado, não a memória.
  • Só no nível All existem cerca de 135 regras CA a mais.

O caso da CA1716

A CA1716 reclama de identificador igual a palavra-chave de alguma linguagem .NET. Por padrão só olha o que é visível de fora (public). Ela não liga no padrão; o Recommended liga. Foi o que derrubou o build do projeto Zero.Lib: o nome escolhido era palavra-chave. Em projeto de teste com nomes Regra_Resultado, a CA1707 (underscore no nome) também aparece — por isso o Norte a desliga só em [tests/**.cs], com motivo escrito no .editorconfig.

4. Regras de estilo (IDE) no build

As regras IDExxxx são do Roslyn/IDE. Para rodar no build precisam de duas condições juntas:

  1. EnforceCodeStyleInBuild=true (testado true e false: com false as IDE somem do build);
  2. a regra ter, no Roslyn, um EnforceOnBuild que permita (Never, Recommended, HighlyRecommended).
Regra EnforceOnBuild Consequência provada
IDE0003 (this.), IDE0001, IDE0002, IDE0009 Never nunca rodam no build, mesmo configuradas como warning
IDE0161 (namespace de arquivo) HighlyRecommended roda; vira erro com warning + TreatWarningsAsErrors
IDE1006 (nomes) Recommended roda; ver abaixo
IDE0044 (campo readonly) roda virou erro no experimento do .editorconfig gerado

Atenção: o primeiro teste desta revisão usou a IDE0003 e "não acusou nada". Não era falha da configuração: a regra nunca roda no build. O teste de controle com a IDE0161 (que roda) confirmou que a configuração estava certa.

Duas formas de dar severidade

# forma A — opção com severidade
csharp_style_namespace_declarations = file_scoped:warning

# forma B — pelo id da regra
dotnet_diagnostic.IDE0161.severity = warning

Provado: as duas funcionam no build, desde que a regra rode no build (as condições acima). Isso corrige a nota antiga do guia (4.2) de que o formato opcao = valor:warning só valia no editor.

Regras de nome (IDE1006)

Cada regra de nome (dotnet_naming_rule.X.severity) tem a sua severidade. A linha dotnet_diagnostic.IDE1006.severity = warning sobrescreve a suggestion de todas as regras de nome de uma vez. No Norte, o método de teste async não leva Async; por isso a regra do sufixo é none em [tests/**.cs].

5. O que o CLI gera (e o perigo de usar sem ler)

Templates provados em SDK 10.0.401 (dotnet new list):

Comando Gera Cuidado
dotnet new buildprops Directory.Build.props traz comentário e só o essencial; --inherit faz o Import
dotnet new packagesprops Directory.Packages.props liga o CPM; versões vêm do que você escrever
dotnet new buildtargets Directory.Build.targets rodar depois do .csproj
dotnet new editorconfig .editorconfig 389 linhas, root = true; 19 regras de nome como suggestion
dotnet new sln .slnx (no SDK 10.0.401) formato novo, não .sln

O .editorconfig gerado quebra o Norte

O arquivo gerado tem linhas com :warning (ex.: dotnet_style_readonly_field = true:warning). Num projeto com TreatWarningsAsErrors=true + EnforceCodeStyleInBuild=true isso vira erro (IDE0044 no teste, num campo que poderia ser readonly). Olhar só as linhas com a palavra "severity" não basta — a severidade também está no sufixo :warning das opções.

Regra de uso: arquivo gerado por template se lê inteiro antes de entrar no repositório; ou se mantém o do Norte (curto, com motivo em cada linha) e se pega do gerado só o que se decidir.

6. Visual Studio × CLI

Pergunta da revisão: "se o CLI é usado pelo VS, posso criar só no CLI?". O experimento comparou o mesmo projeto criado nos dois.

Ponto Resultado
conteúdo do .csproj igual
layout de pastas e nome da solution diferem
arquivos .cs diferem: namespace em bloco (VS) × escopo de arquivo (CLI)
solution .slnx só é gravada depois de Salvar Tudo
referência entre projetos no VS a ProjectReference pode sair invertida se o diálogo for aberto no projeto errado

Conclusão provada: o .csproj igual não prova que "o VS chama o CLI" — os .cs diferem. Cada ferramenta tem o seu template. Um projeto criado no VS, com namespace em bloco, deve falhar no Norte pela IDE0161 — mas esse teste foi cortado: ver a seção 7.

9. Hábito que isto cria no Norte

  1. Cada erro novo do build vira linha no guia (Parte 4) — esta revisão adiciona NU1008, NU1010, CA1716 e IDE0044.
  2. Arquivo gerado se lê inteiro antes de entrar.
  3. Teste de configuração se faz com um controle: se a regra "não acusou", antes de concluir que a configuração falhou, confirmar que a regra roda no build.
  4. Um fator por vez em cada experimento.

Teste-se

  1. Dois Directory.Build.props (um na raiz, um na pasta do projeto). O que o projeto usa, e como herdar o de cima?
  2. Num .editorconfig, uma linha global foi colada depois de [tests/**.cs]. Onde ela vale?
  3. NU1008 e NU1010: qual a diferença de causa?
  4. Por que um Directory.Packages.props sem <Project> na raiz é perigoso?
  5. A IDE0003 em warning não acusa nada no build, com EnforceCodeStyleInBuild=true. A configuração está errada? Como você descobre?
  6. As duas formas de pôr severidade (opcao = valor:warning e dotnet_diagnostic.ID.severity) funcionam no build? Qual a condição?
  7. Por que o .editorconfig gerado pelo dotnet new editorconfig quebra o build do Norte, e por que olhar só as linhas com "severity" engana?
  8. O .csproj do VS e o do CLI são iguais. Isso prova que o VS usa o CLI? Cite a evidência contrária.

Respostas

Mostrar respostas
  1. Usa o mais próximo (o da pasta do projeto); o de cima não é herdado sozinho. Para herdar: Import com GetPathOfFileAbove ou dotnet new buildprops --inherit.
  2. Só nos arquivos que casam [tests/**.cs] — não vale para o código de produção.
  3. NU1008: Version no PackageReference com CPM ligado (versão no lugar errado). NU1010: falta a PackageVersion correspondente (ou ela está no arquivo errado).
  4. O CPM não aplica e não dá erro: as versões deixam de ser centralizadas em silêncio.
  5. Não necessariamente: a IDE0003 tem EnforceOnBuild Never — nunca roda no build. Descobre-se com um controle: uma regra que roda (IDE0161) com a mesma configuração.
  6. Sim, para regras que rodam no build, com EnforceCodeStyleInBuild=true e EnforceOnBuild que permita.
  7. Porque o arquivo traz opções com sufixo :warning (ex.: readonly), que com TreatWarningsAsErrors viram erro (IDE0044). A severidade também está no sufixo, não só na palavra "severity".
  8. Não. Os .cs diferem (namespace em bloco × escopo de arquivo), então cada ferramenta tem o seu template; o .csproj igual não prova chamada do CLI pelo VS.
