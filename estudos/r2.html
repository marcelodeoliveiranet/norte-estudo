R2 — Os 3 arquivos que fazem o build cobrar as convenções

Revisão de sábado, 10/10/2026 · tema T1 (qualidade no build) · Marco M1 · leitura: ~25 min

O melhor caminho para aprender estes arquivos não é copiar um modelo enorme da internet. É entender que problema cada um resolve, o que você escreve nele e quanto isso custa para o time. Esta folha vai nessa ordem, e no fim diz onde estudar mais e como experimentar sem arriscar o norte.

1. O que são, em uma frase cada

Três arquivos na raiz da solution fazem todos os projetos seguirem as mesmas regras, sem repetir configuração em cada .csproj:

Arquivo Problema que resolve
Directory.Build.props Cada projeto repetia as mesmas propriedades de build (net10.0, Nullable, avisos como erro…). Agora ficam num lugar só.
Directory.Packages.props Cada projeto escolhia a sua versão do mesmo pacote. Agora a versão mora num lugar só (Central Package Management, CPM).
.editorconfig Cada pessoa escrevia de um jeito. Agora estilo, nomes e o nível de cada aviso de código são regras compartilhadas pelo editor, pelo compilador e pelo CI.

Uma distinção que evita confusão: o .editorconfig não substitui o compilador, os testes nem as regras de negócio. Ele configura editor, formatador e analisadores. E ele mistura duas decisões diferentes: uma é a convenção de escrita (ex.: arquivo com namespace X;); a outra é a severidade do diagnóstico que acusa o desvio (ex.: isso é só sugestão ou quebra o build?).

2. O que o desenvolvedor escreve em cada arquivo

Arquivo O que você escreve nele Com que frequência
Directory.Build.props Propriedades que valem para todos os projetos: TargetFramework (net10.0), Nullable, ImplicitUsings, TreatWarningsAsErrors, AnalysisLevel, AnalysisMode, EnforceCodeStyleInBuild. Quase nunca: na criação da solution e quando o time decide mudar a regra para todos (vira ADR).
Directory.Packages.props ManagePackageVersionsCentrally=true e uma linha por pacote: <PackageVersion Include="Pacote" Version="x.y.z" />. A mais frequente: todo pacote novo ou atualização. O dotnet add package escreve esta linha e a do projeto juntas.
.editorconfig Regras de estilo e de nome, o nível de cada uma e as exceções, cada exceção com o motivo. Raramente: quando uma regra atrapalha de verdade, ou quando você quer cobrar uma regra a mais.
.csproj (de cada projeto) Só o que é daquele projeto: ProjectReference e PackageReference sem Version. Sempre que o projeto ganha uma dependência.

O que nunca se escreve: versão de pacote dentro do .csproj; NoWarn; #pragma warning disable. Exceção é sempre uma linha no .editorconfig, com o motivo (ADR-004).

Onde eu escrevo isto?

Faça as perguntas nesta ordem e pare na primeira resposta "sim":

  1. É um número de versão de pacote? → Directory.Packages.props.
  2. É uma regra de código (estilo, nome, nível de um aviso, exceção)? → .editorconfig.
  3. É uma configuração de build que vale para todos os projetos? → Directory.Build.props.
  4. É só deste projeto? → o .csproj dele.

3. Como ler uma linha de configuração

Cada linha diz três coisas: onde vale, o que configura e com que valor.

Linha Onde vale O que configura Valor
[*.cs] seção: só arquivos .cs abaixo daquele .editorconfig — —
csharp_style_namespace_declarations = file_scoped:warning na seção acima preferência de estilo: namespace X; file_scoped (o estilo) + warning (a severidade)
dotnet_diagnostic.IDE0161.severity = warning na seção acima só a severidade do diagnóstico IDE0161 warning
<PackageVersion Include="xunit" Version="2.9.3" /> solution inteira (Directory.Packages.props) a versão central do xunit 2.9.3
<TreatWarningsAsErrors>true</TreatWarningsAsErrors> todos os projetos (Directory.Build.props) aviso vira erro true

As duas linhas do meio mostram a distinção da Seção 1: a primeira escolhe o estilo e já traz a severidade junto (:warning); a segunda mexe só na severidade. Não basta conhecer o nome da propriedade: leia a definição e os exemplos da regra na documentação (Seção 8).

Os níveis de severidade

Valor Efeito no editor No build
none desliga a regra nada
silent sem aviso visível; pode oferecer a correção nada
suggestion sugere a mudança normalmente não aparece na saída do build
warning aviso vira erro com TreatWarningsAsErrors=true (o caso do Norte)
error erro quebra o build

(suggestion e silent ficarem fora da saída do build é o comportamento descrito na documentação; não foi testado na R2.)

4. O que decide se uma regra de estilo (IDE) roda no build

O que aparece no editor e o que é verificado no build não são a mesma coisa. Provado na R2:

  1. A regra só roda no build com EnforceCodeStyleInBuild=true (com false, as IDE somem do build).
  2. E a própria regra precisa permitir rodar no build.
Regra Roda no build?
IDE0003 (this.), IDE0001, IDE0002, IDE0009 Nunca, mesmo em warning
IDE0161 (namespace de arquivo), IDE1006 (nomes), IDE0044 (readonly) Sim

Armadilha que custou tempo na R2: a IDE0003 em warning "não acusou nada". A configuração estava certa; a regra nunca roda no build. Antes de culpar a configuração, faça um controle: teste uma regra que roda (IDE0161) com a mesma configuração.

Duas formas de dar nível, e as duas valem no build (para regras que rodam): opcao = valor:warning e dotnet_diagnostic.ID.severity = warning. Isso corrige a nota antiga do guia 4.2.

Regras de nome (IDE1006): cada regra de nome tem a sua severidade, mas é a linha dotnet_diagnostic.IDE1006.severity que decide o que acontece no build. A página oficial de regras de nomenclatura diz o mesmo: a severidade dentro da regra de nome só vale no editor.

5. Como o MSBuild escolhe qual arquivo usar

Cada projeto sobe as pastas a partir da sua e usa o primeiro Directory.Build.props (e Directory.Packages.props) que encontrar. O de cima não é herdado sozinho: o mais próximo "esconde" o outro. Para herdar é preciso pedir (Import com GetPathOfFileAbove, ou dotnet new buildprops --inherit).

O .editorconfig é diferente: todos os arquivos do caminho valem, até um com root = true (que impede a herança de arquivos de pastas superiores, mas continua valendo para as subpastas). Dentro do mesmo arquivo a linha mais abaixo vence; entre arquivos, o mais perto do .cs vence. Uma linha global colada depois de [tests/**.cs] passa a valer só nos testes, e o build de produção deixa de cobrar sem avisar. Regra global fica antes de qualquer [seção].

6. O preço

Decisão O que muda para o time
TreatWarningsAsErrors=true todo aviso novo quebra o build (e o CI fica vermelho); a regra vale para todos, também para quem tem pressa
AnalysisMode=Recommended mais regras cobradas; nomes e padrões que passavam agora falham (foi o caso da CA1716)
Versão central (CPM) uma só versão por pacote na solution; trocar a versão afeta todos os projetos de uma vez
Exceção no .editorconfig cada exceção é dívida: precisa de motivo escrito, senão vira buraco
.editorconfig copiado inteiro de outro lugar regras que você não entende viram erro no seu build (o gerado pelo template, com 389 linhas, quebrou o Norte com a IDE0044)

7. Erros que você vai ver

Código O que significa O que fazer
NU1008 Version dentro do PackageReference com CPM ligado tirar a versão do .csproj; ela mora no Directory.Packages.props
NU1010 falta a PackageVersion do pacote (ou ela está no arquivo errado) pôr a PackageVersion no Directory.Packages.props
CA1716 nome de identificador public igual a palavra-chave de linguagem .NET trocar o nome
IDE0161 namespace em bloco com a regra pedindo escopo de arquivo usar namespace X;
IDE0044 campo que poderia ser readonly ajustar a opção ou o código

Perigo silencioso: um Directory.Packages.props sem <Project> na raiz é ignorado sem erro. O CPM parece ligado e não está.

8. Onde estudar (nesta ordem)

  1. Catálogo das regras de estilo — cada regra, seu código, as opções e exemplos de antes e depois: Regras de estilo de código do .NET.
  2. Como configurar e dar severidade — a sintaxe dotnet_diagnostic.ID.severity e a precedência: Arquivos de configuração das regras de análise e Opções de configuração (inclui AnalysisMode e a configuração por categoria).
  3. Nomes — grupos de símbolos, estilos de nome e severidade: Regras de nomenclatura.
  4. Um arquivo real de projeto grande — como a equipe do .NET organiza convenções e exceções: .editorconfig do .NET Runtime.

Ressalva: o arquivo do Runtime é uma referência de como um projeto grande trabalha, não um modelo para copiar. Ele tem decisões e exceções que são do repositório deles.

(Links conferidos em 11/10/2026. A página de configuração não trata do EnforceCodeStyleInBuild; o que esta folha diz sobre ele vem dos experimentos da R2.)

9. Como experimentar (em D:\temp-norte, sem tocar no norte)

Faça com o Git disponível, para ver o diff e desfazer.

  1. Crie uma solution com um projeto de biblioteca.
  2. Crie um Directory.Packages.props com ManagePackageVersionsCentrally=true e adicione um pacote qualquer com dotnet add package. Abra os dois arquivos e veja as duas linhas que apareceram.
  3. Escreva Version="..." à mão dentro do PackageReference do .csproj e rode dotnet build. Anote o código do erro e a frase da mensagem.
  4. Desfaça o passo 3 e, no Directory.Packages.props, apague a linha do pacote. Rode o build e anote o novo código. (Conferência: os códigos do 3 e do 4 são NU1008 e NU1010.)
  5. Crie um .editorconfig pequeno com root = true e a regra de namespace em warning. Escreva um namespace X { } em bloco e rode o build. Depois troque para none e rode de novo.
  6. Registre o que decidiu: o que a regra faz, por que você a quer, qual o impacto no código e qual severidade escolheu.

10. Em que ordem estudar o .editorconfig

Não comece pelos nomes nem tente estudar todas as regras de uma vez.

Etapa O que estudar Pergunta que você deve responder
1 Formatação (indentação, fim de arquivo, quebras de linha) Como deixar o código visualmente consistente?
2 Convenções de C# (var, chaves, namespace de arquivo) Qual estilo o time adota e por quê?
3 Nomenclatura Como padronizar nomes de classes, interfaces, campos e métodos?
4 Diagnósticos IDE e CA Quais problemas são sugestão, aviso ou erro?
5 Build e CI Como garantir que as regras escolhidas sejam verificadas sozinhas?

11. O que a revisão provou e o que NÃO provou

Provado, com saída vista: a subida de pastas dos arquivos; NU1008 e NU1010; a CA1716 no Zero.Lib; as duas formas de severidade valendo no build; IDE0003 nunca rodando no build; o .editorconfig gerado quebrando o Norte; o .csproj igual no VS e no CLI, com .cs diferentes.

Não provado (não repita como certeza):

Item Estado
Projeto do VS com namespace em bloco quebrando o build do Norte inferido, não executado
Regras CA com EnforceCodeStyleInBuild=false não testado
suggestion e silent ausentes da saída do build comportamento documentado, não testado
Para que servem os ..._warnaserror.globalconfig do SDK só o cabeçalho foi lido
"O VS chama o CLI" sem evidência; os .cs diferem

Teste-se

  1. Em qual arquivo vai a versão de um pacote novo? E o que fica no .csproj?
  2. Você quer mudar Nullable para todos os projetos. Em qual arquivo?
  3. Na linha csharp_style_namespace_declarations = file_scoped:warning, o que é file_scoped e o que é warning?
  4. NU1008 e NU1010: qual a diferença de causa?
  5. Uma linha global foi colada depois de [tests/**.cs]. Onde ela vale?
  6. A IDE0003 em warning não acusou nada no build. A configuração está errada?
  7. Por que um Directory.Packages.props sem <Project> na raiz é perigoso?
  8. Por que não vale copiar um .editorconfig grande de outro projeto?

Respostas

Mostrar respostas
  1. No Directory.Packages.props (PackageVersion). No .csproj fica só o PackageReference, sem Version.
  2. No Directory.Build.props: é configuração de build para todos os projetos.
  3. file_scoped é o estilo (namespace com ;); warning é a severidade do desvio.
  4. NU1008: Version dentro do PackageReference com CPM. NU1010: falta a PackageVersion (ou ela está no arquivo errado).
  5. Só nos arquivos que casam [tests/**.cs]; o código de produção deixa de ser cobrado.
  6. Não necessariamente: a IDE0003 nunca roda no build. Confirma-se com uma regra que roda (IDE0161) com a mesma configuração.
  7. O CPM não é aplicado e não dá erro: as versões deixam de ser centralizadas em silêncio.
  8. Porque traz regras que você não decidiu: com aviso = erro, uma delas (como a IDE0044) quebra o seu build e você não sabe por quê. Use a documentação como catálogo e construa o seu arquivo regra a regra.
