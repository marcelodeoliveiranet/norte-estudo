Norte · S26 — Pedidos: o projeto compartilhado e os limites de tamanho

Quarta, 21/10/2026 (tarde) · tempo líquido: 3h42 (abaixo do limite de 5h) · Marco M1

Hoje você fez duas coisas. Primeiro, o Pedidos passou a recusar no domínio o SKU com mais de 20 caracteres e o criadoPor com mais de 50 (PR #36). Para o número não ficar escrito em três lugares, você criou o projeto compartilhado Norte.Compartilhado, com uma classe Constantes. Depois você moveu o Norte.Api para a pasta src/Api (PR #37) e decidiu, no ADR-008, que o SKU vira sempre maiúsculo (PR #38). A implementação do ADR-008 fica para a S27.

A ideia para guardar: o mesmo fato pode ser ganho e preço ao mesmo tempo. O projeto compartilhado dá uma fonte única do número (ganho). Mas "uma mudança chega a todos os módulos" é exatamente o acoplamento (preço). É o mesmo fato visto de dois lados.

2. Onde isso está no mapa dos níveis

Solution → módulos → funcionalidades → camadas. Hoje apareceu uma peça nova no nível da solution: um projeto que não é módulo e que todos os módulos podem usar (src/Compartilhado/Norte.Compartilhado). Dentro do Pedidos, o trabalho foi na camada de domínio (as validações) e na infraestrutura (o HasMaxLength das colunas).

3. Conceitos

3.1 Projeto compartilhado (shared kernel)

Palavra nova — shared kernel: um conjunto pequeno e explícito de tipos que vários módulos usam juntos. Quem usa concorda com o que está lá.

O problema era este: o limite de 20 do SKU morava em FichaProduto (Catalogo). O Pedidos também precisava do 20. Copiar o número cria dois lugares para lembrar; se o Catalogo subir o limite e o Pedidos não, o pedido recusa um produto que existe.

namespace Norte.Compartilhado;

public static class Constantes
{
    public const int TamanhoMaximoSku = 20;
    public const int TamanhoMaximoCriadoPor = 50;
    public const int TamanhoMaximoAtualizadoPor = 50;
}
Peça Para que serve
Norte.Compartilhado.csproj só <Project Sdk="Microsoft.NET.Sdk">; o resto vem do Directory.Build.props
ProjectReference no Norte.Catalogo, no Norte.Pedidos e no projeto de teste do Pedidos quem usa a constante referencia o projeto
public static class public, porque internal não atravessa projetos; static, porque só tem membros estáticos (regra CA1052)
public const int o valor é gravado no código de quem usa (veja 3.2)

Os quatro cuidados do ADR-007 (regra de entrada):

  1. entra só o que dois ou mais módulos usam (ou vão usar por decisão já tomada) e com o mesmo significado;
  2. sem referência a módulo e sem pacote além do .NET;
  3. o que só um módulo usa fica no módulo;
  4. mudar um valor exige olhar todos os consumidores.
Ganho Preço
Projeto compartilhado uma fonte única do número; o Catalogo e o Pedidos não se desencontram todo módulo passa a depender dele: uma mudança afeta todos; vira depósito de qualquer coisa se ninguém cuidar
Constante só de tamanho pequeno e fácil de revisar a regra de "o que entra" precisa ser lembrada em cada PR

Você respondeu na retenção: o ganho é concentrar as constantes; o preço é ter um projeto novo para administrar e não deixar virar um repositório genérico. Faltou ligar as duas pontas. Você mesmo percebeu depois: "qualquer mudança é refletida nos módulos e nos testes — isso não é acoplamento?" Sim. É o mesmo fato: o que dá a fonte única também é o que acopla.

Por que a decisão ficou assim (ADR-007, opções): (A) uma constante em cada módulo — simples, mas duplica; (B) projeto compartilhado — escolhida; (C) contrato entre Pedidos e Catalogo — o certo para dado de verdade (o SKU existe?), mas pesado demais para um número. O ADR-002 não proíbe projeto compartilhado; a frase "entre módulos nada é compartilhado" do guia era uma descrição do estado de então, não uma regra.

3.2 const é gravada no código de quem usa

Uma public const não é lida em tempo de execução. O compilador copia o valor para dentro do código de quem a usa. Se alguém mudar o 20 no Compartilhado e não recompilar os outros projetos, eles continuam com o 20 antigo.

Hoje isso não machuca: o Norte é um deploy só e tudo é compilado junto. Passa a importar se um dia os módulos forem publicados em separado (M7). Por isso o ADR-007 diz: "mudar valor exige olhar todos os consumidores".

3.3 Os analisadores do build apareceram de novo

Você quis escrever as constantes em maiúsculo com sublinhado (TAMANHO_MAXIMO_SKU), para se diferenciar de variável. O build recusou:

Aviso O que diz Resultado
CA1707 nome com sublinhado vira erro (ADR-004: todo aviso é erro)
CA1052 classe só com membros estáticos deve ser static corrigido com public static class

Você voltou para PascalCase, que é o padrão do .NET para constantes (TamanhoMaximoSku). A lição: eu afirmei que nenhum analisador reclamaria sem conferir; o build mostrou o contrário. (Falha do mentor, registrada.)

3.4 A validação de tamanho no domínio

O banco já recusava SKU acima de 20 (a coluna varchar(20)), mas só ao salvar, com um erro do Postgres. Agora o construtor recusa antes:

if (sku.Length > Constantes.TamanhoMaximoSku)
    throw new ArgumentException(
        $"O sku deve ter no máximo {Constantes.TamanhoMaximoSku} caracteres", nameof(sku));
Onde Regra Exceção
ItemPedido.sku no máximo 20 ArgumentException, ParamName "sku"
Pedido.criadoPor no máximo 50 ArgumentException, ParamName "criadoPor"

Sua razão: "nunca confie só no banco". A regra existe nas duas camadas. O HasMaxLength(Constantes.TamanhoMaximoSku) das configurações usa a mesma constante, então o domínio e a coluna não se desencontram.

Os testes usam o limite, não um número solto:

var limite = Constantes.TamanhoMaximoSku;
var sku = new string('A', limite + 1);

Se o limite mudar, o teste muda junto. Os dois testes foram vistos vermelhos com a prova de git stash push -- <arquivos de domínio> e dotnet test sem --no-build, e depois git stash pop.

Ganho Preço
Validar no domínio e na coluna erro claro antes de ir ao banco; vale para qualquer porta de entrada a regra existe em dois lugares (domínio e coluna); a constante mantém os dois iguais
O limite de 50 do criadoPor decidido agora provisório até o módulo Identidade existir: lá o tamanho real pode ser outro

3.5 Mover o projeto da API

O Norte.Api estava sozinho em src/Norte.Api, ao lado das pastas Modulos/ e Compartilhado/. Você pediu uma pasta Api e moveu o projeto para src/Api/Norte.Api (PR #37). Com o git mv o Git registra renomeação, não "apagou e criou": git diff --cached --stat -M mostra R.

Ao mover, três arquivos tinham caminho antigo: o .slnx, o Norte.Api.csproj (..\..\Modulos\...) e o projeto de teste do Catalogo. O CI só usa dotnet build Norte.slnx e dotnet test Norte.slnx, por isso não mudou. A pasta velha src\Norte.Api ficou só com obj e você apagou depois.

3.6 ADR-008: SKU em forma única (decisão, sem código ainda)

Hoje ABC e abc são SKUs diferentes no Catalogo (a chave diferencia a caixa) e iguais na junção do Pedido (OrdinalIgnoreCase). Isso se desencontra. Sua escolha, opção A:

Peça Mudança
FichaProduto e ItemPedido o construtor converte o SKU com ToUpperInvariant()
GET /catalogo/fichas-produto/{sku} converte antes de buscar
banco CHECK (sku = upper(sku)) nas duas tabelas

Por que ToUpperInvariant e não ToUpper: o ToUpper depende da cultura do computador (em turco, i vira İ). O invariante dá sempre o mesmo resultado.

Ganho Preço
Opção A (domínio converte + CHECK) uma forma só em todo lugar; o banco recusa a forma errada mesmo se alguém escapar do domínio o valor devolvido muda (o Location também); testes e seed com minúsculas mudam; dados que já existem precisam ser convertidos antes (dois SKUs que só diferem na caixa viram colisão de chave); a regra se repete em cada módulo (tensão com o ADR-007)

A opção B (índice único em upper(sku)) exigiria SQL escrito à mão na migration. Fica como alternativa registrada no ADR.

5. Dúvidas e respostas

Por que public na classe Constantes se tudo era internal? Porque internal só vale dentro do mesmo projeto. Como o Catalogo e o Pedidos são outros projetos, a classe precisa ser public. É a exceção de projeto compartilhado.

Por que o projeto de teste do Pedidos referencia o Compartilhado direto, se já chega por transitividade? Porque o teste usa a constante. Referenciar direto o que se usa evita que o teste quebre quando alguém mexer na referência do módulo.

Uma classe Constantes só para tudo, ou uma por assunto? Sua razão: é como arquivos de idioma, um lugar só para o que todo o monolito usa. Ficou uma classe. A regra de entrada do ADR-007 é o que impede o inchaço.

E se o limite de 20 do SKU mudar? Muda em um lugar, mas você precisa olhar o Catalogo, o Pedidos e os dados que já existem. O exemplo concreto do preço: o Catalogo sobe para 30 e o Pedidos continua recusando um produto que existe. Se um dia o dado for de verdade (o SKU existe?), o caminho certo é o contrato (opção C do ADR-007).

7. Avaliação

Travou: o caminho do git add e as aspas do -m no commit; o HasMaxLength do SKU no ItemPedidoConfiguration e a referência do projeto no Norte.Pedidos.csproj ficaram para trás na primeira versão; o commit juntou o projeto e o ADR (eram dois); a mensagem de um commit tinha fatos errados; o if (!Enum.IsDefined...) ficou colapsado em uma linha.

O mentor conduziu mal: afirmou que o ADR-002 proibia o projeto compartilhado; supôs que o git add . já tinha sido rodado quando você só mostrava o comando; afirmou que nenhum analisador reclamaria das maiúsculas, sem conferir; diagnosticou "faltou nomear o acoplamento" na retenção, mas você já tinha dito.

Respostas

Mostrar respostas
  1. Porque o número fica escrito em um lugar só, e o Catalogo e o Pedidos não se desencontram. O preço: todo módulo passa a depender do projeto, então uma mudança chega a todos (acoplamento), e ele pode virar depósito. É o mesmo fato visto dos dois lados.
  2. Porque internal só vale dentro do mesmo projeto. O Catalogo e o Pedidos são outros projetos e precisam enxergar a classe.
  3. O outro projeto continua com o valor antigo, porque o compilador copiou o valor para dentro dele. Só recompilando.
  4. O CA1707 (sublinhado em nome). O build parou porque, no Norte, todo aviso é erro (ADR-004).
  5. Entra só o que dois ou mais módulos usam, com o mesmo significado; sem referência a módulo nem pacote além do .NET; o que só um módulo usa fica nele; mudar valor exige olhar todos os consumidores.
  6. Porque o teste acompanha o limite: se o 20 mudar, o teste muda junto, sem número solto.
  7. Porque o erro do domínio é claro e vem antes de ir ao banco; o banco recusa só ao salvar, com erro do Postgres. A regra vale nas duas camadas, e a mesma constante mantém as duas iguais.
  8. Porque o ToUpper depende da cultura do computador (em turco, i vira İ); o invariante dá sempre o mesmo resultado.
  9. O SKU passa a ser convertido para maiúsculo no construtor e na busca, e o banco ganha CHECK (sku = upper(sku)). Os dados que já existem preocupam porque dois SKUs que só diferem na caixa viram a mesma chave e colidem; é preciso convertê-los antes da restrição.
  10. O Git registra como renomeação (histórico preservado, R no --stat), e não como "apagou um arquivo e criou outro".
