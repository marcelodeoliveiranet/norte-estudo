1. Índice para LIKE '%texto%' (PR #87)

O problema. A listagem do Catalogo filtra com LIKE '%texto%'. Um índice comum (B-tree) é ordenado pelo começo do texto; com % na frente, o banco não sabe onde começar e lê a tabela inteira (Seq Scan).

A solução. A extensão pg_trgm quebra o texto em pedaços de 3 letras (trigramas) e um índice GIN guarda "qual trigrama aparece em quais linhas". Buscar %ouro% vira "ache as linhas que têm os trigramas our e uro".

A prova. Não se acredita no índice: mede-se com EXPLAIN (ANALYZE).

Antes (sem índice) Depois (com índice trigram)
Seq Scan lê todas as linhas Bitmap Index Scan pelo índice, depois Bitmap Heap Scan nas linhas candidatas

Os tempos medidos e o código da migration estão no PR #87.

Preço. O índice ocupa espaço e deixa cada INSERT/UPDATE um pouco mais lento. Com poucas linhas, o planejador pode preferir o Seq Scan mesmo com o índice: tabela pequena é mais barata de ler inteira. Por isso a prova usa volume (o seed de volume da S20).

2. OpenAPI e Scalar (PR #88)

  • OpenAPI é o contrato da API em um documento (rotas, parâmetros, respostas) gerado a partir do código.
  • Scalar é a tela que lê esse documento e deixa explorar/testar a API no navegador.
  • Os TypedResults (S9) é que alimentam o documento com os status certos; por isso "preferir TypedResults" tinha a razão do OpenAPI.

Detalhes de configuração: PR #88.

3. Logging dos conflitos (PR #89)

3.1 O que foi feito

Os três repositórios (Catalogo, Clientes, Representantes) agora registram quando um conflito acontece:

Onde Evento Nível Mensagem (resumo)
Catálogo, AdicionarAsync 1 Warning violação de unicidade da ficha {Sku}
Catálogo, AtualizarAsync 2 Warning ficha {Sku} não atualizada: token desatualizado
Catálogo, ExcluirAsync 3 Warning ficha {Sku} não excluída: token desatualizado
Clientes, Adicionar/Atualizar 1 Warning violação de unicidade do CNPJ {Cnpj}
Representantes, os dois catch 1 Warning violação de unicidade de CPF ou e-mail (sem valores)

Por que Warning para os dois tipos. Os dois significam "alguém tentou algo que o sistema recusou por regra". Mesma gravidade, mesmo nível (decisão sua).

Por que o Representantes não loga valores. CPF e e-mail são dado pessoal (LGPD). Regra: nunca registrar dado pessoal em log. O CNPJ é de empresa, e o SKU é do catálogo: podem entrar.

3.2 [LoggerMessage] em vez de _logger.LogWarning(...)

internal sealed partial class ClientesRepository
{
    [LoggerMessage(EventId = 1, Level = LogLevel.Warning,
        Message = "Violação de unicidade ao gravar o CNPJ {Cnpj}: outra requisição gravou o mesmo CNPJ primeiro")]
    private partial void RegistrarViolacaoDeUnicidade(string cnpj);
}
  • A classe vira partial e o método é declarado sem corpo; o compilador gera o corpo (source generator).
  • Ganho: não monta texto à toa quando o nível está desligado, e o analisador CA1848 (que o build do Norte exige) deixa de reclamar.
  • {Cnpj} é um campo estruturado: o nome entre chaves vira um campo pesquisável no destino do log, não só texto.
  • O EventId é um número estável para achar aquele evento mesmo se a frase mudar.

3.3 O que aparece no console

Com Logging:Console:IncludeScopes: true (só em Development), cada linha traz os escopos: SpanId, TraceId, ParentId, RequestPath, RequestId, ConnectionId. O warn: do conflito tem o mesmo TraceId do ProblemDetails que a resposta devolveu: é a ponte entre "o que o cliente viu" e "o que o servidor registrou".

Camadas de configuração (a última vence): appsettings.json < appsettings.{Env}.json < variáveis de ambiente < linha de comando.

O EF mostra os parâmetros como ? por padrão (esconde valores para não vazar dados); por isso o log de propósito do repositório é o que carrega o {Sku}.

3.4 Log × rastreamento × auditoria

Responde Exemplo
Log o que o sistema disse que aconteceu "SKU duplicado"
Rastreamento (trace) por onde a requisição passou e quanto demorou em cada etapa requisição → EF → banco: 800 ms no banco
Auditoria quem fez o quê (valor legal/negócio) "usuário X excluiu o cliente Y"

Auditoria não está feita (precisa de autenticação e de um destino).

4. Como um TraceId nasce e morre

  1. O ASP.NET Core cria uma Activity para cada requisição que chega.
  2. Se não veio nada junto, nasce uma raiz nova (ParentId de zeros) e um TraceId novo.
  3. Se veio o cabeçalho W3C traceparent, a Activity herda o TraceId dele:
traceparent: 00-<TraceId 32 hex>-<SpanId 16 hex>-<flags>
              ^^                                   ^^ 01 = amostrado, 00 = não
  1. A Activity termina quando a requisição termina. O TraceId é só uma etiqueta: não "fica vivo" em lugar nenhum depois.
  2. O traceId do ProblemDetails é o id da Activity atual.
  3. O RequestId (conexão:sequência do Kestrel) é outra coisa: identifica a requisição para o servidor web, não atravessa serviços.

Microsserviços. O primeiro serviço cria o TraceId; ao chamar o próximo pelo HttpClient, o .NET manda o traceparent sozinho. O segundo serviço mantém o TraceId e cria um SpanId novo, com ParentId = o span de quem chamou. Resultado: uma árvore de spans com um só TraceId. A propagação quebra em canais que ninguém instrumentou (fila sem cabeçalho, chamada manual).

Na busca usa-se o TraceId: é a chave que reúne todos os logs e spans de uma requisição.

5. Onde cada coisa se encaixa (o mapa que tirou a "salada")

Camada Pergunta Exemplos
1. Produzir quem gera o dado? ILogger, [LoggerMessage], Activity, Meter (todos já vêm no .NET)
2. Transportar como o dado sai do app? OpenTelemetry (padrão + protocolo OTLP) ou Serilog (biblioteca)
3. Guardar e buscar onde eu olho? Seq, Kibana/Elastic, Grafana/Loki, Datadog, Application Insights, dashboard do Aspire
  • OpenTelemetry nasceu em 2019 da fusão de OpenTracing e OpenCensus. É um padrão neutro: o app fala OTLP e você troca o destino sem mexer no código. SDK de fornecedor (Application Insights, agente da Datadog) amarra você ao fornecedor.
  • Nuvem = lugar que oferece a camada 3 pronta e gerenciada.
  • ELK = Elasticsearch (guarda/busca) + Logstash (transporta) + Kibana (tela). Ainda aparece em vagas.
  • Três sinais: logs (o que foi dito), traces (por onde passou e quanto demorou), métricas (números ao longo do tempo: p95, erros por minuto).

6. "Está lento": o caminho de investigação

  1. Delimitar: qual rota, desde quando, para quem?
  2. Métrica: p95/p99 daquela rota subiu?
  3. Trace de uma requisição lenta: qual etapa (span) consome o tempo?
  4. Logs daquele TraceId: o que o sistema disse nessa hora?
  5. Causa: se o span lento é o banco, EXPLAIN (a Seção 1 é isso).
  6. Alerta: descrever a regra que teria avisado antes (p95 acima de X por Y minutos).

Em nuvem os nomes mudam, a lógica não (a conferir na S38: Azure Application Insights/Log Analytics com KQL; AWS CloudWatch Logs Insights e X-Ray).

Respostas

Mostrar respostas
  1. O B-tree ordena pelo começo do texto; com % na frente não há onde começar e o banco lê tudo. O pg_trgm indexa trigramas (pedaços de 3 letras) e o índice GIN diz quais linhas os contêm.
  2. Antes: Seq Scan; depois: Bitmap Index Scan + Bitmap Heap Scan. Em tabela pequena ler tudo é mais barato que usar o índice, e o planejador escolhe o mais barato.
  3. Espaço em disco e escrita mais lenta (cada INSERT/UPDATE atualiza o índice).
  4. São dados pessoais (LGPD): log não guarda dado pessoal.
  5. O compilador gera o corpo do método de log; precisa ser partial para que a parte escrita por você e a gerada sejam a mesma classe.
  6. Acrescenta TraceId, SpanId, ParentId, RequestPath, RequestId; o TraceId da linha warn: é o mesmo do ProblemDetails devolvido.
  7. Nasce novo quando a requisição chega sem traceparent; é herdado quando o cabeçalho traceparent vem junto.
  8. É o id conexão:sequência do Kestrel; vale só dentro daquele servidor e não é propagado a outros serviços.
  9. Mantém-se o TraceId; muda o SpanId (novo) e o ParentId passa a ser o span de quem chamou.
  10. Log: o que foi dito. Trace: por onde passou e quanto demorou. Auditoria: quem fez o quê, com valor legal.
  11. Camada 1 (produzir): ILogger; camada 2 (transportar): OpenTelemetry; camada 3 (guardar e buscar): Seq.
  12. Delimitar a rota → ver a métrica p95 → abrir o trace de uma requisição lenta → ler os logs do TraceId → achar a causa (ex.: EXPLAIN) → descrever o alerta.
