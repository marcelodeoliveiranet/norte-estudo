1. O mapa das três camadas, agora com o Norte dentro

Na S37 o mapa estava só no papel. Agora cada camada tem uma peça de verdade:

Camada Pergunta Peça no Norte Estado
1. Produzir quem gera o dado? ILogger e [LoggerMessage] (S37), Activity do ASP.NET Core e do Npgsql, Meter do ASP.NET Core ✅ já vinham no .NET
2. Transportar como o dado sai da aplicação? OpenTelemetry (SDK) + exportador OTLP ✅ ligado no Program.cs
3. Guardar e buscar onde eu olho? Aspire dashboard em contêiner, ao lado do Postgres ✅ no compose.yaml

Três sinais passam pelas três camadas: logs (o que foi dito), traces (por onde a requisição passou e quanto demorou em cada etapa) e métricas (números ao longo do tempo).

OTLP é o contrato entre as camadas 2 e 3, como a interface do ADR-012 é o contrato entre dois módulos: a aplicação fala OTLP e o destino pode ser trocado por configuração (Aspire hoje; Seq, Grafana, Datadog ou um serviço de nuvem amanhã) sem mexer no código da aplicação.

2. A decisão (ADR-016) em poucas linhas

Alternativa O que dá O que falta
A. Ficar como estava (console + EXPLAIN + TraceId nos escopos) funciona, custo zero não mostra o tempo de cada etapa nem busca por campo; nada reúne as linhas de uma requisição numa tela
B. Serilog + Seq busca de logs muito boa traces e métricas não vêm de graça; amarra o formato ao Serilog
C. OpenTelemetry + painel Aspire (escolhida) logs, traces e métricas num lugar só; destino trocável por OTLP veja o preço abaixo

O que fica pior com a C (🧠 saber de cabeça):

  • o painel não guarda histórico: reiniciar o contêiner apaga tudo (✅ medido);
  • o painel roda sem senha (ASPIRE_DASHBOARD_UNSECURED_ALLOW_ANONYMOUS=true) — aceitável só em laboratório local;
  • três pacotes novos para manter atualizados;
  • o que não foi testado fica sem afirmação (seção 11).

O texto completo, com as notas de implementação, está em docs/adr/ADR-016-fundacao-de-observabilidade.md no repositório.

3. As peças (o que mudou no repositório, PR #91)

3.1 O painel no compose.yaml

painel:
  image: mcr.microsoft.com/aspire/dashboard:13.6.2
  container_name: norte-painel
  environment:
    ASPIRE_DASHBOARD_UNSECURED_ALLOW_ANONYMOUS: "true"
  ports:
    - "18888:18888"   # a tela (navegador)
    - "4317:18889"    # OTLP por gRPC (a API envia por aqui)
    - "4318:18890"    # OTLP por HTTP

A porta 4317 é a porta padrão do OTLP por gRPC; por isso a API não precisa de endereço no appsettings: o exportador já olha localhost:4317.

3.2 Os pacotes (Directory.Packages.props, grupo "Observabilidade")

Pacote Versão Para que serve
OpenTelemetry.Extensions.Hosting 1.20.1 liga o OpenTelemetry ao host (AddOpenTelemetry())
OpenTelemetry.Exporter.OpenTelemetryProtocol 1.20.1 envia pelo OTLP
OpenTelemetry.Instrumentation.AspNetCore 1.20.1 spans e métricas da requisição
Npgsql.OpenTelemetry 10.0.3 spans das chamadas ao Postgres

Instrumentações dispensadas de propósito: a do EF Core (o span do Npgsql já mostra a consulta) e a do HttpClient (o Norte não faz chamada HTTP de saída).

3.3 O Program.cs

builder.Services.AddOpenTelemetry()
    .ConfigureResource(r => r.AddService("norte-api"))
    .WithLogging()
    .WithTracing(t => t
        .AddAspNetCoreInstrumentation()
        .AddNpgsql())
    .WithMetrics(m => m
        .AddAspNetCoreInstrumentation())
    .UseOtlpExporter();
Linha O que faz
AddOpenTelemetry() liga o SDK ao contêiner de DI
ConfigureResource(... AddService("norte-api")) dá nome ao serviço. Sem isso o painel mostrava unknown_service:Norte.Api ✅
WithLogging() manda os logs do ILogger (os [LoggerMessage] da S37 continuam iguais)
WithTracing(... AddAspNetCoreInstrumentation, AddNpgsql) spans da requisição e das chamadas ao banco
WithMetrics(... AddAspNetCoreInstrumentation) métricas da requisição, entre elas http.server.request.duration
UseOtlpExporter() um destino só para os três sinais (padrão: gRPC em localhost:4317)

Por que o ConfigureResource foi preciso (🟡): o README do pacote só garante o nome padrão para quem usa IHostApplicationBuilder; aqui a ligação é por builder.Services.AddOpenTelemetry(), e o nome saiu unknown_service:Norte.Api. O mentor previu Norte.Api e errou — por isso a regra: não prever, ver.

4. Ler um trace

Um trace é a história de uma requisição. Cada etapa é um span (uma barra com início e duração). O span raiz é a requisição inteira; os spans filhos são as etapas de dentro.

GET /catalogo/fichas-produto/{sku}                      47 ms   ← raiz
 ├─ CONNECT norte                                        3 ms   ← abrir conexão
 └─ postgresql  SELECT ... WHERE f.sku = @sku            2 ms   ← a consulta

(Esquema de leitura; os números exatos variam.)

Três leituras que apareceram na prática:

O que se vê O que significa
buraco entre a raiz e os filhos (a raiz dura mais que a soma dos filhos) o tempo foi gasto no código da aplicação, onde ninguém criou span ✅
um span CONNECT norte no início a conexão com o banco foi reaberta. Aconteceu depois de a API ficar ociosa. 🟡 Hipótese: o pool do Npgsql descarta conexões ociosas em ~5 min (casos de 9 min e de 5m46s sem requisição são coerentes; não confirmado)
a primeira requisição mais lenta que as seguintes aquecimento: 47 ms → 3,6 a 5,6 ms no GET por SKU; a listagem foi de 0,17 s para ~10 ms ✅

O db.query.text do span do banco mostra a consulta com parâmetros (WHERE f.sku = @sku): o valor não aparece ✅.

5. Achar uma requisição — e o que NÃO aparece

Quero achar... Como Resultado
todas as linhas de uma requisição TraceId (filtro nos logs / abrir o trace) ✅
requisições de um SKU no caminho (GET /catalogo/fichas-produto/SKU-TESTE) na lista de Traces, filtro avançado url.path contains SKU-TESTE ✅
a mesma coisa digitando no campo de texto da lista procura só no nome do trace (GET /catalogo/...), não nos atributos: SKU-TESTE → "No traces found"; SKU → 9 traces ✅
requisições de um SKU que foi no corpo do POST não aparece: o corpo não é capturado ✅
o texto do filtro da listagem (?filtro=...) url.query vem como ?filtro=Redacted por padrão ✅
o valor do parâmetro no SQL do EF mascarado (@filtro_contains='?') enquanto não existir EnableSensitiveDataLogging (não existe no código) ✅

Regra (dd), verificada nas rotas: dado pessoal (CPF, e-mail) nunca entra em telemetria. As rotas do Norte só têm {sku} e ids numéricos no caminho (clienteId, pedidoId, representanteId); a query string só tem filtro, pagina e tamanhoPagina; CPF e e-mail ficam no corpo do POST, que não é capturado. Por isso é seguro mandar o url.path ao painel. Se um dia uma rota ganhar CPF no caminho, essa conclusão cai.

6. Lentidão provocada nº 1 — o atraso no código (Task.Delay)

Por que fazer: saber se o trace separa "o banco está lento" de "o meu código está lento".

O que foi feito: um await Task.Delay(TimeSpan.FromSeconds(2)) temporário no endpoint da listagem (revertido com git restore, nunca commitado). Ideia do aluno: "não é mais fácil adicionar algo no código que espera x segundos?" — foi mesmo a forma mais simples.

Sinal O que mostrou
trace a raiz com 2,02 s e os spans de banco com ~2 ms cada ✅
logs nenhum aviso: o código esperou, não falhou ✅
métrica a requisição aparece na faixa de 2,5 s (🟡 provável efeito dos limites do histograma; não conferido)

Leitura: raiz enorme + filhos minúsculos = o tempo está no código da aplicação, não no banco. Sem trace, "está lento" não diz onde.

7. Lentidão provocada nº 2 — o índice removido (achado de métrica → trace → EXPLAIN)

Cenário: 1.000.044 fichas (as 44 do seed + 1 milhão de linhas sintéticas; a 44ª é a SKU-TESTE). Filtro LAB-0123456 (acha 1 linha). O índice é o ix_fichas_produto_sku_trgm (GIN, pg_trgm) da S37.

Situação Tempo na API EXPLAIN (ANALYZE)
com índice 46 a 68 ms contagem 18,75 ms + página 19,24 ms; Bitmap Index Scan (924 páginas para 1 linha)
sem índice (DROP INDEX) 260 a 310 ms contagem 121,31 ms (Parallel Seq Scan); página 262,30 ms (Index Scan na PK descartando 1.000.043 linhas)
índice recriado (CREATE INDEX) volta a ~7–17 ms nos traces seguintes contagem 18,32 ms

A listagem faz dois comandos (COUNT e a página com LIMIT/OFFSET); por isso o trace mostra dois spans postgresql.

O caminho da investigação (o que se pratica na entrevista):

  1. Métrica: http.server.request.duration da rota subiu (P99).
  2. Trace de uma requisição lenta: o tempo está nos spans postgresql, não num buraco.
  3. db.query.text: a consulta é o LIKE '%...%'.
  4. EXPLAIN (ANALYZE): Seq Scan onde antes havia Bitmap Index Scan.
  5. Correção: recriar o índice; o P99 volta.

Ressalvas honestas:

  • O mentor previu "poucos milissegundos" com índice e 1 milhão de linhas; o real foi 46–68 ms na API (cerca de 19 ms por comando). A previsão estava errada: meça, não preveja.
  • Os SKU sintéticos são parecidos entre si, o que piora a seletividade do trigram; com dados reais o ganho pode ser diferente.
  • Aparece read= nos planos: parte da leitura veio do disco (cache frio), o que também infla o primeiro tempo.
  • O EXPLAIN mostra o custo no banco; a diferença entre ele (~38 ms somados) e o trace (46–68 ms) é o resto do caminho (conexão, mapeamento, HTTP).

8. Métrica de latência e o alerta (só descrito)

Onde: aba Metrics do painel → http.server.request.duration → filtrar por http.route.

Coisa Como ler
P50 / P90 / P99 metade / 90% / 99% das requisições foram mais rápidas que isso. O P99 mostra a cauda lenta; a média esconde os casos ruins
barras em faixas o histograma agrupa em faixas: 2,02 s aparece como 2,5 s (🟡 provavelmente os limites padrão do histograma; não conferido)
janela de tempo "Last 5 minutes" mostra 0 quando não houve tráfego: é ausência de dado, não latência zero
filtro por rota http.route = /catalogo/fichas-produto separa a listagem do resto

Alerta — descrito, não criado (📖):

Se o P99 da rota /catalogo/fichas-produto ficar acima de 1 segundo por 5 minutos seguidos, avisar.

Três partes que todo alerta precisa: o que medir (P99 da rota), o limite (1 s) e por quanto tempo (5 min seguidos, para não disparar por um pico isolado). O Aspire dashboard não envia alerta; quem alerta é uma ferramenta da camada 3 (Grafana, Datadog, Azure Monitor...). No Norte não existe nenhum alerta ativo.

10. O que levar para a entrevista

10.1 As três perguntas (mais a nuvem)

Pergunta Resposta com história verdadeira do Norte
Onde vejo logs, tempos e fluxo? Os logs estruturados, os traces e as métricas vão por OTLP para um painel (Aspire dashboard, em contêiner). Pelo TraceId abro a requisição inteira: os logs dela e o tempo de cada etapa, inclusive a consulta ao banco.
Como sei que está lento? Pela métrica de latência da rota (P99, não a média). Provoquei duas lentidões de propósito: um atraso de 2 s no código e a remoção de um índice com 1 milhão de linhas (de ~50 ms para ~300 ms).
Deu problema: onde eu vejo? Métrica → trace → logs do TraceId → causa. No caso do índice, o trace apontou o banco e o EXPLAIN mostrou Seq Scan; recriei o índice e o tempo voltou. No caso do atraso, a raiz tinha 2,02 s e os spans de banco ~2 ms: o tempo estava no código.
E nas nuvens? Só em conceito. A lógica é a mesma (métrica → trace → log); os nomes mudam (Azure: Application Insights/Log Analytics; AWS: CloudWatch/X-Ray). Esses nomes não foram conferidos na S38.

Resposta de 30 segundos (rascunho para o aluno reescrever com as próprias palavras):

"No meu projeto de estudo montei a observabilidade em três camadas: o código produz logs, traces e métricas com o que já vem no .NET; o OpenTelemetry envia por OTLP; e um painel guarda e mostra. Para lentidão eu olho a latência da rota, abro o trace de uma requisição lenta, vejo em qual etapa está o tempo e leio os logs do mesmo TraceId. Provoquei isso de propósito: tirei um índice de uma tabela com um milhão de linhas, vi no trace que o tempo estava no banco e confirmei com EXPLAIN. Alerta eu só descrevi, não configurei."

Sobre "pronto para volume": o que o Norte tem é o destino trocável (OTLP). Amostragem, coletor e armazenamento de longo prazo são o que se faz em volume — você os conhece em conceito, não os praticou.

Respostas

Mostrar respostas
  1. Produzir (ILogger, Activity, Meter: já vêm no .NET), transportar (OpenTelemetry/OTLP), guardar e buscar (Aspire dashboard).
  2. O nome padrão do serviço não foi aplicado com builder.Services.AddOpenTelemetry(); ConfigureResource(r => r.AddService("norte-api")) deu o nome.
  3. Manda logs, traces e métricas para um destino OTLP; o padrão é gRPC em localhost:4317, que é onde o painel escuta (porta publicada no compose).
  4. Que o tempo foi gasto no código da aplicação, onde não existe span (o "buraco").
  5. A raiz com 2,02 s, os spans de banco com ~2 ms e nenhum aviso nos logs.
  6. Métrica da rota subiu (P99) → trace mostrou o tempo nos spans postgresql → db.query.text é o LIKE '%...%' → EXPLAIN mostrou Seq Scan → recriar o índice.
  7. Com índice: Bitmap Index Scan (~19 ms por comando). Sem índice: Parallel Seq Scan na contagem (121 ms) e Index Scan na PK descartando ~1 milhão de linhas na página (262 ms).
  8. O campo de texto procura no nome do trace, não nos atributos. Achar: filtro avançado url.path contains SKU-TESTE.
  9. O corpo da requisição não é capturado; só caminho, query string e cabeçalhos escolhidos viram atributos.
  10. A média esconde a cauda lenta; o P99 mostra o que os piores 1% enfrentam.
  11. Não houve requisição naquela janela: é ausência de dado, não latência zero.
  12. Medir: P99 da rota /catalogo/fichas-produto; limite: acima de 1 s; duração: 5 minutos seguidos. No Norte só foi descrito; nenhum alerta foi criado.
  13. O painel perde tudo (traces, logs, métricas). A API volta a enviar sozinha, desde que esteja rodando; o que se gera durante a queda não foi testado.
  14. Porque o caminho só tem {sku} e ids numéricos; CPF e e-mail vão no corpo do POST, que não é capturado. Se uma rota passar a ter CPF no caminho, deixa de valer.
  15. É o protocolo do OpenTelemetry para enviar os sinais; permite trocar o destino (painel, Seq, Grafana, nuvem) por configuração, sem mudar o código.
  16. Por exemplo: que configurei um alerta de verdade; que operei ELK, Grafana/Prometheus, Seq ou serviços de nuvem; que o painel guarda histórico; que testei volume real.
