Norte · S11 — FichaProduto e primeiro teste

Data: 02/10/2026 · Marco: M1 · Tempo líquido: 2h20 (14:48–16:10 e 20:16–21:14)

1. Objetivo e resultado

Objetivo (um só): a primeira funcionalidade do Catalogo e o primeiro teste do Norte, ligado a uma regra nomeada.

Resultado: cumprido.

  • CadastrarFichaProduto: POST /catalogo/fichas-produto devolve 201 com SKU e 400 sem SKU, conferido pelo arquivo .http.
  • Projeto Norte.Catalogo.Tests com 2 testes verdes.
  • Ciclo 🔴 → 🟢 feito: com o if do SKU comentado, o teste da recusa falhou; com o if de volta, passou.
  • Regra nomeada: "Ficha exige SKU e NCM". Hoje testada a parte do SKU.
  • Commits na feat/catalogo-ficha-produto, com push.

2. Onde isso está no mapa

Começou o nível 3, a funcionalidade (Parte 0). O caminho de hoje: MapPost → CadastrarFichaProdutoEndpoint.Executar → FichaProdutoRepository → 201 ou 400. O teste chama o Executar direto. Detalhe completo: Parte 3 do guia.

3. Conceitos (a explicação completa está no guia)

Conceito Como era Como é agora Guia
Papéis da funcionalidade Controller + DTO + Service + Repository, um por pasta Request + Endpoint + Repository, o papel no sufixo (padrão REPR) 3.1
record class com get; set; record em uma linha, imutável, compara por valor 3.2
Respostas IActionResult, BadRequest(ModelState) Results<Created<...>, ValidationProblem>, 400 em ProblemDetails 3.3
Testar a API à mão Postman arquivo .http no repositório 3.4
Projeto de testes — Norte.Catalogo.Tests + InternalsVisibleTo 3.5
Teste controller com mock Arrange–Act–Assert chamando Executar direto 3.6
Prova do teste — vermelho com a regra quebrada, verde com ela de volta 3.7
Sintaxe curta — [], =>, namespace X;, new() 3.8

A frase do dia: um teste só protege o que ele exercita, e só prova alguma coisa se você já o viu falhar.

4. Termos técnicos

  • REPR: Request–Endpoint–Response, organização de uma funcionalidade em três peças.
  • record: tipo de dados imutável com igualdade por valor.
  • ProblemDetails: formato padrão (RFC) de erro em JSON (application/problem+json).
  • .http: arquivo de requisições HTTP que a IDE executa.
  • xUnit: biblioteca de testes; [Fact] marca um teste.
  • AAA: Arrange (prepara), Act (executa), Assert (confere).
  • InternalsVisibleTo: deixa um projeto nomeado ver o que é internal.
  • Red → green: ver o teste falhar com a regra quebrada e passar com ela restaurada.

5. Dúvidas do aluno e as respostas

  • "O FichasProdutoEmMemoria é o service de antes?" Não: é o repositório. O papel do service é do Executar.
  • "São essas as nomenclaturas que se usa? Antes ficava mais explícito." Crítica procedente. O nome FichasProdutoEmMemoria (do mentor) dizia como, não o quê, e virou FichaProdutoRepository. O papel agora está no sufixo (Request, Endpoint, Repository). Em M2, a pasta por funcionalidade devolve a clareza de "tudo num lugar".
  • "O .http é do .NET 10?" Não: é da IDE (VS 2022 desde 2023; VS Code e JetBrains antes).
  • "Não deveria dar erro?" (com o if comentado e só o teste do 201): não, porque esse teste manda com SKU e nunca passa pelo if. Foi a pergunta mais importante da sessão.
  • "Não tem que dar o git push?" Sim; o PR fica para quando a regra do NCM fechar.

7. Avaliação

O que você fez bem:

  • As duas retenções sem pista, inclusive o processo compartilhado (erro da S10, agora certo).
  • Decidiu a regra pelo negócio ("os dois dados são obrigatórios").
  • Questionou os nomes até fazer sentido.
  • Escreveu Arrange e Act do teste certos e deu um nome melhor que o do modelo (..._e_devolve_400).
  • Perguntou "não deveria dar erro?".

Onde travou e por quê:

  • O endpoint precisou de esqueleto: record, Results<...> e ValidationProblem eram novos.
  • O Assert do teste da recusa veio copiado do modelo e conferia o 201. É o A7: sobra de modelo pela 3ª vez, agora no sentido de uma linha, não num nome.
  • Duas linhas de Assert não podiam falhar (NotEmpty, Null de um SKU nunca enviado).

O que o mentor conduziu mal:

  • O nome FichasProdutoEmMemoria.
  • O comando curl.exe com escape que depende da versão do PowerShell.
  • A pergunta de autoavaliação no fim: composta e repetida três vezes, num dia longo. A nota 1 reflete também isso.

8. Pontos a melhorar

  • Você: ao adaptar um modelo, fazer em cada bloco copiado a pergunta "esta linha ainda é verdade para o caso novo?" (proposta do A7, a decidir). Em teste, a pergunta vale sobretudo para o Assert.
  • Mentor: pergunta de fechamento numa parte só; comandos de terminal testados para PowerShell 5.1 e 7; nomes por papel.

9. Perguntas de recuperação (respostas no fim)

  1. No Norte, qual classe e qual método fazem o papel que o FichaProdutoService.Cadastrar() fazia na arquitetura com pastas técnicas?
  2. O endpoint CadastrarFichaProdutoEndpoint.Executar retorna Results<Created<FichaProduto>, ValidationProblem>. Num teste, qual chamada descobre qual dos dois resultados aconteceu?
  3. O teste Cadastra_ficha_com_sku_e_devolve_201 envia uma ficha com SKU. Se alguém apagar o if que recusa ficha sem SKU, esse teste fica verde ou vermelho?

  5. Os tipos do módulo Catalogo são internal (ADR-002). O que permite que o projeto Norte.Catalogo.Tests use o CadastrarFichaProdutoEndpoint?
