Norte · S22 — Catálogo fechado e o Pedido: modelagem e primeira classe

Sexta, 16/10/2026 · tempo líquido: 7h59 (acima do limite de 5h) · Marco M1

Hoje você fechou as pontas do Catalogo e modelou o Pedido inteiro em português, sem banco. No fim, escreveu o primeiro teste e a primeira classe do Pedido em um módulo novo de testes. O erro a evitar: tratar um teste vermelho como defeito do teste. Vermelho quase sempre é o código errado; o teste é o contrato.

2. Onde isso está no mapa dos níveis

Solution → módulos → funcionalidades → camadas. Hoje o Catalogo ficou completo (CRUD, limite do SKU, testes) e o módulo Pedidos ganhou o primeiro projeto de teste e o primeiro tipo de domínio (Pedido, OrigemPedido, SituacaoPedido). O Pedido ainda não tem persistência, itens nem endpoint.

3. Conceitos

3.1 O que é do pedido e o que é do item

Fica no pedido Fica no item Fica em outro módulo
PedidoId, Origem, Situacao Sku quem reservou e quando (Estoque)
ClienteId, RepresentanteId Quantidade, QuantidadeReservada razão social e dados do cliente (dono do cadastro, a decidir)
CriadoPor, DataHoraCriacao (nunca mudam) QuantidadeCancelada, QuantidadeFaturada descrição do produto (Catalogo)
carimbo do comercial (nome e data/hora; nunca muda) PrecoUnitario (o único dado que congela), ValorDesconto
UltimaAtualizacaoPor, DataHoraUltimaAtualizacao (sobrescrevem, sem histórico) saldo = quantidade − faturada − cancelada

Regra de decisão para saber onde um dado mora: quem é o dono do dado? O pedido guarda o identificador; o nome vem de quem é dono. Só o preço congela, porque a tabela de preço pode mudar depois (R3 do DOMINIO.md).

3.2 Situações do pedido

Digitado → Aprovado → FaturadoParcialmente / FaturadoTotalmente; Cancelado é possível enquanto há saldo. A situação é guardada (não só calculada) para facilitar a vida de quem opera. O cancelamento age sobre o saldo (por isso o item tem QuantidadeCancelada).

3.3 Decisões de negócio tomadas hoje

  • Origem do pedido é uma lista fechada: Feira, WhatsApp, App, Site, E-mail, Interno.
  • Quem criou e quando é imutável. A última atualização sobrescreve, sem histórico (por enquanto).
  • O carimbo do comercial é um fato imutável (quem e quando verificou). Checagem de crédito por gerente comercial e financeiro fica em aberto.
  • A reserva de estoque mora no Estoque; o pedido só mostra a quantidade reservada. Só o estoque cancela uma reserva.
  • O representante pode mudar até o faturamento. Quem congela o representante é a venda.
  • O pedido nasce sem itens (opção B). A regra "não aprova sem item" fica para a próxima sessão, com dois testes.

3.4 Projeto de teste novo e InternalsVisibleTo

O Pedido é internal sealed. Para o projeto de teste enxergá-lo, o Norte.Pedidos.csproj ganhou:

<InternalsVisibleTo Include="Norte.Pedidos.Tests" />
Como era Como é agora O que mudou
atributo [assembly: InternalsVisibleTo("...")] num .cs item MSBuild <InternalsVisibleTo Include="..." /> no .csproj o .csproj gera o atributo; não precisa de arquivo solto

A classe de teste continua public (o xUnit exige).

3.5 Teste de valor que o próprio objeto gera

O construtor gera PedidoId (Guid.NewGuid()) e as datas (DateTimeOffset.UtcNow, lido uma vez em agora). Você não pode comparar com um valor fixo. Dois padrões:

Assert.NotEqual(Guid.Empty, pedido.PedidoId);        // foi gerado
Assert.InRange(pedido.DataHoraCriacao, antes, depois); // caiu na janela do teste

antes é lido antes do Act; depois, depois. A data tem de cair entre os dois. As propriedades que nunca mudam têm só { get; }; as que podem mudar têm private set.

Veja o mesmo raciocínio de construtor e teste em 6.12–6.13.

3.6 O teste vermelho de duas formas

Forma Como aparece Exemplo de hoje
Não compila erro de build, um de cada vez, em cadeia CS0234 (o using do namespace), depois CS0246 (o tipo)
Falha na asserção Expected / Actual trocamos Digitado por Aprovado no construtor: Expected: Digitado, Actual: Aprovado

O estrago foi desfeito com git restore e o teste voltou ao verde. Conclusão: quando o Actual está errado, o defeito está no código; o teste descreve o que o Pedido deve ser.

3.7 Enums com valor explícito

internal enum SituacaoPedido
{
    Digitado = 1,
    Aprovado = 2,
    FaturadoTotalmente = 3,
    FaturadoParcialmente = 4,
    Cancelado = 5,
}

O que fica pior sem o valor explícito: quem reordenar os nomes muda o número que já foi gravado no banco. Os enums moram em Dominio/ (organização por assunto); não criamos pasta Enums/ sem decisão.

3.8 CancellationToken obrigatório no cadastro

O token passou a ser exigido no cadastro. Foi provado com o seed: 40 → 39 → 40 fichas (a prova apagou uma ficha e o seed devolveu).

5. Dúvidas e respostas

O que é "código da aplicação"? O código que roda para o usuário (em oposição ao código dos testes).

O que o teste tem que fazer? Fixar uma regra de negócio: descrever, com valores que você controla, o que deve ser verdade depois do Act.

Como atualizo o Solution Explorer? Um projeto novo só aparece depois do dotnet sln add (ou de editar o .slnx). Hoje o .slnx ganhou a pasta virtual /tests/Modulos/Pedidos/.

O build deu 4 erros e 20 avisos. Por quê? A API ainda estava rodando e travou as DLLs (MSB3026, "locked by Norte.Api"). Fechar a API e rodar o build de novo.

7. Avaliação

Fez bem: decidiu o negócio do pedido com clareza (cliente, nome fantasia, representante, reserva no estoque); identificou sozinho o método que prefere (criar os arquivos usando o Catalogo como referência); questionou a pasta dos enums.

Travou: na primeira versão do teste, o Assert comparava variáveis locais com literais (nunca falharia) e o construtor recebia campos demais; leu o vermelho da prova ao contrário ("teríamos que alterar o teste").

O mentor conduziu mal: previu o erro do primeiro vermelho sem ver (o compilador mostrou só o using); sugeriu nomes de carimbo/verificação sem conferir; deixou o glossário do repositório para o fim.

Respostas

Mostrar respostas
  1. Porque o preço é o único dado que não pode mudar depois (R3); o nome pertence a outro módulo, que é o dono do dado. O pedido guarda o identificador.
  2. Porque o Guid e a data são gerados pelo próprio construtor. Não dá para prever o valor, então o teste verifica que o Guid não é vazio e que a data caiu entre o instante lido antes do Act e o lido depois.
  3. No código. O teste descreve o contrato (Digitado); o Actual: Aprovado mostra que o construtor está errado.
  4. O build não conseguiu copiar a DLL porque a API ainda estava rodando. Feche a API e rode o build de novo.
  5. Porque a reserva é do Estoque; o pedido só mostra a quantidade reservada. Só o estoque cancela uma reserva.
  6. Libera os tipos internal ao projeto de teste. O xUnit só descobre classes de teste public.
  7. Reordenar os nomes muda o número já gravado no banco.
  8. Quantidade − quantidade faturada − quantidade cancelada.
