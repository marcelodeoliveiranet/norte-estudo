2. Onde isso está no mapa dos níveis

Solution → módulos → funcionalidades → camadas. Hoje o trabalho foi na camada de domínio do módulo Pedidos: um tipo novo (ItemPedido) e uma regra nova no construtor do Pedido. Ainda não há banco, endpoint nem validação dos campos obrigatórios.

3. Conceitos

3.1 O pedido nasce com itens

Na S22 o pedido podia nascer sem itens. Você mudou isso hoje, com um bom argumento: pedido sem item não faz sentido no negócio.

Como era (S22) Como é agora (S23) O que mudou
new Pedido(origem, criadoPor, clienteId, representanteId) new Pedido(origem, criadoPor, clienteId, representanteId, itens) o construtor recebe a lista de itens
lista vazia era aceita lista vazia lança ArgumentException o domínio se protege

O nome Digitado continua certo. Ele quer dizer "ainda não foi conferido", não "ainda não tem item".

3.2 ItemPedido: o que o item recebe e o que começa em zero

internal sealed class ItemPedido
{
    public ItemPedido(string sku, int quantidade, decimal precoUnitario, decimal valorDesconto)
    {
        Sku = sku;
        Quantidade = quantidade;
        PrecoUnitario = precoUnitario;
        ValorDesconto = valorDesconto;
    }

    public string Sku { get; private set; }
    public int Quantidade { get; private set; }
    public decimal PrecoUnitario { get; private set; }
    public decimal ValorDesconto { get; private set; }
    public int QuantidadeReservada { get; private set; }
    public int QuantidadeFaturada { get; private set; }
    public int QuantidadeCancelada { get; private set; }
}
Vem de fora (construtor) Começa em zero (muda depois)
Sku, Quantidade, PrecoUnitario, ValorDesconto QuantidadeReservada, QuantidadeFaturada, QuantidadeCancelada

Os campos que começam em zero só mudam por regras que ainda vão nascer (reserva, faturamento, cancelamento). Por isso não entram no construtor.

3.3 O construtor que recusa lista vazia

public Pedido(OrigemPedido origem, string criadoPor, int clienteId, int representanteId,
    IReadOnlyList<ItemPedido> itens)
{
    if (!itens.Any())
        throw new ArgumentException("O pedido deve ter pelo menos um item.", nameof(itens));

    var agora = DateTimeOffset.UtcNow;
    PedidoId = Guid.NewGuid();
    // ... demais campos como na S22 ...
    Itens = itens;
}

public IReadOnlyList<ItemPedido> Itens { get; private set; }

Palavra nova: IReadOnlyList<T>. É uma lista que só se pode ler. Quem recebe o Pedido consegue ver os itens, mas não consegue colocar nem tirar item pela propriedade. É o mesmo cuidado do private set, agora para listas.

Este é o mesmo raciocínio do construtor da FichaProduto (S18): o construtor protege o domínio. A regra está no lugar onde o objeto nasce, então nenhum Pedido inválido existe.

3.4 Os dois testes

O teste da S22 e o teste novo viraram um só, porque os dois respondiam à mesma pergunta: "como o pedido nasce?". Dois testes ficaram:

Teste Pergunta que responde
Pedido_novo_nasce_com_situacao_digitado_e_com_itens O pedido novo guarda o que recebeu, gera o que é dele e traz os itens?
Pedido_com_itens_vazio_deve_retornar_exception O pedido recusa uma lista vazia, dizendo qual parâmetro está errado? 
[Fact]
public void Pedido_com_itens_vazio_deve_retornar_exception()
{
    // Arrange — quais dados eu preciso para montar o pedido?
    var origem = OrigemPedido.App;
    var criadoPor = "Marcelo";
    var clienteId = 123;
    var representanteId = 23;

    // Act + Assert — o que acontece se a lista de itens vier vazia?
    var itens = new List<ItemPedido>();
    var excecao = Assert.Throws<ArgumentException>(
        () => new Pedido(origem, criadoPor, clienteId, representanteId, itens));

    Assert.Equal("itens", excecao.ParamName);
}

Dois pontos para guardar:

  • Assert.Throws<ArgumentException> roda o código do lambda e exige que ele lance aquela exceção. Se nada for lançado, o teste falha.
  • ParamName diz qual parâmetro está errado. Confirmar "itens" garante que a exceção veio da regra certa, e não de outro if.

No primeiro teste, a lista tem um item, e o Assert usa Assert.Single(pedido.Itens) (a lista tem exatamente um) e depois compara cada campo do item com as variáveis do Arrange, nunca com um literal repetido.

3.5 A prova do vermelho, nos dois testes

Teste Estrago mínimo O que o teste disse
1 no construtor, Itens = []; Assert.Single() Failure: The collection was empty
2 comentar o if da recusa Assert.Throws() Failure: No exception was thrown

Em cada caso o defeito estava no código, e o teste continuava certo. Se o estrago fizesse o teste passar, o teste não protegeria nada. Depois de ver o vermelho, o estrago foi desfeito e os dois testes voltaram ao verde (total: 2; succeeded: 2).

3.6 Decisões de domínio de hoje

Tema Decisão

PedidoId vira o número criado pelo banco; hoje continua Guid e a troca fica para a sessão da persistência. Nenhum teste depende disso

3.7 Nomes do glossário

No glossário, o termo é o nome da propriedade (Origem, Situacao), e não o nome do tipo (OrigemPedido, SituacaoPedido). Quem lê o negócio pensa em "origem" e "situação". A regra do arquivo continua valendo: um termo entra quando aparece no código, com o nome usado no código.

3.8 Git do dia a dia: o -m e o -u

Comando Para que serve
git add . coloca no próximo commit tudo o que mudou (confira antes com git status)
git commit -m "mensagem" cria o commit com a mensagem (-m = mensagem)
git push -u origin <branch> envia a branch e liga a local à remota (o -u é só do push)
gh pr create --base main --head <branch> --title "..." --web abre o PR no navegador, com o template
gh pr status mostra o estado do seu PR e dos checks

O erro de hoje foi usar -u no commit. O -u não existe ali. Outro cuidado: sem git add . o commit sai vazio.

4. Termos da sessão

Termo Em uma linha
IReadOnlyList<T> lista que só se lê; não deixa trocar os itens por fora
Assert.Throws<T> exige que o código lance a exceção T
ParamName nome do parâmetro que causou a ArgumentException
Assert.Single a coleção tem exatamente um elemento
Fusão de testes juntar dois testes que respondem à mesma pergunta
Digitado "ainda não conferido"
Estrago mínimo a menor mudança no código que deve deixar o teste vermelho

5. Dúvidas e respostas

O pedido sem item não podia existir já na S22? Podia, e foi uma escolha da S22. Hoje você mostrou que, para o negócio, não faz sentido. Mudar agora é barato: ainda não há banco.

Por que não validar a lista vazia no Request da API? Ainda não existe endpoint de pedido. A regra mora no construtor, que protege o domínio de qualquer entrada.

Por que o teste de domínio não usa o banco? Porque a regra não depende do banco. O projeto Norte.Pedidos.Tests só tem o xUnit.

Respostas

Mostrar respostas
  1. Porque pedido sem item não faz sentido no negócio. O nome Digitado continua certo porque quer dizer "ainda não foi conferido", e não "ainda não tem item".
  2. Lança ArgumentException com a mensagem "O pedido deve ter pelo menos um item.", apontando o parâmetro itens.
  3. Mostra qual parâmetro está errado. Confirmar "itens" garante que a exceção veio dessa regra, e não de outra.
  4. No código. O teste descreve o contrato (o pedido traz o item); o estrago mostrou que, sem a atribuição de Itens, a coleção fica vazia e o teste avisa.
  5. Porque eles começam em zero e só mudam por regras futuras (reserva, faturamento, cancelamento). Não vêm de fora na criação do item.
  6. O commit sai vazio: o Git avisa no changes added to commit, porque nada foi colocado na área de preparo.
  7. No git push -u origin <branch>: liga a branch local à remota. O git commit usa -m para a mensagem.
  8. Porque o glossário usa o nome que o negócio e o código usam para o dado (a propriedade). Quem procura "origem" ou "situação" acha o termo direto.
