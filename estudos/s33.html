Norte · S33 — O contrato entre módulos e o POST /pedidos

Terça, 27/10/2026 · tempo: 12h17 (9:31–21:48, sem pausas informadas) · Marco M1

Hoje o Pedidos aprendeu a perguntar uma coisa ao Clientes sem enxergar o interior dele. Primeiro o Clientes ganhou os endpoints que faltavam (DELETE, PUT e listagem). Depois nasceu o contrato entre módulos (ADR-012): um projeto Norte.Clientes.Contratos com uma interface. Por fim o endpoint POST /pedidos usou esse contrato, com 201, 404 e 400, e a validação nativa do .NET 10 foi levada até onde ela vai. Nove PRs na main (#58 a #66), 153 testes, CI verde.

A ideia para guardar: a fronteira entre módulos é uma interface em um projeto que não tem nada dentro; quem consulta só conhece a pergunta, e o módulo dono responde do jeito dele. O compilador garante a pergunta; só a execução garante que alguém a respondeu (por isso existe um teste com a API de verdade).

Antes de ler: a explicação completa de cada peça está na entrada 8.12 da Parte 8 do guia. Esta página é o roteiro de estudo da sessão.

2. Onde isso está no mapa dos níveis

Solution → módulos → funcionalidades → camadas. Hoje apareceu uma peça no nível dos módulos: a fronteira entre eles. O Pedidos passou a depender de um projeto novo (Norte.Clientes.Contratos), que é público e quase vazio. O Norte.Clientes (o módulo) continua internal por dentro e implementa a interface. Quem liga as duas pontas é o host (Norte.Api), pelo contêiner de injeção de dependência.

3. Conceitos

3.1 O contrato entre módulos (guia 8.12)

Palavra nova — contrato: o que um módulo aceita responder aos outros. É uma interface pública, num projeto separado, que não referencia nenhum módulo.

namespace Norte.Clientes.Contratos;

public interface IConsultaClientes
{
    Task<bool> ClienteExisteAsync(int clienteId, CancellationToken ct);
}

internal sealed class ConsultaClientes(ClientesRepository clienteRepository) : IConsultaClientes
{
    public async Task<bool> ClienteExisteAsync(int clienteId, CancellationToken ct)
    {
        return await clienteRepository.ExisteClientePeloIdAsync(clienteId, ct);
    }
}
Peça Onde mora Por quê
IConsultaClientes Norte.Clientes.Contratos (public) é a única coisa que o Pedidos enxerga
ConsultaClientes Norte.Clientes (internal sealed) a implementação é detalhe do dono do dado
AddScoped<IConsultaClientes, ConsultaClientes>() AddClientes o contêiner entrega a implementação a quem pedir a interface
ProjectReference ao projeto de contratos Norte.Pedidos.csproj o Pedidos não referencia o Norte.Clientes

Regras do ADR-012 (resumo): um projeto de contratos por módulo consultado; quem consulta referencia só ele; a implementação é internal e fica no módulo dono; o projeto de contratos não referencia módulo nenhum; começa sem expor nada e cada método nasce de uma pergunta concreta, desenhada por caso de uso ("o cliente existe?"), não por dado ("devolva o cliente").

Por que não as outras opções (ADR-012):

Opção Por que ficou de fora
Interface dentro do Norte.Compartilhado contraria o ADR-007 (só constantes); o projeto viraria depósito de contratos
Interface public dentro do próprio Norte.Clientes quando o Clientes precisar perguntar ao Pedidos (regra do DELETE), os dois se referenciariam; o .NET não aceita referência circular
Eventos (o Clientes publica, o Pedidos guarda cópia) cópia pode ficar defasada; pede mensageria; custo grande para um bool
Ganho Preço
Um projeto de contratos por módulo a fronteira é garantida pelo compilador e o módulo dono continua livre para mudar o interior um projeto a mais por módulo consultado; o contrato não elimina o acoplamento, só o torna explícito; quem consulta depende da interface

3.2 Ligação na compilação × ligação na execução

São duas garantias diferentes:

Garantia Quem dá O que falha se faltar
a interface existe e o Pedidos a usa certo compilador (ProjectReference) erro de build
alguém registrou uma implementação contêiner de DI, em tempo de execução exceção na primeira requisição que pedir IConsultaClientes

Por isso o ADR-012 diz: "a ligação em tempo de execução pode falhar; um teste do endpoint com a API de verdade cobre esse caso".

3.3 AnyAsync × FirstOrDefaultAsync

A pergunta do dia (sua) foi por que o ExisteClientePeloIdAsync usa AnyAsync, e não o método que já busca o cliente.

AnyAsync FirstOrDefaultAsync / ObterClientePeloIdAsync
SQL EXISTS: responde sim ou não traz a linha inteira
Devolve bool o objeto (ou null)
Quando serve só importa se existe você vai usar os dados

O contrato pergunta "existe?"; trazer a linha inteira para jogar fora seria trabalho a mais. E o ExcluirClientePeloIdAsync não serve aqui porque apagaria o cliente: um método que muda dado nunca responde a uma pergunta de consulta.

3.5 Testar com um dublê: ConsultaClientesFake

O teste do Pedidos não sobe o Clientes de verdade. Ele troca a implementação do contrato:

internal sealed class ConsultaClientesFake(bool existe) : IConsultaClientes
{
    public Task<bool> ClienteExisteAsync(int clienteId, CancellationToken ct)
        => Task.FromResult(existe);
}

using var fabricaComClienteExistente = fabrica.WithWebHostBuilder(builder =>
    builder.ConfigureServices(services =>
        services.AddScoped<IConsultaClientes>(_ => new ConsultaClientesFake(existe: true))));
Peça O que faz
WithWebHostBuilder cria uma variação da fábrica de teste, só para este teste
AddScoped<IConsultaClientes>(...) registra depois do AddClientes; o contêiner usa a última registração, e o fake vence
existe: true / false decide a resposta sem banco de clientes

Palavra nova — dublê (test double): qualquer objeto que ocupa o lugar de um colaborador no teste. Os tipos mais comuns são stub (responde o que você mandou), fake (uma implementação simples e funcional) e mock (também confere se foi chamado). O nome ConsultaClientesFake foi sua escolha (o primeiro nome era ConsultaClientesFalsa): "vai ao encontro de Tests etc." O Fake descreve o papel; o sufixo em inglês segue o padrão de Tests.

3.6 Validação nativa do .NET 10 levada ao limite

O CriarPedidoRequest é public (exceção do ADR-003) e a validação roda antes do endpoint.

Campo Atributo Detalhe
Origem [Range(1, 6)] você decidiu receber o código (int), não o nome
CriadoPor [Required] + [StringLength(Constantes.TamanhoMaximoCriadoPor)] [StringLength] ignora null; o [Required] fecha
ClienteId, RepresentanteId [Range(1, int.MaxValue)] [Range] é inclusivo
Itens [Required] + [MinLength(1)] [Required] barra null; [MinLength] barra lista vazia
PrecoUnitario, ValorDesconto [Range(typeof(decimal), "0.01", "79228162514264337593543950335", ParseLimitsInInvariantCulture = true, ConvertValueInInvariantCulture = true)] veja abaixo
desconto × preço × quantidade IValidatableObject no item veja 3.7

[Range] com decimal. Atributo só aceita constante, e decimal não é constante de atributo. Por isso os limites vão como texto. Sem os dois ...InvariantCulture, "0.01" seria lido com a cultura do servidor; em pt-BR o ponto é separador de milhar e o valor virava 1. Os dois true mandam ler os limites e o valor recebido com a cultura invariante (o ponto decimal do JSON).

Origem como int. Sua razão: "número não dá erro de digitação". O Enum.IsDefined continua no construtor do domínio (segunda barreira). O [Range(1, 6)] não pode ler o enum (atributo só aceita constante), então o limite está escrito à mão e um teste de reflexão garante que ele acompanha o enum:

Assert.Equal(codigos.Min(), (int)range.Minimum);
Assert.Equal(codigos.Max(), (int)range.Maximum);
// Sem buracos: o Range só é suficiente se os códigos forem contínuos
Assert.Equal(codigos.Max() - codigos.Min() + 1, codigos.Count);

Se alguém acrescentar OrigemPedido.Telefone = 7 e esquecer o Range, o teste fica vermelho. Se alguém pular um número (1, 2, 4), o último Assert também.

3.7 IValidatableObject: a regra que olha três campos

Um atributo no campo só enxerga aquele campo. A regra "o desconto deve ser menor que preço × quantidade" olha três:

public IEnumerable<ValidationResult> Validate(ValidationContext validationContext)
{
    if (ValorDesconto >= PrecoUnitario * Quantidade)
        yield return new ValidationResult(
            "O valor do desconto deve ser menor que o valor total do item",
            [nameof(ValorDesconto)]);
}

O segundo argumento ([nameof(ValorDesconto)]) diz qual campo aparece em Errors no 400. A regra é a mesma do construtor do ItemPedido (S24): a API barra primeiro e o domínio é a segunda defesa.

Ganho Preço
Validar na entrada e no domínio a API responde 400 com o campo certo; o domínio protege qualquer outra porta a regra do desconto existe em dois lugares
IValidatableObject sem biblioteca nova; a regra composta fica junto do Request a regra fica escrita em código dentro do Request; se as regras compostas crescerem, o FluentValidation (adiado) volta à conversa

Limite não coberto: PrecoUnitario * Quantidade pode estourar o decimal (preço 79228162514264337593543950335 × quantidade 2). O resultado seria uma exceção de estouro, e a API devolveria 500. Fica anotado como dívida (preço e quantidade máximos), junto com o contrato Pedidos ↔ Catalogo.

3.8 O teste do 400 que troca um campo de cada vez

var corpo = new JsonObject { ["origem"] = 1, ["criadoPor"] = "vendedor.teste", ... };
corpo[campo] = JsonNode.Parse(valorInvalidoJson);
Peça Papel
TheoryData<string, string> (campo, valor inválido em JSON) cada linha troca um campo por um valor ruim
JsonObject e JsonNode.Parse montam o corpo e permitem pôr null, [], " " como JSON de verdade
um campo ruim por vez os outros ficam válidos para só uma regra poder falhar

Para os itens, ItensInvalidos faz o mesmo dentro do item (SKU nulo, vazio, só espaços, 21 caracteres; quantidade 0 e −1; preço 0 e −1; desconto −1, 21,00 e 25,00). O item válido do teste é 2 × 10,50 = 21,00; por isso 21,00 é recusado (a regra é "estritamente menor") e 25,00 também.

5. Dúvidas e respostas

O que a origem do pedido tem a ver com o contrato do cliente? Nada diretamente. A decisão da origem (código int) é sobre o formato da entrada do POST /pedidos; o contrato é sobre perguntar ao Clientes se o cliente existe. As duas coisas aparecem no mesmo endpoint, mas são decisões separadas.

Por que não usar o ExcluirClientePeloIdAsync? Porque ele apaga. Consulta nunca pode alterar dado.

Por que AnyAsync e não FirstOrDefaultAsync? Porque a pergunta é "existe?", e não "quem é?". Veja 3.3.

O Request do pedido é public. Isso não fura o internal? É a exceção do ADR-003 (a validação nativa precisa enxergá-lo); o Response, o endpoint e o repositório seguem internal.

Onde está o limite do decimal? O [Range] usa o maior decimal como teto, mas preço × quantidade pode passar dele. Hoje o teto de preço e de quantidade não existe.

Respostas

Mostrar respostas
  1. Porque o Clientes e o Pedidos vão precisar perguntar um ao outro (o DELETE de cliente pergunta ao Pedidos); se a interface morasse no módulo, haveria referência circular, que o .NET não aceita. Um projeto de contratos sem referências quebra o ciclo e mantém o interior do módulo internal.
  2. Não. Referencia só o Norte.Clientes.Contratos.
  3. O compilador garante que a interface existe e que o Pedidos a usa certo (ProjectReference). Só a execução garante que alguém registrou uma implementação no contêiner de DI; sem registro, a primeira requisição que pedir a interface falha. Por isso há um teste com a API de verdade.
  4. Porque a pergunta é "existe?": AnyAsync vira EXISTS e devolve bool, sem trazer a linha. FirstOrDefaultAsync traz a linha inteira, o que só vale se os dados forem usados.
  5. Troca a implementação do contrato: WithWebHostBuilder + AddScoped<IConsultaClientes>(_ => new ConsultaClientesFake(existe: false)). O endpoint pergunta ao fake, que responde false, e devolve 404.
  6. O contêiner entrega a última implementação registrada para uma interface. O fake é registrado depois do AddClientes, então vence a implementação real, só naquele teste.
  7. Stub devolve o que foi combinado; fake é uma implementação simples que funciona; mock também confere como foi chamado. O ConsultaClientesFake devolve o bool que o teste mandou: na prática é um stub, e o nome Fake foi escolhido por coerência com Tests.
  8. Atributo só aceita constante e decimal não é constante de atributo; os limites vão como texto. Sem ParseLimitsInInvariantCulture o "0.01" seria lido com a cultura do servidor (em pt-BR o ponto é separador de milhar).
  9. O Range não pode ler o enum (atributo só aceita constante), então o limite é escrito à mão. O teste confere por reflexão que o mínimo e o máximo do Range são os do enum e que não há buracos; se o enum crescer e o Range ficar, o teste fica vermelho.
  10. Porque a regra olha três campos (desconto, preço e quantidade) e um atributo no campo só enxerga aquele campo. O Validate olha o objeto inteiro.
  11. ValorDesconto: o Validate devolve o erro com [nameof(ValorDesconto)]. Com 21,00 o desconto é igual ao total (2 × 10,50) e a regra é "estritamente menor".
  12. O estouro de PrecoUnitario * Quantidade no decimal: o cálculo lançaria uma exceção de estouro e a API devolveria 500. Falta definir preço e quantidade máximos (dívida anotada).
  13. Porque o histórico prova que o teste ficou vermelho antes do código existir; se o teste viesse junto com o código, ninguém saberia se ele consegue falhar.
  14. Porque o --web abre o formulário do GitHub já com o template do repositório (O que muda / Como verificar / Decisões). --body e --body-file pulam o template.
