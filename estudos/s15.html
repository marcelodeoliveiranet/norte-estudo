Norte · S15 — CI básico (GitHub Actions)

Sexta, 09/10/2026 · 14:19 → 15:50 · 1h31 líquidas, sem pausas · Marco M1

Objetivo da sessão: fazer o GitHub compilar e testar o código a cada push e a cada PR, e ver o aviso funcionar nos dois sentidos (verde e vermelho). Entregue: .github/workflows/ci.yml na main (PR #5) e a prova do vermelho (PR #6, descartado).

1. O problema que o CI resolve

Na S14 descobrimos que a main (36a5bbb) não compilava (CS8604) e ninguém percebeu na hora. Quem garantia "a main está verde" era a memória do desenvolvedor. O CI troca a memória por uma máquina que roda sempre, igual, no servidor.

Antes (sem CI) Depois (com CI)
"Rodei na minha máquina" Roda numa máquina limpa, sem nada instalado de antemão
O build quebrado aparece quando alguém abre o projeto O build quebrado aparece no PR, antes do merge
Depende de lembrar de rodar dotnet test Roda sozinho em todo push e PR para main

2. O vocabulário (de-para)

Termo do GitHub Actions O que é Analogia no que você já conhece
Workflow Um arquivo .yml que descreve o que rodar e quando Um script de build/pipeline
Gatilho (on) O evento que dispara o workflow (push, PR) O "quando"
Job Um bloco de trabalho que roda numa máquina Um estágio do pipeline
Runner A máquina (virtual) que executa o job O agente de build
Step Um passo dentro do job: uses (ação pronta) ou run (comando) Uma linha do script
Check O resultado (verde/vermelho) que aparece no PR O "semáforo" do PR
Annotation Mensagem anexada ao check (erro de compilação, aviso) A saída resumida do build

3. O ci.yml linha a linha

Arquivo obrigatoriamente em .github/workflows/ na raiz do repositório (é onde o GitHub procura). O nome do arquivo é livre; a pasta não.

name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

permissions:
  contents: read

jobs:
  build-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-dotnet@v6
        with:
          dotnet-version: 10.0.x
      - run: dotnet build Norte.slnx
      - run: dotnet test Norte.slnx --no-build
Linha O que faz Onde age O que acontece sem ela
name: CI Nome que aparece na aba Actions e no check Interface do GitHub Usa o nome do arquivo; funciona, só fica menos legível
on: push … [main] Roda quando entra commit na main GitHub Não confere a main depois do merge
on: pull_request … [main] Roda quando um PR aponta para a main GitHub Não confere o PR antes do merge — perde o ponto principal
permissions: contents: read O workflow só pode ler o repositório Token do workflow Fica com permissões padrão, mais largas que o necessário
jobs: build-test: Nome do job (livre) Workflow Obrigatório haver ao menos um job
runs-on: ubuntu-latest Tipo de máquina Runner Obrigatório: sem ele não há onde rodar
actions/checkout@v7 Baixa o código do repositório para o runner Runner A máquina começa vazia: o build não acha Norte.slnx
actions/setup-dotnet@v6 + dotnet-version: 10.0.x Instala o SDK do .NET 10 Runner Pode vir outro SDK (ou nenhum) e o build quebrar por motivo que não é do código
dotnet build Norte.slnx Compila a solution (com as regras da ADR-004: aviso é erro) Runner Sem build, o teste não tem o que rodar
dotnet test Norte.slnx --no-build Roda os testes sem recompilar Runner Sem teste, o check só diz "compila", não "funciona"

De onde vem o conteúdo: os comandos dotnet build/dotnet test são os mesmos que você roda no terminal; as ações checkout e setup-dotnet são ações oficiais publicadas pelo GitHub (actions/), com versão fixada (@v7, @v6) para o resultado não mudar sozinho.

Aviso visto nas annotations: "ubuntu-latest will migrate to Ubuntu 26 beginning October 19, 2026". Decisão pendente: manter ubuntu-latest (acompanha a migração) ou fixar ubuntu-24.04 (estável, mas envelhece). É um preço de cada lado, a decidir antes de 19/10.

4. As provas (verde e vermelho)

PR O que tinha Resultado Tempo Prova de quê
#5 ci.yml correto ✅ verde 28 s O CI roda e aprova código bom
#6 ("NÃO MESCLAR") ! removido de Sku no Executar ❌ vermelho, annotation CS8604 20 s O CI teria pego o erro que quebrou a main antiga (36a5bbb)

O que aprendemos vendo:

  • O botão de merge do GitHub continua clicável com o check vermelho. Não há proteção de branch configurada: o CI avisa, não impede. (Se o plano do repositório privado permite proteção de branch: a conferir.)
  • O GitHub manda e-mail ao autor quando o workflow de um PR falha.
  • A annotation aponta o arquivo, a linha e o código do erro — a mesma mensagem que o build local mostra.

5. O preço do CI (ganho × preço)

Ganho Preço
A main não quebra em silêncio O PR leva ~30 s a mais até estar "liberado"
Ambiente limpo revela dependência escondida na sua máquina Mais um arquivo para manter (versões das ações, SDK, imagem do runner)
Registro público de quando passou/falhou O ubuntu-latest muda sozinho: um dia o CI pode quebrar sem o código mudar
Base para o que vem (formato, banco real) Sem proteção de branch, o aviso pode ser ignorado: depende de disciplina

6. Git: as três cópias de uma branch

Dúvida da sessão: "quando apago uma branch no GitHub, ela some localmente?" Não. Existem três coisas diferentes:

Cópia Onde mora Quem apaga
Branch no servidor GitHub Botão "Delete branch" do PR
Branch local Seu computador (git branch) git branch -d <nome> (só se já foi mesclada) ou -D (força)
Referência remota local origin/<nome> Seu computador (cache do que o servidor tinha) git fetch --prune

Receita usada na sessão, para mover um commit que caiu na main local para uma branch:

git switch -c feat/ci-basico          # a branch nova nasce com o commit
git branch -f main origin/main        # a main local volta ao que o servidor tem

Opcional (decisão sua): git config --global fetch.prune true faz o git fetch limpar sozinho as referências de branches já apagadas no servidor.

9. Perguntas de recuperação (responda sem consultar)

  1. Por que o workflow precisa do passo actions/checkout?
  2. Em que pasta e em que nível do repositório o GitHub procura workflows?
  3. O check do PR ficou vermelho. O que o GitHub impede e o que ele não impede hoje no Norte?
  4. Por que o PR #6 provou mais do que o #5?
  5. Cite um preço (não um ganho) de ter o CI ligado.
  6. Apaguei a branch no GitHub. Em que lugares ela ainda pode existir no meu computador?
  7. Qual a diferença entre git branch -d e -D?
  8. (Das sessões anteriores) Qual middleware captura a exceção, qual escreve o corpo, qual preenche um 4xx vazio?

Respostas

Mostrar respostas
  1. Porque o runner começa vazio; sem o checkout, o código do repositório não está na máquina e o dotnet build não encontra Norte.slnx.
  2. Em .github/workflows/, na raiz do repositório. O nome do arquivo é livre; a pasta, não.
  3. Não impede o merge (botão continua clicável, não há proteção de branch). Faz: mostra o check vermelho, as annotations e manda e-mail ao autor.
  4. Porque mostrou o CI reprovando um erro real (CS8604, o mesmo que quebrou a main antiga). Um CI que só viu verde não provou que sabe falhar.
  5. Por exemplo: ~30 s a mais por PR; arquivo para manter; ubuntu-latest muda sozinho; sem proteção de branch o aviso depende de disciplina. (Qualquer um, com o efeito.)
  6. Na branch local (git branch) e na referência origin/<nome> (git branch -r). Limpa-se com git branch -d e git fetch --prune.
  7. -d só apaga branch já mesclada (protege contra perda); -D força, mesmo sem merge (descarte consciente — foi o caso da teste/ci-vermelho).
  8. AddProblemDetails() escreve o corpo; UseExceptionHandler() captura a exceção não tratada; UseStatusCodePages() preenche o corpo de um 4xx/5xx vazio.
