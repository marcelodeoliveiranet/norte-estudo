Norte · S28 — O dono do cliente: o módulo Clientes e a ficha mínima (ADR-011)

Quinta à noite, 22/10/2026 · tempo líquido: 1h53 (sessão extra da noite; o dia somou 7h52) · Marco M1

Hoje não houve código. Houve uma decisão: quem é o dono do cadastro do cliente e o que a ficha precisa ter para o cliente existir. O resultado está no ADR-011 (escrito, ainda não commitado) e numa mudança de escopo: o módulo Crm saiu do Norte.

A ideia para guardar: o dono de um dado é o módulo que cria e altera. Os outros guardam só o número. E um módulo se chama pelo assunto (Clientes), nunca pelo departamento (Comercial).

2. Onde isso está no mapa dos níveis

É a camada de domínio estratégico: fronteira entre módulos. Nenhum projeto foi criado e nenhum teste mudou. O Pedido continua validando só ClienteId > 0.

3. Conceitos

3.1 Dono do dado e a palavra que divide

Em DOMINIO.md, "cliente" tinha quatro sentidos (Crm, Ordering, Billing, Shipping). Sem o Crm, sobram três:

Contexto O que "cliente" é ali
Ordering (módulo Pedidos) quem recebe o pedido; guarda só o ClienteId
Billing sacado com dados fiscais e títulos em aberto
Shipping endereço com janela de entrega

O cadastro (quem é o cliente) é uma quarta coisa, que vive antes do pedido. Por isso ele não pode morar dentro de Pedidos: o Billing e o Shipping passariam a depender de Pedidos só para saber quem é o cliente.

Palavra nova — dono do dado: o módulo que cria e altera aquele dado. Os outros módulos guardam só o identificador.

3.2 A ficha mínima

Campo Tipo Regra
ClienteId int, gerado pelo banco código curto que o pessoal decora
Cnpj texto (18) com máscara, letras em maiúscula; obrigatório e único
RazaoSocial texto (120) obrigatória; nome legal (fiscal)
NomeFantasia texto (120) obrigatório; nome do dia a dia
RepresentanteId int obrigatório, maior que zero, provisório (carteira, R9)

Portão: só um cliente com a ficha completa pode receber um pedido.

3.3 Duas vezes RepresentanteId, dois significados

Onde Significa Muda?
Cliente.RepresentanteId de quem é a carteira quando a carteira é transferida (R9)
Pedido.RepresentanteId quem vende este pedido até o faturamento; a venda congela

Os dois são int > 0 e nenhum é conferido até o Partners existir (M3). O vínculo cliente↔representante (hotspot 6) passa para o Partners nessa data. Quando o código tiver os dois campos, o glossário precisa distinguir os dois.

Um erro de raciocínio que aconteceu na sessão e vale guardar: os argumentos a favor de pôr o representante no cliente valiam igualmente para o pedido. Foi você quem mostrou. Um argumento que serve para dois lugares não decide entre os dois.

3.4 CNPJ: um formato só

O CNPJ agora pode ter letras (CNPJ alfanumérico). Como o banco compara texto, duas escritas do mesmo CNPJ viram duas linhas. É a mesma lição do SKU (ADR-008 e ADR-009).

Parte Decisão
Guardar com máscara: XX.XXX.XXX/XXXX-DD (18 caracteres)
Letras em maiúscula
Domínio aceita um padrão exato; entrada fora dele é recusada
Banco índice único (a garantia final)
Aplicação consulta antes de gravar e responde 409 (como o SKU)
Dígitos verificadores não validados
Ganho Preço
Só o padrão sem cálculo; foco no que o mercado pede de .NET um CNPJ com padrão certo e dígitos errados é aceito
Índice único o banco impede a duplicata mesmo se a aplicação falhar uma corrida ainda pode dar 500 (23505), como no SKU

Se algum dia importar, o cálculo entra como função pura do domínio, com testes, conferida na documentação oficial da Receita.

3.5 Cortar o Crm: custo × valor

Você pediu para ser convencido do contrário, com algo que gerasse valor. O que se avaliou:

Pergunta Resposta
O Crm ensinava ferramenta que os outros módulos não ensinam? não
O Crm tinha horas planejadas no orçamento? não: o M2 não depende dele
Cortar economiza tempo? só se você reduzir o teto do M2; sem isso, as horas apenas ficam para outro assunto
O que se perde? lead, oportunidade, proposta e funil (R10 e os eventos da Fase 1)

Regra de corte usada: só entra no código o que tem regra e teste. O DOMINIO.md e o EVENT-STORMING.md registram o corte.

3.6 Ordem: contrato antes do endpoint

O Pedido não confere se o cliente existe. Quem confere é o endpoint, por um contrato do Clientes ("o cliente existe e tem a ficha completa?"). Por isso o contrato nasce antes do endpoint de criação do pedido: os testes do endpoint já nascem preparando um cliente real (ou um dublê) e os testes de domínio existentes não mudam. Esta ordem ainda precisa da sua confirmação.

3.7 Git: o que mudou no método

Comandos do dia a dia (status, diff, add, commit, push, switch -c, dotnet build/test) não são mais mostrados antes de rodar: se errar, o comando falha e você corrige. Os que destroem ou reescrevem (reset --hard, push --force, branch -D, clean, rebase, checkout --, restore sobre trabalho não salvo) continuam sendo mostrados antes.

Respostas

Mostrar respostas
  1. É o módulo que cria e altera o dado; os outros guardam só o número. Se o cadastro ficasse em Pedidos, o Billing e o Shipping dependeriam de Pedidos só para saber quem é o cliente, e o cadastro existe antes do pedido.
  2. Módulo se chama pelo assunto (ADR-001). Comercial é departamento: mistura cadastro, pedido e venda sob uma pessoa e não sob um assunto.
  3. ClienteId (int, banco), Cnpj (texto 18, com máscara, único), RazaoSocial (120), NomeFantasia (120), RepresentanteId (int > 0, provisório).
  4. No cliente é "de quem é a carteira" (muda na transferência, R9). No pedido é "quem vende este pedido" (muda até o faturamento; a venda congela).
  5. O banco compara texto: ab.123... e AB.123... seriam dois valores. Com um formato só (máscara fixa, maiúsculas), o índice único funciona. É a mesma lição do SKU.
  6. O índice único do banco (garantia final). A aplicação consulta antes e responde 409. Em corrida, o banco pode devolver 500 (23505).
  7. Um CNPJ com padrão certo e dígitos errados é aceito. Se importar, entra uma função pura no domínio, com testes, conferida na documentação da Receita.
  8. Para os testes do endpoint já nascerem preparando um cliente real (ou dublê) e os testes de domínio do Pedido não mudarem: a existência do cliente é checada no endpoint, não no domínio.
  9. Porque o mesmo argumento servia também para o Pedido. Um argumento que vale para os dois lados não decide entre eles; o que decide é o significado de cada campo.
  10. Só se o teto do M2 for reduzido: o Crm não tinha horas planejadas e o conteúdo do M2 não depende dele. Sem reduzir o teto, as horas apenas ficam para outro assunto.
