Norte · S16 — EF Core 10: o Catalogo grava no Postgres

Segunda, 12/10/2026 · 09:31 → 18:02 · 6h20 líquidas (pausas de 0h41 e 1h30) · Marco M1

Objetivo da sessão: fazer a ficha de produto sobreviver ao reinício da API, gravando e lendo do PostgreSQL com o EF Core 10. Entregue (três PRs na main): consulta por SKU, persistência com migration (PR #7), um schema do Postgres por módulo (PR #8, ADR-006) e a reorganização das pastas do módulo (PR #9). Decisão registrada em ADR: a entidade vira class (ADR-005).

Antes de ler: a explicação completa de cada peça está na Parte 6 do guia. Esta página é o roteiro de estudo da sessão: o que aconteceu, o que decidir sozinho em cada ponto e como se testar.

1. O problema que a sessão resolve

Até a S15 o FichaProdutoRepository guardava as fichas numa lista dentro do processo. O experimento do início da aula mostrou o efeito:

Passo O que aconteceu
POST /catalogo/fichas-produto com LUV-001 201 Created, com Location: /catalogo/fichas-produto/LUV-001
GET /catalogo/fichas-produto/LUV-001 200 OK com a ficha
parar e subir a API, GET de novo 404 Ficha não encontrada — a memória do processo se foi

O 404 do último passo veio do código do Norte (título "Ficha não encontrada"), não do roteamento: a rota funciona, a ficha é que sumiu. Resolver isso pede três coisas fora do C#: um banco rodando, o texto que diz como entrar nele e o pacote que ensina o EF Core a falar com esse banco.

2. As peças, na ordem em que foram montadas

# Peça O que você faz Onde mora
1 Postgres 18 num container descreve em compose.yaml e sobe com docker compose up -d raiz do norte
2 Connection string uma chave Norte na seção ConnectionStrings appsettings.Development.json do host
3 Provider instala Npgsql.EntityFrameworkCore.PostgreSQL Norte.Catalogo (a versão no Directory.Packages.props)
4 Entidade como classe troca record por internal sealed class com construtor e private set Dominio/FichaProduto.cs
5 DbContext herda de DbContext, expõe um DbSet, aplica o mapeamento CatalogoDbContext.cs
6 Mapeamento (Fluent API) tabela, chave, colunas, obrigatoriedade Configuracoes/FichaProdutoConfiguration.cs
7 Migration dotnet ef migrations add e database update Migrations/ (gerada)
8 Schema do módulo HasDefaultSchema + MigrationsHistoryTable contexto e AddCatalogo
9 Repositório assíncrono AdicionarAsync, ObterPorSkuAsync, AddScoped FichaProdutoRepository.cs
10 Pastas do módulo Funcionalidades/, Dominio/, Configuracoes/ módulo Catalogo

Regra de decisão da sequência: o banco existe → a API sabe onde ele está → o EF sabe falar com ele → o EF sabe qual classe vira qual tabela → a tabela existe → o repositório usa o contexto. Cada peça depende da anterior; por isso a ordem não é intercambiável.

3. Como ler as linhas que mais confundem

3.1 O compose.yaml

services:
  postgres:
    image: postgres:18
    container_name: norte-postgres
    environment:
      POSTGRES_USER: norte
      POSTGRES_PASSWORD: <senha do container local>
      POSTGRES_DB: norte
    ports:
      - "5432:5432"
    volumes:
      - norte-postgres-dados:/var/lib/postgresql

volumes:
  norte-postgres-dados:
Linha O que faz O que acontece sem ela
image: postgres:18 imagem oficial, versão 18 sem a versão, a imagem pode mudar de versão principal sozinha
POSTGRES_USER / _PASSWORD / _DB criam usuário, senha e banco na primeira subida sem a senha o container nem sobe
ports: "5432:5432" porta da sua máquina : porta do container a API não alcança o banco
volumes: …:/var/lib/postgresql liga um volume nomeado ao diretório de dados os dados morrem junto com o container

No Postgres 18 o volume aponta para /var/lib/postgresql; até a 17 era /var/lib/postgresql/data.

3.2 A connection string

Host=localhost;Port=5432;Database=norte;Username=norte;Password=<senha do container local>

Os valores têm de ser exatamente os do compose.yaml. Atenção: o Postgres diferencia maiúscula de minúscula no nome do banco (norte, não Norte). Uma connection string de SQL Server (Server=, User Id=) não serve: os nomes dos parâmetros mudam.

3.3 Onde cada configuração mora (camadas)

O .NET lê a configuração em camadas; a de baixo vence se repetir a chave.

Camada Vale em Pode ter senha?
appsettings.json todo ambiente não (vai para o git)
appsettings.{Ambiente}.json só naquele ambiente só se for descartável (container local)
user-secrets só Development, na sua máquina sim, mas não existe em stage
variáveis de ambiente qualquer ambiente sim
argumentos de linha de comando qualquer ambiente sim

3.4 A entidade e o mapeamento

internal sealed class FichaProduto
{
    public FichaProduto(string sku, string descricao, string ncm)
    {
        Sku = sku;
        Descricao = descricao;
        Ncm = ncm;
    }

    public string Sku { get; private set; }
    public string Descricao { get; private set; }
    public string Ncm { get; private set; }
}
Escolha Motivo
class, não record o EF usa igualdade por referência; o record compara por valor (ADR-005)
construtor com parâmetros o EF liga cada parâmetro à propriedade de mesmo nome e o chama; não precisa de construtor vazio
private set sem setter a propriedade não é mapeada; com public set qualquer código muda a ficha
chave declarada (Sku) a convenção só reconhece Id ou FichaProdutoId

3.5 O dotnet ef, com dois projetos

dotnet ef migrations add <Nome> --project src/Modulos/Catalogo/Norte.Catalogo --startup-project src/Norte.Api -- --environment Development
dotnet ef database update      --project src/Modulos/Catalogo/Norte.Catalogo --startup-project src/Norte.Api -- --environment Development
Parte Para que serve
--project onde a pasta Migrations/ é criada (o módulo)
--startup-project o host, que a ferramenta compila e executa para ler a configuração
-- --environment Development tudo depois do -- vai para o aplicativo; a connection string só existe em Development

O pacote Microsoft.EntityFrameworkCore.Design entra no host (Norte.Api), com PrivateAssets all. No Central Package Management a versão fica no Directory.Packages.props, mas a PackageReference precisa estar no .csproj do projeto que usa o pacote (a instalação ficou pela metade na sessão por esse motivo).

3.6 O schema por módulo

Configuração O que move Onde
HasDefaultSchema(Schema) as tabelas do contexto OnModelCreating
MigrationsHistoryTable("__EFMigrationsHistory", Schema) a tabela de histórico opções do provider, em AddCatalogo

Faltando a primeira, a tabela vai para public. Faltando a segunda, só o histórico vai para public.

4. O preço de cada decisão (ganho × preço)

Decisão Ganho Preço
Entidade como class (ADR-005) o EF rastreia e atualiza a entidade perde a igualdade por valor; teste que compara fichas inteiras passa a conferir propriedade por propriedade
Postgres no Compose qualquer máquina recria o banco com um comando mais um arquivo; a porta 5432 só serve a um container por vez
Senha de container local no appsettings.Development.json o clone do repositório já roda só vale porque o banco é descartável; em stage e produção a senha vem por variável de ambiente
Mapeamento em arquivo próprio por entidade o OnModelCreating não cresce um arquivo a mais e um nível de indireção
Schema por módulo (ADR-006) a fronteira do módulo existe no banco duas configurações por módulo; o nome do schema aparece em SQL escrito à mão; separa por organização, não por impedimento
Repositório sobre o contexto o EF Core fica isolado num ponto uma camada que pode só repassar chamadas
Funcionalidades/ + Dominio/ + Configuracoes/ cada pasta tem um critério só mover custa using; a pasta Dominio/ convida a criar outras pastas por tipo
Rota por recurso o Location do cadastro responde a um GET ações que não são cadastro/consulta/alteração/exclusão ficam sem encaixe natural

9. O que ficou de fora de propósito

  • Nenhum teste toca o banco. O teste de unidade do cadastro protegia uma lista em memória e foi apagado; sobram 4 testes (3 de recusa 400 e 1 do 500). Teste da gravação pede o Postgres real (Testcontainers), porque o provider em memória e o SQLite aceitam o que o Postgres recusa.
  • 409 no SKU duplicado: regra de negócio, decisão da próxima sessão.
  • CancellationToken no repositório, seed, paginação e projeções, concorrência otimista, índices.

12. Teste-se (sem consultar, uma pergunta por vez)

  1. A FichaProduto nasceu como record. Por que virou class, e o que se perde?
  2. O que o private set faz no EF Core, e por que o construtor vazio não é necessário?
  3. Dê duas coisas que HasDefaultSchema move, e diga o que acontece se faltar a MigrationsHistoryTable.
  4. Qual a diferença entre --project e --startup-project no dotnet ef?
  5. O que o Add faz e o que o SaveChangesAsync faz? Por que o repositório é AddScoped?
  6. Cadastrar o mesmo SKU duas vezes devolve 500. Qual a causa e qual deveria ser o status?
  7. Por que GET /catalogo/fichas-produto/ devolve 405?
  8. Por que o schema por módulo não impede um módulo de ler a tabela de outro?
  9. Cite um preço (não um ganho) do schema por módulo.
  10. (Revisão das sessões anteriores) Qual middleware escreve o corpo do erro, qual captura a exceção e qual preenche o corpo vazio de um 4xx?

Respostas

Mostrar respostas
  1. O EF usa igualdade por referência (uma instância por entidade, rastreamento); o record compara por valor, e a documentação o trata como inadequado para entidade. Perde-se a igualdade por valor automática e o with; testes que comparam fichas inteiras precisam conferir propriedade por propriedade.
  2. Propriedade sem setter não é mapeada por convenção; com private set o EF mapeia e o código de fora não altera a ficha. O construtor vazio não é necessário porque o EF chama o construtor cujos parâmetros casam (nome e tipo) com as propriedades mapeadas.
  3. Move as tabelas do modelo (e outros objetos, como sequências). Sem a MigrationsHistoryTable, só o __EFMigrationsHistory fica em public, e dois módulos dividiriam a mesma tabela de histórico.
  4. --project é o destino (onde a pasta Migrations/ nasce: o módulo). --startup-project é o que a ferramenta compila e executa para descobrir configuração e connection string (o host).
  5. Add só marca a ficha como nova; o INSERT acontece no SaveChangesAsync. O contexto é scoped (uma instância por requisição) e um singleton que dependesse dele prenderia aquela instância para sempre.
  6. A chave primária em sku (PK_fichas_produto): o banco recusa (23505), o EF lança DbUpdateException e o tratamento global devolve 500. Deveria ser 409 Conflict (regra de negócio ainda a decidir).
  7. A barra final casa com a rota do cadastro (POST /fichas-produto): o caminho existe, mas só para POST; o roteamento responde 405 com Allow: POST e o endpoint de consulta nem é chamado.
  8. Porque separa por organização, não por impedimento: mesmo banco, mesmo usuário; uma consulta atravessa schemas. O que impede é convenção e revisão (e, como reforço não adotado, permissões por schema).
  9. Por exemplo: duas configurações para lembrar a cada módulo novo (se faltar a do histórico, só ela vai para public); o nome do schema aparece em SQL escrito à mão (catalogo.fichas_produto). (Qualquer um, com o efeito.)
  10. AddProblemDetails() escreve o corpo; UseExceptionHandler() captura a exceção não tratada; UseStatusCodePages() preenche o corpo de um 4xx/5xx vazio.
