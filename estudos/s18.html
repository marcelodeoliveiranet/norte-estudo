Norte · S18 — A ficha recusa valor vazio e o Catalogo ganha um seed

Terça, 13/10/2026 · 19:33 → 22:14 · 2h39 líquidas (pausa de 0h02) · Marco M1 · segunda sessão do dia (a S17 foi pela manhã; o dia somou 6h21)

Objetivo da sessão: fechar duas pendências do Catalogo: (1) a FichaProduto deixa de aceitar SKU, descrição e NCM vazios; (2) o módulo grava fichas iniciais (seed) sem quebrar ao rodar duas vezes. Entregue (dois PRs na main): o construtor que recusa valor vazio, com 6 testes (PR #12, merge 37b86a2), e o seed, a fábrica de teste em ambiente Testing e os testes do 400 no banco descartável (PR #13, merge 41d94d8). A main termina com 11 testes verdes. A listagem e a paginação não foram feitas: ficam para a S19.

Antes de ler: a explicação completa de cada peça está nas entradas 6.12 a 6.15 da Parte 6 do guia. Esta página é o roteiro de estudo da sessão.

1. O problema que a sessão resolve

Situação Resultado
new FichaProduto("", "", "") funcionava: criava uma ficha sem SKU, sem descrição e sem NCM
POST com um campo vazio 400, porque o Request do endpoint barra antes de chegar à ficha

Só o endpoint protegia a ficha. Quem a criasse por outro caminho (um teste, um seed, outro módulo) passava direto. A regra "uma ficha nunca existe com SKU, descrição ou NCM vazios" pertence à ficha.

O segundo problema veio da próxima tarefa, a listagem: para listar, o banco de desenvolvimento precisa de fichas gravadas, e ele só tinha as cadastradas à mão.

3. Como ler o código

3.1 O construtor

internal sealed class FichaProduto
{
    public FichaProduto(string sku, string descricao, string ncm)
    {
        ArgumentException.ThrowIfNullOrWhiteSpace(sku);
        ArgumentException.ThrowIfNullOrWhiteSpace(descricao);
        ArgumentException.ThrowIfNullOrWhiteSpace(ncm);

        Sku = sku;
        Descricao = descricao;
        Ncm = ncm;
    }

    public string Sku { get; private set; }
    public string Descricao { get; private set; }
    public string Ncm { get; private set; }
}
Trecho Significado
ArgumentException.ThrowIfNullOrWhiteSpace(sku) se sku for nulo, vazio ou só espaços, lança a exceção; senão, não faz nada
antes das atribuições a ficha nunca existe pela metade: ou nasce válida, ou o construtor lança
ArgumentException o tipo da exceção para vazio ou só espaços. Para null, a documentação diz que o método lança ArgumentNullException
nome do parâmetro a exceção traz ParamName == "sku" sem você escrever o nome: o parâmetro paramName é opcional e foi preenchido sozinho (visto na saída: (Parameter 'sku'))

3.2 Um teste de unidade que espera falha

[Fact]
public void FichaProduto_Com_Sku_Vazio_Lanca_Excecao()
{
    // Arrange: com que valores preparo o cenário?
    var skuInvalido = "";

    // Act + Assert: a criação da ficha deve falhar com ArgumentException
    var excecao = Assert.Throws<ArgumentException>(
        () => new FichaProduto(skuInvalido, "Luva nitrilica", "40151900"));

    // Assert: o que prova que a regra foi cumprida? O campo recusado foi o SKU
    Assert.Equal("sku", excecao.ParamName);
}
Parte Pergunta que responde Neste teste
Arrange com que valores eu preparo o cenário? SKU vazio; descrição e NCM válidos, para que só o SKU explique a falha
Act qual ação deve falhar? new FichaProduto(...), embrulhada em () => ...
Assert o que prova que a regra foi cumprida? a exceção do tipo esperado foi lançada e o ParamName é "sku"

Assert.Throws<T>(() => ...) executa a ação por você dentro de um try/catch e confirma que ela lançou. Por isso o Act e o Assert ficam numa linha só.

Assert.Throws exige o tipo exato. Visto na sessão: com o construtor lançando ArgumentException e o teste esperando ArgumentNullException, o teste falhou com Exception type was not an exact match (Expected: ArgumentNullException, Actual: ArgumentException).

Por que o teste confere o ParamName e não a mensagem? A mensagem é detalhe de como o erro foi escrito; se alguém a reescrever, o teste quebra sem a regra ter mudado. O ParamName diz qual campo foi recusado, que é o que a regra exige.

Os três vazios: null, "" e " ". O null não tem teste: o parâmetro é string (sem ?), então o compilador recusa passar um null conhecido (o aviso de nulidade vira erro pelo ADR-004; o número do erro não foi visto). Os testes cobrem o que o compilador não pega: "" e só espaços.

3.3 O seed

internal sealed class CatalogoSeed
{
    private readonly FichaProdutoRepository _repositorio;

    public CatalogoSeed(FichaProdutoRepository repositorio)
    {
        _repositorio = repositorio;
    }

    public async Task ExecutarAsync()
    {
        await GarantirFichaAsync("LUV-NIT-001", "Luva nitrilica tamanho M", "40151900");
        await GarantirFichaAsync("LUV-NIT-002", "Luva nitrilica tamanho G", "40151900");
        await GarantirFichaAsync("LUV-LAT-001", "Luva de latex tamanho M", "40151900");
    }

    private async Task GarantirFichaAsync(string sku, string descricao, string ncm)
    {
        var existente = await _repositorio.ObterPorSkuAsync(sku);
        if (existente is not null)
            return;

        await _repositorio.AdicionarAsync(new FichaProduto(sku, descricao, ncm));
    }
}
Trecho O que faz
GarantirFichaAsync "garante que a ficha exista": consulta o SKU; se achar, sai sem gravar; se não achar, grava
new FichaProduto(...) passa pelo construtor protegido: um valor vazio no seed lançaria exceção na subida
internal sealed o host não enxerga a classe (ADR-002); por isso existe o método público abaixo 
public static async Task SemearCatalogoAsync(this WebApplication app)
{
    if (!app.Environment.IsDevelopment())
        return;

    using var escopo = app.Services.CreateScope();
    var seed = escopo.ServiceProvider.GetRequiredService<CatalogoSeed>();
    await seed.ExecutarAsync();
}
Trecho O que faz
this WebApplication app método de extensão: chamado como app.SemearCatalogoAsync()
if (!IsDevelopment()) return; fora de Development, não faz nada
CreateScope() cria um escopo à mão: o DbContext e o repositório são scoped, e na subida não existe requisição para lhes dar um escopo
using var escopo o escopo é descartado ao fim, o que libera o DbContext

No Program.cs, a chamada entra depois dos Map... e antes do app.Run() (o Run() bloqueia atendendo requisições; depois dele a linha nunca executaria):

await app.SemearCatalogoAsync();

app.Run();

E no AddCatalogo entra o registro services.AddScoped<CatalogoSeed>();.

4. O que provou que o seed é idempotente

Três execuções do host em Development, olhando o log do EF e o banco:

Execução Estado do banco antes O que o log mostrou Banco depois
1ª as 3 fichas do seed já existiam 3 SELECT ... WHERE f.sku = @sku e nenhum INSERT 5 linhas, nenhuma duplicada
(preparação) DELETE ... WHERE sku = 'LUV-LAT-001' — 4 linhas
2ª falta LUV-LAT-001 3 SELECT e 1 INSERT INTO catalogo.fichas_produto 5 linhas: a ficha voltou com a descrição do seed; as outras 4 intactas

As fichas cadastradas à mão (LUV-001 e a de SKU 9de5783c) foram preservadas.

5. O que quebrou no caminho (e por quê)

5.1 O seed rodou dentro da fábrica de teste, antes da migration

Depois de ligar o seed ao Program.cs, o teste do 409 (o único que usa o Postgres descartável) falhou com:

Npgsql.PostgresException : 42P01: relation "catalogo.fichas_produto" does not exist

O rastro mostrou a cadeia: ApiComPostgresFabrica.InitializeAsync() → SemearCatalogoAsync → CatalogoSeed.GarantirFichaAsync. A fábrica estava em Development; ao tocar em Services, ela sobe a API inteira, o Program.cs roda até o seed, e o contêiner ainda não tem tabela (a MigrateAsync vem depois). O seed só funciona num banco que já tem a tabela.

Conserto: builder.UseEnvironment("Testing"); no ConfigureWebHost da fábrica. Qualquer nome diferente de Development serve, porque o IsDevelopment() do seed é que decide.

5.2 O CI pegou o que a máquina local escondia

Com tudo verde local, o CI do PR #13 falhou em 3 de 11 testes, os três do 400, com Failed to connect to 127.0.0.1:5432 ... Connection refused. Rastro: CreateClient() → Program.cs → SemearCatalogoAsync. Esses testes usavam a fábrica comum, que sobe em Development; a partir do seed, subir a API passou a abrir uma conexão. No computador o Postgres de desenvolvimento estava de pé; no CI não existe. Antes do seed, esses testes nunca abriam conexão (a validação recusava a requisição antes de tocar o banco).

Conserto: os 3 testes passam para a classe CadastrarFichaProdutoComBancoApiTests (fábrica com Postgres descartável, ambiente Testing), com SKU gerado por Guid. Isso também fecha a pendência da S17: nenhum teste que pode gravar toca o banco de desenvolvimento.

A lição: antes de ligar à subida da API algo que usa infraestrutura, perguntar "o CI tem isso?". E esperar a caixa de checks do PR ficar verde antes do merge: o CI avisa, mas não impede.

6. O preço de cada decisão (ganho × preço)

Decisão Ganho Preço
Recusar com exceção (ArgumentException), e não devolver um resultado de sucesso/falha a ficha nunca existe inválida; nenhum chamador precisa lembrar de checar; não mexe no construtor de 3 parâmetros (ADR-005) quem cria a ficha fora do endpoint e não trata recebe uma exceção (num endpoint, viraria 500). Aceito: o endpoint já barra a entrada vazia com 400 antes do construtor; o que sobra é bug do código
Uma linha ThrowIfNullOrWhiteSpace por campo, e não if manual com mensagem própria uma linha por campo; "" e só espaços lançam o mesmo tipo; o teste confere a regra, não o texto a mensagem passa a ser a padrão do .NET, em inglês. Não chega ao cliente (o endpoint barra antes)
null por conta do compilador, sem teste próprio testa só o que o compilador não pega um null em tempo de execução (código com nullable desligado) não tem teste; forçar com null! silenciaria o compilador, contra o ADR-004
Seed no código do módulo, só em Development, e não HasData na migration só o desenvolvimento recebe as fichas um método público novo e uma chamada no Program.cs. Com HasData, os dados entrariam em todo banco que aplica a migration, inclusive produção
Seed insere só o que falta, e não apaga e regrava preserva o que o desenvolvedor cadastrou; roda de novo sem duplicar uma consulta por ficha do seed; se alguém alterar uma ficha do seed no banco, o seed não corrige, porque só adiciona
Fábrica de teste em Testing, e não Development o seed não roda no banco descartável, que só tem o que o teste coloca nele a fábrica deixa de reproduzir o ambiente de desenvolvimento. A alternativa (o seed aplicar a migration antes de gravar) faria o host migrar sozinho na subida e o banco dos testes nasceria com as fichas
Testes do 400 na classe do banco descartável nenhum teste que grava toca o banco de desenvolvimento; um só contêiner; o CI passa sem Postgres fora dos testes a classe mistura 400 e 409, e o nome ComBanco diz a infraestrutura, não o assunto

12. Teste-se (sem consultar, uma pergunta por vez)

  1. Por que a regra "ficha sem SKU, descrição ou NCM" pertence à ficha e não só ao endpoint?
  2. O que ArgumentException.ThrowIfNullOrWhiteSpace(sku) faz? Qual exceção sai para null e qual sai para ""?
  3. Por que o teste confere ParamName e não a mensagem da exceção?
  4. Por que o null não tem teste de unidade?
  5. Descreva em Arrange / Act / Assert o teste "SKU vazio lança exceção".
  6. Assert.Throws<ArgumentNullException> e o código lança ArgumentException. O teste passa? Como isso foi visto?
  7. Como você viu que os testes da descrição e do NCM realmente protegem a regra?
  8. Por que o seed consulta o SKU antes de gravar, e o que acontece rodando o host duas vezes?
  9. Dê um preço (não um ganho) de o seed inserir só o que falta, em vez de apagar e regravar.
  10. Por que o seed quebrou o teste do 409 e como a fábrica passou a evitar isso?
  11. Por que 3 testes passavam no computador e falharam no CI depois do seed?
  12. O que fazer antes de ligar à subida da API algo que usa banco?

Respostas

Mostrar respostas
  1. Porque a ficha pode ser criada por outros caminhos (teste, seed, outro módulo) que não passam pelo Request; a regra mora onde protege todos eles.
  2. Recusa o valor nulo, vazio ou só com espaços, antes das atribuições. Para null, lança ArgumentNullException; para "" (e só espaços), lança ArgumentException.
  3. A mensagem é detalhe de escrita: reescrevê-la quebraria o teste sem a regra mudar. O ParamName diz qual campo foi recusado, que é o que a regra exige.
  4. O parâmetro é string (sem ?): o compilador recusa passar um null conhecido, então o teste nem compila. Os testes cobrem o que o compilador não pega.
  5. Arrange: SKU vazio, descrição e NCM válidos. Act: criar a ficha (a ação que deve falhar). Assert: a exceção do tipo esperado foi lançada e o ParamName é "sku".
  6. Não passa: Assert.Throws<T> exige o tipo exato. Foi visto: Exception type was not an exact match, com Expected e Actual diferentes.
  7. Tirando (comentando) as linhas da descrição e do NCM no construtor e rodando uma vez: os 4 testes ficaram vermelhos (Failed: 4, Passed: 2) e os 2 do SKU continuaram verdes.
  8. Para só gravar o que falta: se o SKU existe, pula. Rodando duas vezes: na primeira grava o que falta; na segunda só consulta, sem gravar e sem erro.
  9. Uma consulta por ficha do seed em toda subida; e se alguém alterar uma ficha do seed no banco, o seed não corrige, porque só adiciona.
  10. A fábrica estava em Development: ao subir a API, o seed rodou antes da migration e o contêiner não tinha a tabela (42P01). A fábrica passou a subir em Testing, e o IsDevelopment() do seed devolve falso.
  11. Subir a API passou a abrir conexão com o banco (o seed); no computador o Postgres de desenvolvimento estava de pé, no CI não existe (Connection refused).
  12. Perguntar "o CI tem isso?" e, se não tiver, mover para o banco descartável os testes que sobem a API e podem gravar.
