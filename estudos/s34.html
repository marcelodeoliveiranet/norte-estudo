Norte · S34 — O contrato nos dois sentidos, o SKU no pedido e o módulo Representantes

Quarta, 28/10/2026 · tempo: 10h56 (09:31–22:20, pausas 13:14–13:29 e 16:01–17:39) · Marco M1

Hoje o Pedidos ganhou o GET /pedidos/{id} (com Assert de verdade nos itens), o Clientes passou a perguntar ao Pedidos antes de excluir um cliente, o Pedidos passou a perguntar ao Catalogo se o SKU existe, e nasceu um módulo novo: o Representantes, com POST /representantes/. Quatro PRs na main (#67 a #70), 157 testes, CI verde.

A ideia para guardar: o contrato entre módulos agora vai e volta, e nenhum módulo referencia o outro. Clientes → Pedidos.Contratos; Pedidos → Clientes.Contratos e Catalogo.Contratos. Cada pergunta é uma interface num projeto quase vazio; cada resposta é do módulo dono do dado.

Antes de ler: a explicação completa está na entrada 8.13 da Parte 8 do guia. Esta página é o roteiro de estudo da sessão.

2. Onde isso está no mapa dos níveis

Solution → módulos → funcionalidades → camadas. Hoje mexemos no nível dos módulos: a fronteira ganhou mais dois projetos de contratos (Pedidos.Contratos, Catalogo.Contratos) e um módulo novo entrou na solution (Representantes, com DbContext, schema e migration próprios).

3. Conceitos

3.1 Assert que confere os itens de uma lista (guia 8.13)

Conferir só que "a lista não está vazia" não prova que os valores voltaram. O teste do GET /pedidos/{id} grava N itens, lê o corpo e compara item a item:

foreach (var i in Enumerable.Range(0, quantidadeItensIncluidos))
{
    // o POST usa 10m + i de preço e i como quantidade; o Assert usa as mesmas fórmulas
    Assert.Equal(sku, item.GetProperty("sku").GetString());
    ...
}

A falha da tarde foi Expected: 1 Actual: 2: o POST mandava Quantidade: 2 fixo e o Assert esperava i. Regra: a fórmula do Arrange e a do Assert precisam ser a mesma. O 404 usa ProblemDetails tipado e um id que não existe (int.MaxValue).

3.2 O contrato nos dois sentidos (regra B)

O DELETE /clientes/{id} agora pergunta ao Pedidos se existem pedidos para o cliente:

Peça Onde mora Papel
IConsultaPedidos Norte.Pedidos.Contratos (public) a pergunta
ConsultaPedidos Norte.Pedidos (internal) a resposta, via AnyAsync (EXISTS)
ProjectReference Norte.Clientes.csproj → Norte.Pedidos.Contratos Clientes não referencia Norte.Pedidos

Sem o projeto de contratos, Clientes → Pedidos e Pedidos → Clientes seriam uma referência circular. Por isso o ADR-012 escolheu um projeto por módulo. Se há pedidos, o endpoint responde 400 "Existem pedidos para esse cliente" e não exclui.

3.3 O helper do teste devolve a fábrica (e o using var fica no teste)

Para trocar o IConsultaPedidos por um fake, o teste cria uma fábrica derivada:

private WebApplicationFactory<Program> CriarFabricaComPedidos(bool existemPedidos)
{
    return fabrica.WithWebHostBuilder(builder =>
        builder.ConfigureServices(services =>
            services.AddScoped<IConsultaPedidos>(_ => new ConsultaPedidosFake(existe: existemPedidos))));
}

using var fabricaComPedidos = CriarFabricaComPedidos(existemPedidos: true);
var cliente = fabricaComPedidos.CreateClient();

Erro da tarde: um using var dentro do helper descartava a fábrica antes do teste usar o HttpClient (ObjectDisposedException, 3 testes vermelhos). A fábrica derivada precisa viver até o fim do teste; quem a descarta é o teste. (O mentor tinha aconselhado o contrário sem verificar.)

3.4 Regra C: o SKU precisa existir no Catálogo

public interface IConsultaCatalogo
{
    Task<bool> NaoExisteSkuAsync(string sku, CancellationToken ct);
}

Dois pontos de desenho:

  • Um laço só. A primeira versão tinha dois foreach (um para montar o ItemPedido, outro para consultar o Catálogo). Você pediu para melhorar; ficou um foreach: cria o ItemPedido, pergunta ao Catálogo, devolve 400 se o SKU não existe, adiciona à lista.
  • O SKU é consultado normalizado. O construtor do ItemPedido aplica ToUpperInvariant (ADR-009); a consulta usa o valor já normalizado.

Consequência nos testes: todo teste que faz POST /pedidos agora precisa dos dois fakes (ConsultaClientesFake e ConsultaCatalogoFake), inclusive o do GET. Sem o fake do Catálogo a API tenta o banco do Catálogo e responde 500. O helper CriarFabrica(bool clienteExiste, bool skuExiste = true) concentra o registro.

3.5 Quem é o dono do dado? Representantes como módulo

A conversa de domínio do meio do dia: vários representantes ↔ vários pedidos; 1 representante ↔ N clientes. Sua conclusão: dono = dono do dado (ADR-011): quem cria e altera é o módulo dono. Como o representante é o elo da carteira, ele merece módulo próprio (Representantes), em vez de ficar um int solto no Pedido. O vínculo Cliente.RepresentanteId segue provisório.

3.7 FluentValidation × validação nativa: a decisão

Sua decisão (com o porquê): Pedidos fica com AddValidation (não se mexe no que está pronto e testado); FluentValidation entra só no Representantes, para aprender, numa próxima fatia. A primeira fatia do Representantes usou DataAnnotations. Regra de estado ou de negócio continua no domínio ou no endpoint.

5. Dúvidas e respostas

Por que o Clientes não referencia o Pedidos? Porque o Pedidos já referencia o contrato do Clientes; uma referência direta fecharia um ciclo. Os dois falam por projetos de contratos.

400 ou 409 para "existem pedidos para esse cliente"? Ficou 400 (a requisição pede uma exclusão que a regra recusa). O 409 ficou para duplicidade (CPF/CNPJ/SKU). A discussão está nos PRs como "o que fica pior".

Por que o Select ignorou o Include? Quando a consulta projeta para outro tipo (Response), o EF monta o SELECT só com o que a projeção usa; o Include só vale quando a entidade inteira é devolvida.

O Representantes não tem teste automatizado? Não: decisão sua, coberta pelo .http (265 linhas de cenários, com dados fictícios).

7. Avaliação

Fez bem: escreveu sozinho o Assert dos itens e o teste do 404; resolveu as regras B e C pedindo só o enunciado ("deixe eu quebrar a cabeça"); achou os dois laços da regra C e pediu para melhorar; identificou que o helper do teste tinha de espelhar o CriarFabrica; separou o que é pendência do que é plano; defendeu o escopo ("deixar as coisas pedirem"); contrariou o mentor com evidência (representante, .editorconfig, pendência do preço); modelou o Representantes inteiro e corrigiu sozinho o PedidoId copiado do Pedidos, o set público do telefone e o e-mail sem normalização; testou todos os cenários pelo .http.

Recursos novos: Enumerable.Range num Assert de lista; segundo contrato (Pedidos.Contratos, Catalogo.Contratos); fábrica derivada com using var no teste; Select × Include; unicidade com 23505 num módulo novo; migration de módulo novo.

O mentor conduziu mal: afirmou o using var no helper sem verificar (3 testes vermelhos); cobrou o .editorconfig como se faltasse; explicou argumentos nomeados que você já conhecia; inventou a "pendência" do preço; entregou texto longo quando você pediu o código errado; esqueceu o fake do Catálogo ao planejar a regra C (quebrou testes do Pedidos).

Respostas

Mostrar respostas
  1. Porque o POST grava o valor e o Assert confere o valor lido; se as fórmulas diferem, o teste falha por erro do próprio teste (Expected: 1 Actual: 2), não por defeito do código.
  2. O Pedidos oferece Norte.Pedidos.Contratos (interface pública, projeto quase vazio); o Clientes referencia só esse projeto. Se referenciasse o Norte.Pedidos, haveria ciclo com o Pedidos → Clientes.Contratos.
  3. A fábrica derivada é descartada antes do teste usar o cliente: ObjectDisposedException. O using var fica no teste.
  4. O endpoint consulta o Clientes (cliente existe?) e o Catalogo (SKU existe?); sem o fake de qualquer um, a API usa a implementação real e o teste cai em 500.
  5. O construtor do ItemPedido guarda o SKU em maiúsculas (ADR-009) e o Catalogo guarda assim; consultar o texto digitado em minúsculas diria "não existe" para um SKU que existe.
  6. Um laço só cria o item, consulta e acumula; dois laços percorrem a lista duas vezes e separam duas partes da mesma decisão.
  7. Com projeção para outro tipo, o EF monta o SELECT só com as colunas usadas; o Include só vale quando a entidade é devolvida.
  8. Dono do dado é o módulo que cria e altera o dado. O representante é o elo da carteira de clientes e pedidos; por isso tem módulo próprio, com o vínculo do cliente ainda provisório.
  9. Mesma decisão do CNPJ (ADR-011): só o padrão é validado; os dígitos verificadores custam código e teste que o laboratório não precisa.
  10. Para que Ana@x.com e ana@x.com não sejam dois cadastros; acontece no construtor e no Atualizar do Representante, e a consulta também usa minúsculas.
  11. CPF ou e-mail já existentes. A consulta antes de gravar cobre o caso comum; dois cadastros simultâneos são cobertos pelo índice único e pela captura do 23505 no AdicionarAsync.
  12. Regra permanente sua: nenhum commit ou PR leva linha de autoria.
